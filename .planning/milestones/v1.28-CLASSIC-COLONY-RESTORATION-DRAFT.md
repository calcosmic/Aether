# v1.28 Classic Colony Restoration — Milestone Draft

This is the **implementation milestone** for the February–April restoration described in the 35,921-word `.aether/dreams/2026-09-01-comprehensive-aether-colony-review.md`. That report is the authoritative owner brief and research input. The 72-row capability ledger supplies traceability during roadmapping; it is not a pre-milestone approval gate or a list of questions Callum must answer again.

For dummies: the large report is already the renovation brief. v1.28 does the renovation.

## Outcome

Reunite Aether's modern Go safety kernel with the understandable, visible, Queen-led colony experience Callum remembers from February–April. The result must be safe, causally real, enjoyable to use, and explain itself without requiring the owner to operate manifests or memory plumbing.

For dummies: keep the new engine and brakes, restore the dashboard, steering feel, crew, and journey. This is not a rollback to old scripts and not another coat of biological vocabulary.

## Entry conditions

- v1.27 closes with Phase 198.3 verified at 94/94 truths, 6/6 roadmap criteria, and 6/6 STAM requirements.
- The comprehensive report and composite historical refs define the functional and experiential target.
- Milestone roadmapping maps the 72 Classic capability rows to restoration work, demonstrated successors, or genuinely unresolved owner choices without repeating the prior discovery conversation.
- No pending capability is pruned merely because the current Go runtime has no caller.

## Composite baseline

The target is deliberately composite:

- `3a5b81c2` (2026-02-15): Open Chambers and the visible colony;
- `v5.0.0` (2026-02-20): pure-shell worker emergence;
- `v5.4` (2026-04-04): the wrapper-rich hybrid experience.

Historical source is evidence, not production code to copy blindly. The current runtime keeps state authority.

## Mandatory phase method

The feature names in this draft are investigation areas, not predetermined solutions. Before planning implementation, each Phase 199-204 must:

1. reconstruct the relevant Classic mechanism from exact historical source, specifications, state/event flow, fixtures, and user-visible behavior;
2. trace the same outcome through the current public path and Go architecture;
3. explain which causal parts made the old experience effective or enjoyable;
4. compare keeping the current design, restoring the behavior on the modern kernel, or replacing both with a demonstrated better design;
5. record the conclusion and rejected alternatives in a phase `CLASSIC-SYNTHESIS.md` linked to implementation tasks, tests, CAP rows, and verification.

The 35,921-word report is the starting map for these focused studies. It prevents repeated owner discovery, but it does not let a phase substitute “bring Swarm back” for source archaeology and architecture synthesis.

## Modern kernel that must survive

- atomic writes, locks, immutable attempts, replay protection, and recovery;
- deterministic free checks and named-risk gates;
- evidence journals, honest elapsed/cost reporting, and provenance;
- sanitization, bounded teams, dirty-worktree preservation, and resume integrity;
- memory/Hive trust boundaries and fail-closed external finalizers.

## Proposed phases

The approved live roadmap numbers these Phases 199-205. The executable Golden Era corpus is a cross-cutting ratchet that begins inside Phase 199 alongside visible front-door delivery; it is not a standalone reconciliation or planning gate.

### Phase 199 — Front Door and Lifecycle Grammar

Restore one coherent normal journey across help, init, colonize, status, pause/resume, seal, and canonical Next Up. Hide protocol plumbing behind expert/system namespaces and translate internal terms the first time they appear.

**Exit:** A new user can start, understand, pause, resume, and finish a colony without reading implementation docs.

### Phase 200 — Iterative Planning

Restore the visible Scout → Route-Setter confidence loop: domain/territory research, five confidence dimensions, gap targeting, delta explanation, stall detection, owner discussion, and a complete final plan. Keep modern plan revision and finalizer proof underneath.

**Exit:** A real plan visibly improves across iterations and explains why each iteration ran and stopped.

### Phase 201 — Queen-led Build, Continue, and Autopilot

Make the Queen visibly choose the smallest capable team, explain each worker, show waves/results/checks/recovery/learning, and advance as one story. `aether run` must render the same accepted result model rather than a thin alternate mode.

**Exit:** A one-task change uses one Builder plus free checks; complex work expands only for stated reasons; build and continue tell one coherent story.

### Phase 202 — Swarm, Oracle, and Live Colony Visibility

Restore a substantive four-lens Swarm, the Oracle research wizard and cockpit, and a live watch view sourced from typed runtime events. Include cross-hypothesis comparison, ranked repair, verification, rollback on failed repair, durable synthesis, active question/confidence/contradiction visibility, worker lineage, signals, findings, cost, and recovery.

**Exit:** Callum can run a stubborn real defect and a multi-round research question, watch both evolve, and understand their conclusions.

### Phase 203 — Biological Runtime

Implement typed `RecruitmentIntent`, admission/refusal, root/host-mediated dispatch where native nesting is unsafe, `RecruitmentResult`, acknowledged `TrophallaxisPacket` delivery, follow-on waves, subtree accounting, typed signal decision domains, influence attribution, and outcome-weighted reinforcement.

**Exit:** A real worker discovers a specialist need, receives governed help, acknowledges the packet, changes a downstream decision, and leaves an outcome-scored signal.

### Phase 204 — Learning Governor

Build the permanent evaluation bank, failure-to-eval conversion, outcome/intervention ledger, candidate shadow evaluation, tiered promotion, source-change PR boundary, and automatic rollback. Learned behavior may never weaken free checks or named safety gates.

**Exit:** A promoted behavior shows better verified useful-task outcomes per owner intervention without hard-gate regression.

### Phase 205 — Owner Acceptance and Restoration Seal

Run the complete lifecycle in real repositories, reconcile every ledger promise to delivered proof, and capture owner acceptance. This phase owns experience acceptance; it does not massage metrics to manufacture parity.

**Exit:** Callum states, “This feels like Aether again, and I trust how to use it.” Only then may the owner-watched proof benchmark the reunited system.

## Milestone-wide acceptance

- Outcome parity: the user reaches the same or better useful result.
- Behavior parity: the Queen/team/research/recovery loops actually happen and leave typed evidence.
- Experience parity: the user can see what is happening, why, and what comes next.
- Safety parity: malformed, stale, replayed, or out-of-scope inputs fail before mutation.
- Owner acceptance: live use, not snapshots alone, is the final gate.

## Explicit exclusions

- No return to shell or wrapper text as state authority.
- No endpoint-count or broad “80% parity” claim as completion proof.
- No irreversible pruning before the signed 72-row ledger.
- No fake recursive delegation where a platform cannot safely provide it.
- No Codex lifecycle-skill project inside this milestone; that follows only after the general experience is stable.
- No proof showdown against the fragmented interim product before restoration.
