<objective>
Make the spawn ledger's parser tell "there is no ledger yet" apart from "there is a ledger and it
has been tampered with", and make the ledger's sibling run-state file draw the same distinction.
Today both answer the same way — an empty result and a nil error — which is the root cause of the
whole-run budget being resettable to zero by one shell command.

Purpose: 173-VERIFICATION.md reproduced a working exploit. After the run's 20-helper budget was
legitimately exhausted and the 21st helper correctly refused, one line of non-pipe-format text
written over `.aether/data/spawn-tree.txt` made the identical refused request succeed and report
`budget_consumed:1`, as if the run had never happened. No special tool access is needed: the
`PreToolUse` hook matches `Write|Edit|Agent|Task` and never `Bash`, so an ordinary shell redirect
is enough. `parseFile()` swallows every read error and `parseSpawnTreeBytes` silently discards
every line it cannot parse, so no caller can tell a legitimately empty colony from a corrupted
one. `loadRunStateLocked()` has the identical swallow one file over. This plan fixes both at the
boundary; plan 12 turns the resulting errors into refusals.

Output: a spawn-tree parser with three distinguishable outcomes (absent, valid, corrupt), a
run-state reader that distinguishes absent from unreadable, a write path that refuses to overwrite
a corrupt ledger, and package-level red-proofs for each.
</objective>

Every field written by this package passes through `sanitizeSpawnField` (line 435), which replaces
`|` with `¦` and strips newlines — so a legitimately written line can never contain a stray pipe,
and the field counts above are EXACT, not lower bounds. That is what makes a true field count a
sound classifier.

Two writer-producible shapes are easy to reject by accident and must not be:
- a completion line whose status field is empty. `updateStatus` (line 255) normalises its status
  argument through `normalizeSpawnStatus`, which returns `""` for an empty or whitespace input, and
  then writes the line anyway. Today `parseSpawnTreeBytes` accepts that line's shape and ignores its
  content (`if status != ""`), and that behaviour must be preserved exactly.
- a spawn line whose task or status field is empty — still exactly 7 fields.

The trap this plan's revision exists to avoid: `strings.SplitN(line, "|", 4)` returns 4 fields for
ANY line containing three or more pipes, because everything past the third pipe is merged into the
last element. A 7-field spawn line with a non-numeric depth therefore "passes" a bounded 4-field
completion test with `fields[2]` landing on the CASTE field (e.g. `builder`), which normalises
non-empty — so a corrupt line would be accepted as a bogus completion record and no error returned.
Classification must be decided from the true field count before any field is read.

Classify every remaining line by its TRUE field count, taken ONCE with an unbounded split, before
any field is read: `fields := strings.Split(line, "|")`. Then switch on `len(fields)`:

- exactly 7 — a spawn-entry-shaped line. `strconv.Atoi(fields[5])` must succeed. If it does, build
  the entry exactly as today (same field order, same `normalizeSpawnStatus(fields[6])`, same
  `nameToIdx` bookkeeping). If it does NOT, the line is corrupt, and it must NOT be retried against

  line WITHOUT error. That ignore-without-error branch is today's behaviour and is required — see
  the round-trip rule below.
- anything else — corrupt. Return immediately with an error wrapping `ErrSpawnTreeCorrupt` that
  names the 1-based line number and the observed field count.

The bounded `strings.SplitN` calls the current code uses (`SplitN(line, "|", 7)` and
`SplitN(line, "|", 4)`) must not survive as classifiers. `SplitN(line, "|", 4)` returns 4 fields
for ANY line with three or more pipes, so a 7-field spawn line with a non-numeric depth would fall
through the spawn branch and then "pass" the completion test with `fields[2]` landing on the caste
field, which normalises non-empty — the corrupt line would be silently accepted as a bogus
completion record and no error returned. Deciding the shape from one true field count is what
prevents that, and is the reason this rule set is a switch on a single count rather than a sequence
of fallbacks.

Two cases that are silently skipped today become corruption errors, and this is the point of the
change: a 7-field line whose depth field is not a whole number (currently `continue // skip
malformed`), and any line whose true field count is neither 7 nor 4 — which includes the one-token
line the verifier's `echo "garbage" > spawn-tree.txt` produces.

One invariant outranks strictness everywhere above: THE PARSER MUST NEVER REJECT BYTES THIS
PACKAGE'S OWN WRITER CAN PRODUCE. `formatSpawnTreeLines` emits exactly the shapes listed in
`<interfaces>`, and `sanitizeSpawnField` guarantees no written field contains a pipe. In
particular, a completion line with an empty status field (`updateStatus` writes one whenever its
status argument normalises to empty) and a spawn line with an empty task or status field must both
keep parsing with a nil error. A parser that rejects its own writer's output converts a corruption
guard into a way to brick a live colony — a worse failure than the one this plan closes.

State the bound this rule set does NOT reach rather than implying it does: classification is by
shape only, so a line that is well-formed but false — a hand-written 4-field line, for instance —
is still accepted, and an attacker who copies the format can still empty the ledger. Closing that
requires integrity data the file does not carry (an append-only log, or a signature), which is out
of scope here and belongs in the phase's residue record. Do NOT add a timestamp-format check or a
known-status allowlist as a substitute: ledgers written by earlier versions may carry shapes those
checks would reject, and bricking existing colonies to inconvenience an attacker who can simply
copy the format is a bad trade.

The error message must NOT contain the offending line's own text. A spawn-tree line carries the
task description a worker was given; D-11 already refuses to write task text into the failure
record for this reason, and the same reasoning applies to an error string that will be printed to
a terminal and pasted into a bug report. Name the line number and the field count; never the
content.
