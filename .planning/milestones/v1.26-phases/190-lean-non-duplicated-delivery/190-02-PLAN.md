<objective>
Remove the TypeScript host's independent hive-wisdom computation and attachment (`hive_section`) so a
worker dispatched through the Go `internal-worker-adapter` boundary sees "HIVE WISDOM (Cross-Colony
Patterns)" exactly once -- via the Go colony-prime context capsule, the already-established, already
multiply-consumed single channel -- never twice.

Today `.aether/ts-host/src/hive-injector.ts`'s `readHiveWisdom` computes its OWN hive-wisdom section by
calling Go's `hive-read`/`registry-list` CLI directly, formats the IDENTICAL header text
("## HIVE WISDOM (Cross-Colony Patterns)") a SECOND time, and `.aether/ts-host/src/host.ts` attaches
it as `dispatch.hive_section` at four call sites (the shared dry-run runner covering build/plan/continue,
plus each workflow's own real-dispatch runner). That value flows through
`.aether/ts-host/src/worker-dispatch.ts` into a JSON request POSTed to Go's `internal-worker-adapter`
subcommand, where `cmd/internal_worker_adapter.go:404` MERGES it into `codex.WorkerConfig.SkillSection`
-- delivered to the worker ALONGSIDE `ContextCapsule`, which already contains the SAME hive content
from `cmd/colony_prime_context.go`'s `buildColonyPrimeOutput`. Both named live paths are confirmed
reachable: continue's interactive wrapper explicitly routes through `aether host continue --dry-run`
(`.opencode/commands/ant/continue.md:263`), and build's autopilot lane (`/ant-run`) drives
`runDispatchedBuildCommand` directly (the interactive wrapper is explicitly forbidden from this path,
`build.md:348`).

`hive_section`)"). Fixed at all four mechanically-identical call sites in one sweep, not just the two
named in the ROADMAP's parenthetical (190-CONTEXT.md D-09) -- the plan/build dry-run and plan's real

proof-of-presence tests.
