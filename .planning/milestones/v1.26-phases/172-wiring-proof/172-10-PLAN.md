<objective>
Close verification GAP A's core: success criterion 4's durability half is still false
after two attempts, both of which asserted on the TEXT of `.github/workflows/ci.yml`.
Attempt 1 used a whole-file substring search and was defeated by a decoy line elsewhere
in the file. Attempt 2 (plan 172-07) used a step-scoped substring search and was defeated
by `; true`, `|| exit 0`, an appended second `-run`, `| cat`, and a commented-out command.

**A third, cleverer text check is not what this plan builds.** Enumerating known-bad
spellings is a blocklist, and a blocklist cannot establish the property the criterion
asks for. The criterion states the method itself: *verified by deleting a caller and
observing the gate go red, not by reading the workflow file.*

Purpose: assert the gate's BEHAVIOUR. Take the release gate's command verbatim from
ci.yml, run it against a deliberately broken tree, and require a non-zero exit; run it
against an unbroken tree and require zero. Every mutation above collapses that
discrimination and is therefore caught by the mechanism rather than by a pattern list —
including the sixth mutation nobody has thought of yet.

Output: an execution harness in the guard file, a discrimination test over the real
command, a table test proving the harness catches all five reproduced bypasses, and both
tests wired into the named CI step.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| .github/workflows/ci.yml → the guard test | A contributor-editable workflow file supplies a command string that the guard then executes |
| the guard test → the CI runner shell | `sh -c` executes that string as a subprocess during `go test` |
| the probe module → the filesystem | Generated Go source and a module file are written before execution |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-172-47 | Elevation of Privilege | `sh -c` execution of a command read from ci.yml | accept | The same string is already executed by the CI runner as the real workflow step, so the guard grants no capability an attacker does not already have by editing the workflow; execution is confined to `cmd.Dir` under `t.TempDir()` and bounded by a 120s context. Plan 172-11 additionally pins the run line to an exact expected command, narrowing what can reach the shell at all |
| T-172-48 | Tampering | the extracted command diverging from what CI runs | mitigate | `releaseGateCommandFromWorkflow` reads the run line at test time; a hardcoded second copy is forbidden by an acceptance criterion that counts occurrences of the command text in Go source |
| T-172-49 | Denial of Service | a mutated or hung gate command stalling every CI run | mitigate | `exec.CommandContext` with a 120s deadline; a deadline is a `t.Fatalf`, never a silent pass; probe modules have zero dependencies so no network fetch can stall them |
| T-172-50 | Spoofing | a probe module that always fails (or always passes) making the guard vacuous | mitigate | `gateCommandDiscriminates` requires BOTH halves — exit 0 on the clean tree and non-zero on the broken one — so a probe that cannot pass, or cannot fail, is itself reported |
| T-172-51 | Repudiation | a future reader assuming the mutation table is the mechanism and extending it instead of trusting execution | mitigate | The table's doc comment states explicitly that the table is evidence and execution is the mechanism; the control row proves the harness discriminates on an unmutated command |
| T-172-52 | Information Disclosure | none — the probe writes only to a temp directory and reads only checked-in workflow text | accept | No secret, credential or network egress is involved |
</threat_model>
