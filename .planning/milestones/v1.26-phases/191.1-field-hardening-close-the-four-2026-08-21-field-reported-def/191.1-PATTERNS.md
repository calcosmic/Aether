# Phase 191.1 — Field Hardening: Patterns

House patterns executors must follow. Extracted from direct codebase reading during planning (191.1-CONTEXT.md), not assumed.

---

## Pattern 1: Field Reproduction As Test Case

Every fix in this phase traces to a verbatim reproduction quoted in one of the four todo files. The regression test for each fix must reproduce that SAME sequence through the REAL entrypoint the field hit — not a shortcut that exercises equivalent logic through a more convenient function.

Concretely in this phase:
- Plan 01's deadlock hardening test must call `stageBuildAttemptCompletion` (the function under the real `aether build-completion-stage` CLI command) before calling `runCodexBuildFinalize` — not skip straight to finalize the way the existing `TestForcedRedispatchAfterBuiltIsNotADeadlock` does. That existing test is good and stays; the new test closes the specific gap that it bypasses the stage step the wrapper protocol actually calls first (`cmd/command_guide.go:322`).
- Plan 02's checker-fix test must exercise `evaluateCriterionCheck` with a real `codexVerificationStep{Command: ..., Summary: ..., Passed: true}` and assert the returned evidence string is built from the real outcome, not echoed back from the command string.
- Plan 02's pause-race test must simulate the actual race: verification completes, `state.Paused` becomes true before `advancePhase` commits, and the test asserts the payload survives that specific failure path (not a generic "state gets saved somewhere" check).
- Plan 03's ceremony test must run fresh verification against a fixture repo's actual disk state, not against a canned/mocked "already verified" flag.

**Fail-then-pass is the default, not optional**, per the phase spec's fifth success criterion. Where the underlying behavior is ALREADY fixed (Plan 01's deadlock — see 191.1-CONTEXT.md D-01), fail-then-pass is not re-demonstrable for the already-fixed code path itself (it would require reverting a landed fix), so the new test proves the field SEQUENCE end-to-end instead; where the underlying behavior is genuinely new (Plans 01 Task 2/3, 02, 03), fail-then-pass must be shown directly: write the test, confirm it fails against the pre-fix code (or a deliberately-reverted local diff), then confirm it passes after the fix, and record the transcript in the plan's SUMMARY.

## Pattern 2: Ratchet House Style

Established by `cmd/colony_state_atomicity_ratchet_test.go`, `cmd/build_finalize_deadlock_test.go`, and Phase 191's `cmd/colony_zero_reader_config_ratchet_test.go`. Every new ratchet test in this phase follows it:

1. **Header doc comment** names: the field-report source (todo filename + date), the specific failure mode being guarded against, and what "fails loudly, never vacuously" means for THIS check specifically (e.g., "fails if zero destruction sites are found, not just if an unsafe one is found" — a guard that can silently stop checking anything is worse than no guard).
2. **Per-item failure, not aggregate pass/fail.** Use `t.Errorf` (continues checking) over `t.Fatalf` (stops at first failure) wherever multiple independent things are being verified, so one test run reports everything wrong, not just the first thing.
3. **Failure messages are actionable**, not just descriptive: name the specific violation, the rule/property it violates, and what a human should do about it (fix the code, or update the ratchet with new evidence — never just "this failed").
4. **Assert the preconditions the test's own narrative depends on**, not just the final outcome — e.g., before asserting "finalize succeeds after forced redispatch," assert the fixture actually has `CompletionSHA256 == ""` and all dispatches `planned`, so a fixture regression can't quietly turn the test into a no-op that still passes.

## Pattern 3: Reuse the Shared Call-Graph Reachability Guard — Do Not Reinvent a Weaker One

`cmd/worktree_destruction_reachability_test.go` already implements a generic, reusable AST-based call-graph builder for the entire `cmd/` package:

- `buildCmdFuncGraph(cmdDir string) (*cmdFuncGraph, error)` — parses every `.go` file under `cmd/` (excluding `_test.go`), indexes every top-level function's call set, and indexes every registered Cobra command as a `"cobra:<Use string>"` graph node.
- `reachableFrom(g *cmdFuncGraph, startNodes []string) map[string]bool` — generic BFS/DFS over that graph; not specific to worktree destruction.
- `lifecycleEntryCommands` (package-level `var`, same file) — the hand-maintained list of automatic lifecycle entry point command names (build, continue, init, resume-colony, run, build-finalize, continue-finalize, etc.), cross-checked at test time against the live command registry so it cannot silently drift from what is actually registered.

This exists BECAUSE a simpler, string-grep-based reachability ratchet (`TestWorktreeReapHasNoLifecycleCaller`, since replaced) was defeated by CR-05: a second destructive function existed, in an already-hardcoded file, under a name neither hardcoded string matched, and the grep-based test passed anyway.

**Plan 03's reachability ratchet for the new `verify-out-of-band` command must reuse `buildCmdFuncGraph`, `reachableFrom`, and `lifecycleEntryCommands` directly** (same package, `cmd`, so no import needed — just call them from a new test file). Build the graph, compute the reachable set from `lifecycleEntryCommands`, and assert the new command's `"cobra:verify-out-of-band <phase>"` node (and any function it alone calls to perform its state-mutating close) is NOT in that reachable set. Do not write a second grep-based ratchet — that regresses exactly the failure mode `worktree_destruction_reachability_test.go`'s own header comment documents.

## Pattern 4: Honesty Invariant Over Named-Section Presence

Per CLAUDE.md's Definition of Done: "prefer a test that asserts a proportion or an invariant over one that asserts a section exists." Plan 03's honesty ratchet (FIELD-05's "never fabricate worker receipts" property) must assert a STRUCTURAL invariant:

> The ceremony's produced/updated `buildAttemptRecord` has `Dispatches` and `WorkerRuns` fields byte-identical (or at minimum: same length, same statuses, no new entries) to what they were immediately before the ceremony ran.

This is checkable regardless of how the ceremony's internals evolve later, and it cannot be satisfied by a ceremony that happens to name its provenance field something honest-sounding while still writing synthetic dispatch entries under the hood — which a test that only checked for the PRESENCE of a `"verified-out-of-band"` string would miss entirely.

## Pattern 5: Extend the Shared Core, Don't Patch Each Caller

Phase 188 established (and ROADMAP.md's Phase 188 entry states directly) that both continue paths — `runCodexContinue` (native) and `advanceExternalContinue` (wrapper-external) — advance through the ONE shared `advancePhase()` core (`cmd/advance_phase.go`) specifically so a fix lands once and both callers inherit it, rather than each caller independently reimplementing "commit phase completion" with its own drift risk.

Plan 02's pause-race preservation mechanism (FIELD-04) must follow this precedent: extend `cmd/advance_phase.go` itself (or a function living in the same file, called by both `codex_continue.go:916` and `codex_continue_finalize.go:1168`), not two independent per-caller patches. This is not a style preference — a fix landed in only the wrapper-external path and not the native path recreates exactly the kind of divergence Phase 188 was built to close.

## Pattern 6: Validate Before Crediting — Never Trust a Worker's Self-Reported Task List

`dispatchCoveredTaskIDs` (`cmd/codex_build.go:2240`) already establishes the trust boundary for the RUNTIME-coalesced case: covered task IDs come from the MANIFEST (something the runtime itself constructed and hashed into the attempt journal), never from a worker's self-report, so a worker cannot claim credit for work never assigned to it.

Plan 01's new `codexExternalBuildWorkerResult.CoveredTaskIDs` field (FIELD-02) inverts WHO writes the covered list (now the worker, since the wrapper bundled the work on its own and the manifest never learned about it) but must NOT invert the trust boundary. Every ID a worker result names in `covered_task_ids` must be validated against `manifest.Dispatches`' own `TaskID`/`CoveredTaskIDs` set before any credit is granted — an unrecognized ID is a contract violation (same `contractViolation` shape already used throughout `cmd/codex_build_finalize.go`), not a silently-accepted claim.
