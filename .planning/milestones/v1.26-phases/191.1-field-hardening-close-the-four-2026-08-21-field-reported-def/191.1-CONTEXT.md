## Contract (success criteria, verbatim from the phase spec)

1. The deadlock state (attempt committed + dispatches planned) is unreachable, or self-healing in-band — proven by a test reproducing the exact field sequence (`build-completion-stage` → both refusals) and showing the exit.
2. A worker that covered N tasks the manifest lists separately CAN file honestly (packet expressibility), validated against the manifest — and finalize detects the 1-result-for-N-dispatches shape and offers the repair in-band rather than the provenance refusal.
3. Continue's embedded checker returns real verdicts: the field bug (reason = the check's own description/command text) has a named regression test; a completed verification that loses the supersession race to a pause is preserved for re-apply after resume, not discarded.
4. An owner-invoked out-of-band reconciliation ceremony exists: fresh verification of CURRENT disk state against the phase's own success criteria, recorded with verified-out-of-band provenance — with a ratchet asserting it can NEVER fabricate worker receipts (the honesty property).
5. Each fix's test reproduces the FIELD failure first (fail-then-pass) — the reproductions in the todos are the test cases.

### D-05: The wrong-field bug is code-located, not inferred

`evaluateCriterionCheck`'s default branch, `cmd/criterion_evidence.go:618`:

```
return true, fmt.Sprintf("%s check passed: %s", check, strings.TrimSpace(step.Command)), ""
```

reports a PASSING required check's evidence using `step.Command` — the raw, configured shell command string (the check's own DEFINITION) — instead of the actual verified outcome (`step.Summary`, e.g. `"tests passed"`, built by `successSummaryForStep`). This is the exact bug shape the todo describes: *"the code populating the verdict/reason maps the wrong field from the check definition (its description/command) instead of the check's actual output/result."* The FAILURE branch three lines below (line 623) already correctly uses `step.Summary`; only the PASS branch has the bug. This asymmetry (fixed on failure, broken on success) is consistent with the field report's mix of "successful" runs carrying description-shaped text.

This is the confirmed, fixable instance of the bug class. It is planned as a direct fix + regression test. Whether it is the ONLY instance that produced every quoted downstream string cannot be confirmed without the downstream repo's exact check configuration (their `## Verification Commands` section) — the fix targets the mechanism, which is sufficient: it is architecturally impossible for a PASSING check to report its own command text after this fix, for any configuration.

### D-06: `--skip-watchers` + a `watcher`-required criterion is intentional, not a bug

`evaluateCriterionCheck`'s `"watcher"` case (`cmd/criterion_evidence.go:609-613`) requires an actually-passed, non-skipped watcher when a bound criterion names `watcher` in its `Checks` list — `--skip-watchers` setting `watcher.Status = "skipped"` correctly fails this check. This is the exact "compounding factor" the todo names, and the todo's own text treats the session's workaround (dispatching reviewers directly, bypassing the broken embedded checker) as the *correct* move, not evidence this gate should be weakened. **Decision: not a bug. Not touched.** A criterion that explicitly requires a reviewer's sign-off must not be satisfiable by skipping the reviewer — that would be a quality/security hole, not a UX fix.

### D-07: Pause-race fix takes the "preserve + cheap re-apply" shape, not the "lease" alternative

The todo offers two shapes: "(preserve the completed verification result for a re-apply after resume) or (have continue take a lease the stop hook respects)." The phase spec's own criterion 3 text says only *"preserved for re-apply after resume, not discarded"* — selecting the preserve+reapply shape as the locked decision. The lease alternative is not planned.

**Design, grounded in the existing mechanism:** `advancePhase` (`cmd/advance_phase.go`) is the single shared core both `runCodexContinue` (`cmd/codex_continue.go:916`) and `advanceExternalContinue` (`cmd/codex_continue_finalize.go:1168`) call. It fails closed via `validateRuntimeStateStillCurrent`, whose FIRST check is `if state.Paused { return runtimeStateSupersededError(phaseNum, "colony is paused") }` (`cmd/codex_build.go:2668`, shared helper). On this specific supersession reason, both callers currently discard everything they already computed (`verification`, `assessment`, `gates`, `review` — the expensive ~10-minute payload) and return a generic `continueSupersededResult`, which carries none of it forward. Fix: when (and only when) the supersession reason is specifically "colony is paused" — not a genuinely stale phase/build identity, which must still discard — persist the already-computed bundle durably, keyed to phase ID + `BuildStartedAt`, and consume it automatically (skip re-verification) the next time continue/continue-finalize runs against a colony state whose phase and build identity still match exactly.

### D-08: The preserve mechanism lives in the shared core, not duplicated per caller

Consistent with Phase 188's own stated principle (both continue paths advance through one shared `advancePhase()` with the supersession check) — extend `cmd/advance_phase.go` itself (or a thin sibling in the same file) so both `codex_continue.go` and `codex_continue_finalize.go` get the preserve/replay behavior from one place, not two independently-maintained copies.

### D-09: Criterion 4's ceremony is a new, distinctly-named command — not an extension of `aether reconcile`

`aether reconcile` (`cmd/reconcile.go:119`) is confirmed read-only (`Long: "...without mutating .aether/data..."`) and answers a different question (repo/version/state hygiene report). The new ceremony needs to MUTATE — closing a stuck attempt and advancing colony state — so it cannot be a mode of `reconcile` without breaking that command's own read-only contract. **Decision:** new command, `aether verify-out-of-band <phase>`, named and structured after `worktree-reap`'s precedent (`cmd/worktree_reap.go`): explicit `Use` string, operator-only, mutating action gated behind an explicit flag where the action is destructive/state-changing, protected by a reachability ratchet mirroring `TestWorktreeReapHasNoLifecycleCaller`'s intent (see D-10, Plan 03).

### D-10: The ceremony reuses existing evidence-gathering machinery; it does not reinvent verification

"Fresh verification against current disk state" is built from pieces that already exist and are already trustworthy:
- `runVerificationStep` (`cmd/codex_continue.go:2897`) for the repo's real build/types/lint/tests commands, run live.
- `snapshotBuildArtifact` / `attachBuildArtifactEvidence` (`cmd/criterion_evidence.go:283,303`) for hash-verifying specific files against disk NOW — seeded from the phase's own bound `CriterionEvidenceRequirement.Artifacts` (`flattenPhaseCriterionEvidenceRequirements(phase)`, same file), not from worker self-reports.
- `advancePhase` (`cmd/advance_phase.go`) to actually close/advance, called with a distinct `Source` value (`"verify-out-of-band"`) for auditability in the events log, exactly as its `Source` field already supports.

This is not a new verification engine — it is the same evidence primitives continue already trusts, pointed at "what exists on disk right now" instead of "what a worker journal claims," with a distinct provenance marker so the two are never confused.

### D-11: The honesty ratchet is stated as a structural invariant

Per CLAUDE.md's Definition of Done ("prefer a test that asserts a proportion or an invariant over one that asserts a section exists"): the ceremony's `buildAttemptRecord.Dispatches` and `WorkerRuns` must be provably UNCHANGED by the ceremony (it only sets the new provenance marker + `Claims` built from real, hash-verified artifact evidence). The regression test asserts this directly — `len`/content equality before and after — rather than asserting "no fake worker" by name-pattern-matching, which a future rename could quietly defeat.
