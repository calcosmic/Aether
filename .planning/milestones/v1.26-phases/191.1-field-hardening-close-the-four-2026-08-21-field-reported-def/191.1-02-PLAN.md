(`.planning/todos/pending/2026-08-21-continue-checker-captures-wrong-field.md`): a downstream colony's embedded
continue watcher failed 3 of 5 runs and, on two of the "successful" ones, reported the CHECK'S OWN

(191.1-CONTEXT.md D-05): `evaluateCriterionCheck`'s default-case PASS branch formats its evidence string from
`step.Command` (the raw configured shell command -- the check's DEFINITION) instead of `step.Summary` (what was
actually verified). The FAILURE branch three lines below already does this correctly; only PASS is broken.

**FIELD-04** is the "small pause-race UX item" folded into the same todo: a ~10-minute embedded verification
run that finishes just as a stop hook pauses the colony gets its completed, PASSING result discarded --
`advancePhase`'s shared core (`cmd/advance_phase.go`) refuses with "colony is paused" (correctly -- Phase 188's
supersession protection working as designed) but the caller then throws away everything it just computed. This
plan makes that specific supersession reason preserve-and-replay instead of discard, while every OTHER
supersession reason (stale phase/build identity) keeps discarding exactly as today (191.1-CONTEXT.md D-07).

Purpose: continue's own verdict-reporting was the single most disruptive downstream defect (3 of 5 runs wrong),
and its compounding pause-race gap turns an already-expensive verification pass into wasted work. Fixing the
verdict bug without the preservation half would still leave a correct-but-discarded result look like a failure.
Output: one production fix + regression test (FIELD-03); one shared preserve/replay mechanism wired into both
continue call sites + regression tests (FIELD-04).

func evaluateCriterionCheck(check string, steps []codexVerificationStep, claims codexClaimVerification, watcher codexWatcherVerification) (bool, string, string) {
	check = strings.ToLower(strings.TrimSpace(check))
	switch check {
	case "claims":
		if claims.Present && claims.Passed && !claims.Skipped {
			return true, "current-build claims verified", ""
		}
		return false, "", "current-build claims were missing, skipped, or failed verification"
	case "watcher":
		// D-06: this branch is INTENTIONAL and stays exactly as-is -- do not touch.
		if watcher.Present && watcher.Passed && !strings.EqualFold(strings.TrimSpace(watcher.Status), "skipped") {
			return true, fmt.Sprintf("watcher %s passed", firstNonEmpty(watcher.Worker, "verification")), ""
		}
		return false, "", "an executed Watcher review did not pass"
	default:
		for _, step := range steps {
			if strings.EqualFold(strings.TrimSpace(step.Name), check) {
				if step.Passed && !step.Skipped {
					// BUG (FIELD-03): this line reports step.Command (the raw configured
					// shell command -- the check's DEFINITION) instead of the actual
					// verified outcome. Change the second %s argument from step.Command to
					// step.Summary (built by successSummaryForStep, e.g. "tests passed").
					return true, fmt.Sprintf("%s check passed: %s", check, strings.TrimSpace(step.Command)), ""
				}
				if step.Skipped {
					return false, "", fmt.Sprintf("required %s check was skipped", check)
				}
				return false, "", fmt.Sprintf("required %s check failed: %s", check, step.Summary)
			}
		}
		return false, "", fmt.Sprintf("required %s check was not present", check)
	}
}

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| In-flight, already-computed continue verification payload vs. a racing pause request from a stop hook | A completed but not-yet-committed result and an operator-initiated pause can arrive in either order; the system must not silently destroy real, already-verified work when pause wins the race. |
| Dispatched/subprocess watcher output -> parsed pass/fail verdict | The runtime must report what a check actually found, not what the check was configured to run. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-191.1-02-01 | Repudiation | `evaluateCriterionCheck` pass-branch evidence text | mitigate | Fixed to report `step.Summary` (the verified outcome), never `step.Command`; regression-locked by `TestCriterionCheckReportsOutcomeNotRawCommandText` |
| T-191.1-02-02 | Denial of Service | Pending-advance records accumulating if never replayed (operator never resumes, or resumes into a different phase) | mitigate | A pending record whose phase/`BuildStartedAt` identity no longer matches current state is discarded (deleted) the next time it is checked, not kept indefinitely |
| T-191.1-02-03 | Tampering / Elevation of Privilege | A stale preserved verification result replayed against colony state that has since moved on | mitigate | Replay requires an exact phase ID + `BuildStartedAt` match against CURRENT state; `advancePhase`'s own `validateRuntimeStateStillCurrent` independently re-checks identity at commit time regardless, so even a wrongly-replayed stale payload is refused by the same gate an ordinary stale write would hit |
| T-191.1-02-04 | Spoofing | N/A -- no new external input surface | accept | The preserved payload is written and read by the same local process/session from local disk only; no new untrusted input crosses a boundary |
