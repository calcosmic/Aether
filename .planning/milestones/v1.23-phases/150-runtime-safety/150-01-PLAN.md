# Plan 150-01: Classify Provider API Errors Before JSON Parsing

**Objective:** When a worker subprocess fails due to provider auth, rate limits, or model errors, the user sees the real cause -- not "parse worker output: no JSON found".

## must_haves

- Worker invocation classifies provider errors by exit code and stderr patterns before attempting JSON parse
- Auth failures report "provider auth failure"
- Rate limit failures report "rate limited"
- Model/availability failures report "provider unavailable"
- All other failures fall back to existing "no JSON found" behavior
- A test verifies each error classification

## tasks

### Task 1: Define error classification rules

<read_first>
- pkg/codex/worker.go (Invoke, error handling)
- pkg/codex/worker_test.go (existing tests)
</read_first>

<action>
1. In worker.go, before attempting to parse worker output as JSON:
   a. Check the subprocess exit code
   b. Scan stderr for known provider error patterns:
      - "authentication" / "auth" / "API key" / "401" → provider auth failure
      - "rate limit" / "429" / "too many requests" / "throttled" → rate limited
      - "model not found" / "model unavailable" / "503" / "overloaded" → provider unavailable
      - "context length" / "token limit" / "too long" → context exceeded
   c. If a pattern matches, return a WorkerResult with Status="failed" and Error containing the classified message
   d. Only if no pattern matches, attempt JSON parse
2. Document the classification rules in a comment block in worker.go
</action>

<acceptance_criteria>
- Classification rules are documented in worker.go comments
- At least 4 provider error categories are handled
</acceptance_criteria>

### Task 2: Implement error classification in worker invocation

<read_first>
- pkg/codex/worker.go (the actual Invoke/InvokeWithProgress functions)
</read_first>

<action>
1. In the Invoke/InvokeWithProgress functions, after the subprocess completes:
   a. If exit code != 0, run classifyProviderError(stderr, exitCode)
   b. If classification returns non-empty, construct WorkerResult with:
      - Status: "failed"
      - Error: fmt.Errorf("provider error: %s", classification)
      - RawOutput: stderr + stdout
   c. Skip JSON claims parsing entirely for classified provider errors
   d. If classification is empty, proceed with existing JSON parse logic
2. Ensure FakeInvoker behavior is unchanged
</action>

<acceptance_criteria>
- Provider errors bypass JSON parsing entirely
- FakeInvoker still works as before
- Existing worker tests still pass
</acceptance_criteria>

### Task 3: Add classification tests

<read_first>
- pkg/codex/worker_test.go (test patterns)
- pkg/codex/dispatch_test.go (if exists)
</read_first>

<action>
1. Create `pkg/codex/worker_error_classify_test.go` with tests:
   - TestClassifyAuthFailure: stderr contains "authentication failed" → "provider auth failure"
   - TestClassifyRateLimit: stderr contains "rate limit exceeded" → "rate limited"
   - TestClassifyUnavailable: stderr contains "model overloaded" → "provider unavailable"
   - TestClassifyContextExceeded: stderr contains "context length exceeded" → "context exceeded"
   - TestClassifyUnknownError: stderr contains random text → "" (fallback to JSON parse)
   - TestProviderErrorSkipsJSONParse: verify that a classified error does not attempt JSON parsing
2. Use table-driven tests
</action>

<acceptance_criteria>
- `go test ./pkg/codex/... -run TestClassify -count=1 -v` passes
- All 6 test cases pass
</acceptance_criteria>

### Task 4: Update build and continue to surface classified errors

<read_first>
- cmd/codex_build.go (worker result handling)
- cmd/codex_continue.go (worker result handling)
</read_first>

<action>
1. In build and continue, when a worker result has Error != nil and Status == "failed":
   a. If the error message contains "provider error:", render a user-friendly message:
      - "Provider authentication failed. Check your API key and try again."
      - "Rate limited by provider. Wait a moment and retry."
      - "Provider temporarily unavailable. Try again later."
   b. Log the raw error for debugging
2. Update any existing error rendering to use the classification
</action>

<acceptance_criteria>
- Build/continue render user-friendly messages for classified provider errors
- Raw error is preserved in logs
</acceptance_criteria>

## risks

- Provider error messages change over time -- patterns may need updating
- Some provider errors may look like valid worker output -- false positives
- The classification is heuristic, not guaranteed
