# Phase 198.1: Code Review Report

**Reviewed:** 2026-08-30T12:11:42Z
**Depth:** standard
**Files Reviewed:** 41
**Status:** issues_found

## Summary

Phase 198.1 wires build/check worker outcomes into four memory stores
(midden.json, learning-observations.json, instinct application history,
pheromones.json) plus phase-end hive promotion. The overall design is
careful: nil-store guards exist everywhere a fresh colony could hit these
paths, memory-feed failures are consistently warned-to-stderr rather than
propagated as build/check failures, dedup keys are mostly well-chosen, and
the test suite is unusually rigorous — it drives real dispatch/continue
flows through the runtime's own parsers rather than typing fixture structs
by hand, and several tests explicitly assert non-blocking behavior (e.g.
`TestFeedingMemoryNeverFailsABuild`, `TestHiveFailureNeverBlocksThePhase`).

Two real defects were found. First, the native (in-process) swarm lane
(`executeSwarmWave`) silently drops an entire category of legitimate worker
failures from the failure log — the exact opposite of what its own inline
comment claims it does — because its status-transition check only fires on
a Go-level invoker error, not on a worker that itself successfully returns a
"failed" or "timeout" status. The parallel wrapper-lane function
(`mergeExternalSwarmResults`) gets this right by checking the final merged
status unconditionally; the native lane should do the same. Second, two of
the four new midden-writing functions this phase introduces
(`recordFailedChecksToMidden`, `recordQuickFailureToMidden`) skip the
sanitization step every sibling function in the same commit applies before
writing worker-adjacent text to a store that later gets injected verbatim
into a future AI worker's prompt — an inconsistency this phase's own design
shows it was aware needed guarding against.

## Critical Issues

### CR-01: Native swarm lane silently drops self-reported worker failures from the failure log

**File:** `cmd/swarm_cmd.go:1008-1024`
**Issue:** `executeSwarmWave` is supposed to record every failed or timed-out
swarm worker to midden.json (this is the stated purpose of T-198.1-02, and
the parallel wrapper-lane function `mergeExternalSwarmResults` — lines
792-798 — does it correctly by checking `execution.Status == "failed" ||
execution.Status == "timeout"` on the final, fully-merged status). But the
native lane only calls `recordSwarmWorkerFailureToMidden` in two narrow
cases:

```go
if execution.Status == "" {
    execution.Status = "failed"
    recordSwarmWorkerFailureToMidden(swarmID, target, execution)
}
if execErr != nil && execution.Status == "completed" {
    execution.Status = "failed"
    recordSwarmWorkerFailureToMidden(swarmID, target, execution)
}
```

If the invoker call itself succeeds (`execErr == nil`) but the worker's own
`codex.WorkerResult.Status` (or `swarmWorkerResponse.Status`) is directly
`"failed"` or `"timeout"` — the ordinary, expected way a worker reports its
own failure without any Go-level plumbing error — neither branch fires:
`execution.Status` is already non-empty (so branch 1 is skipped) and
`execErr` is nil (so branch 2 is skipped). The failure is never written to
midden.json, never counted toward `middenAutoRedirectThreshold`, and never
reaches a future worker's "Recent Failures" context.

The only test exercising this path (`TestSwarmWorkerFailureReachesTheFailureLogOnBothLanes`
in `cmd/memory_feed_continue_test.go`) uses `failingWorkerInvoker`, which
returns a Go-level error from `Invoke` — it never exercises a worker that
returns a normal (`err == nil`) result carrying `Status: "failed"`, so this
gap is untested and would pass the existing suite unchanged.

**Fix:** Mirror the wrapper lane exactly — check the final status once,
after all transitions, rather than gating on how the status got there:

```go
if execErr != nil {
    execution.Blockers = append(execution.Blockers, execErr.Error())
}
if execution.Status == "" {
    execution.Status = "failed"
}
if execErr != nil && execution.Status == "completed" {
    execution.Status = "failed"
}
if execution.Status == "failed" || execution.Status == "timeout" {
    recordSwarmWorkerFailureToMidden(swarmID, target, execution)
}
```

### CR-02: Two of four new midden writers skip the sanitization pipeline the phase itself established, letting untrusted tool output reach a future worker's prompt

**File:** `cmd/memory_feed_continue.go:127-154`
**Issue:** This phase introduces four functions that append to midden.json
from outcome text: `middenMessageForFailedWorker` (`cmd/memory_feed.go:132`),
`recordSwarmWorkerFailureToMidden` (`cmd/memory_feed_continue.go:160`),
`recordFailedChecksToMidden` (`cmd/memory_feed_continue.go:127`), and
`recordQuickFailureToMidden` (`cmd/memory_feed_continue.go:145`). The first
two explicitly call `colony.SanitizeSignalContent` before storing — the same
sanitizer that rejects XML structural tags, prompt-injection phrases, and
shell-injection patterns before pheromone content is stored (per CLAUDE.md's
Pheromone System section and `pkg/colony/sanitize.go`). The other two do
not:

```go
// recordFailedChecksToMidden
message := fmt.Sprintf("%s — check on phase %d", trimmed, phase.ID)
// trimmed comes straight from result.BlockingIssues -- raw build/vet/lint/
// test tool output -- with no sanitisation call anywhere in this function.

// recordQuickFailureToMidden
message := fmt.Sprintf("%s — quick query %q failed", errText, strings.TrimSpace(question))
// errText comes straight from err.Error() -- again, no sanitisation call.
```

This matters because midden.json is not a passive log: `resolveRecentFailuresSection`
(`cmd/memory_feed.go:206-243`, new this phase) reads these entries back and
injects them verbatim into a future builder's prompt via
`composeBuildManifestBrief`'s self-contained (native `aether build <phase>`
and `--print-brief`) path, and the pre-existing colony-prime capsule's own
"## Recent Failures" section does the same for the wrapper lane. Neither
read path re-sanitizes; `writePheromoneSignal` happens to re-sanitize
because it is a separate store, but midden.json's own read paths do not.
Build, lint, and test tool output is not fully trusted — it can be shaped by
a malicious dependency, a compromised file in the repo, or (for the quick
path) an adversarial or copy-pasted question — and this phase's own design
already recognizes that risk for two of the four call sites. The other two
should get the same treatment for consistency and because they are just as
reachable by the same class of content (compiler/linter/test-runner stdout
and stderr are exactly the kind of place a crafted prompt-injection string
would be planted).

**Fix:** Route both messages through the same sanitizer before storing,
falling back the same way `middenMessageForFailedWorker` does on rejection:

```go
func recordFailedChecksToMidden(phase colony.Phase, result deterministicFloorResult) {
	for _, issue := range result.BlockingIssues {
		trimmed := strings.TrimSpace(issue)
		if trimmed == "" {
			continue
		}
		sanitized, err := colony.SanitizeSignalContent(trimmed)
		if err != nil {
			sanitized = "a check failure could not be safely recorded"
		}
		message := fmt.Sprintf("%s — check on phase %d", sanitized, phase.ID)
		if err := recordWorkerFailureToMidden(middenCategoryCheckFailed, "aether continue", message, []string{"check"}); err != nil {
			fmt.Fprintf(os.Stderr, "warning: could not record failed check to memory: %v\n", err)
		}
	}
}
```

(and analogously for `recordQuickFailureToMidden`'s `errText`).

## Warnings

### WR-01: `--no-learn` no longer disables all learning writes, only the legacy `learn.Entry` capture

**File:** `cmd/memory_feed_continue.go:41-44`
**Issue:** `captureContinueMemory` is documented and tested to run
`feedContinueWorkerMemory` unconditionally, regardless of `noLearn`:

```go
func captureContinueMemory(phase colony.Phase, workerFlow []codexContinueWorkerFlowStep, gates codexContinueGateReport, runID string, noLearn bool, now time.Time) {
	captureContinueLearning(phase, workerFlow, gates, runID, noLearn, now)
	feedContinueWorkerMemory(phase, workerFlow)
}
```

`TestCheckWorkerLessonsBecomeObservationsOnBothLanes`'s "fast path" subtest
passes `noLearn=true` specifically to prove observations are still written.
This is a deliberate, documented choice ("a check that blocked still
records what it learned and what broke"), and the reasoning for decoupling
the eligibility *gate* (all workers succeeded AND gates passed) from memory
feeding is sound. But `noLearn` is the same flag `isLearningEnabled(noLearn)`
resolves from the user-facing `--no-learn` flag — a user who explicitly asks
not to learn from a run will still have that run's lessons and failures
written to `learning-observations.json` and `midden.json`, then surfaced in
worker prompts on later phases. This is a behavior change from what the flag
name promises, not a bug in the mechanical sense, but it is worth a
one-line callout in user-facing docs (`--no-learn` help text /
`.aether/docs/`) so this isn't discovered by surprise.
**Fix:** Either rename the bypassed check clearly in a doc comment on the
CLI flag itself, or add a second, narrower flag/gate if a future user
genuinely wants zero writes to any memory store on a given run.

### WR-02: `appendMiddenEntryOnce`'s dedup key can only be reasoned about because callers happen to embed variable attribution in the message

**File:** `cmd/memory_feed.go:181-196`
**Issue:** `appendMiddenEntryOnce` dedups on exact `(category, message)`
equality against unacknowledged entries. This works correctly today only
because every message built by this phase's callers embeds enough
call-specific detail (phase ID, worker name, status) to make genuinely
different failures produce genuinely different strings, and enough
consistency (same phase, same issue text) to make genuine repeats collapse
as intended (`TestFailedCheckWritesOneFailureRecordOnBothLanes` explicitly
proves the repeat case). There is no test proving the inverse — that two
distinct failures which happen to render into byte-identical messages (e.g.
two different phases whose `trimmed` check-output text happens to match,
with `phase.ID` coincidentally equal is not possible, but `recordQuickFailureToMidden`
has no phase ID in its message at all, so two different quick queries whose
`err.Error()` text is identical, worded around a different `question`, are
still distinguished only by the question text making it into the message)
never collapse into one silently-suppressed entry. Low risk today, but the
dedup contract is implicit in message construction rather than an explicit,
documented key — a future caller that builds a less-detailed message could
silently reintroduce suppression of real, distinct failures.
**Fix:** No code change required now; consider documenting the "message
must be locally unique across genuinely distinct failures" contract
directly on `appendMiddenEntryOnce`'s doc comment so a future caller doesn't
violate it by accident.

### IN-01: `golden_continue.txt`'s test-duration line changed for reasons unrelated to this phase's own code

**File:** `cmd/testdata/golden_continue.txt:45`
**Issue:** The diff changes `Tests ✓ (0.5s)` to `Tests ✓ (0.0s)` in the
golden fixture, alongside the intended additions (the new "Steering
signals" and "Your standing instructions" lines from `emitPhaseCompletionFeedback`).
This particular line has no apparent connection to phase 198.1's own
changes and suggests the golden file was regenerated from a live run rather
than hand-edited only where needed — worth a second look to confirm the
`0.0s` value isn't a flake (e.g., a test double or fake clock producing a
non-deterministic duration) that could make this golden test intermittently
fail for unrelated future changes.
**Fix:** Confirm the golden generator use a fixed/faked timer for this
line; if not, pin it the same way other golden entries are pinned (e.g.
`Worker-XX`).
