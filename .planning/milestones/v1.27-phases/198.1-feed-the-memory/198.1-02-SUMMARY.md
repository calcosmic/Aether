# Phase 198.1 Plan 02: Feed the Memory (check, quick, swarm) Summary

**Continue's reviewers, the program's own build/type/lint/test checks, one-off queries, and bug-swarm workers now all write into the same failure log (midden.json) and observation log (learning-observations.json) `aether memory-capture` already uses -- on every lane that can produce them, including when the check blocked.**

## Accomplishments

- Every check-lane reviewer's `ReusableLessons` becomes a "pattern" observation and every `WeakSpots` entry becomes a "redirect" observation, on the wrapper-driven (external) lane and the fast (default) lane alike -- proven by driving a real external continue completion packet through `mergeExternalContinueResults` and the finalize path for one row, and the exact `captureContinueMemory` entry point the fast path itself calls for the other.
- A check that blocks (gates failed, or a reviewer failed) still records what it learned and what broke: `feedContinueWorkerMemory` runs unconditionally from `captureContinueMemory`, even though `captureContinueLearning`'s own eligibility gate (unchanged) returns early and writes no `learn.Entry`.
- A failing build, type, lint or test step -- or a criterion-evidence gap -- now leaves exactly one failure record whose message leads with that check's own summary text, written from inside `runDeterministicFloor` itself so all four of its callers (both continue lanes, the automatic check-fix retry, and build-finalize's own verify pass) get the write for free, with no lane-specific plumbing. Running the same failing check twice still produces one record (`appendMiddenEntryOnce`, reused unchanged from Plan 01).
- `consolidation-phase-end --dry-run` still writes nothing (instincts.json, learning-observations.json, midden.json all byte-identical before/after), confirmed with midden.json newly added to the watched-file set now that a writer targets it.
- A `/ant-quick` dispatch that fails to invoke its scout worker, and a swarm worker that fails or times out on either the in-process or wrapper-driven lane, each write one failure record carrying the worker's own error text or summary.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Environment-warning test fixture initially misfired against the wrong code path**
- **Found during:** Task 2
- **Issue:** The first fixture (`tests: this-command-does-not-exist-xyz`) was rejected entirely by `looksLikeVerificationCommand`'s recognized-prefix allowlist and never resolved to a command at all. The second attempt (`tests: sh -c missing-binary-does-not-exist-xyz`) resolved and ran, but exited 127, which `isCommandUnresolvable` classifies as "command unavailable, skip" (Passed:true) rather than an environment-class failure -- a distinct, pre-existing code path from the one this test needed to exercise (`classifyVerificationError`'s environment-pattern match on a real product-shaped failure).
- **Fix:** Changed the fixture to `echo permission denied 1>&2; exit 1` -- a recognized command (`echo` prefix) that exits non-zero without tripping the "command unresolvable" classification, correctly routing through `classifyVerificationError` to `ErrorClassEnvironment`.
- **Files modified:** cmd/memory_feed_continue_test.go
- **Verification:** Test passes; floor.Warnings is non-empty and floor.BlockingIssues is empty, confirmed by reading the actual `deterministicFloorResult` the fixture produces at each iteration rather than guessing.
- **Committed in:** `124fa67c` (test commit)
