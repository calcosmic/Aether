<objective>
Make finishing a project a decision the owner takes, not something that happens. Show a short
state-of-play card, run the what-did-we-learn review, then ask — and only complete when the
answer is recorded.

Purpose: today there is no confirmation of any kind in the runtime. The only "are you sure"
is wrapper prose telling the owner to retype the command with an override flag. D-04..D-07
require a real gate, the review before the question, and an explicit second question naming
whatever is still broken.

Output: `cmd/seal_confirmation.go`, an extracted `runSealWisdomReview` so the review runs
exactly once and before any state change, the wrapper triplet describing the new stop, and
six named lock tests.
</objective>

  <behavior>
    - With nothing failing and no recorded answer, the seal prints the card, runs the review, asks one question and exits without changing colony state.
    - With something failing and no recorded answer, the card names each problem and a second, explicit question is asked naming how many there are.
    - With a recorded owner answer of yes and no named problems, the seal proceeds and completes.
    - With named problems and a recorded plain yes that does not cover those problems, the seal still does not proceed.
    - With named problems and a recorded finish-anyway answer that names them, the seal proceeds.
    - A recorded no leaves the project unfinished, and the lessons from the review are still present in the store afterwards.
    - decideSealConfirmation is total and side-effect free: it never reads the rendered card and never touches the store.
  </behavior>
  <action>
Create `cmd/seal_confirmation.go` and wire it into `sealCmd` between the blocker check and
`completeSealRuntime`.

1. `sealStateOfPlay` struct + `buildSealStateOfPlay(state colony.ColonyState, blockers, issues []colony.Flag) sealStateOfPlay` carrying: phases completed and total, the named still-failing checks and unresolved items derived from `checkSealBlockers`'s existing outputs, the open warnings, and a short list of what finishing actually does. Compute nothing new — read what the seal flow already computed.

2. `renderSealStateOfPlayCard(card sealStateOfPlay) string` — house style (SEE-12): an emoji heading, a plain-English parenthetical, one line per item, nested detail with the `└──` marker capped per category with an honest "(+N more)". Every repo word is translated inline: finishing the project means writing a summary document, filing the project away, and pooling its lessons into the shared store other projects read. Never a bordered table.

3. `sealConfirmationInput` / `sealConfirmationDecision` / `decideSealConfirmation(input) sealConfirmationDecision` — a pure, total policy evaluated in one fixed order, mirroring `decideBuildCheckin`:
   - autopilot or any non-interactive caller: never proceed, and never treat the absence of an answer as a yes (D-07);
   - a recorded owner answer covering the named problems: proceed;
   - a recorded plain yes with named problems outstanding: do not proceed, and ask the second question;
   - no recorded answer: do not proceed, ask the first question (and the second when problems are named).
   Inputs are already-resolved facts (`RecordedAnswer`, `NamedProblems []string`, `Autopilot bool`, `Force bool`); the function must not read the store or any rendered string.

5. In `sealCmd`: build the card, print it, run `runSealWisdomReview` (D-05 — before the

   next" resolver so two surfaces cannot name different commands (Phase 197 S-01). When it
   proceeds, call `completeSealRuntime` with the already-run review.
