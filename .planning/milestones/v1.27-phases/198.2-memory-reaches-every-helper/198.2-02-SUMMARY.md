# Phase 198.2 Plan 02: Oracle Research Reaches the Next Helper Automatically Summary

**A finished, capped, or interrupted Oracle deep-research run now files its write-up, points the colony at it, and promotes strong findings into origin-labelled habits, all with zero hand-typed follow-up commands.**

- **Started:** 2026-08-30T00:00:00Z (approximate; not machine-timed at start)
- **Completed:** 2026-08-30T01:00:00Z (approximate)
- **Tasks:** 3
- **Files modified:** 10 (9 modified, 1 created)

## Accomplishments

- A completed or capped Oracle run's write-up is saved and automatically registered on `COLONY_STATE.json`'s `research_docs` pointer list, so the next build/plan/research-scout brief reads it via the existing `loadColonyResearchDocs` → `resolveColonyResearchSection` path with no hand-typed `aether init --research <path>`.
- An owner-stopped run (either the loop's own in-process stop check, or the `aether oracle stop` CLI command killing the loop's process tree from outside) still files and registers whatever it gathered, with a "partial — stopped after N rounds" label as the literal first line of the document body a worker prompt actually receives.
- A run whose write-up produced no content — no synthesis at all — files nothing, registers nothing, and says nothing; this is the expected shape of an owner stop before any research happened, not a failure.
- Findings that clear the existing confidence bar are promoted into instincts automatically at the end of a run, through the same `runOraclePromote`/`memory.PromoteService` path the hand-typed `aether oracle promote` command already used — no second promotion mechanism. Every instinct promoted this way carries a `from research: <topic>, <date>` origin label on a dedicated `Provenance.OriginLabel` field, never folded into the finding text a later helper acts on.
- Findings are sanitised through `colony.SanitizeSignalContent` (the same 198.1 boundary applied to worker-authored text) before the admissibility gate, since Oracle findings originate outside the repository and are replayed verbatim into later worker prompts.
- `aether oracle promote --dry-run` still writes nothing at all, proven by a test that snapshots every store the promote path can touch (`instincts.json`, `entries.json`, `instinct-graph.json`, `COLONY_STATE.json`) and asserts byte-equality before and after.

## Decisions Made

- **Newest-first by registration order, not filename sort.** `saveOracleResearchDocument`'s same-day collision suffix (`-2.md`) sorts *before* the unsuffixed name in plain ASCII because `-` < `.`; a reverse-alphabetical ordering would have put the *older* of two same-day write-ups first, exactly on the D-08 case ("researching the same topic twice") the ordering exists to serve. `registerColonyResearchDoc` instead prepends the just-registered document to whatever order was already on disk, so recency is encoded at write time and never re-derived from a filename.
- **Widened gate covers `status == "stopped"`,** which covers both `manual_stop` and the `ctx.Err()`-triggered `cancelled` stop reason, in addition to the pre-existing `complete` / `max_iterations_reached`. `blocked` (worker error/timeout/no-progress) remains unfiled, matching the plan's explicit "Blocked and manually stopped runs do not [get filed]" framing for the pre-existing behavior — only the latter half of that sentence changed.
- **`runOraclePromote` takes an explicit `provenance string` parameter** rather than deriving it internally from global state, so each call site (the automatic loop path and the hand-typed CLI path) is the single source of truth for its own topic/date; `oracleResearchProvenanceLabel(state)` is the one function that builds the label shape, called from both.
- **`OriginLabel` added to `pkg/colony` and `pkg/memory`, outside this plan's declared `files_modified`.** The plan's own action text for Task 3 requires a new field "on the record `promoteOracleFindingAsInstinct` builds" and explicitly names `colony.Observation` as already carrying `SourceType`/`EvidenceType` alongside it — implementing this without touching the struct that defines those fields was not possible. Verified against the other four wave-1 plans in this phase (198.2-01, 03, 04, 05) that none declares `pkg/colony/instincts.go`, `pkg/colony/learning.go`, or `pkg/memory/promote.go`, so this carries no merge-conflict risk with sibling worktrees.

That did not happen literally in this session's git history: implementation and tests were written together as one coherent pass, because Task 2's own action text ("one body, two entry points — do not duplicate the save/register/promote logic") and Task 3's action text ("Call `runOraclePromote(...)` from `finalizeOracleLoop`'s terminal branch, after filing and registering") both describe modifications to the *same* shared function, `finalizeOracleResearchArtifacts`, in a way that made genuinely independent per-task RED/GREEN cycles impossible without either (a) an artificial, less-correct intermediate implementation shape, or (b) a git history where earlier "task" commits reference functions/signatures that only exist in later commits (non-buildable intermediate states).

In place of literal RED-then-GREEN commits, the two most safety-critical assertions were verified to genuinely fail before being restored, during this session (not committed):

Both were restored immediately after confirming the failure, and the full suite (`go test ./...`) was re-run clean afterward. This satisfies the CLAUDE.md "a test must be able to fail" requirement in substance, though not as a literal git-history RED commit per task.
