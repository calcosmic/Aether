# Phase 198.2: Code Review Report

**Reviewed:** 2026-08-30T16:43:23Z
**Depth:** standard
**Files Reviewed:** 53
**Status:** issues_found

## Summary

Phase 198.2 threads colony memory (steering notes, hive wisdom, prior-phase
carry-forward, survey digests, oracle research provenance) through every
helper-facing surface: build/plan/research briefs, the colonize/plan
delegate-manifest wrappers, the session-start greeting, and Oracle's
auto-filing pipeline. The bulk of this phase is unusually well-tested — new
`_198_2_test.go` files build fixtures through the real runtime writers
(`learn.NewColonyStore`, `hiveStoreCmd.RunE`, `memory.NewPromoteService`)
rather than hand-typed struct literals, and several tests (`TestEveryMemoryPackPartHasALiveWriter`,
`TestMemoryPackHasNoEmptyHeadings`, dry-run mutation guards) are exactly the
kind of invariant-shaped, fail-by-name tests this project's "Definition of
Done" calls for.

One real logic bug was found in the new previous-phase carry-forward
resolver: a criterion in the "needs owner confirmation" state is silently
excluded from what the next phase's builder sees, directly contradicting
the function's own doc comment and the feature's stated purpose — and the
gap is untested. Three warnings cover a bypassed file-lock on
`COLONY_STATE.json` in a newly-automatic write path, a budget/sanitizer
boundary interaction in the survey digest, and a minor accounting
inflation in the same function.

## Critical Issues

### CR-01: Carry-forward never surfaces "needs owner confirmation" criteria, contradicting its own contract

**File:** `cmd/phase_carry_forward.go:104-115`

**Issue:** `resolvePreviousPhaseCarryForward`'s doc comment states: "only failed
(non-skipped) checks and unmet **or unconfirmed** criteria are selected."
The `codexCriterionVerification.State` field is defined (`cmd/criterion_evidence.go:65-72`)
specifically to carry `needs_owner_confirmation` on a criterion where
`Passed` stays `true` — "Passed stays true (the phase still advances) but
this field is the separate signal the owner_confirmation_pending gate and
`aether seal` read." The loop that is supposed to catch this case:

```go
for _, c := range verification.Criteria {
    if c.Passed && c.State == "" {
        continue
    }
    if c.Passed {
        continue
    }
    items = append(items, flaggedItem{...})
}
```

The first `continue` (ordinary passed criterion, `State == ""`) is entirely
subsumed by the second, unconditional `if c.Passed { continue }` immediately
below it — so **every** passed criterion is skipped regardless of `State`,
making the `State == ""` check dead code. A criterion sitting at
`needs_owner_confirmation` from the previous phase — exactly the case the
feature (D-09..D-11, WIRE-07) was built to surface to the next phase's
builder — never reaches `items`, and therefore never reaches the build
brief. The next phase's builder gets no signal that the prior phase left an
unconfirmed criterion behind.

This is untested: `cmd/brief_growth_cap_198_2_test.go`'s
`TestCarryForwardNamesOnlyWhatFailedOrWasFlagged` only seeds
`Passed: false` criteria; no test in the diff seeds `Passed: true, State:
"needs_owner_confirmation"` and asserts it appears in the carry-forward
section, so the gap between the doc comment and the code shipped green.

**Fix:**
```go
for _, c := range verification.Criteria {
    if c.Passed && c.State == "" {
        continue // ordinary passed criterion — nothing to say
    }
    if !c.Passed {
        items = append(items, flaggedItem{
            label:    c.Criterion,
            sentence: fmt.Sprintf("Criterion %q was not met: %s", c.Criterion, firstNonEmpty(c.Summary, "not met")),
        })
        continue
    }
    // c.Passed && c.State != "" — e.g. needs_owner_confirmation
    items = append(items, flaggedItem{
        label:    c.Criterion,
        sentence: fmt.Sprintf("Criterion %q still needs the owner's confirmation: %s", c.Criterion, firstNonEmpty(c.Summary, "no summary recorded")),
    })
}
```
Add a test seeding `codexCriterionVerification{Criterion: "...", Passed: true, State: criterionStateNeedsOwnerConfirmation}` and asserting it appears in `resolvePreviousPhaseCarryForward`'s output.

## Warnings

### WR-01: `registerColonyResearchDoc` bypasses the store's file lock on a now-automatic write path

**File:** `cmd/colony_research.go:196-256`

**Issue:** `registerColonyResearchDoc` reads and rewrites `COLONY_STATE.json`
with raw `os.ReadFile` / `os.WriteFile` (lines 203, 254), bypassing
`pkg/storage.Store`'s `FileLocker`/`atomicWriteLocked` machinery that every
other in-process writer of this file goes through. This project's own
history (the "state corruption bug" / "Frankenstein state" failure mode —
an LLM or process reconstructing the full JSON and racing another writer)
is exactly the shape of risk this function reintroduces: a read-modify-write
of the entire state file with no exclusive lock held across the read and
the write.

Before this phase, filing research into the colony's `--research` pointer
list was a manual, occasional step (`aether init --research <path>`). This
phase makes it automatic on **every** completed or stopped Oracle run
(`cmd/oracle_loop.go:1387`, called from both `finalizeOracleLoop` and the
`aether oracle stop` path), raising how often this unlocked write executes
concurrently with anything else that might be touching `COLONY_STATE.json`
(e.g., a build's parallel workers in `in-repo` mode, or another terminal
running `/ant-continue`). A lost update here means either the newly-filed
research document's pointer is dropped, or an unrelated concurrent change
to state is clobbered.

Note: raw `os.WriteFile` to `COLONY_STATE.json` already exists elsewhere in
the codebase (e.g. `abandon_cmd.go`), so this is not a wholly novel pattern
— but this phase measurably increases its call frequency by removing the
"only when a human types the command" gate.

**Fix:** Route the read-modify-write through `store.LoadRawJSON` /
`store.AtomicWrite` (or an equivalent locked helper) so the read-modify-write
of `COLONY_STATE.json` is protected by the same `FileLocker` every other
writer uses, rather than two unsynchronized raw file operations.

### WR-02: Survey digest's per-report cap doesn't reserve room for its own truncation notice, risking a sanitizer rejection at the boundary

**File:** `cmd/helpers.go:205-210, 337-346`

**Issue:** `surveyDigestPerReportChars` (400) caps how much of a report's raw
content is kept before appending a truncation notice
(`"\n\n_(truncated — full report: .aether/data/survey/%s)_"`, ~50-100+
bytes depending on filename length). The combined string is then passed to
`colony.SanitizeSignalContent`, which hard-rejects anything over 500
characters (`pkg/colony/sanitize.go:25-27`). For a survey report filename
long enough that `400 + len(notice) > 500`, a report that was correctly
truncated to fit its per-report budget will instead be rejected outright by
the sanitizer and land in the "not included" omission list — not because it
didn't fit the digest budget, but because the truncation notice itself
pushed it over the sanitizer's unrelated 500-char ceiling. Today's
surveyor-nest/-disciplines output filenames (`BLUEPRINT.md`, `CHAMBERS.md`,
etc.) are short enough that this isn't hit in practice, but the constant
relationship is not guarded — nothing in the code or tests asserts
`surveyDigestPerReportChars + maxNoticeOverhead <= 500`.

**Fix:** Either lower `surveyDigestPerReportChars` to leave headroom for the
longest expected notice (e.g. 350), or reserve the notice's length from
`budget` before slicing `content`, e.g.:
```go
noticeLen := len(fmt.Sprintf("\n\n_(truncated — full report: .aether/data/survey/%s)_", name))
if budget > noticeLen {
    budget -= noticeLen
}
```

### WR-03: `used` budget accounting includes the truncation-notice suffix, understating remaining budget for later reports

**File:** `cmd/helpers.go:349` (`used += len(content)`)

**Issue:** When a report's content is truncated, `content` is reassigned to
`cut + "\n\n_(truncated ...)_"` before `used += len(content)` runs. The
truncation notice text itself is not part of the report's actual content
budget, but it's counted against `surveyDigestBudgetChars` the same as if
it were report body — so later reports in the loop see less `remaining`
budget than the design intends. This doesn't break anything (the loose
sanity ceiling test `TestMapDigestStaysInsideItsOwnBudgetAndNamesOmissions`
only asserts `len(digest) <= budget*2`), but it's an avoidable accounting
skew in a function whose own doc comment emphasizes deterministic,
byte-exact budgeting.

**Fix:** Track the pre-truncation-notice length for `used`, e.g. capture
`used += len(cut)` (the truncated body only) before appending the notice
suffix to `content`.

## Info

### IN-01: `latestHandoffSentence` and instinct `Action` text reach the session-start greeting unsanitized

**File:** `cmd/next_action_input.go:126-158` (`latestHandoffSentence`),
`cmd/next_action_input.go:88-92` (habit text from `loadStrongestRuntimeInstincts`)

**Issue:** Unlike the other worker-authored text this phase threads into
prompts (survey digest, phase carry-forward, Oracle promotions), all of
which are explicitly passed through `colony.SanitizeSignalContent` with a
doc comment justifying it, `latestHandoffSentence`'s `Summary` /
`NextWorkerInstructions` / `DoNotRepeat` text and the instinct `Action` text
reach `renderNextActionMemory` and the terminal greeting card unsanitized.
This is lower risk than the other paths — the greeting is terminal output
read by a human, not a subsequent LLM prompt, so prompt-injection is not the
primary concern — but raw worker-authored text (which could contain control
characters or escape sequences) reaching the terminal unfiltered is
inconsistent with the sanitization boundary this phase otherwise applies
consistently everywhere else worker/reviewer-authored text crosses into a
new surface.

**Fix:** Consider running `RelayNote` and `Habits` entries through the same
sanitizer (or a terminal-safe equivalent) before rendering, for consistency
with the rest of this phase's trust-boundary handling — optional given the
lower actual risk.
