# Phase 198.3: Code Review Report

**Reviewed:** 2026-09-01T20:39:46Z
**Depth:** standard
**Files Reviewed:** 84
**Status:** issues_found

## Narrative Findings (AI reviewer)

The Phase 198.3 implementation still has six shipping blockers. The most serious paths let an external swarm completion write outside its assigned data directory, let self-authored/replayed completion evidence rewrite swarm truth, and let unattended advancement mistake a replacement blocker for an unchanged baseline. Seal and reviewer compatibility paths also fail open on malformed evidence, while visual checkpoint provenance is not actually immutable.

In plain English: the happy-path overnight run works, but carefully malformed or simply stale evidence can still make Aether say “safe to continue” when the proof changed or could not be trusted.

Targeted Plan 17–22 tests completed with 155 passing cases. `git diff --check` and `go vet ./cmd ./pkg/codex` also completed cleanly. Those checks do not exercise the adversarial cases below. The known 300-second aggregate-gate cap, external-swarm fixture failure, and macOS `/tmp` versus `/private/tmp` assertion were treated as test-environment facts and are not findings in this report.

## Critical Issues

### CR-01: Unvalidated external `swarm_id` permits data-directory traversal before rejection

**Classification:** Critical
**File:** `cmd/swarm_cmd.go:549-568`
**Related:** `cmd/swarm_cmd.go:688-720`, `cmd/swarm_strikes.go:118-149`

**Issue:** `mergeExternalSwarmResults` requires only a non-empty `manifest.SwarmID`. `runSwarmFinalize` then passes that value to `initializeSwarmRun`, which joins it directly into both OS and store paths and writes `responses/`, `findings.json`, `display.json`, and `timing.json`. The stricter `safeIdentifierSegment`/`isValidSwarmResultID` validation runs only later inside `saveSwarmResultRecord`. A completion with `swarm_id: "../escaped"` therefore writes outside `.aether/data/swarms` before finalization returns an error. Spawn-tree and midden mutations can also occur before the late validation.

**Fix:** Validate the identifier before `beginRuntimeSpawnRun` or any filesystem/state mutation, using the same canonical rules as durable result storage. For example:

```go
swarmID := strings.TrimSpace(manifest.SwarmID)
if _, err := safeIdentifierSegment(filepath.Join(store.BasePath(), "swarms"), "swarm id", swarmID); err != nil {
    return nil, fmt.Errorf("invalid swarm_manifest swarm_id: %w", err)
}
if !isValidSwarmResultID(swarmID) {
    return nil, fmt.Errorf("invalid swarm_manifest swarm_id %q", swarmID)
}
```

Add traversal tests asserting that neither the data directory nor spawn/midden state changes on rejection.

### CR-02: External swarm manifests are self-asserted, replayable, and able to rewrite durable strike truth

**Classification:** Critical
**File:** `cmd/swarm_cmd.go:377-416`
**Related:** `cmd/swarm_cmd.go:648-720`, `cmd/swarm_cmd_test.go:1011-1072`, `cmd/swarm_strikes.go:479-496`

**Issue:** Plan-only returns a manifest but persists no immutable issuance record, nonce hash, or runtime signature. Finalization accepts the manifest embedded in the same untrusted completion file and checks only its shape, root, and caller-controlled timestamp. A wrapper can therefore alter the target, ID, dispatch plan, and matching results together and have that invented run recorded as runtime truth. The same fresh completion is explicitly replayable. Because `result.json` is overwritten by ID, a changed replay can replace a failed/blocked result with a successful one (or vice versa), while an already-created escalation flag is not reconciled. Durable strike history and blocker state can consequently contradict one another.

**Fix:** Bind finalization to a runtime-issued manifest. Persist an immutable issuance record containing a random capability hash and canonical manifest digest (or sign the manifest with a durable runtime secret), require the capability at finalization, and consume it once. Permit repeated calls only when the completion digest exactly matches the already-recorded completion and return the original result without rewriting; reject altered replays. Add tests for forged manifests and same-ID replays with changed status/target.

### CR-03: Same-count blocker replacement bypasses the overnight Iron Law

**Classification:** Critical
**File:** `cmd/blocker_snapshot.go:26-33`
**Related:** `cmd/blocker_snapshot.go:142-159`, `cmd/codex_continue.go:3815-3827`, `cmd/blocker_snapshot_test.go:282-294`

**Issue:** `compareBlockerSnapshots` reports only a count increase or newly escalated IDs. It deliberately ignores ordinary ID churn. The autopilot continue exception therefore passes when baseline `{old}` becomes `{replacement}`: one prior blocker was resolved, one brand-new blocker appeared, the net count stayed one, and no escalation was added. This violates the phase contract that a *new blocker* is a genuine stop. The unit test currently codifies the unsafe result for “same-count ordinary ID replacement.”

**Fix:** Track added ordinary IDs as well as count/escalation movement and permit the baseline exception only when every unresolved after-ID was present before. Treat missing/duplicate identifiers conservatively because their identity cannot be proven. Add both gate-level and live-run regressions for `{old} -> {replacement}`.

### CR-04: Seal treats malformed legacy blocker storage as an empty blocker set

**Classification:** Critical
**File:** `cmd/codex_workflow_cmds.go:1330-1342`

**Issue:** When `pending-decisions.json` is absent, `checkSealBlockers` loads legacy `flags.json` but handles only the success case. A malformed, unreadable, non-regular, or permission-denied legacy file is silently ignored, after which seal can proceed as if no flags existed. This bypasses the fail-closed blocker reader introduced elsewhere in Plan 22 and makes “truth unavailable” indistinguishable from “verified empty” at the final lifecycle boundary.

**Fix:** Replace the ad hoc two-file load with `readCanonicalBlockerFlags`, or duplicate its exact error semantics: only `os.ErrNotExist` for both stores means empty; every other error must append a durability blocker and prevent seal. Add tests for malformed and unreadable legacy `flags.json` with the canonical file absent.

### CR-05: Legacy reviewer findings skip severity validation and can evade the Critical gate

**Classification:** Critical
**File:** `cmd/codex_continue_finalize.go:817-833`
**Related:** `cmd/codex_continue_finalize.go:885-900`, `cmd/codex_continue_finalize.go:1217-1243`, `cmd/codex_continue.go:1699-1715`

**Issue:** Explicit `artifacts.review` findings are restricted to `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, or `INFO`, but the compatibility branch for top-level findings validates only that title/description is non-empty. A completed Gatekeeper or other legacy external reviewer can return `CRITCAL`, an empty severity, or another malformed value; it produces no evidence error, and both direct signal evaluation and external gates ignore it because they stop only on exact `CRITICAL`. A typo in the security review contract can therefore authorize advancement.

**Fix:** Run legacy findings through the same severity normalization and `validReviewArtifactSeverity` check as explicit artifacts. Append an evidence error for every invalid/missing severity so the report fails closed, and add direct plus external-finalizer tests for misspelled and absent severity.

### CR-06: Visual checkpoint evidence is not bound to the built attempt that supposedly produced it

**Classification:** Critical
**File:** `cmd/autopilot_checkpoints.go:396-430`
**Related:** `cmd/autopilot_checkpoints.go:451-504`, `cmd/autopilot_checkpoints_test.go:317-329`

**Issue:** The visual checkpoint validator binds only the attempt ID, manifest, and claims *path*. It then reads and hashes whatever bytes currently occupy that path, without comparing them to the claims embedded in the built attempt journal. The test suite demonstrates that replacing the claims file after the attempt is already `built` is accepted as a new work generation. Changing it to omit UI paths returns no checkpoint; changing it to different UI paths asks the owner to approve evidence the attempt did not commit. The “immutable authorization provenance” is therefore derived from a mutable file.

**Fix:** At the built transition, persist a canonical claims digest in the attempt record (or use the existing embedded `attempt.Claims`) and require the file to match it before deriving a checkpoint. New-schema built attempts should fail closed when embedded claims/digest are absent. Add a regression that mutates the claims file and asserts an error plus byte-for-byte unchanged pending decisions.

## Warnings

### WR-01: Replan cadence consumes stale decisions outside the active colony scope

**Classification:** Warning
**File:** `cmd/compatibility_cmds.go:738-745`
**Related:** `cmd/autopilot_lessons.go:229-245`

**Issue:** The unattended run passes every row from `pending-decisions.json` to `evaluateAutopilotReplan`. Cadence projection filters only by decision type and `PlanRevisionID`, not by session/goal scope. Plan revision IDs are deterministic for a revision number and plan definition, so a prior session with the same plan can carry the same ID. Its checkpoint phase then raises `LastHandledBoundary` and suppresses a current evidence-driven replan.

**Fix:** Filter decisions with `pendingDecisionMatchesScope(decision, loadCurrentPendingDecisionScope())` before cadence evaluation, and validate the expected source/key metadata. Add a test with two sessions sharing an identical plan revision and prove the stale row cannot satisfy the current boundary.

### WR-02: Every reissued checkpoint capability remains valid indefinitely

**Classification:** Warning
**File:** `cmd/autopilot_checkpoints.go:696-735`
**Related:** `cmd/autopilot_checkpoints.go:930-950`, `cmd/autopilot_checkpoints_test.go:807-845`

**Issue:** Each idempotent materialization or seal rendering issues a fresh bearer capability, appends its hash, and accepts every historical hash until the decision is resolved. There is no bound or expiry. Repeated status/seal attempts therefore grow verifier state and preserve authorization for every command copied into old logs or screenshots, even after newer commands were issued.

**Fix:** Keep a bounded grace window (or issued/expiry timestamps) and retire older hashes atomically when a new capability is rendered. Tests should verify the current and explicitly supported grace token work, while an evicted/expired token is rejected without mutation.

### WR-03: Morning reports retain HIGH findings but omit the CRITICAL findings that stopped the run

**Classification:** Warning
**File:** `cmd/autopilot_report.go:28-37`
**Related:** `cmd/autopilot_report.go:181-200`, `cmd/autopilot_report.go:595-607`

**Issue:** `recordSignals` stores only findings whose severity is exactly `HIGH`; `autopilotPhaseReport` has no Critical collection, and the status renderer reports only the HIGH count. A Critical finding may correctly stop the run, but the durable morning report/status card omits its file, line, description, and proposed fix. Some detail reaches recovery-log evidence, but the report explicitly described as the frozen status source does not expose it, leaving the owner without the actionable reason on the primary surface.

**Fix:** Persist Critical and High findings in a unified typed collection (or add `CriticalFindings`), render both severity counts and concise details, and round-trip them in report tests. Keep the stop decision unchanged.
