## User Constraints (from CONTEXT.md)

### Locked decisions

- **D-01:** `aether run` stops only when continuing would be unsafe or impossible. Owner-only runtime and visual checks are durable work for later, not automatic overnight stops.
- **D-02:** In headless mode, runtime-verification and visual checkpoints are queued and the run continues. Interactive mode may pause. `aether seal` still waits for every unresolved owner checkpoint.
- **D-03:** Genuine stops are: deterministic verification still failing after its one repair path; an Auditor score below 60 when an Auditor actually ran; a Critical reviewer finding; a new or escalated blocker; corrupt/non-runnable colony state; or an unavailable provider after the bounded timeout-only retry. Cancel, timeout, and max-phase limits are named normal stops.
- **D-04:** The Auditor score floor is `< 60`; `60` passes. Never dispatch an Auditor merely to manufacture a score.
- **D-05:** Only Critical reviewer findings stop the run. High findings survive into the morning report but do not halt it.
- **D-06:** Existing blockers are shown and counted before work, but do not by themselves stop an overnight run. Stop if the blocker count rises or a blocker is escalated. `aether status` must show the same truth.
- **D-07:** `aether run --dry-run` names every trigger and labels its headless/interactive disposition: stop, queue-and-continue, or normal stop.
- **D-08:** These decisions supersede the older pause document where headless owner-only checks queued and then stopped, and restore the Auditor score floor that document omitted.
- **D-09:** A due replan queues and continues in headless mode, pauses in interactive mode, and never silently rewrites the plan.
- **D-10:** Replanning becomes due only when the interval is reached **and** at least one confirmed lesson exists since the last successful plan.
- **D-11:** Replan evidence is unique, confirmed lessons since the last successful plan revision. Raw observations and promoted habits are not substitutes.
- **D-12:** Maintain one unresolved replan decision per active plan revision; update its lesson count and first/latest checkpoints instead of creating duplicates.
- **D-13:** Provider readiness gets at most two attempts, with the second attempt only after a timeout. Auth/login/missing-binary failures return immediately.
- **D-14:** A successful readiness check is shared by every worker in one phase; the next phase must check again.
- **D-15:** Both timeout attempts preserve completed work, stop unfinished work, and resume the exact phase. Never switch provider or skip phase automatically.
- **D-16:** Every live Go/TypeScript readiness path uses `AETHER_PREFLIGHT_TIMEOUT`, default 45 seconds.
- **D-17:** The final run report is outcome-first, followed by queued decisions/blockers, elapsed time, honest measured cost, the exact next command, and compact per-phase outcomes.
- **D-18:** Elapsed time is invocation wall-clock time, including waits and retry delays but excluding time while Aether was not running. It is not the sum of worker durations.
- **D-19:** Cost uses the Phase 196 ledger contract: measured totals and per-phase rows only; missing telemetry is `— not reported`; no estimates.
- **D-20:** Persist the report and have `aether status` render that same record.
- **Carried constraints:** Keep the deterministic verification floor; owner confirmation may permit phase advancement but still blocks seal; reviewer workers remain optional; autopilot never seals; existing stores stay authoritative; Go owns behavioral truth.
- **Folded work:** Avoid routine extra reviewers or check-ins; use one shared phase preflight; include elapsed time; add a six-or-more-phase unattended fixture.
- **Deferred unless a live caller is found:** The deprecated TypeScript dispatcher's fixed five-second path belongs to Phase 198.4, not this phase.

## Executive Summary

The overnight runner is not missing one condition; it currently lacks a single, typed policy boundary. `runCompatibilityAutopilot` mixes detection, display text, retry behavior, state mutation, and stop decisions in one loop (`cmd/compatibility_cmds.go:388`). It calls the broad legacy `checkAutopilotPauseConditions` (`cmd/autopilot.go:49`), while `pauseAutopilotRun` always means “stop” (`cmd/run_visuals.go:141`). That architecture makes a queueable owner check indistinguishable from a genuine blocker and makes dry-run drift from enforcement likely.

The safe implementation is to introduce one canonical trigger catalogue and one evaluator. Each trigger has a stable code, owner-facing label, detection evidence, headless disposition, interactive disposition, and exact next action. The run loop consumes typed evaluations; dry-run renders the same catalogue; the persisted report stores the evaluated outcomes; status reads that report and the same live blocker snapshot. No prose parser participates in control flow.

Most supporting pieces already exist:

- pending decisions are durable (`cmd/pending_decision.go:11`);
- build and continue state already permit exact-phase recovery;
- worker results already preserve task-specific JSON artifacts (`pkg/codex/worker.go:78`);
- the deterministic verification floor is already authoritative;
- learning capture already writes evidence-rich entries (`cmd/codex_continue_finalize.go:1565`);
- spend ledgers already distinguish measured telemetry from missing telemetry (`cmd/spend_ledger.go:288`, `cmd/spend_ledger.go:397`, `cmd/spend_cmd.go:39`);
- direct and TypeScript-hosted dispatch already meet most of the desired timeout retry semantics.

The phase should therefore consolidate and wire existing evidence instead of inventing parallel stores. Ten plans are appropriate: trigger/blocker truth; review/checkpoint evidence; phase-scoped preflight; run/replan policy; durable reporting/recovery integration; guided insert; swarm escalation; behavior-neutral legacy-autopilot cleanup with its staged fixture shrink; behavior-neutral recovery/Medic cleanup with the final fixture shrink; and the multi-phase proof plus full gates.

## Current Runtime Topology

```text
aether run
  -> runCompatibilityAutopilot
       -> aether build current phase
            -> provider readiness -> worker dispatch -> durable build artifacts
       -> broad legacy pause scan
       -> aether continue
            -> deterministic floor -> optional reviewers -> learning capture
       -> broad legacy pause scan
       -> phase-count-only replan stop
       -> thin terminal result

Desired control path
  -> snapshot live blockers
  -> evaluate build/continue evidence against canonical trigger catalogue
  -> STOP genuine blockers
  -> QUEUE owner/replan checkpoints and continue when headless
  -> NORMAL STOP for cancel/timeout/max/complete
  -> persist one invocation report
  -> render that report from run and status
```

## Finding 1 — One typed trigger catalogue must own both enforcement and explanation

`runCompatibilityAutopilot` is the live loop (`cmd/compatibility_cmds.go:388`). It invokes `checkAutopilotPauseConditions` after build and continue (`cmd/compatibility_cmds.go:495`, `:541`), and its replan decision is a phase-count modulus (`cmd/compatibility_cmds.go:647`). `pauseAutopilotRun` then converts every pause into a terminal result (`cmd/run_visuals.go:141`). Dry-run has a separately assembled description. This is the central drift risk.

Recommended type:

```go
type autopilotDisposition string

const (
    dispositionStop             autopilotDisposition = "stop"
    dispositionQueueAndContinue autopilotDisposition = "queue_and_continue"
    dispositionNormalStop       autopilotDisposition = "normal_stop"
    dispositionContinue         autopilotDisposition = "continue"
)

type autopilotTriggerSpec struct {
    Code        string
    Label       string
    Detection   string
    Headless    autopilotDisposition
    Interactive autopilotDisposition
    Next        string
}

type autopilotTriggerEvaluation struct {
    Spec     autopilotTriggerSpec
    Active   bool
    Evidence map[string]any
}
```

Canonical catalogue:

| Code | Detection | Headless | Interactive |
|---|---|---|---|
| `deterministic_verification_failed` | Current continue result still fails deterministic floor after its existing repair opportunity | stop | stop |
| `auditor_score_below_floor` | A completed Auditor review reports an artifact score `< 60` | stop | stop |
| `critical_review_finding` | Current completed reviewer evidence contains Critical severity | stop | stop |
| `blocker_count_increased` | Post-step blocker count exceeds invocation/phase baseline | stop | stop |
| `blocker_escalated` | Live blocker snapshot contains escalation evidence not present at baseline | stop | stop |
| `colony_not_runnable` | State missing/corrupt or lifecycle state cannot build/continue | stop | stop |
| `provider_unavailable` | Bounded readiness policy exhausts or returns immediate auth/binary failure | stop | stop |
| `runtime_verification_needed` | Continue criteria require owner/runtime confirmation | queue and continue | pause |
| `visual_checkpoint_needed` | Build claims show UI-affecting paths | queue and continue | pause |
| `replan_due` | Interval reached and at least one unique confirmed lesson exists since active plan revision | queue and continue | pause |
| `cancelled` | Process/context cancellation | normal stop | normal stop |
| `worker_timeout` | Build/continue timeout after state was durably preserved | normal stop | normal stop |
| `max_phases_reached` | Invocation limit reached | normal stop | normal stop |
| `colony_complete` | Last phase advanced | normal stop | normal stop |

`--dry-run` must render this exact slice, including inactive trigger names and both dispositions. Tests should compare catalogue codes, not fragments of independently written prose. The evaluator may have stage-specific inputs, but no second trigger list.

## Finding 2 — Blocker truth is duplicated and too broad

`flag-check-blockers` is defined in `cmd/flag_cmds.go:220`; status independently counts flags in `countFlags` (`cmd/status.go:1367`). The live escalation marker is `FlagEntry.Source == "escalation"`; there is no separate severity field. The legacy pause scan also mixes unresolved blocker flags with stale gates, signals, and midden records, so it can stop for evidence unrelated to the current build/continue result.

Add one pure reader:

```go
type blockerSnapshot struct {
    Count          int
    IDs            []string
    EscalatedCount int
    EscalatedIDs   []string
}
```

All three consumers use it:

1. `flag-check-blockers` remains a diagnostic adapter over the shared reader.
2. `aether run` takes a baseline before dispatch, prints existing blockers, and proceeds unless escalation already makes the colony unsafe. After build/continue it stops when count rises or escalation appears.
3. `aether status` prints the same blocker and escalated counts.

The comparison should follow the locked contract literally: count increase or escalation. Replacing one ordinary blocker ID with another while keeping the count flat must not be silently reinterpreted as a different policy. Preserve IDs in evidence for diagnosis, but do not expand the stop rule.

## Finding 3 — Owner checkpoints should be durable decisions, not blockers

The verification system already records `needs_owner_confirmation` (`cmd/criterion_owner_confirmation.go:15`). `checkSealBlockers` synthesizes unresolved owner confirmations into seal blockers (`cmd/codex_workflow_cmds.go:1276`). Pending decisions already carry IDs, questions, status, and resolution (`cmd/pending_decision.go:11`). Those are the right primitives.

Implement two typed pending-decision kinds:

- `runtime-verification`: derived from current continue criteria in `needs_owner_confirmation`.
- `visual-checkpoint`: derived from actual build claims paths (created/modified files matching UI extensions or UI directories), not an untrusted worker boolean.

Headless behavior:

1. Upsert/deduplicate the pending decision.
2. Record its ID in the current phase summary and final report.
3. Continue the phase/run.

Interactive behavior pauses with the exact `aether decision-answer <id> ...` command. `recordDecisionAnswer` must mark the matching queue row resolved, rather than merely append a separate resolved clarification and leave stale queue output behind. `aether seal` must treat every unresolved runtime/visual checkpoint as a named blocker with its recovery command.

One existing edge must change: the final phase currently treats owner confirmation as an advancement gate even though `aether run` never seals. Final phase advancement should follow every earlier phase; sealing remains the only compulsory owner boundary.

## Finding 4 — Reviewer control evidence is being dropped at the hosted seam

`pkg/codex.WorkerResult` already carries `Artifacts map[string]json.RawMessage` (`pkg/codex/worker.go:78`), and the internal adapter preserves artifacts. The external continue shape (`cmd/codex_continue_plan.go:14`) does not carry them into normalized continue review evidence. The continue worker-flow record also has findings but no score.

Use a task-specific reviewer artifact:

```json
{
  "review": {
    "overall_score": 59,
    "findings": [
      {"severity": "Critical", "title": "...", "detail": "..."}
    ]
  }
}
```

Required rules:

- parse `overall_score` only for a successfully dispatched/completed `auditor` worker;
- validate the score as `0..100`;
- `< 60` stops, `60` passes;
- absence of an Auditor means absence of a score trigger, never an automatic Auditor dispatch;
- Critical stops; High and lower persist for the morning report;
- a legacy `blocking: true` bit on a High finding must not override the severity rule;
- current normalized result evidence, not old global gate files, drives the run decision.

The direct and hosted/TypeScript paths must normalize to the same typed review structure. A narrow raw-output compatibility fallback is acceptable for old worker output, but the artifact is authoritative and tests must cover both seams.

## Finding 5 — Provider retry is mostly correct; cache scope and an outer retry are not

The hosted platform dispatcher already uses a 45-second default and performs a second readiness attempt only after timeout. The remaining live auth-availability probe uses `AETHER_PROBE_TIMEOUT`, creating two knobs. The TypeScript host's active preflight config already uses `AETHER_PREFLIGHT_TIMEOUT`; the old fixed-five-second dispatcher appears to have no live caller.

Two changes complete the contract:

1. Make the live availability probe use `AETHER_PREFLIGHT_TIMEOUT`, default 45 seconds. Preserve immediate return for auth/login/binary errors and timeout-only second attempt.
2. Scope successful readiness caching to `(platform, phase)`. Build and continue in phase N share one success; phase N+1 misses and checks again. For non-phase workflows, the existing bounded/TTL behavior may remain.

The TypeScript host currently invokes the internal preflight adapter without a phase. Add an explicit `--phase` field passed from the build/continue manifest. Bump the cache schema and clear all scopes for a platform on invalidation.

Remove `aether run`'s outer retry of the whole build. Retrying the entire build after any error violates the timeout-only rule and can repeat completed work. Readiness owns its two attempts; a build/worker timeout terminates unfinished execution with durable state and exact-phase recovery guidance.

## Finding 6 — Replan evidence exists, but the trigger ignores it

`captureContinueLearning` writes phase learning with evidence after successful worker flow and gates (`cmd/codex_continue_finalize.go:1565`). The run loop currently stops whenever the planned-phase count reaches the interval (`cmd/compatibility_cmds.go:647`), even with no lessons, and does not say what changed.

Define a confirmed lesson for autopilot as an entry with:

- non-empty content and phase > 0;
- status not blocked/disproven;
- evidence timestamp after the active plan revision (fallback to `Plan.GeneratedAt`);
- non-empty worker evidence with all recorded workers completed;
- `GatesTotal > 0` and `GatesPassed == GatesTotal`.

Deduplicate by a normalized-content hash. Do not use “promoted habit” status as a proxy and do not count raw observations. The trigger is:

```text
replan interval reached AND unique confirmed lessons since plan revision > 0
```

Extend pending decisions with optional typed metadata. Upsert one `replan` item per active revision containing the revision ID/time, unique lesson count, first checkpoint, and latest checkpoint. A new plan revision resolves or supersedes the older note. `--continue` remains the explicit bypass.

## Finding 7 — The report belongs in the existing autopilot state file

`buildRunExecutionResult` is currently thin (`cmd/compatibility_cmds.go:698`) and `syncRunAutopilotState` stores only basic lifecycle state (`cmd/compatibility_cmds.go:714`). The existing `autopilot/state.json` is already the status handoff and should own an optional `last_report`; creating a second report store would create another truth.

Recommended persisted shape:

```go
type autopilotInvocationReport struct {
    SchemaVersion int
    InvocationID  string
    StartedAt     time.Time
    FinishedAt    time.Time
    ElapsedSecs   float64
    Outcome       string
    StopReason    string
    CurrentPhase  int
    Phases        []autopilotPhaseReport
    Queued        []string
    BlockersBefore blockerSnapshot
    BlockersAfter  blockerSnapshot
    Spend          autopilotSpendReport
    Next           string
}
```

Every terminal branch funnels through one `finishAutopilotInvocation`. The function stamps finish time, computes wall-clock elapsed from this process invocation, loads measured spend ledgers per completed/attempted phase, writes `last_report`, and renders it. A later `aether run` invocation receives a new start time, so offline time is excluded.

Reuse `loadSpendLedgersForPhase` (`cmd/spend_ledger.go:288`), `computeSpendTotals` (`cmd/spend_ledger.go:397`), and `renderSpendCostLineFromLedgers`. The missing-telemetry glyph remains `spendNotReportedFigure = "—"` (`cmd/spend_cmd.go:39`). No character/token/currency estimates may be added. `aether status` renders the same report object and live blocker snapshot; JSON exposes the same data without recomputation.

Report order:

1. outcome and stop reason;
2. queued decisions and blocker movement;
3. elapsed wall-clock;
4. measured cost/usage and `— not reported` rows;
5. exact next command;
6. compact per-phase outcomes, including High findings.

## Finding 8 — Recovery helpers are useful, but their public orphan adapters are not

The recovery classifier and recovery-log functions have live internal callers, while their standalone Cobra adapters remain on the orphan allowlist (`failure-classify`, `recovery-log-read`, `recovery-log-write`). `medic-auto-spawn-check` is likewise a public orphan command, while Medic eligibility logic can be used internally. The seven older autopilot management subcommands duplicate the live `aether run`/`aether status` lifecycle.

Recommended cleanup:

- remove the seven orphaned autopilot Cobra adapters but keep the state/evaluator helpers;
- remove `failure-classify`, `recovery-log-read`, `recovery-log-write`, and `medic-auto-spawn-check` Cobra adapters while retaining internal functions;
- after a genuine terminal failure, classify it, persist/read the normal recovery log, evaluate Medic eligibility, and show `aether medic --deep` as advice when appropriate;
- never dispatch a routine recovery worker merely for an owner checkpoint or normal stop;
- keep `flag-check-blockers` as a useful diagnostic over the shared live snapshot;
- regenerate command catalog/parity fixtures and shrink the current orphan allowlist. Baseline files remain monotonic history unless their tests explicitly require regeneration.

This closes audited dead surface without building another recovery lifecycle.

## Finding 9 — Guided insert belongs in the Go adapter

`phase-insert`/`insert-phase` is implemented in `cmd/state_extra.go:120` and currently requires `--after`, `--name`, and `--description`. The historical guided flow gathered an issue, goal, and constraints, derived a short “Stabilize …” name, and inserted after the current phase. Current Claude/OpenCode wrappers simply pass through to the Go command, so wrapper-only prompting would leave Codex and automation behind.

Implement one Go request resolver:

- optional positional issue plus optional `--name`, `--description`, `--constraints`;
- omitted `--after` resolves to current phase;
- when issue is supplied and name/description are absent: description is the issue and name is `Stabilize <short phrase>` (bounded to six useful words);
- zero input on a TTY prompts for issue, desired outcome, and constraints;
- zero input without a TTY returns a non-mutating structured `input_required` result with an exact command example;
- explicit existing flag usage remains compatible.

Update `.aether/commands/insert-phase.yaml`, generated/managed Claude and OpenCode copies, command-guide output, and byte-parity tests together.

## Finding 10 — Swarm needs a persisted same-problem strike evaluator

`runSwarmCompatibility` starts at `cmd/swarm_cmd.go:156`, and finalize writes a per-run result under `.aether/data/swarms/<id>/result.json` (`cmd/swarm_cmd.go:628`). Those results are not consulted before the next run.

Add a shared result recorder/evaluator used by direct and external finalize lanes:

- normalize the target (case/space/punctuation-stable) into a fingerprint;
- scan previous result files for consecutive `failed`/`blocked` outcomes for that fingerprint since its last successful completion;
- attempts one and two record normally;
- the third failed outcome upserts one unresolved blocker flag with `Source: "escalation"` and evidence containing the prior swarm IDs;
- a fourth attempt refuses dispatch and prints the exact guided `aether insert-phase` command;
- a successful result resets the consecutive streak;
- unrelated targets never share strikes.

Because escalation uses the real flag store, the shared blocker snapshot automatically makes `run` stop and `status` explain why. Do not add a separate strike database.

## Test Strategy

### Focused contract tests

- Catalogue completeness: dry-run codes equal enforcement catalogue codes.
- Disposition matrix: queueable conditions continue headlessly and pause interactively; genuine/normal stops retain their categories.
- Blockers: existing ordinary baseline continues; count increase stops; escalation stops; status and diagnostic counts agree.
- Review evidence: direct and hosted artifact paths; Auditor 59 stops, 60 passes, no Auditor does nothing; High never blocks; Critical blocks.
- Owner checkpoints: visual path classification and runtime criterion queue exactly once, resolution clears the queue, final phase advances, seal still refuses unresolved decisions.
- Provider readiness: build+continue in one phase probe once; next phase probes again; timeout retries once; auth/binary does not retry; Go and TypeScript use the same timeout flag.
- Replan: interval without lessons does nothing; confirmed unique lessons queue/upsert; interactive pauses; duplicate text does not inflate count.
- Report: every terminal path persists; elapsed excludes offline gap; cost is measured-only; High finding is retained; status renders the same report.
- Guided insert: explicit flags retain behavior, issue shorthand derives a bounded name, non-TTY missing input does not mutate, wrapper triplets remain byte-identical.
- Swarm: first/second failures do not escalate; third produces one escalation; fourth does not dispatch; success resets; other issue is isolated.
- Orphan audit: removed adapters disappear from catalog/current allowlist while internal functions remain covered.

### Required six-phase proof (STAM-06)

Use a fixture colony with at least six phases and invoke the actual `runCompatibilityAutopilot` loop with simulated build/continue workers. Across the six phases include:

- one UI-affecting build claim;
- one `needs_owner_confirmation` criterion;
- a due replan with a confirmed lesson;
- an existing ordinary blocker baseline;
- one High reviewer finding;
- measured and unreported spend rows;
- shared preflight instrumentation.

Assert that one invocation completes all six phases, persists runtime/visual/replan decisions, never calls seal, reports blocker baseline unchanged, renders High in the morning report, probes readiness once per phase, and leaves exact next action `aether seal`. Add a mutation-style guard: replacing queue-and-continue with stop for any queueable condition must make the fixture fail before phase six. This prevents a test that merely exercises a pure evaluator while bypassing the actual loop.

## Pitfalls to Avoid

1. **Do not keep the broad pause scanner in the control path.** Stale gate/midden/signal data would still stop unrelated future phases.
2. **Do not infer scores from reviewer prose.** Use a validated structured artifact.
3. **Do not turn missing Auditor evidence into a failed score.** Optional means optional.
4. **Do not queue and then return a stopped result in headless mode.** That is the precise behavior this phase replaces.
5. **Do not permit phase completion to bypass seal's owner boundary.** Advancement and sealing are distinct.
6. **Do not retry the whole build.** Only provider readiness gets the bounded timeout retry.
7. **Do not count raw observations as lessons.** Replan must name verified learning since the plan revision.
8. **Do not calculate cost from text, characters, or worker duration.** Missing telemetry remains visibly missing.
9. **Do not add another report, blocker, or swarm-strike store.** Extend existing durable records.
10. **Do not edit the dead TypeScript dispatcher unless a caller is proven.** The active host path is the required scope.
