# Phase 198.3: Overnight Stamina — Codebase Patterns

**Mapped:** 2026-08-31  
**Purpose:** Give executors the closest existing analogues, file ownership, and test conventions for Phase 198.3. This is a map of the current repository, not a second design document; binding behavior remains in `198.3-CONTEXT.md` and the implementation recommendation remains in `198.3-RESEARCH.md`.

## Architectural Rule

The Go runtime owns the behavior. TypeScript host files and Claude/OpenCode wrapper files may transport phase/context arguments or mirror owner instructions, but they must not decide whether the run stops. In simple terms: Go is the referee; wrappers carry the referee's decision to the screen.

The phase should extend existing durable stores:

| Concern | Existing authority | Extension |
|---|---|---|
| Run lifecycle/report | `.aether/data/autopilot/state.json` via `cmd/autopilot.go` | Add optional schema/versioned invocation report fields |
| Owner work | `.aether/data/pending-decisions.json` via `cmd/pending_decision.go` | Add typed checkpoint/replan metadata and upsert helpers |
| Blockers/escalation | flags store via `colony.FlagsFile` | Add one shared read-only snapshot helper; swarm writes a real escalation flag |
| Current verification/review | continue plan artifacts | Normalize current result into typed run signals |
| Worker review payload | `pkg/codex.WorkerResult.Artifacts` | Add/consume `artifacts.review` at the external continue seam |
| Provider readiness | `cmd/preflight_cache.go` + `pkg/codex/platform_dispatch.go` | Add phase scope; pass phase through active TS host adapter |
| Lessons | existing learning entries and evidence | Add a pure selector since active plan revision |
| Spend | existing spend ledgers | Read and aggregate; do not write a parallel cost store |
| Swarm history | `.aether/data/swarms/<id>/result.json` | Scan existing results; no strike-counter file |

## Pattern 1 — Pure domain object, thin Cobra adapters

Closest analogues:

- `cmd/pending_decision.go`: data types and filtering separate from command handlers.
- `cmd/spend_ledger.go`: read/normalize/aggregate helpers are reusable by multiple renderers.
- `cmd/preflight_cache.go`: cache policy is below individual workflow commands.

Apply the same shape to Phase 198.3:

```text
pure reader/evaluator/upserter
  -> run adapter
  -> dry-run renderer
  -> status renderer
  -> diagnostic command (where retained)
```

Do not put stop policy inside Cobra `RunE`, and do not make visual text an input to policy. Stable typed codes are control data; prose is output.

Recommended new production files where separation prevents another large compatibility file:

- `cmd/autopilot_policy.go` — catalogue, dispositions, typed evaluations.
- `cmd/blocker_snapshot.go` — live flag snapshot and comparisons.
- `cmd/autopilot_report.go` — persisted report, spend assembly, shared render projection.
- `cmd/autopilot_lessons.go` — confirmed-lesson selector and replan evidence.
- `cmd/autopilot_checkpoints.go` — owner checkpoint classification/upsert.
- `cmd/swarm_strikes.go` — historical result scan and escalation decision.

Naming can vary, but these responsibilities should not be copied into `run`, `status`, and diagnostic commands independently.

## Pattern 2 — Stable trigger codes; render labels at the edge

`cmd/run_visuals.go` already separates some labels from the run loop through `humanizeAutopilotPauseReason` and has dedicated phase/pause renderers (`renderRunEngageLine`, `renderRunPhaseHeader`, `renderRunPhaseAdvancement`, `renderRunPauseBlock`). Keep that separation, but replace string-reason branching with a typed trigger catalogue.

Expected link:

```text
autopilotTriggerSpecs()
  -> evaluateAutopilotStage(...)
       -> runCompatibilityAutopilot (enforces disposition)
  -> renderRunDryRunContract (lists same specs)
  -> report/status projection (shows evaluated code + label)
```

Tests should compare sets/slices of codes. A test that only searches the rendered words cannot prove the enforcement list is the same list.

## Pattern 3 — Shared flag-store reads

Current duplicate readers:

- `cmd/flag_cmds.go` backs `flag-check-blockers`.
- `cmd/status.go:1367` implements `countFlags` again.
- `cmd/autopilot.go:49` scans blockers as one part of a broader legacy pause check.

Consolidate only the read semantics. Preserve existing write APIs and `colony.FlagEntry`. The snapshot helper should:

- load through `storage.Store`;
- ignore resolved entries;
- count `Type == "blocker"`;
- recognize `Source == "escalation"`;
- sort/deduplicate IDs for deterministic JSON/tests;
- return an empty snapshot for a valid empty/missing flags file according to existing flag-store conventions;
- return an error only where corrupted storage is already considered non-runnable.

Use table tests for resolved, ordinary, escalation, duplicate/malformed, and missing-file cases. Keep `flag-check-blockers` public and make it an adapter over this helper.

## Pattern 4 — Structured worker artifacts cross dispatch seams

Closest analogues:

- `pkg/codex/worker.go:78` carries `Artifacts map[string]json.RawMessage`.
- `cmd/internal_worker_adapter.go` serializes artifacts through the bridge.
- plan/scout paths already decode named artifact payloads such as `scout_report`.
- `pkg/codex/worker_output_regression_test.go` pins field survival through provider conversion.

For reviewer evidence:

1. Define one typed artifact schema near continue review normalization.
2. Add `Artifacts` to `codexContinueExternalDispatch` so the hosted result does not discard the payload.
3. Decode `artifacts["review"]` in both direct and external normalization.
4. Validate caste/status/score bounds before emitting an Auditor score signal.
5. Preserve findings even when their severity does not stop the run.

Avoid regex/parsing the model's summary for `overall_score`. A raw-output fallback, if retained for backwards compatibility, must be visibly secondary and covered by a test that proves the structured artifact wins.

## Pattern 5 — Owner decisions are records with exact recovery commands

Closest analogues:

- `PendingDecision` / `PendingDecisionFile` in `cmd/pending_decision.go`.
- `recordDecisionAnswer` in `cmd/handoff_decisions_cmd.go:102`.
- phase-research decision upsert/resolution in `cmd/phase_research_decision.go`.
- owner-confirmation synthesis in `cmd/criterion_owner_confirmation.go`.
- seal blocker aggregation in `cmd/codex_workflow_cmds.go:1276`.

Checkpoint helper requirements:

- deterministic key from type + phase + source criterion/path group;
- upsert, not append-on-every-run;
- optional metadata remains backward-compatible under JSON `omitempty`;
- exact phase scope;
- resolution updates the matching unresolved entry;
- render the exact decision-answer command using shared next-action/command translation conventions;
- seal enumerates unresolved runtime/visual checkpoints even though run ignores them as blockers.

Use the existing scope-filter tests in `cmd/pending_decision_test.go` and phase-research decision tests as the closest model. Never introduce a `checkpoints.json` file.

## Pattern 6 — UI detection comes from claims paths

Build already persists a claims artifact and gives run a build result containing the claims path. Classify a visual checkpoint from actual created/modified paths after loading that artifact.

The classifier should be pure and conservative. Suitable signals include existing web/UI directories and extensions (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.css`, `.scss`, `.html`) while avoiding docs/test fixtures where the existing repository conventions can identify them. Keep the suffix/path sets centralized and table-tested.

Do not add `ui_touched: true` to the worker contract and trust it. The worker-produced claims already provide evidence that the runtime can inspect.

## Pattern 7 — Continue's normalized result is the run-control boundary

Continue already gathers:

- deterministic verification report;
- reviewer flow/findings;
- gate report;
- task/criterion evidence;
- owner-confirmation states;
- captured learning.

Add a typed, JSON-safe run-signal projection to the continue result rather than making `aether run` reopen stale global gate/midden files. The projection should include only current-phase/current-attempt evidence:

```text
deterministic floor result
Auditor present? + score
Critical count/details
High count/details
owner/runtime confirmation IDs or criteria
```

The run loop may still read the live blocker store before/after the phase because blockers are global durable state. Reviewer/gate decisions, however, should come from this current result projection.

## Pattern 8 — One readiness check per `(platform, phase)`

Closest analogue is `gatedProviderPreflight` in `cmd/preflight_cache.go:330`. Preserve its singleflight/concurrency behavior and layer phase scope into its key instead of wrapping it with another cache.

Implementation path:

```text
build/continue manifest phase
  -> direct WorkerDispatch.Phase OR TS host manifest phase
  -> internal-worker-adapter --preflight --phase N
  -> gatedProviderPreflight(..., phase=N)
  -> cache entry platform+phase
```

Rules:

- cache schema bump with backward-compatible old-entry handling;
- one successful entry is reusable for the same phase;
- next phase always misses;
- failure is not cached as success;
- platform invalidation clears all that platform's scoped entries;
- unscoped plan/colonize calls may use phase `0` and their existing TTL semantics;
- `AETHER_PREFLIGHT_TIMEOUT` is the one environment variable in every live Go/TS path;
- timeout permits exactly one retry; auth/login/binary returns immediately.

Test with an instrumented preflighter rather than time sleeps. Use contexts and fake clocks where the cache already supports them.

## Pattern 9 — Evidence-backed learning selector

`captureContinueLearning` in `cmd/codex_continue_finalize.go:1565` is the write authority. Do not change its status vocabulary merely to make replan work. Add a pure selector that reads its evidence and the active plan revision.

Closest patterns:

- normalized-content hashing/dedup used elsewhere in memory and signal handling;
- `Plan.GeneratedAt` and plan revision timestamps already used for age/drift logic;
- pending-decision upsert behavior in phase-research decisions.

Selector output should carry the lesson text, source phase, evidence timestamp, and hash. Replan metadata should store summary counts/checkpoints, not a second copy of every learning record.

Tests must independently seed:

- pre-revision lesson (excluded);
- raw observation with no passing evidence (excluded);
- incomplete worker evidence (excluded);
- incomplete gate evidence (excluded);
- duplicate normalized content (one lesson);
- valid lessons across phases (included, ordered deterministically).

## Pattern 10 — Funnel terminal branches through one report finalizer

`runCompatibilityAutopilot` has many early returns. Leaving report construction at each return will guarantee drift. Make every branch choose a typed outcome/reason/next action, then call one finalizer.

Closest analogues:

- lifecycle finalizers that build a result map and pass it to one visual renderer;
- spend ledger aggregation, which cleanly separates measured and unreported rows;
- status renderers that consume stored state rather than re-running a workflow.

The report finalizer should be the only place that:

- stamps finish time and elapsed duration;
- attaches live final blocker snapshot;
- aggregates spend across invocation phase summaries;
- writes `LastReport` to the existing autopilot state;
- produces the final result map/render projection.

`aether status` loads the stored object and calls the same report-section renderer. It may add fresh live blocker counts beside it, but must not reconstruct historical elapsed/cost/outcome.

Tests need an injected clock or `startedAt`/`finishedAt` values; avoid sleeping.

## Pattern 11 — Recovery helpers stay internal

The repository already separates useful helper functions from Cobra adapters in `cmd/recovery_classify.go` and `cmd/medic_auto_spawn.go`. Remove only orphan command registration/handlers and command-specific tests; retain internal classifier, recovery-log, and Medic eligibility tests.

At a genuine run stop:

```text
typed trigger evaluation
  -> existing failure classifier
  -> existing phase recovery log writer
  -> existing Medic eligibility check
  -> report recovery advice (when eligible)
```

Do not invoke this path for queued owner decisions, replan notes, max phases, cancellation, or successful completion. Do not auto-spawn Medic from the overnight loop unless an existing, explicit policy already authorizes it; Phase 198.3 asks for bounded advice, not more routine workers.

## Pattern 12 — Guided command input resolver

`cmd/state_extra.go:120` is the live `phase-insert` command and `insert-phase` alias. Preserve its mutation body and extract input resolution ahead of it.

Closest analogue patterns:

- command handlers that return structured `input_required` in non-interactive mode;
- shared TTY detection/prompt helpers already used by lifecycle commands;
- platform command-guide generation and wrapper byte-parity tests.

Input precedence:

```text
explicit flags > positional issue-derived defaults > TTY answers > structured input_required
```

Validation occurs after merging. A non-TTY missing-input response must be produced before loading/writing colony state so tests can prove no mutation. Keep existing explicit `--after --name --description` callers passing unchanged.

Managed surfaces to update together:

- `.aether/commands/insert-phase.yaml` (source);
- `.claude/commands/ant/insert-phase.md`;
- `.opencode/commands/ant/insert-phase.md`;
- any published/global mirror identified by the repository's wrapper parity helper;
- `cmd/command_guide.go` and command/parity fixtures.

Do not manually diverge the copies; use the repository's normal sync/generation path where available and verify byte equality.

## Pattern 13 — Swarm history is event history, not mutable counters

Both `runSwarmCompatibility` (`cmd/swarm_cmd.go:156`) and `runSwarmFinalize` (`cmd/swarm_cmd.go:628`) converge on persisted result files. Put target fingerprint and strike evaluation in a helper shared by both completion lanes.

Recommended algorithm:

1. Load prior swarm result records, newest first.
2. Compare normalized target fingerprint.
3. Stop scanning that fingerprint at its last completed result.
4. Count consecutive failed/blocked results.
5. When persisting the third failure, upsert one escalation flag containing evidence IDs.
6. Before dispatch, refuse when three unresolved consecutive failures already exist.

Sort filesystem input before evaluation for deterministic behavior. Malformed unrelated result files should be reported or skipped according to the existing swarm history convention, never treated as a strike for every target.

The escalation writer should reuse the normal flags format. A dedup key in the source/description or an explicit stable ID prevents a second third-strike run from adding duplicate flags.

## Test Conventions

### Command-package isolation

`cmd/run_autopilot_test.go:95` supplies `seedRunFixture`; its `completingRunInvoker` at line 51 is the closest simulated-worker seam. Extend or add a sibling fixture rather than creating a fake parallel runner.

Tests that change `rootCmd`, global paths, invokers, environment, or output writers must call `saveGlobalsCmd(t)` first. Use `t.Setenv`; avoid leaking `AETHER_OUTPUT_MODE`, provider timeout settings, or platform selection.

### TDD requirement inside execution plans

Each behavior task should name the failing test first and include a mutation/proof clause where a false-positive risk is high. Important mutation guards:

- change queue disposition to stop -> six-phase test fails;
- change Auditor threshold from `< 60` to `<= 60` -> score-60 test fails;
- let High block -> High test fails;
- remove phase from preflight key -> next-phase probe-count test fails;
- count observations as lessons -> no-confirmed-lesson test fails;
- recompute status report -> byte/struct equality test fails;
- permit fourth swarm dispatch -> invocation counter test fails.

### Snapshot/catalog regeneration

- `cmd/audit_catalog_test.go` owns `cmd/testdata/command_catalog.json`.
- `cmd/parity_test.go` owns `cmd/testdata/parity_snapshot.json`.
- `cmd/subcommand_reachability_ratchet_test.go` owns `cmd/testdata/orphan_allowlist.json` through `-update-orphan-allowlist`.
- Do not edit `orphan_allowlist_baseline.json` merely because the live list shrinks; its ratchet is intentionally historical/monotonic.

Use the test-provided update flags or repository scripts, then inspect the diff. Avoid hand-deleting JSON entries from generated snapshots.
