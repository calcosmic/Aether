# Phase 198.3: Overnight Stamina - Context

**Gathered:** 2026-08-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Restore `aether run` as a safe unattended build/check/advance loop that can be
left running overnight. In headless mode, anything that merely needs the
owner's eyes (hands-on runtime verification, a visual checkpoint, or a replan
suggestion) is recorded for morning and the run continues. Machine-confirmed
unsafe or impossible states stop with durable state and one exact resume
command. Interactive runs still pause for those owner moments.

This phase restores the named stop contract against the **current** runtime
rather than reviving obsolete assumptions from v5.4: the deterministic checks
remain the non-skippable floor, reviewers remain optional judgement, and an
Auditor is never spawned just to manufacture a score. The same canonical
trigger catalogue must drive enforcement, `aether run --dry-run`, persisted run
state, the closing report, and `aether status`.

It also restores lesson-aware replan advice, the pre/post-build blocker-count
gate, elapsed-time plus measured-cost reporting, bounded provider readiness
checks, and an end-to-end fixture of at least six phases that finishes under a
single headless `aether run`. The audit subjects named on the roadmap
(`autopilot-*`, `flag-check-blockers`, guided corrective insertion, swarm
three-strike escalation, failure classification/recovery logging, Medic
eligibility, and escalated-flag status) are part of the phase's recovery and
visibility closure; they must not become parallel sources of lifecycle truth.

Out of scope: automatic provider/model switching; silently rewriting the plan;
weakening or skipping the deterministic floor; sealing without the owner;
adding routine workers or check-ins; the broad `cmd` test-parallelism/model-
routing/brief-compression programme from the turnaround todo; deleting the
wider orphan surface (Phase 198.4); and the real owner-observed overnight run
(Phase 199).

</domain>

<decisions>
## Implementation Decisions

### What stops the night

- **D-01:** The governing rule is **stop only when continuing would be unsafe
  or impossible**. A machine-confirmed failure stops; something that only a
  person can judge waits for morning.
- **D-02:** Headless runtime-verification and visual-checkpoint prompts become
  durable pending decisions and **do not stop phase advancement**. They remain
  unresolved until the owner answers, and seal still waits for them. In an
  interactive run the same triggers pause and ask.
- **D-03:** Genuine stops include: the deterministic floor still failing after
  its already-bounded repair attempt; an Auditor score below 60 when an Auditor
  actually ran; a Critical reviewer/audit/security finding; a new blocker or
  an existing blocker becoming escalated; corrupt/non-runnable state; and a
  required worker provider still unavailable after the bounded timeout retry.
  Explicit operator limits (cancel, overall timeout, `--max-phases`) remain
  named normal stops rather than being disguised as failures.
- **D-04:** Restore the original Auditor floor at **score < 60**. The score is
  consumed only when an Auditor was already selected; Aether must not dispatch
  an Auditor merely to obtain it.
- **D-05:** Only **Critical** reviewer findings halt an unattended run. High
  findings stay recorded and appear in the morning review, but do not stop.
- **D-06:** Preserve Phase 198's headless build-start ruling: existing blockers
  are shown and counted, then the run proceeds. The pre/post-build comparison
  stops only when the count rises or a blocker becomes escalated. `aether
  status` shows the same blocker and escalation truth.
- **D-07:** `aether run --dry-run` names every trigger and its disposition in
  the selected mode: **stop**, **queue and continue**, or **normal completion**.
  A trigger may not exist only in prose or only in a test catalogue.
- **D-08:** These decisions supersede two lines in the 2026-08-16 autopilot
  disposition: headless no longer "queues and still stops" for human-only
  checkpoints, and the Auditor score floor is no longer retired. Unaffected
  dispositions remain useful historical mappings, subject to the current
  deterministic-floor and optional-reviewer architecture.

### Replanning overnight

- **D-09:** When replanning becomes advisable, interactive mode pauses;
  headless mode queues the suggestion and continues. Headless mode never
  rewrites the remaining plan on its own.
- **D-10:** A replan trigger needs **both** the configured completed-phase
  interval and at least one new confirmed lesson. Reaching two phases with zero
  new lessons is not a reason to interrupt or queue anything.
- **D-11:** "Learnings accumulated" means the count of **unique confirmed
  lessons recorded since the last successful plan**. Repeated copies count
  once; raw observations and only-long-term-promoted habits are both the wrong
  count.
- **D-12:** One unresolved replan note is updated rather than duplicated. It
  carries the current unique-lesson total and the first and latest phase
  checkpoints at which the trigger fired.

### Provider timeouts and turnaround

- **D-13:** A provider readiness check gets **two attempts total**: the normal
  attempt plus one retry, and only a timeout retries. A real missing-login,
  missing-binary, or rejected-auth result surfaces immediately.
- **D-14:** One successful readiness check is cached for the current phase and
  shared by all of that phase's workers. The next phase checks again. Never
  repeat the same preflight for every worker.
- **D-15:** If both timed attempts fail, preserve every completed phase and
  stop on the current unfinished phase. Do not switch provider automatically
  and do not skip the phase. The stop report gives one exact resume command.
- **D-16:** Every **live** Go and TypeScript-host provider readiness path uses
  one setting, `AETHER_PREFLIGHT_TIMEOUT`, with a **45-second default**. There
  is no hidden five-second production path and no second setting for auth
  probes.

### The morning report

- **D-17:** Lead with the outcome: either "completed N phases" or "stopped at
  Phase N", then the queued decisions, blocker/escalation count, elapsed time,
  measured cost, and one exact next command. Compact phase detail follows;
  never lead with a chronological event dump.
- **D-18:** Elapsed means real wall-clock time from this `aether run`
  invocation starting until it completes or stops, including checks, retries,
  and provider waits. It excludes time when Aether was not running between
  separate resume invocations and is not the sum of worker durations.
- **D-19:** The cost portion shows one measured run total plus a compact
  per-phase breakdown. It reuses Phase 196's arithmetic and honesty rules:
  unreported usage renders as `— not reported`, does not enter the measured
  total, and is never estimated.
- **D-20:** Persist the report. `aether status` renders the same outcome summary
  from that persisted record — stop reason, phases completed, queued decisions,
  blockers/escalations, elapsed time, cost, and resume command — so closing the
  terminal does not lose the night.

### Carried forward — binding, not re-asked

- **Phase 193:** the deterministic floor cannot be skipped; a human-only
  criterion becomes `needs_owner_confirmation`, the phase may advance, and
  seal waits; a failed floor gets exactly one bounded automatic repair attempt.
- **Phase 194:** reviewers are judgement, forced only by named risk, and no
  reviewer is added just to satisfy a hidden gate.
- **Phase 198 D-07:** autopilot never seals. It completes the last phase and
  hands the owner the seal command.
- **Phase 198 D-09/D-10:** headless build-start advisories print without asking;
  human output stays compact, headed, append-only, and in one terminal.
- **Phases 198.1/198.2:** use the existing pending-decision, learning, midden,
  handoff, and outcome stores; do not create a second memory/recovery pipeline.
- **Wrapper/runtime contract:** Go owns state, stop/queue classification,
  reporting data and rendering; wrappers only pass through and spawn the exact
  requested workers.

### Planner's Discretion

- The exact persisted run-summary schema/file, provided the loop and status
  consume one record and one renderer rather than reconstructing two answers.
- Exact reason-code names, wording, headings and emoji within the settled
  append-only headed-section display standard.
- The deterministic identity/dedup key for manual checkpoints, High findings,
  and the single replan note.
- How the runtime snapshots "last successful plan" and computes unique
  confirmed lessons, provided the count comes from durable live writers and is
  testable across process boundaries.
- The phase-scoped provider-check cache implementation and invalidation on an
  actual dispatch failure. The cache boundary (one phase), retry limit, timeout
  setting and failure outcome are locked.
- How the roadmap's failure-classification, recovery-log, Medic, three-strike,
  guided corrective-phase and legacy `autopilot-*` audit subjects share
  internal functions. They may support bounded recovery but may not create an
  endless retry loop, a second autopilot, or routine extra workers.
- Fixture construction and simulated-worker mechanics, provided at least six
  phases complete under one real `aether run` invocation and the test injects
  queueable conditions that would fail if misclassified as stops.

### Folded Todos

- **Worker turnaround is too slow**
  (`.planning/todos/pending/2026-08-27-worker-turnaround-is-too-slow.md`) — this
  phase must add no routine dispatch or check-in, share provider readiness once
  per phase, record elapsed wall-clock honestly, and prove the six-phase run.
  The todo's broader test-suite parallelism, model routing and brief-size work
  remain outside this phase.
- **TS-host preflight timeout hardcoded**
  (`.planning/todos/pending/2026-08-01-ts-host-preflight-hardcoded-timeout.md`)
  — the main production preflight has already moved to the shared 45-second
  resolver and Go already retries timeouts once. Close the overnight risk by
  proving every live lane uses that contract and the phase cache. The remaining
  fixed five-second `runProbe` is in the deprecated forensic launcher with no
  production caller found during discussion; do not revive dead code merely to
  "fix" it — its deletion/disposition belongs to Phase 198.4 unless planning
  finds a live caller.

## Existing Code Insights

### Reusable Assets

- `runCompatibilityAutopilot` and `buildRunDryRunResult`
  (`cmd/compatibility_cmds.go`) — the real `aether run` loop, including the
  current pre/post checks, replan interval, dry-run plan and result envelope.
- `checkAutopilotPauseConditions` (`cmd/autopilot.go`) — current central pause
  check. It sees pending-decision blockers, test/gate failures, critical Chaos
  midden entries and an uncommitted-change marker, but not the restored full
  contract.
- `autopilotPauseTriggerCatalog`, `pauseAutopilotRun`,
  `queueAutopilotPauseDecision`, `renderRunReplanBanner` and the run renderers
  (`cmd/run_visuals.go`) — an existing catalogue/queue/display seam. Today
  headless queues a generic `autopilot_pause` and then still stops; split
  trigger detection from mode-specific disposition instead of adding another
  loop.
- `flag-check-blockers` (`cmd/flag_cmds.go`) — already computes blocker,
  issue, note and escalation truth from the pending-decision/flag store; wire
  one shared read into run and status rather than parsing visual output.
- Spend readers/renderers (`cmd/spend_cmd.go`, `cmd/spend_cost_line.go`) — pure
  measured-token arithmetic and `— not reported` behaviour to aggregate across
  the phases completed by this invocation.
- `syncRunAutopilotState` and `.aether/data/autopilot/state.json` — existing
  persisted run status with an initialization timestamp; extend or replace
  through one canonical record rather than creating an unrelated report truth.
- Go provider availability (`pkg/codex/platform_dispatch.go`, especially
  `runAvailabilityProbe`) — already uses the shared 45-second setting, retries
  timeouts once, refuses retries for real auth failures, sanitizes diagnostics
  and tears down the process group.
- TypeScript host `preflight-config.ts` and `worker-dispatch.ts` — production
  TypeScript already resolves `AETHER_PREFLIGHT_TIMEOUT` and sizes the Go
  adapter budget for two attempts. `platform-dispatcher.ts` is explicitly
  deprecated/test-forensic and its fixed-five-second `runProbe` has no live
  production caller found in the scout.

### Established Patterns

- One catalogue is already intended to feed dry-run preview, pause tests and
  the disposition record. Keep that singleness and add the missing queue/stop
  disposition; do not build separate `if` lists for run, dry-run and status.
- Pending decisions are durable and deduplicated. Phase 193 already allows a
  human-only criterion to advance while seal waits, which is the exact state
  model STAM-01 needs.
- Build/continue spend ledgers are phase-scoped and read-only at display time.
  A run aggregate must select only phases completed by this invocation and
  reuse their measured classification.
- Runtime state is authoritative on all lanes. The TS host can cache/forward a
  preflight result, but cannot decide that a phase advances or that a stop is
  queueable.

### Integration Points

- Before `runCodexBuildWithOptions` and after its result in
  `runCompatibilityAutopilot`: snapshot and compare blocker/escalation truth.
- After `runCodexContinue`: classify owner-only checks, reviewer score/findings,
  deterministic failure, replan advice and completion through the canonical
  trigger catalogue.
- `renderRunCompatibilityVisual` and `status.go`: render the same persisted
  outcome-first run summary; `countFlags` currently counts severity only and
  must regain escalated truth from the shared blocker reader.
- `cmd/run_autopilot_test.go` and the black-box/simulated adapter harness: grow
  the existing two-phase coverage into the required six-plus-phase unattended
  fixture, including queueable visual/runtime checkpoints.
- `failure-classify`, recovery-log, Medic eligibility, swarm attempt history and
  guided `insert-phase`: use as bounded recovery inputs/actions where the
  canonical stop policy calls for them; never let them invent a competing stop
  policy or unbounded worker loop.

<specifics>
## Specific Ideas

- Morning headline shape: `Completed 6 phases` or `Stopped at Phase 4 — provider timed out twice`.
- Replan note shape: `7 unique confirmed lessons since the last successful plan — first due after Phase 2, updated after Phase 4`.
- Provider contract: one phase-scoped check, 45 seconds per attempt, at most two
  attempts, timeout-only retry.
- Status must answer the morning questions without the original terminal:
  outcome, phases completed, queued items, blocker/escalation count, elapsed,
  measured cost and the exact resume command.
- Dry-run should show each named trigger together with `stops`, `queues in
  headless`, or `normal ending`, so "runtime verification needed" is visible
  without falsely implying it halts headless mode.

</specifics>

<deferred>
## Deferred Ideas

- Automatic provider switching was considered and rejected for this phase; it
  changes routing and cost behaviour rather than improving stamina safely.
- Automatic plan rewriting was considered and rejected; a headless run may
  recommend a replan but never replace the owner's remaining roadmap.
- The broad worker-turnaround programme (parallelising the `cmd` suite,
  complexity-based model routing and wider brief compression) remains future
  work; this phase owns only overhead it directly introduces or can eliminate
  in the overnight loop.
- The real owner-observed overnight run belongs to Phase 199; Phase 198.3 proves
  the contract with a realistic simulated fixture.
