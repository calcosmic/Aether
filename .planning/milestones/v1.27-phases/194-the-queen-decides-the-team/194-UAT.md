## Tests

### 1. Ordinary Job Uses One Worker
expected: For a normal one-task bug fix with no named risk and no explicit team proposal, the build team contains only the Builder. Continue does not summon an AI reviewer, while the program's own build, vet, test, and lint checks still run normally.
result: pass

### 2. Named Risk Adds One Explained Reviewer
expected: A plain job such as CSV export adds no reviewer. Password/authentication or payment wording adds one security reviewer; release sign-off, data deletion, or database migration wording adds one quality reviewer. The CLI quotes the matched phrase in a plain-English reason, announces the reviewer for the checking step, and never dispatches that caste at both build and continue.
result: pass

### 3. Every Proposed Worker Needs Its Own Reason
expected: A worker proposed with `--castes` and a matching `--caste-why caste=reason` reaches the dispatch list on build and continue. A proposed worker without its own reason is refused by name without dropping valid teammates. Aliases and comma-separated proposals resolve to the same canonical workers.
result: pass

### 4. Review Controls Behave Predictably
expected: Light and standard review add no unconditional AI reviewers; heavy review adds the security and quality reviewers plus coverage review when the phase produces testable code. An explicit reasoned worker and a named-risk reviewer both survive a light request, and merely being the final phase does not raise review depth.
result: pass

### 5. Team Check-In Explains the Team Clearly
expected: The pre-build card is split into clearly labelled sections with visual separators and space between workers. Each worker has a phase-specific reason separate from its generic "what it does" description. REQUIRED means the Builder; any reviewer required after the work is announced separately with the triggering signal. A one-worker build still pauses at this check-in.
result: pass

### 6. Actual Changed Files Can Raise Risk
expected: If the plan wording misses a risk but the implementation changes an authentication, credential, payment, deletion, or migration path, continue adds the appropriate reviewer and says the files triggered it. Git-detected changes still count when a handoff omits them, unrelated longer words do not create false alarms, and the native and wrapper continue lanes choose the same reviewer set.
result: pass

### 7. Reviewer Waiver Is Owner-Only and Time-Bounded
expected: A live check-in shows an exact `aether decision-answer` command for declining one forced reviewer on one signal in one phase. Only that protected command can resolve the waiver; generic resolution is refused, repeated card renders do not invalidate an earlier displayed command, and a recorded decline before dispatch remains honored. A decline after dispatch starts is refused, autopilot cannot waive, and dispatch stops if the waiver-window closure cannot be saved durably.
result: pass

### 8. Discovery Uses a Researcher Instead of a Builder
expected: A discovery-mode build with no explicit proposal sends exactly one Scout because research findings, rather than implementation code, are the deliverable.
result: pass

### 9. Help, Documentation, and Recovery Match the Runtime
expected: `aether build --help` and `aether continue --help` both expose `--caste-why`. The shipped guidance describes the Builder-only ordinary floor and five named risk signals, preserves valid phase IDs when wrapper flags are present, and Codex blocked-state recovery shows native `aether ...` commands rather than unsupported slash commands.
result: pass
