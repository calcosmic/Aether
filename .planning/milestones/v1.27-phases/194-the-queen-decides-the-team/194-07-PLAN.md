  <action>
Create `cmd/forced_reviewer_waiver.go` following `cmd/criterion_owner_confirmation.go`
line for line in structure — a stable question text, a matcher, a command
string, and no persisted state of its own.

`forcedReviewerWaiverQuestionText(phaseID int, signal string, plainEnglish
string) string` builds the deterministic sentence the owner's answer is matched
against, in the shape: Phase 7: a security reviewer is being added because this
touches logins and passwords. Waive it? Include the phase number and the signal
name so the text is unique per phase and per signal — that uniqueness IS the
scoping rule in D-03, exactly as the criterion confirmation text scopes by phase
and task.

`forcedReviewerWaiverCommand` returns the exact `aether decision-answer`
invocation, with the question text passed through the existing `shellQuote`
helper, never Go quoting — the owner pastes this into a real shell and the
signal's plain-English words are free-form text. This is the CR-02 precedent
from Phase 193; reuse the helper rather than writing a second one.

`forcedReviewerWaiver(phaseID int, signal string) (bool, string)` matches the
normalised question text against `answeredDecisionTexts()` the same way
`ownerConfirmationAnswered` does, and additionally returns the owner's recorded
resolution text so the card can show the reason. If the existing helper only
returns presence, extend it or read the pending-decision file directly using the
same normalisation — do not introduce a second normalisation.

`applyForcedReviewerWaivers(phaseID int, hits []riskSignalHit) (kept, waived
[]riskSignalHit)` filters at the SIGNAL level, before `collapseToForcedReviewers`
merges signals into castes. That ordering is what makes "one signal for one
phase" true: a phase with a waived credentials signal and a live payments signal
still gets the security reviewer, forced by payments alone, and its reason names
payments only.

Call `applyForcedReviewerWaivers` inside `queenForcedContinueReviewers` — the
one function both continue lanes already go through after plans 194-01 and
194-06 — so the waiver applies identically on the in-process and wrapper lanes
with no second implementation. Because the changed-files hits are unioned inside
that same function, filtering there is also what makes a waived signal stay
waived when the files re-detect it. Pass the waived hits back out so the card and
the continue output can say what was waived and why.

In `renderCeremonyTeamCheckin`, add `waived` (per signal: the plain-English
words and the owner's recorded reason) and `waive_commands` (per live forced
signal: the exact pasteable command) to the result map, and render both on the
card — a waived signal shown as declined by the owner with the reason, and a
live forced signal accompanied by the command that would decline it.

Write the tests first and watch them fail. `TestOnlyTheOwnerCanWaiveAForcedReviewer`
must prove the negative: with no recorded answer, the reviewer is dispatched at
light depth, at standard depth, with an explicit caste proposal that omits it,
and with a proposal that explicitly names other castes — four attempts to get
rid of it that all fail. `TestAutopilotNeverWaives` asserts the same for the
code path autopilot reaches. `TestWaiverCoversOneSignalOnOnePhase` covers the
three non-carry cases. `TestWaivedSignalStaysWaivedWhenTheFilesRedetectIt`
records a waiver, then runs `queenForcedContinueReviewers` with changed files
matching the same signal's path patterns and asserts nothing comes back.
`TestTeamCheckinDoesNotMutateWithAWaiverPresent` extends the existing
non-mutation contract for the check-in command. Add
`TestOneWorkerTeamStillPauses` to `cmd/ceremony_team_checkin_test.go`: a
manifest whose team is a single implementation worker still renders a card and
still reports that approval is needed (D-14).
