<objective>
Make both checking-step lanes carry the same team, from both directions: what
the builder actually changed can raise a reviewer the plan's wording missed, and
the owner's own instructions reach the lane people actually run rather than only
the heavy plan-only lane.

Ordering rationale: this plan edits `cmd/codex_continue.go` and
`cmd/codex_continue_plan.go`, which plans 194-01 and 194-03 also edit, and it
fills the `PathPatterns` field on the table plan 194-01 declared. It also depends
on plan 194-05's fallback retune for the autopilot assertion in task 2. Both
tasks live here rather than in separate plans because they are the same
invariant seen from two sides — the two lanes must agree — and splitting them
would put the parity assertion in a different plan from half of what it asserts.

Purpose: the file-detection half of TEAM-02, and the "owner's dials work on the
path people run" half of TEAM-05.
Output: an add-only changed-files detector wired identically into both lanes,
and a proposal that behaves the same on the fast path as on the plan-only path.
</objective>

Fill in `PathPatterns` on each entry of `queenRiskSignalTable` and implement
`queenRiskSignalHitsFromPaths(paths []string) []riskSignalHit` with source
"changed files". Patterns are Claude's discretion; seed them as path-segment
substrings on the lowercased slash-normalised path:
`credentials/auth` -> `auth/`, `/login`, `session`, `credential`, `secrets`;
`payments` -> `payment`, `billing`, `checkout`, `stripe`;
`data deletion` -> `delete`, `purge`;
`database migration` -> `migrations/`, `migrate/`, `.sql`.
`release sign-off` gets no path patterns — no file path reliably means a
release gate, and a pattern that fires on the word "release" in a path would be
a false alarm with no upside.

Wire it into `queenForcedContinueReviewers`: the changed-file hits are UNIONED
with the recorded hits and can only ADD a caste or ADD a signal to an existing
caste's reason. The function must never remove a caste or a signal that the
build's record carried — write that as a doc comment naming D-02, and prove it
with `TestChangedFilesCanOnlyAddAForcedReviewer`, which runs the function twice
on the same recorded set (once with an empty changed-file list, once with a
list matching no pattern) and asserts the output is identical, then a third
time with a `migrations/0007_add_column.sql` path and asserts the quality
reviewer was added and the recorded security reviewer survived.

Supply `changedFiles` at both continue boundaries from
`phaseChangedFilesFromHandoffs(phase.ID)`: in `cmd/codex_continue.go` where
`plannedContinueReviewDispatches` is composed, and in
`cmd/codex_continue_plan.go` inside `plannedExternalContinueDispatches`. Both
lanes must behave identically — the 2026-08-21 review gate found the in-process
lane half-wired, and nothing enforces this parity but discipline. Add
`TestBothContinueLanesForceTheSameReviewers` asserting the two lanes return the
same caste set for the same phase, the same recorded set and the same changed
files.

A file-detected signal carries the same reason shape as a wording-detected one,
with the source read "the files changed" rather than "the plan mentions" — for
example: this touches changing the database structure (a file under
