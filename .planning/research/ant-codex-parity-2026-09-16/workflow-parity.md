## Finding in plain English

Changing the names to `$ant-*` would make commands easier to find, but would not make the experience match Claude. Aether already has most of the engine: typed plans, evidence checks, worker manifests, safe finalizers, recovery, and memory. Codex needs a reliable conductor around that engine: ask the current questions, deliver the full worker context, launch and track the right helpers, use their results, and stop at the same owner decisions.

This is **not a ground-up port**. The nine core flows already have substantial Codex instructions. Their current gaps are mainly stale or incomplete orchestration, plus a few genuinely missing native-host integrations. Some deeper defects are shared by Claude/OpenCode's native-wrapper path and must be budgeted separately.

## B. Runtime available, but Codex orchestration is stale or incomplete

### P0/P1: bring the nine core flows to the current contract

1. **Init/discuss/spec sequencing and actual approval.** Claude init explicitly offers proceed/revise/cancel, persists signals only after successful init, then hands off to discuss (`.claude/commands/ant/init.md:337–368`). Codex creation ends `Next Up: aether plan` (`.aether/skills/colony/aether-colony-creation/SKILL.md:106–122`), and guide init explicitly insists on that stale next step (`cmd/command_guide.go:233–234`). The guide's discuss block still calls discuss-analyze, asks a compact generic set and routes settled discussion to plan (`:480–494`), while the current Codex research skill correctly requires the full runtime material batch and a separate spec approval (`.aether/skills/colony/aether-colony-research/SKILL.md:98–136`). Because skills declare command-guide authoritative, this is an active contradiction. User effect: wrong next command, repeated/unbound questions, or hitting the plan gate before the spec exists. **Fix:** one current shared contract for init → discuss → spec → staged plan; respect existing explicit owner instructions rather than adding redundant approval.

2. **Deliver the context capsule, not only the brief.** Claude explicitly constructs `manifest.context_capsule + brief/brief_path + skill_section + newest decision-answer prompt_section` (`.claude/commands/ant/build.md:348–366`; analogous continue `:140–186`, colonize `:58`). The Codex build-cycle skill never mentions `context_capsule`, and merely says pass the brief verbatim (`:282–301`). Runtime deliberately removes steering from wrapper briefs (`cmd/codex_build.go:4643–4661,4674–4721`) and puts it in the manifest (`:2972`). User effect: an apparently valid Codex worker can miss hard signals and previous-worker handoffs. **Fix:** serialize one exact prompt assembly contract, tested against the actual native dispatch request, with each section included once.

3. **Use Queen judgment and the current team decision UI.** Claude build reads `caste_roster`, classifies relevant/unchanged domains, and submits per-caste reasons (`.claude/commands/ant/build.md:141–237`); heavy continue does the same (`.claude/commands/ant/continue.md:85–138`). Go already accepts `--castes`, `--caste-why`, and boundary proposals (`cmd/codex_workflow_cmds.go:318–322,519–543`) and exposes roster/decision/forced-reviewer facts (`cmd/codex_build.go:797–806`). Codex guide/skill primarily render runtime choices and omit this decision layer. User effect: expensive irrelevant workers or missing useful specialists when keyword fallback is inadequate. **Fix:** shared concise decision logic, bounded by runtime floors/budgets, with no fixed reviewer list. Guide seal incorrectly says dispatch Gatekeeper/Auditor/Probe (`cmd/command_guide.go:459`), while current Claude says use the runtime-selected team (`.claude/commands/ant/seal.md:49–54`).

4. **Complete owner interaction and answer propagation.** Runtime build returns `blocker_advisory`, `blocker_advisory_question`, `checkin_requested/reason/summary` (`cmd/codex_build.go:907`, `cmd/codex_workflow_cmds.go:365–397`). Claude provides the heads-up, render/data team card, trim/waive/redirect semantics and re-fetch (`.claude/commands/ant/build.md:272–328`), then handles worker questions between waves and appends runtime-rendered answers (`:359–366`), then offers verify/stop/steer (`:405–422`). Codex skill contains check-in status prose but lacks the concrete card/answer/refetch flow, inter-wave answer relay and post-build choice. Claude continue additionally asks outstanding worker questions and approves/dismisses suggested steering (`.claude/commands/ant/continue.md:235–249`). **Fix:** drive host questions from typed runtime cards and exact returned commands; do not mint authority or silently skip unanswered required decisions. Preserve prior user authorization.

5. **Seal must handle the pending-confirmation result, not just success/error.** Claude branches on `awaiting_owner_confirmation`, asks the exact runtime question, records the exact answer, and reruns the same finalization (`.claude/commands/ant/seal.md:163–192`). ## C. Actual missing integration/behavior

### Codex-specific native integration

**Native worker lifecycle and honest capabilities.** Codex native subagents exist (parent researcher verified current official docs and is using them here). Aether's direct Go adapter still launches `codex exec --json --ephemeral` with the TOML instructions injected and output schema (`pkg/codex/worker.go:385–445`), not a chat-native child. `ShouldUseAgentDelegatePath` only selects Claude/OpenCode (`pkg/codex/platform_dispatch.go:309–338`). The native skill is a different existing path: plan-only → platform spawn → finalizer. Make that choice explicit, keep exactly one launch owner, bind native child identity to dispatch/attempt, journal each terminal result, and implement wait/interruption/recovery without redispatching completed work. Existing Go adapter code is a reusable model (`cmd/internal_worker_adapter.go:180–255`); do not route native workers through it and also spawn them.

**Native Codex usage attribution is absent.** `cmd/wrapper_usage_resolve.go:92–109,136–261` reads Claude transcripts/OpenCode stores and otherwise uses attached provider usage. There is no Codex native-session collector. Direct Codex subprocess usage is already parsed (`pkg/codex/usage.go:99–168`). Native completion packets are intentionally not trusted for model-reported token numbers. Add an authenticated/provider-owned native usage source and worker/session/time binding if the host exposes it; otherwise display “not reported.” Do not label missing measurement as zero cost. This is a real Aether integration gap; availability of a suitable host source needs verification.

**Permission translation needs an explicit native capability contract.** Direct adapter enforces read-only/workspace-write using CLI flags (`pkg/codex/worker.go:427–437`; `pkg/codex/permission_profile.go:178–204`). Native agent definitions mostly carry instructions (e.g. `.codex/agents/aether-watcher.toml:1–5`), and the skills assert enforcement without a tested native launch binding. Preserve per-dispatch profiles and document honest limitations; do not pretend prompt-only restrictions are filesystem isolation. Most review castes intentionally use workspace-write plus behavioral restrictions already (`permission_profile.go:53–102`), so avoid inflating scope into a new universal sandbox.

### Shared native-wrapper hardening — budget separately from a Codex port

1. **Governed helper recruitment is reachable but not a complete real-host integration.** Every wrapper build brief includes `aether recruit` and expressly forbids alternative helper launch (`cmd/codex_build.go:4752–4794`); direct build and continue also inject it (`:2592–2600`, `cmd/codex_continue.go:2016,2529`). The registered CLI calls `dispatchRecruitment` (`cmd/recruitment.go:20–21,279,359`). Its default is `codex` or `AETHER_CODEX_PATH`, argv is just `--caste ... --objective ...`, and it directly executes that instead of using the normal provider invoker (`cmd/recruitment_dispatch.go:42–71,163–200`). It does not honor `AETHER_WORKER_PLATFORM` or supply the normal prompt/schema/provider plumbing. `native-bind` is only an enum/selector: the production caller always selects root-mediated and does not call the probe (`:74–80,215–223`). The only production result-bind callers are `recruitment.go:310` and `recruitment_lane.go:257`, both this subprocess route. There is no public native admit → launch → result-bind API. Ordinary spawn-can-spawn/log/complete does not replace the recruitment ledger.

   The helper's summary is stored but not returned by `recruit` (`cmd/recruitment.go:297–339`); its handoff call supplies name/status with no WorkerResult (`:319–329`), whereas handoff extraction reads actual summary/handoff only from WorkerResult (`cmd/codex_dispatch_contract.go:864–884`). Thus even a successful substitute process is not useful-result proof. Repair using existing admission, lineage, budgets, permission and result contracts, expose a native coordinator route or invoke the proper provider adapter, and prove the parent receives and uses a bounded helper's evidence. The proof researcher confirmed tests substitute a Go test child rather than a real host. This defect affects Claude/OpenCode too; do not price it as exclusively Codex parity.

2. **Worktree behavior differs by execution lane.** Direct runtime workers already allocate a worktree, run at its path, admit paths and sync back (`cmd/codex_build_worktree.go:380–425,459–522,970–1016`), with external finalizers also capable of merging recorded worktrees (`cmd/codex_build_finalize.go:613–622,814–827`). But the only production `allocateBuildWorktree` call is in that direct execution loop. Plan-only build computes parallel mode and emits the root manifest/receipt (`cmd/codex_build.go:777–851,858–907`), and current native wrappers/skills do not carry an allocation/cwd/finish protocol. Saying “one worktree per job” is not enough. Add Go-owned per-job workspace leases and native child cwd binding, or clearly choose the working Go lane for worktree execution until supported. Preserve dirty user edits and uncredited branches; do not reimplement merge-back in prompt prose.

3. **Native swarm lacks direct-lane checkpoint control.** Both current Claude and Codex instructions use plan-only, native investigators → builder → watcher, then one finalizer. Direct swarm ranks evidence and saves/restores a repair checkpoint before/after the builder (`cmd/swarm_cmd.go:464–588`). External finalization receives already-finished workers and explicitly records `CheckpointSaved:false`, `CheckpointRestored:false` (`:1087–1139,1227–1238`). Therefore current Claude prose promising automatic rollback does not establish actual parity. Reuse the Go checkpoint/synthesis machinery through stage boundaries before the native builder, or retain runtime execution for this safety-sensitive flow. Do not claim this is a feature Codex alone lacks.

## Smallest architecture

1. Keep Go as the only authority for state, manifests, permissions, approval bindings, verification, repair/merge and advancement. Use existing typed results and exact next commands.
2. Make the nine `$ant-*` skills thin command-specific adapters over one current orchestration contract. Put semantic steps in canonical structured command metadata or a shared runtime-produced recipe; generate/project the host-specific tool instructions. Do not maintain a fourth hand-copied Claude prompt tree.
3. Implement one native dispatch bridge: runtime-issued dispatch → exact context assembly → named native child → provider/thread binding → terminal receipt → Go finalizer. Journal child results as they arrive. Use the existing Go subprocess lane explicitly where native capabilities cannot satisfy permissions or workspace binding; identify the actual execution owner.
4. Keep decisions typed: pending cards pause only dependent work, answers flow through existing Go APIs, and stale manifests are re-fetched. Distinguish ordinary owner choices from actual authority changes. No invented success, costs or completion.
5. Prove each core workflow and interruption path in scratch repositories using real Codex children. Focus tests on binding, context delivery, no duplicate launch/credit, stale replay, helper result use, workspace preservation, and actual native event/usage availability. Parent evidence report owns the acceptance matrix.
