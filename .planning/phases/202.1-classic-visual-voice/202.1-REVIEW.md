# Phase 202.1: Code Review Report

**Reviewed:** 2026-09-12
**Depth:** standard
**Files Reviewed:** 28
**Status:** issues_found

## Summary

This phase restores a per-line emoji/glyph "voice" to eight ordinary lifecycle
screens (plan, discuss, spec, status, build, continue, seal, what-next) via one
shared glyph table (`voiceGlyphMap`) and one funnel (`voiceLine`), backed by a
screen corpus, a density gate derived from real Classic-era source, a
plain-English scan, a raw-state-token scan, and a structural guard against a
second hand-rolled glyph table. The test suite added for this phase
(`classic_voice_*_test.go`, `claudemd_classic_voice_test.go`) is unusually
rigorous: every guard is paired with a `...CanFail` test that plants a
synthetic violation and proves the check actually fires, and the reference
density figure is derived from git-extracted historical blocks with a digest
check rather than a typed-in literal — this is exactly the kind of test that
can fail, which CLAUDE.md's own "definition of done" demands.

I traced the three specific risks the phase's own history names (glyph
wedged into an exact-substring guardrail, wrong glyph for a line's meaning,
multi-rune truncation) and found the known instances of each already fixed
correctly (the `Choice: `/`Alternative: ` label ordering, the `goal`→👑 /
`phase`→📍 assignment, and `lifecycleStatusFitLine`/`planningSplitVisibleWord`
token-aware truncation). However, I found two real, demonstrable gaps that
were not caught by the new guards because they sit outside what those guards
measure: an override-precedence bug in a new glyph-stripping helper, and an
inconsistently-applied glyph on the single most important line of a
widely-reused "Next Up" renderer. Neither is a crash or data-loss risk, so
both are filed as warnings rather than blockers, but both are genuine defects
in shipped code, not style preferences.

## Warnings

### WR-01: `planningStripLeadingVoiceGlyph` bypasses the glyph override precedence `voiceLine` itself establishes

**File:** `cmd/planning_visuals.go:1171-1178`
**Issue:**

```go
func planningStripLeadingVoiceGlyph(plain string) string {
	for _, glyph := range voiceGlyphMap {
		if candidate := strings.TrimPrefix(plain, glyph+" "); candidate != plain {
			return candidate
		}
	}
	return plain
}
```

Every line an operator actually sees is produced by `voiceLine(kind, text)`,
which resolves its glyph through `voiceGlyph(kind)` — and `voiceGlyph` checks
an operator override in `loadVisualsConfig().VoiceGlyphMap` *before* falling
back to the hardcoded `voiceGlyphMap` (`cmd/codex_visuals.go:255-265`).
`planningStripLeadingVoiceGlyph` does not go through `voiceGlyph()` at all —
it iterates the raw, hardcoded `voiceGlyphMap` directly. If an operator
supplies a `voice_glyph_map` override (a real, wired-up, documented field —
`cmd/visuals_config.go:26`, `yaml:"voice_glyph_map"`) that changes any of the
glyphs used on the planning cards (e.g. `history`, `status`, `evidence`), the
actual rendered line will carry the *overridden* glyph, but this stripper will
never recognize it, fall through unchanged, and `planningVisualLineMayOverflow`
(the function this helper exists solely to serve, per its own doc comment)
will then fail to exempt indivisible identifier/hash lines from wrapping —
exactly the "correctness regression this change would otherwise introduce"
the surrounding comment says it is preventing. The bug is currently dormant
in default operation because the config file this override reads from
(`colony/ceremony/visuals.md`) was deleted in Phase 191 and no test
constructs a `VoiceGlyphMap` override, but the override mechanism is live,
documented, and reachable the moment any repo or test supplies one — and
nothing in this phase's new test suite exercises that path.

**Fix:**
```go
func planningStripLeadingVoiceGlyph(plain string) string {
	for kind := range voiceGlyphMap {
		if glyph := voiceGlyph(kind); glyph != "" {
			if candidate := strings.TrimPrefix(plain, glyph+" "); candidate != plain {
				return candidate
			}
		}
	}
	return plain
}
```
Add a test that sets `visualsPathOverride` to a fixture file overriding one of
the glyphs used here (e.g. `history`) and asserts an identifier line still
survives `planningVisualLineMayOverflow`'s exemption.

### WR-02: `renderNextUp`'s primary recommendation line is not glyph-led, unlike its own alternatives

**File:** `cmd/codex_visuals.go:661-679`
**Issue:** This phase changed `renderNextUp`'s alternative-line rendering to
go through `voiceLine("alternative", ...)`, but left the primary line
untouched:

```go
func renderNextUp(primary string, alternatives ...string) string {
	...
	if strings.TrimSpace(primary) != "" {
		b.WriteString(translateHintCommandsForPlatform(primary, platform))
		b.WriteString("\n")
	}
	for _, alt := range alternatives {
		...
		b.WriteString(voiceLine("alternative", translateHintCommandsForPlatform(alt, platform)))
		b.WriteString("\n")
	}
	...
}
```
`renderNextUp` is called from many screens across the codebase with a plain,
un-glyphed prose string as `primary` — e.g. `renderUnplannablePhase`
(`cmd/codex_visuals.go:1955`), `renderSignalVisual`
(`cmd/codex_visuals.go:3579`), `renderNextUpVisual`
(`cmd/codex_visuals.go:3586-3595`, the renderer behind the `print-next-up`
command), and the phase-detail "Next Up" block
(`cmd/codex_visuals.go:4383-4391`). On every one of these screens the single
most important line — the actual recommendation — has no leading symbol,
while its lesser alternative immediately below it does. This is precisely the
"wrong/missing glyph for the line's meaning" failure mode this phase's own
history names, just on the primary line rather than a mislabeled one. None of
the eight density-gated screen families require `renderNextUp` specifically
(only `renderNextActionCard`'s own path is registered as `"what-next card"`),
so no existing guard catches this, and `TestPrintNextUpVisualOutput` and
similar tests only assert the recommendation text is present, not that it is
glyph-led.

**Fix:**
```go
if strings.TrimSpace(primary) != "" {
	b.WriteString(voiceLine("next", translateHintCommandsForPlatform(primary, platform)))
	b.WriteString("\n")
}
```
Verify no exact-substring test elsewhere asserts the un-glyphed primary line
verbatim (the same class of check that broke on the `Choice:`/glyph
interaction this phase already had to fix once).

### WR-03: `lifecycleStatusGlyphTokens` handles variation selectors but not the wider zero-width-rune class `planningRuneWidth` already covers

**File:** `cmd/lifecycle_status_render.go:471-489`
**Issue:** `lifecycleStatusGlyphTokens` (backing `lifecycleStatusFitLine`,
the status screen's truncation function) only fuses a base rune with an
immediately-following `U+FE0F` variation selector:

```go
func lifecycleStatusGlyphTokens(line string) []string {
	runes := []rune(line)
	tokens := make([]string, 0, len(runes))
	for i := 0; i < len(runes); i++ {
		if i+1 < len(runes) && runes[i+1] == '️' {
			tokens = append(tokens, string(runes[i])+string(runes[i+1]))
			i++
			continue
		}
		tokens = append(tokens, string(runes[i]))
	}
	return tokens
}
```
The sibling fix in the same phase, `planningRuneWidth`
(`cmd/planning_visuals.go:1125-1133`), treats a wider class of zero-width
runes as never starting their own chunk: `U+FE0F`, `U+FE0E`, `U+200D`
(zero-width joiner) and any Unicode `Mn` (combining mark) rune. Every glyph
in the current `voiceGlyphMap`/`casteEmojiMap` tables happens to be a single
base rune plus at most one `U+FE0F`, so this does not misbehave against
today's data, but it is a narrower, duplicate implementation of the same
concept the phase already had to build correctly once elsewhere, and it will
silently mis-truncate the moment a ZWJ-joined glyph (e.g. a compound emoji)
or a combining-mark glyph is added to either table.

**Fix:** Either share `planningRuneWidth`'s zero-width classification (extract
it to a shared helper both files call) or extend
`lifecycleStatusGlyphTokens`'s zero-width check to match it:
```go
if i+1 < len(runes) && (runes[i+1] == '️' || runes[i+1] == '︎' || runes[i+1] == '‍' || unicode.Is(unicode.Mn, runes[i+1])) {
```

## Info

### IN-01: `answer.Open.Signals` is glyphed uniformly as `feedback` regardless of the underlying signal's type

**File:** `cmd/next_action_card.go:65-71`
**Issue:** `renderNextActionCardForPlatform` wraps every entry of
`answer.Open.Signals` with `voiceLine("feedback", ...)` unconditionally. The
doc comment candidly explains why (the resolver has already flattened the
signal to plain text, discarding its FOCUS/REDIRECT/FEEDBACK type by the time
this renderer sees it), so this is a deliberate, documented trade-off rather
than an oversight — but the practical effect is that a hard-constraint
REDIRECT ("don't do this") reads with the same 💬 speech-bubble glyph as a
gentle FEEDBACK nudge, which is a real semantic softening of exactly the kind
of line CLAUDE.md calls a "hard constraint" elsewhere in this document.
**Fix:** If worth the cost, thread the signal type through
`nextActionInputForState`'s `Signals` field (currently `[]string`) as a typed
pair so this card can call `signalTypeGlyph` per entry instead of a single
fixed kind. Otherwise, no action needed — this is a known and reasoned
limitation, not a bug.

### IN-02: `checkpoint` (💾) is used for "Success Criteria" and "Repairs" headings, both of which read more like `requirement`/`evidence` than a saved state

**File:** `cmd/codex_visuals.go:465-471, 480-486, 191-194 (comment block)`
**Issue:** `voiceGlyphMap`'s own doc comment carefully derives each glyph's
meaning from a Classic ancestor or an explicit semantic analogy, but a few of
the mappings chosen when wiring the plan-visual sections read as assigned by
convenient availability rather than meaning: "Success Criteria" (what proves
a task/phase is done) and "Repairs" (fixes applied to a plan) both use
`checkpoint` (💾, "a saved state"), where `requirement` (📋) or `evidence`
(🔎) would read more precisely. This is exactly the class of mismatch the
phase's own history names as its second named risk (glyph assigned by
section rather than by the line's actual meaning), just milder than the
crown/pin example that motivated the original fix.
**Fix:** Low priority, cosmetic. Consider retagging these two call sites to
`requirement`/`checkpoint` split by whether the line describes a criterion
(requirement) versus an actually-recorded repair (checkpoint is fine there).

### WR-02 was two regressions, not one

Chasing WR-02 surfaced that `nextActionSuggestionLine` gained its glyph in plan 01
while four existing callers already composed their own line around its result:

1. **Double glyph on screen.** `renderNextUp` wrapped already-glyphed alternatives in
   `voiceLine("alternative", …)`, rendering `🔀 ➡️ Run \`aether status\` — …` on every
   screen using the non-projection path of the what-next card. Reproduced before fixing.
2. **Glyph leak into machine-readable JSON.** `nextActionPrimarySuggestion` feeds
   `result["next"]` in `cmd/closeout_cmd.go:57` and `cmd/codex_plan.go:341`, and
   `nextActionAlternativeSuggestions` feeds `cmd/build_flow_cmds.go:265`. Before this
   phase those returned plain text (verified at `2757534e`); after plan 01 they carried
   `➡️`. This project's own rule is that JSON stays raw.

**Repair.** The JSON-facing helpers return unglyphed bodies again; `renderNextUp` is the
single visual funnel and voices the primary as well as the alternatives. This also closes
WR-02 as filed — the primary is now voiced on every one of `renderNextUp`'s ~70 call sites.

Locked by `cmd/classic_voice_nextup_funnel_test.go`:
`TestNextUpLinesCarryExactlyOneGlyph`, `TestMachineReadableNextSuggestionCarriesNoGlyph`,
and `TestNextUpFunnelGuardsCanFail` (plants a double-glyphed line and fails if the guard
does not catch it).
