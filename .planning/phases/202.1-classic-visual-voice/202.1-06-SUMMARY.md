# Phase 202.1 Plan 06: The Planning Screens (Primary + Legacy Branches) Summary

**All ten planning cards in the program -- the seven primary cards in `cmd/planning_visuals.go` plus the three legacy/repair fallback branches in `cmd/codex_visuals.go`'s `renderPlanVisual` -- now render through the shared `voiceLine` funnel, with a corrected width-wrap helper so a multi-rune glyph can never be cut across a wrapped line, and every fixture figure/identifier/evidence sentence proven unchanged.**

## Accomplishments

- **Task 1 (the primary planning cards):** Routed every content line of the seven primary planning card renderers (`renderPlanningIterationVisual`, `renderPlanningDecisionVisual`, `renderPlanningCandidateVisual`, `renderPlanningPresetVisual`, `renderPlanningStageVisual`, `renderPlanningStopVisual`, `renderPlanningAcceptanceVisual`) through `voiceLine`, using the plan's suggested semantic mapping (`goal`, `phase`, `task`, `evidence`, `blocked`, `question`, `history`, `requirement`, `checkpoint`, `decision`, `alternative`, `avoid`, `next`, plus `casteIdentity`'s own glyph for stage-worker identity lines). Gave `renderPlanningSpecSection` and `renderPlanningValueList` an explicit `lineType` parameter, mirroring `renderSpecCommandVisualSection`'s identical fix from plan 03, and updated every call site in the file (including the two orphaned/test-only functions that share the helpers). Fixed `planningVisualLineMayOverflow`'s prefix-match exemption (a new `planningStripLeadingVoiceGlyph` helper strips a leading glyph before matching, since every exempted line — `Candidate hash:`, `SPEC hash:`, `Next: aether ...`, etc. — now carries one), and fixed `planningSplitVisibleWord` so a zero-width rune (variation selector, ZWJ, combining mark) is never split away from the rune before it during character-level wrapping. Created `cmd/classic_voice_plan_test.go` registering all seven cards into the shared voice-screen corpus, with `TestPlanScreenMeetsTheReferenceDensity`, `TestPlanningCardsKeepEveryFigureAndIdentifier`, and `TestPlanningCardsFitTheirBandWithSymbols`.
- **Task 2 (the legacy and repair plan branches):** Routed every content line of `renderPlanVisual`'s fallback branches (repair, existing-plan, plan-only, next-iteration, plus the common confidence/planning-loop/dispatch/artifacts/phases-loop/coordination code shared by all of them) through `voiceLine`, leaving the function's early delegation to the primary planning renderer (`renderCanonicalPlanningResult`) exactly as it was and touching no command-advice literal. Registered `plan-repair`, `plan-existing`, and `plan-iteration-legacy` into the same corpus, extended `TestPlanScreenMeetsTheReferenceDensity` to all ten registrations, and added `TestPlanVisualStillDelegatesToThePrimaryCard`, which asserts `renderPlanVisual`'s output for an accepted-primary-path input is byte-identical to what the primary renderer itself returns.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Overflow exemption silently broken by every glyph this plan adds**
- **Found during:** Task 1, before writing any test (identified by inspection while planning the candidate-card edit)
- **Issue:** `planningVisualLineMayOverflow`'s indivisible-identifier prefix check (`"Candidate hash: "`, `"SPEC hash: "`, `"Next: aether "`, etc.) matches only at the start of the line. Once every one of those lines gets a leading glyph via `voiceLine`, the prefix no longer starts the line, so the exemption would silently stop firing and those hash/command lines would start wrapping mid-value at narrow widths.
- **Fix:** Added `planningStripLeadingVoiceGlyph`, which strips a leading glyph (read from the production `voiceGlyphMap`, not re-typed) before the prefix check runs.
- **Files modified:** `cmd/planning_visuals.go`
- **Verification:** `TestPlanningVisualsWidthSafeIdentifierException` and `TestPlanningVisualsWidthBandsBoundMajorCards` (pre-existing) still pass; `TestPlanningCardsFitTheirBandWithSymbols` (new) passes at the narrowest supported width.
- **Committed in:** `8bd0b463` (Task 1 commit)

**2. [Rule 1 - Bug] A zero-width rune could be split away from its base glyph during character-level line wrapping**
- **Found during:** Task 1, per the plan's own explicit instruction to fix this class of bug
- **Issue:** `planningSplitVisibleWord` split a "word" (an unbreakable run of characters with no space) purely by accumulated display width, with no awareness that a variation selector, ZWJ, or combining mark must stay attached to the rune before it. At an extreme narrow width this could, in principle, put a bare modifier rune as the first character of a wrapped continuation line -- a symbol cut in two.
- **Fix:** A zero-width rune is now always appended to whatever chunk holds the preceding rune, never starting a new chunk on its own.
- **Files modified:** `cmd/planning_visuals.go`
- **Verification:** `TestPlanningCardsFitTheirBandWithSymbols` renders all seven cards at width 24 and asserts no line begins with a bare variation-selector/ZWJ/combining-mark rune; passes.
- **Committed in:** `8bd0b463` (Task 1 commit)

**3. [Rule 1 - Bug] Standalone caste-identity lines never counted as glyph-led**
- **Found during:** Task 1, while measuring density on the first voiced card
- **Issue:** The existing `"Identity: " + casteIdentity(caste)` pattern puts the plain word "Identity:" as the first thing on the line; `casteIdentity`'s own leading glyph sits after it, so the density scanner (which requires the glyph to be the very first thing on the line) never counted these lines as led, even after full voicing.
- **Fix:** Dropped the `"Identity: "` label everywhere it preceded a bare `casteIdentity(...)` call (7 sites across the file), letting `casteIdentity`'s own glyph lead the line directly. No test asserted the literal label.
- **Files modified:** `cmd/planning_visuals.go`
- **Verification:** `TestPlanScreenMeetsTheReferenceDensity` passes for all seven cards; no dependent test asserted the removed label.
- **Committed in:** `8bd0b463` (Task 1 commit)

**4. [Rule 1 - Bug] A gloss placed after a long value can wrap onto a different line than the word it explains**
- **Found during:** Task 1, while writing `TestVoicedScreensSpeakPlainEnglish`'s `plan-decision` subtest
- **Issue:** The "Queen recommends: {value}" line, with the plain-English gloss appended after the value (mirroring discuss.go plan 03's exact fix), wrapped at the registered width (96) into two physical lines, separating "Queen" from its cue -- a violation the scanner correctly caught since it treats each wrapped line as its own sentence.
- **Fix:** Moved the gloss to immediately follow the label, before the value: `"Queen recommends (this project's coordinator): {value}"`, guaranteeing the cue survives on the same wrapped line as "Queen" regardless of how long the value is.
- **Files modified:** `cmd/planning_visuals.go`
- **Verification:** `TestVoicedScreensSpeakPlainEnglish/plan-decision` passes; `TestPlanningVisualsDecisionSemanticAuthority` (pre-existing, asserts the substring "Queen recommends" in order) still passes.
- **Committed in:** `8bd0b463` (Task 1 commit)

**5. [Rule 1 - Bug] Two pre-existing "colony" mentions in renderPlanVisual had no plain-English cue, exposed for the first time by joining the corpus**
- **Found during:** Task 2, while registering `plan-existing` and `plan-iteration-legacy`
- **Issue:** "Existing colony plan loaded." and "...before the colony plan is written." carry "colony" with no nearby explanation, and were never exercised by the plain-English scan before this plan's registrations reached them.
- **Fix:** Preserved "Existing colony plan loaded" verbatim (a positive test pins this exact substring) and appended " — this project already has one." in the same sentence; reworded the second sentence to drop "colony" ("...before the plan is written.") since no test pinned it.
- **Files modified:** `cmd/codex_visuals.go`
- **Verification:** `TestVoicedScreensSpeakPlainEnglish/plan-existing` and `/plan-iteration-legacy` pass; `TestRenderPlanVisual_ExistingPlan`, `TestRenderPlanVisualExistingPlanNoFinalizerDoesNotPromptPlanningWorkers`, and `TestRenderPlanVisualPlanOnlyPlannedDispatchesAreNotExecutionResults` (all pre-existing, asserting "Existing colony plan loaded" or the absence of the old default-branch sentence) still pass.
- **Committed in:** `1aa55d4c` (Task 2 commit)

**6. [Rule 1 - Bug] The "Workers" section header broke an exact pre-existing test literal once glyph-led**
- **Found during:** Task 2, running `TestRenderPlanVisual_RealDispatch` after voicing the confidence/dispatch section
- **Issue:** `TestRenderPlanVisual_RealDispatch` asserted the exact substring `"\nWorkers\n"`; once `voiceLine` prefixed a glyph, that exact byte sequence no longer appeared.
- **Fix:** Widened the dependent test's assertion to `"\n🐜 Workers\n"`, matching plan 04's precedent for widening a dependent literal in the same commit as the wording/glyph change that necessitated it.
- **Files modified:** `cmd/codex_visuals_test.go`
- **Verification:** `TestRenderPlanVisual_RealDispatch` passes with the widened literal.
- **Committed in:** `1aa55d4c` (Task 2 commit)
