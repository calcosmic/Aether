# Phase 202.1 Plan 01: Classic Visual Voice — Tracer Slice Summary

**One semantic glyph vocabulary, a density figure computed (never typed) from six extracted Classic display blocks, the what-next card wired through both, a screen corpus for later plans to join, and four hand-rolled signal-glyph literals absorbed behind an AST guard that refuses a fifth.**

## Accomplishments

- **Task 1 (tracer):** Added `voiceGlyphMap`/`voiceGlyph`/`voiceLine` beside the existing caste tables in `cmd/codex_visuals.go`, with an operator-override funnel following `commandEmoji`'s exact shape. Extracted six Classic display blocks verbatim from commits `3a5b81c2` and `794fadfb` into `cmd/testdata/classic-voice/`, each recorded in `manifest.json` with its commit, path, extraction markers, and a sha256 that a drift guard re-checks against the live git object on every run. Built `voiceDensity`/`voiceContentLines`/`classicReferenceDensity`, which reduce those six blocks to one house figure — computed, never typed. Wired the what-next card (`cmd/next_action_card.go`) through `voiceLine` section-by-section, and gave the shared next-step funnel (`nextActionSuggestionLine`/`renderNextUp`) its own glyphs, so the card now measures at or above the derived figure on both the Claude and Codex platform spellings while still passing every pre-existing guardrail test named in the plan.
- **Task 2:** Built the screen corpus (`voiceScreenRegistry`/`registerVoiceScreen`/`renderedVoiceScreens`) later plans register their own screens into, one `init` per screen in that screen's own test file. Widened the existing plain-English check (`untranslatedRepoWords`) onto the whole corpus rather than just the what-next card, reusing the production function and its `repoInventedWords` table without copying either.
- **Task 3:** Found and absorbed **four** hand-rolled `{"FOCUS":…,"REDIRECT":…,"FEEDBACK":…}`-shaped literals (three named in the plan, plus a fourth in `cmd/status.go`'s `renderPheromoneSummary` the plan's own research had not caught) into one `signalTypeGlyph` function. Added an AST-based structural guard (`TestVoiceGlyphsHaveOneTable`) that walks every non-test `.go` file in `cmd/` and refuses any third caste/signal-shaped glyph table, tuned by both match count and match ratio so it does not false-positive on a legitimately unrelated table that merely shares a few vocabulary-coincidence key names.

## Decisions Made

- Owner ratified `one-standard` at the plan's pre-resolved checkpoint (2026-09-12): every screen is held to one house-wide density figure derived from the February reference as a whole, including screens February never had. This executor did not re-ask; it implemented the `one-standard` branch as instructed.
- Standing-instructions lines use a single `feedback` glyph rather than deriving each signal's real type, since the resolver had already flattened signals to plain strings before this pure-rendering layer sees them — deriving type here would be a second read, which the plan's own CEC-05 guardrail forbids.
- The glyph-table AST guard requires both an absolute caste/signal key-match count (≥2) and a match-ratio threshold (≥50% of the literal's own keys) — an absolute count alone flagged `commandEmojiMap` (which incidentally shares "oracle"/"chaos"/"porter"/"medic" with caste names) as a false positive.
