# Phase 202.1: Classic Visual Voice - Research

**Researched:** 2026-09-12
**Domain:** Terminal UX rendering (Go source, in-repo — no external library domain)
**Confidence:** HIGH

## Summary

This phase's research obligation IS success criterion 1, so this document is written as the cited mechanism study the criterion demands, not a preamble to one.

The finding, in one sentence: **the machinery this phase needs already exists and is already tested, it is simply not called from most of the screens the owner reads.** `casteIdentity()`, `casteEmojiMap`, `casteColorMap`, `casteLabelMap`, `renderBanner`, `renderStageMarker` (all in `cmd/codex_visuals.go`, locked by `TestCasteIdentityUsesHouseStyle` in `cmd/caste_house_style_test.go:13`) are already wired into the live colony cockpit (`cmd/watch_live.go:305`, `cmd/watch_dashboard.go:197`) and into a handful of worker-list lines inside `continue` (`renderContinueWorkerFlowLine`, `cmd/codex_visuals.go:2632`) and `status`'s advanced spawn-tree view (`renderSpawnEntry`, `cmd/status.go:1595-1605`). But the *primary* screens an owner actually lands on by default — the full/compact status card (`renderLifecycleStatusFull`, `cmd/lifecycle_status_render.go:42`), the plan card (`renderPlanVisual`, `cmd/codex_visuals.go:1417`), the discuss card (`renderDiscussVisual`, `cmd/discuss.go:1511`), the spec card (`renderSpecCommandVisual`, `cmd/spec_cmd.go:691`), the build/continue/seal section prose, and the what-next card (`renderNextActionCardForPlatform`, `cmd/next_action_card.go:45`) — render section headers and content lines as plain `Label: value` text with zero caste/status glyphs. Compare `renderLifecycleStatusActorLine` (`cmd/lifecycle_status_render.go:283-298`), which formats an active worker as `Active: Mason-42 (builder) — running: ...`, against `renderSpawnEntry` twelve lines away in spirit (`cmd/status.go:1595`), which formats the same fact as `✓ 🔨🐜 Builder Mason-42 — running: ... [active]` using the identical `casteIdentity()` call the first function simply never makes. This is this project's own named signature failure — "machinery exists but was never switched on" — reproduced inside the very phase meant to fix voice regression, which is strong independent confirmation that the Classic-to-Go synthesis protocol's Step 2 (audit the current mechanism) is doing real work here.

The Classic reference at `3a5b81c2` (v3.1 "Open Chambers", 2026-02-15) and its immediate predecessor `794fadfb` (2026-02-08) show a consistent, learnable house style across every command template: a double-rule letter-spaced banner, then **every content line opens with a glyph that names either the acting caste or the status/category of the line** (👑 goal, 📍 phase, 🎯/🚫 focus-and-avoid, 🧠 instincts, 🚩 flags, 🏆 milestone, 💭 dreams, 🔨/👁️/🎲 caste-tagged worker lines, ✅/❌ task outcomes), and a closing "Next Steps" menu that names each command's real-world effect beside it (`/ant:build 1        🔨 Start building Phase 1`). Measuring the quoted Classic `status` template (section 2 below) gives roughly 7 of 10 content lines glyph-led (~70%); the quoted Classic `build` compact/full templates give ~85-95%. The current equivalents measure at or near 0%. That gap — not a subjective "it looks flatter" — is the reference density criterion 5 asks this phase to fix and lock.

One confirmed defect closes a second, independent criterion: `nextActionEventSentence` (`cmd/next_action.go:986-994`) takes the *last* `|`-delimited field of a saved lifecycle event string as "the message," but the pause/resume event writer (`pauseResumeLifecycleEvent`, `cmd/session_flow_cmds.go:1462-1464`) puts the raw handoff ID and an internal boundary-state token into that exact field, quoted verbatim in this research context: `handoff=handoff-060d355f95c7b74a744bd164 between_commands_boundary`. This is not a display bug in the renderer — the renderer is doing exactly what the code says; the defect is upstream, in what the event writer put in the field the renderer trusts to already be a sentence.

**Primary recommendation:** Do not build a new "voice layer." Extend the existing, tested `casteIdentity`/`casteEmojiMap`/`renderStageMarker` machinery to the section-prose functions that currently bypass it (`renderLifecycleStatusFull`, `renderPlanVisual`, `renderDiscussVisual`, `renderSpecCommandVisual`, the section bodies of `renderBuildVisualWithDispatches`/`renderContinueVisual`/`renderSealVisual`, and `renderNextActionCardForPlatform`), fix `nextActionEventSentence` at its true source (the event writer, not the reader), and lock the target density with a test derived from the Classic templates quoted below — never a typed-in number.

**Verbatim confirmation of the leak's exact shape**, read directly from source this session:

- `pauseResumeLifecycleEvent` signature and body [VERIFIED: cmd/session_flow_cmds.go:1462-1464]: `func pauseResumeLifecycleEvent(now time.Time, command, handoffID, detail string) string { return fmt.Sprintf("%s|lifecycle_%s|%s|handoff=%s %s", now.UTC().Format(time.RFC3339), command, command, handoffID, detail) }`
- Two call sites feed raw enum tokens as `detail`:
  - Pause [VERIFIED: cmd/session_flow_cmds.go:379]: `state.Events = append(state.Events, pauseResumeLifecycleEvent(now, "pause", handoffID, safeBoundary))` — `safeBoundary` comes from `pauseSafeBoundary` [VERIFIED: cmd/session_flow_cmds.go:1017-1041], whose exact return values are: `"worker_completion_boundary"`, `"interrupted_attempt_boundary"`, `"interrupted_execution_boundary"`, `"post_build_verification_boundary"`, `"completed_episode_boundary"`, `"idle_command_boundary"`, `"between_commands_boundary"` — the last one is the exact literal quoted in the confirmed defect.
  - Resume [VERIFIED: cmd/session_flow_cmds.go:636]: `state.Events = append(state.Events, pauseResumeLifecycleEvent(now, "resume", handoff.HandoffID, string(provenance)))` — `provenance` is a `colony.RecoveryProvenance`, whose exact declared values are [VERIFIED: pkg/colony/lifecycle.go:106-110]: `RecoveryProvenanceConfirmed = "confirmed"`, `RecoveryProvenanceReconstructed = "reconstructed"`, `RecoveryProvenanceConflicting = "conflicting"`, `RecoveryProvenanceUnknown = "unknown"`. A resume event will therefore leak `handoff=<id> confirmed` / `reconstructed` / `conflicting` / `unknown` onto the what-next card exactly as the pause path leaks the boundary token — this is a sibling of the same class the research brief asked to be enumerated, not a separate bug.
- Reader [VERIFIED: cmd/next_action.go:964-978, 986-994]: `changedFromInput` calls `lastEventTexts(state.Events, 3)` then `nextActionEventSentence(event)` on each; `nextActionEventSentence` does `parts := strings.Split(event, "|"); return strings.TrimSpace(parts[len(parts)-1])` — for a pause/resume event this is exactly the `"handoff=<id> <token>"` field, verbatim, with no sentence-forming step at all.

**No other event writer in the codebase uses this `handoff=%s %s` shape** — `grep -rn "handoff=" cmd/*.go` (non-test) returns only `cmd/session_flow_cmds.go:1463`, so this is the sole producer of this exact leak shape. It is not, however, the only place a raw boundary token could reach an owner-facing line: any future caller of `pauseSafeBoundary` or any renderer that reads `state.Events` raw (rather than through `nextActionEventSentence`) inherits the same risk, which is why the fix belongs in the writer (stop putting non-sentence tokens in the message field) rather than patched only in the one reader that happened to be caught.

## Selected Architecture

- **Authoritative components:** the existing `cmd/codex_visuals.go` glyph tables (`casteEmojiMap`, `casteColorMap`, `casteLabelMap`) and helpers (`casteIdentity`, `casteEmoji`, `renderBanner`, `renderStageMarker`, `visualDividerStr`) remain the single source of glyph/color truth. No new table is introduced for caste identity.
- **New, small addition needed:** a **status/category glyph map** for the non-caste glyphs Classic used (👑 goal, 📍 phase, 🎯 focus, 🚫 avoid/redirect, 🧠 instincts/learning, 🚩 flags, 🏆 milestone, 💭 dreams, 📊 status/count, 📁 files, 💾 checkpoint/persistence, ✅/❌ task outcome, ➡️/🐜 next-step). This is presentation-only data (a `map[string]string` keyed by semantic line type), lives beside the existing caste maps in `cmd/codex_visuals.go`, and is the one piece of "new machinery" this phase legitimately needs — everything else is wiring existing machinery into renderers that currently skip it.
- **Event/state flow:** unchanged. No lifecycle fact, projection, or state transition changes. This phase touches only the string-formatting layer downstream of already-resolved `LifecycleProjection` / `nextAction` / `colony.ColonyState` values, plus the one upstream writer fix (`pauseResumeLifecycleEvent` / its callers) needed to close the identifier leak at its source.
- **Queen/worker/verifier/runtime/owner responsibilities:** unchanged from the wrapper-runtime UX contract — all rendering stays in Go (`cmd/`); wrapper markdown (`.claude/commands/ant/*.md`, `.opencode/commands/ant/*.md`) is never re-given presentation logic, per `.aether/docs/wrapper-runtime-ux-contract.md`'s explicit "Wrappers must never replicate them" for banner/glyph/status formatting.

## Reference Density Metric Proposal (criterion 1 and 5)

**Definition:** For a given rendered screen, **glyph density = (number of non-blank content lines whose first non-whitespace rune, after ANSI stripping, is a glyph drawn from the caste/status glyph set) ÷ (total non-blank content lines)**, where "content lines" excludes: the banner line (`renderBanner` output), divider/rule lines (`visualDividerStr` output, `━`/`═` repeats), and stage-marker lines (`renderStageMarker` output, `── Title ──`). The glyph set is the union of `casteEmojiMap`'s values (`cmd/codex_visuals.go:42-88`) plus the new status/category glyph map proposed above.

**Why this cannot be gamed by a rename:** the metric counts a structural property of the *rendered byte output* (does line N start with a glyph from a closed, tested set), not a section name, a function name, or a heading string. Renaming `renderLifecycleStatusFull` to anything else, or renaming its section headers, does not change whether its content lines start with a glyph. This satisfies criterion 5's "whatever a future renderer is called."

**How the threshold must be derived (not typed in):** the plan should write a small fixture that parses the *quoted Classic templates in section 2 above* (or, better, re-derives them by `git show 3a5b81c2:.claude/commands/ant/<file>.md` at test time and extracts the display block) and computes the historical density per screen type, then asserts the current renderer's density is `>=` that computed historical value (or a plan-chosen fraction of it, e.g. 0.9x, if an exact match is judged too brittle for lines that have no Classic analog such as `spec`). This keeps the number honestly sourced from the reference commit rather than a plausible-looking literal — consistent with this project's own `Definition of Done` rule that "a test must be able to fail" and fixture values must be derived the way the runtime derives them.

**Worked examples from evidence gathered this session** (computed by hand from the verbatim quotes in section 2, for the planner's calibration — the plan's own test must compute these programmatically, not hardcode them):

| Screen | Classic content lines | Glyph-led lines | Approx. density |
|---|---|---|---|
| Status (`status.md` display block) | 10 | 7 (`👑`,`📍`,`🎯/🚫`,`🧠`,`🚩`,`🏆`,`💭`) | ~70% |
| Build compact (`build.md` ~793-812) | 8 | 7 | ~85% |
| Build full (`build.md` ~845-905) | ~20+ | ~19 | ~90%+ |
| Council/discuss analog (`council.md` header) | 4 | 2 (banner-adjacent `👑` line, others are indented sub-fields) | ~50% (smallest historical sample; treat as a floor, not a target, for `discuss`) |

**Screens with no Classic ancestor** (`spec`, and any section of `discuss` beyond the council analog): the plan should apply the *median* density across the screens that do have a direct ancestor (roughly 80-85% per the table above) as the target, since criterion 2 requires these screens to render "in the Classic voice" even though no literal predecessor exists to diff against — the voice is a house style, not a per-screen copy.

- **Conclusion for the plan:** no new platform branch is needed anywhere in this phase. Every glyph and color decision should route through the existing `casteIdentity`/`casteEmoji`/`colorizeCaste`/`shouldUseANSIColors` functions, which already have the platform/terminal-safety logic solved.

## Common Pitfalls

### Pitfall 1: Building parallel glyph machinery instead of wiring the existing one
**What goes wrong:** A new renderer helper reinvents `casteIdentity()`-equivalent logic locally (e.g., a local `switch caste { case "builder": return "🔨" ...}` inline in `renderLifecycleStatusFull`).
**Why it happens:** The touched functions (`renderLifecycleStatusFull`, `renderPlanVisual`, etc.) are in different files (`lifecycle_status_render.go` vs `codex_visuals.go`) and a quick fix might not notice the shared helper already exists two files over.
**How to avoid:** Every new glyph line must call into `cmd/codex_visuals.go`'s existing exported-within-package functions (`casteIdentity`, `casteEmoji`, and the new status/category glyph map proposed above), never a local literal switch.
**Warning signs:** A `grep -c "🔨\|👁️\|🎲"` literal (rather than a call to `casteEmoji`/`casteIdentity`) appearing in a newly-edited file.

### Pitfall 2: The voice work quietly reintroduces jargon the plain-English test would catch — if it scanned these screens
**What goes wrong:** Classic vocabulary ("pheromone", "hive", "midden", "caste" as a bare category word) lands on build/status/continue/seal content lines without the CLAUDE.md-mandated inline explanation, because `TestNextActionCardSpeaksPlainEnglish` currently only scans the what-next card, not these screens.
**Why it happens:** The existing guard's scope (`renderedNextActionCards`) predates this phase and was never extended to the screens this phase is about to make more "Classic."
**How to avoid:** The plan must explicitly decide and test one of: (a) extend the plain-English scan to the newly-voiced screens, or (b) restrict new vocabulary on those screens to words that function as identity labels (Builder, Watcher, Queen as names/labels attached via `casteIdentity`) rather than bare category jargon.
**Warning signs:** A rendered build/status card containing the word "pheromone" or "caste" with no explanatory cue in the same sentence, and no test that would have caught it.

### Pitfall 3: Fixing the identifier leak by patching the reader instead of the writer
**What goes wrong:** `nextActionEventSentence` gets a special case that strips a `handoff=` prefix, closing only the one instance already found.
**Why it happens:** The reader is the file the bug report pointed at, and is the smaller, more localized diff.
**How to avoid:** Fix `pauseResumeLifecycleEvent`'s callers (or the function itself) to write a real sentence into the message field, matching the reader's own documented contract. See `SYN-VOICE-03` above.
**Warning signs:** A test that asserts `!strings.Contains(rendered, "handoff=")` passes, but a test that plants a *new* raw-enum-into-event-message call site elsewhere in the codebase would still leak — i.e., the fix only covers the symptom's current location, not the class.

### Pitfall 4: New machinery built but never called (this project's own named signature failure)
**What goes wrong:** A new status/category glyph map and a new density test are built and merged, but the actual call sites in `renderLifecycleStatusFull`/`renderPlanVisual`/etc. are left unchanged, or only some are updated.
**Why it happens:** This is explicitly documented elsewhere in this repo's own memory as the recurring failure mode: "Aether's capability is rarely deleted, just never called; verify by execution, not grep."
**How to avoid:** The plan's own density test (per screen) is the mechanism that prevents this — if a renderer is left unwired, its density stays at/near 0% and the test fails. This pitfall is the direct justification for criterion 5 existing at all; treat the density test as non-optional and written *before* the wiring work, not after.
**Warning signs:** A plan wave that adds the glyph map/helper functions but has no corresponding wave that edits every renderer named in the "Current Go Mechanism Audit" table above, or a density test that only covers one or two screens instead of all eight named in criterion 2.

### Pitfall 5: Treating "spec" and "discuss" as needing a literal Classic screenshot match
**What goes wrong:** Planning stalls looking for a `spec.md`/`discuss.md` command at `3a5b81c2` that does not exist, or forces an artificial one-to-one mapping.
**Why it happens:** The phase description says "compare... against every current ordinary lifecycle screen," which could be misread as requiring a 1:1 historical screen for every current one.
**How to avoid:** Use `council.md` as discuss's nearest analog (both are intent-clarification loops) and treat `spec` as a new artifact type that should adopt the *house style* (banner + glyph density in the calibrated range) rather than a specific historical template, per the Comparative Synthesis Matrix and Reference Density sections above.
**Warning signs:** A plan task phrased as "port `council.md`'s exact wording to `discuss`" rather than "apply the established glyph/density house style to `discuss`'s existing, richer content."
