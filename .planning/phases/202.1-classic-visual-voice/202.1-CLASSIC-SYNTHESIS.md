# Phase 202.1 Classic-to-Go Synthesis

This is the mandatory Classic-to-Go mechanism study for Phase 202.1 (CEC-09),
written against `.planning/phases/202.1-classic-visual-voice/202.1-RESEARCH.md`
— this phase's own cited mechanism study, produced before any renderer was
edited, as success criterion 1 requires. That document already performs
sections 2 through 5 of the mandatory synthesis in full (Classic mechanism
reconstruction, current Go mechanism audit, comparative synthesis matrix, and
selected architecture); this artifact cites it by section rather than
duplicating it, per the milestone's own instruction that a second copy of the
same study is a drift risk, not added rigor. Sections 6 through 8 below are
new: the research-to-plan linkage, the four-dimension verification contract,
and the open decisions and rulings this phase actually made, including the
one thing it deliberately did not do.

`cap_rows` is empty above because Phase 202.1 was not part of the original
72-row Classic capability ledger `.planning/research/v1.28-classic-capability-ledger.md`
scoped at milestone start — it was inserted afterward, on 2026-09-12, in
direct response to an owner observation ("it just didn't look good") that no
CEC-01..08 requirement owned. This is recorded plainly, not left implicit: a
phase can exist, and can still require a full synthesis under the milestone's
own protocol, without a corresponding ledger row.

## 1. Outcome under investigation

- **Owner-visible outcome:** the rendered voice of the eight ordinary
  lifecycle screens (plan, discuss, spec, status, build, continue, seal, and
  the what-next card) — whether the colony still reads as itself, or as
  correct but flattened plain text.
- **Operational outcome:** every one of those screens' content lines carries
  a caste/status glyph and colony vocabulary at a density measured against
  the actual February 2026 reference commits, next-step menus name each
  option's effect beside its command, no owner-facing line exposes a raw
  internal identifier or state token, and a named, non-gameable test locks
  all of the above so it cannot silently regress again.
- **Why this phase owns it:** the roadmap routes `CEC-09` here exclusively
  (`.planning/ROADMAP.md` §Phase 202.1); no other phase in the milestone
  claims the rendered voice.
- **Non-goals:** this phase changes only how a screen speaks, never what it
  claims — CEC-01..08's content guarantees (identity, plain-English,
  honest-next-action, purity) are explicitly preserved, not revisited. It
  does not widen the executable Classic contract corpus
  (`cmd/testdata/classic-contract/v1/`); see the corpus discharge in §8.

For dummies: the information on every screen you actually read day to day
was already correct — this phase is only about whether it *looks and reads*
like this project again, with a check that fails if that look ever quietly
fades away a second time.

## 2. Classic mechanism reconstruction

See `202.1-RESEARCH.md`, section "Classic Mechanism Reconstruction (Section 2
of the mandatory synthesis)". That section inspects the Classic reference
directly via `git show 3a5b81c2:...` and `git show 794fadfb:...` across
`status.md`, `build.md`, `council.md`, and `entomb.md`, quoting the Classic
display templates verbatim (`OLD-STATUS`, `OLD-BUILD-COMPACT`,
`OLD-BUILD-FULL`, `OLD-COUNCIL`, `OLD-ENTOMB`, `OLD-COMMIT`) and concluding
that Classic's voice was pure text rendering over already-computed state —
safe to restore verbatim as a presentation layer because it never encoded
authority or state.

## 5. Selected architecture

See `202.1-RESEARCH.md`, section "Selected Architecture". As delivered: the
existing `cmd/codex_visuals.go` glyph tables (`casteEmojiMap`,
`casteColorMap`, `casteLabelMap`) remain the single source of caste truth;
the one new addition — `voiceGlyphMap`, read through the `voiceGlyph`/
`voiceLine` funnel — carries the non-caste status/category glyphs (👑 goal,
📍 phase, 🎯 focus, 🚫 avoid, and so on), exactly as scoped. No lifecycle
fact, projection, or state transition changed; every fix in this phase is a
string-formatting change downstream of an already-resolved value, plus the
one upstream writer fix (`pauseResumeLifecycleEvent`) needed to close the
identifier-leak class at its source. `signalTypeGlyph` absorbed four
independently hand-rolled `{"FOCUS":...}`-shaped literals discovered during
plan 01, closing exactly the kind of drift the selected architecture exists
to prevent.

## 8. Open decisions and confidence

| Open item | Ruling | Recorded at | Blocking? |
|---|---|---|---|
| **Reference-standard choice** (`202.1-RESEARCH.md` Open Question, escalated as plan 01's checkpoint) | The owner ratified `one-standard` on 2026-09-12: every screen — including `spec` and `discuss`, which have no direct February ancestor — is held to one house-wide density figure derived from the February reference as a whole, rather than a per-screen or tiered target. | Plan 01's SUMMARY, "Decisions Made" | No — resolved before implementation began. |
| **Glyph vocabulary as ratified** (`202.1-RESEARCH.md` Open Question 2) | Glyphs for concepts with no Classic precedent (e.g. `spec`'s revision/delta fields) are picked by semantic analogy to the nearest Classic category and recorded once in `voiceGlyphMap`, never per call site. | Plans 01, 03, 06 | No — applied consistently throughout. |
| **Assumption A1** (median density as the target for ancestor-less screens) | Superseded by the `one-standard` ruling above: rather than a median-of-ancestored-screens estimate, every screen — ancestored or not — is held to the single house figure. A1 as originally framed did not need to be separately decided once `one-standard` was ratified. | Plan 01 | No. |
| **Assumption A2** (caste labels attached to a name via `casteIdentity()` do not need their own inline explanation the way bare category words do) | Confirmed by implementation: every plan that hit the widened plain-English scan (02, 03, 04, 06) found and fixed *bare category word* violations (`caste`, `worker`, `colony`, `queen` as a category), never treated a name like "Builder" or "Mason-1" as requiring its own gloss. This is the same distinction CLAUDE.md's own vocabulary table draws between a word and a name. | Plans 02, 03, 04, 06 (deviation logs) | No. |
| **Corpus discharge** — this phase does not widen the executable Classic contract corpus (`cmd/testdata/classic-contract/v1/schema.json`'s `synthesis_decision` pattern, currently `^SYN-(?:199-(?:0[1-9]|10)\|200-(?:0[1-9]\|1[0-2])\|201-(?:0[1-9]\|1[0-4])\|202-(?:0[1-9]\|1[0-2]))$`) | Decided, not omitted: the corpus keys its synthesis identifiers on whole phase numbers only — it has no slot for a decimal sub-phase like `202.1`, and the already-approved first plan of Phase 203 (`203-01-PLAN.md`) widens this exact pattern next, to add `203-(?:0[1-9]|1[0-2])`, by quoting its current value verbatim. A competing widening here, for a phase the corpus schema was never shaped to admit, would invalidate an already-approved downstream plan for no added proof — especially since this phase's own assertions are rendered-output proportion checks, and the corpus's own rule is that a proportion check must not stand alone as a text assertion in that registry. Phase 203's plan 203-01 is the named owner of the next widening. | This document, §1 and here | No — a deliberate scope boundary, not a gap. |
