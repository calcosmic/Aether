<objective>
Prove the whole voice-restoration mechanism end-to-end on one screen — the what-next card — with the measurement that will police every other screen already in place and already derived from the February reference.

Purpose: this phase's named failure mode is its own project's signature one — machinery that exists, is correct, and is never called. RESEARCH.md found `casteIdentity`, `casteEmojiMap` and `renderStageMarker` already tested and already feeding the live cockpit, and simply not called from the screens the owner lands on. The risk is therefore not "can we add glyphs" but "will the additions be measured, and can the measurement fail". So the thin slice is: one new semantic glyph table, one screen wired through it, and one density figure derived from commit `3a5b81c2` rather than typed — all green before a second screen is touched.
Output: `voiceGlyphMap`/`voiceGlyph`/`voiceLine` beside the existing caste tables; a reference fixture extracted verbatim from the reference commits with a drift guard; a `voiceDensity` measurement that reads the production glyph tables; a what-next card that meets the derived figure; and a screen registry later plans register into.

Tracer note: Task 1 is this phase's tracer. It touches every layer the phase will modify — new glyph data, an existing renderer, the reference extraction, the measurement, and the gate — on exactly one screen and one path. Tasks 2 and 3 expand the harness sideways; plans 02 to 06 expand the wiring sideways. No plan may edit a second screen before Task 1 is green.

Flagged planner assumption (RESEARCH.md Assumption A1, unresolved): screens with no February ancestor (`spec`, and the parts of `discuss` beyond the council analog) are held to the same single house-wide figure as every other screen rather than to a per-screen historical match. The checkpoint below puts that choice to the owner rather than assuming it; if the owner picks per-screen matching instead, Task 1's derivation changes shape and plans 02 to 06 inherit the change.

  <name>Checkpoint: ratify the voice standard and the symbol vocabulary</name>
  <decision>What standard the restored look is held to, and which symbols carry it</decision>
  <context>
The screens went plain between February and now. Putting the look back is easy; the reason it drained away unnoticed is that nothing measured it. So this phase adds an automatic check that fails if the screens ever go plain again — and that check needs a standard to measure against. Whatever is chosen here gets written into a test, and changing it later means changing every screen at once, so it is worth thirty seconds now.

The February screens have been measured. Roughly seven out of every ten information lines started with a little symbol that told you what kind of fact it was — a crown for the goal, a pin for where you are, a target for what to focus on, a tick or a cross for finished or failed work. Some February screens were much better than that (the finished-a-phase screen was about nine in ten); one was much worse (the archive screen had none at all).

The symbol vocabulary proposed, in plain words: crown = the project's goal, pin = which stage you are on, target = something to concentrate on, no-entry = something to avoid, brain = a lesson learned, flag = something needing attention, trophy = a milestone reached, tick = finished, cross = failed, folder = files, floppy disk = saved, arrow = what to run next, ant = the project itself and its helpers. Each type of helper keeps the symbol it already has today (hammer for the one writing code, eye for the one checking it, and so on) — those are already in use and are not being changed.

Nothing about what the screens SAY changes either way. Only how they look.
  </context>
