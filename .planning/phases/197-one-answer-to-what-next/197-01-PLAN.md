<objective>
Build the one piece of logic that answers "what next", and make it structurally
incapable of naming a command that does not exist.

Purpose: today five different functions each decide the next step independently
— `workflowSuggestionsForState`, `nextCommandFromState`, `nextCommandForHookState`,
`nextUpSuggestionsForState` and `closeoutNextCommand` — and roughly two hundred
call sites hand-type advice around them. They have already drifted: the pause
card offers the same command twice, once described as a dashboard. This plan
creates the single answer the rest of the phase renders from. Nothing renders
from it yet; that is deliberate, because a card built over a resolver that can
still emit a dead command is a confidently wrong instruction.
Output: the eight-field answer, the pure resolver, the thin loader, and the
availability gate that criterion 6 names.
</objective>

<interfaces>
The resolver lives in package `cmd` and NOT in `pkg/`. That is forced by
criterion 6: availability must be resolved against the live Cobra tree, and
`rootCmd` lives here. A resolver in `pkg/` could only check a copied list, which
is the defect this phase exists to close, not the fix.

Split pure from impure. `resolveNextAction(in nextActionInput) nextAction` reads
nothing from disk and calls no global. `loadNextActionInput()` does the reading
and is the only impure half. Every behaviour test in this plan drives the pure
half directly.

The eight fields the answer carries, one per bullet in NEXT-01:
standing (state plus current phase and its name), what changed since the last
command, open flags and active signals, the recommendation in plain English,
the exact command, two to four alternatives, context health, and recovery or
checkpoint state. Give each a json tag — the whole struct is what later plans
marshal into the machine-readable envelope, so a field with no tag is a field
the wrapper cannot see.

Context health is a small enumeration plus a reason code, not prose:
keep / safe / clear-recommended, each with a machine-readable reason. The prose
sentence is a rendering concern and belongs to plan 197-02's card, not here.

Preserve one existing invariant exactly. `renderContextClearGuidanceForPlatform`
already refuses to say the context is safe to clear unless the handoff file is
verifiably on disk, and records why in its own comment. When that decision moves
into the resolver it keeps that rule: handoff-absent may never resolve to safe.
A softer wording is a regression, not a style change.

S-01 binds the command values. The resolver emits the runtime form
(`aether continue`, `aether build 3`). It never emits a slash form and never
consults `detectPlatform`. Translation stays where it already lives, at the
visual writer, and is applied by plan 197-02's card renderer.

Reuse, do not re-derive, the state readers that already exist and are already
tested: `normalizeLegacyColonyState`, `colonyNeedsEntomb`, `recoveryPhase`,
`activePlanFinalizeFailureFlag`, `loadActiveRecoveryGuidance`,
`buildForceRedispatchCommand`, `sessionActiveTodosFromState`. The loader calls
them; the resolver receives their results as plain input fields.

Do NOT change any of the five existing deciders in this plan. Collapsing them is
plan 197-02's job, and doing it here would put this plan's file ownership across
`codex_visuals.go`, which the next wave needs.

Do NOT add anything to `visualFunctions` in `cmd/worker_economy_test.go`. That
list is pinned to an old audit document and adding to it forces an unrelated
golden refresh.

Write the availability tests first and record the failing run.

Add the gate: a function that takes a candidate command string in runtime form,
splits off the verb path, and resolves it through the live Cobra tree the same
way the orphan ratchet already does — find the target and require its command
path to match what was asked for, so a fuzzy or prefix match cannot pass for a
real command. Return the candidate only when it resolves.

Route every recommendation and every alternative through the gate before the
resolver returns. When a candidate does not resolve, drop it; when the primary
recommendation does not resolve, fall back to a command that is itself gated
rather than to a literal, and record the substitution in the answer's reason so
the owner is never silently redirected.

Prove the gate can fail in three ways, because a gate that has never been seen
to refuse anything is a rule about nothing. First, drive the resolver over the
whole state table and assert every emitted command resolves. Second, hand the
gate a verb that is deliberately not registered and assert it refuses. Third,
assert that the candidate set the resolver draws from is itself checked, so the
day a command is renamed this test goes red rather than the owner being told to
type something that no longer exists.

Do not build a copy of the command list to check against. S-02 is explicit: the
list is the defect and the tree is the fix.

Separately, lock S-01 in `cmd/next_action_neutrality_test.go`: drive the whole
state table and assert every command value the resolver produces is in the
runtime form the wrapper and the TS host can execute, on every platform value
the runtime recognises. Set the platform environment variable across those
values inside the test to prove the resolver ignores it.
