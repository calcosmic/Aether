<objective>
Make worker debug artifacts reliable evidence: written on every failure mode,
carrying the facts needed to diagnose, capped so they do not accumulate, and
surviving worktree cleanup.

The user hit this directly on 2026-07-27: three failed `/ant-plan` runs whose real
cause was invisible. The bar for this plan is that stated in CONTEXT.md — could an
operator have diagnosed it from the terminal plus the debug file alone, without
hunting session transcripts?

Today `writeHostedWorkerOutputDebug` is called on exactly two paths (provider error
envelope and claims parse failure). The timeout branch and the non-zero-exit branch
return an error and write nothing. Both existing call sites pass `config.Root`,
which in worktree mode is the worktree path that `finalizeBuildWorktree` deletes
before anyone can read the artifact — so the path printed in the error message
resolves to nothing. Evidence that vanishes is the quietest silent failure there is.

Purpose: decisions D-03, D-04, D-05, and threat T-160-02. Contributes to LOUD-06's
"a failed context, survey, or gate call is visible" by making the failure evidence
survive.
Output: two new debug call sites, corrected root resolution on all four, an
extended payload, write-time retention, `data-clean` wiring, and tests that drive
real subprocess failures rather than calling the writer directly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| provider subprocess stdout/stderr → debug artifact on disk | Raw provider output may contain credentials from the worker's prompt or environment; it crosses into a persisted file here |
| worker prompt argv → debug artifact | The argv vector includes the full prompt; `safeHostedWorkerArgs` redacts by argument identity at this boundary |
| worktree filesystem → tracking root filesystem | Debug artifacts must be written across this boundary to survive `git worktree remove` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-160-02 | Information Disclosure | A worker debug artifact capturing raw provider stdout/stderr including a leaked credential | mitigate | Both new call sites route through the existing `writeHostedWorkerOutputDebug`, which applies `safeHostedWorkerArgs`, `sanitizeWorkerDiagnosticOutput` and `workerOutputExcerpt`; `TestWorkerDebugArtifactRedactsOnEveryFailureMode` asserts a credential-shaped token is absent on both new paths |
| T-160-14 | Information Disclosure | New payload fields (`exit_code`, `duration_ms`, `provider_run_id`, `failure_mode`) leaking sensitive content | mitigate | All four are scalars derived from process metadata, not from provider output; no raw stdout or stderr body is added to the payload, and the existing excerpt/byte-count fields are unchanged |
| T-160-15 | Denial of Service | Unbounded growth of `.aether/data/worker-debug/` filling the user's disk | mitigate | Age-then-cap prune enforced on every write, plus a `data-clean` step; `TestWorkerDebugRetentionCapEnforcedOnWrite` asserts the cap |
| T-160-16 | Repudiation | Evidence of a worker failure disappearing with the worktree, leaving the operator with an error message pointing at a path that does not exist | mitigate | All four call sites pass `workerTrackingRoot(config)`; `TestWorkerDebugArtifactUsesTrackingRootNotWorktreeRoot` fails if any reverts to `config.Root` |
| T-160-17 | Tampering | An inspection command deleting artifacts the operator was about to read | mitigate | `data-clean` without `--confirm` reports `worker_debug_prunable` and deletes nothing; `TestDataCleanWorkerDebugDryRunDoesNotMutate` asserts file set and mod times are unchanged |
| T-160-01 | Information Disclosure | `check-antipattern` gate with no live caller | transfer | Owned by Plan 04 of this phase |
</threat_model>
