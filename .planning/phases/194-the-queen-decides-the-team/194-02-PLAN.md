<objective>
Give every worker that spawns a one-line reason the owner can read, and refuse
by name any proposed worker that arrives without one. Today the reason slot
exists and is filled with score arithmetic on the fallback path and with a
single team-wide sentence on the proposal path, so the card can show a worker
whose stated justification is "Score 40 >= threshold 30 for build flow".

Purpose: TEAM-03, and the data Phases 196, 197 and 198 render without recomputing.
Output: a per-caste reason that travels from the proposal or the runtime, through
the judgement, into the manifest, onto the card, and into the dispatch record.
</objective>

- **TEAM-03 / adjacency (unresolved).** Probe: "When two things are exactly
  equal or just touch, do they merge, collide, or separate?" Planner's answer:
  they MERGE. A caste that the Queen proposed with its own reason AND that the
  runtime forced by a named signal gets one dispatch and one sentence carrying
  both. **Assumption:** the owner would rather read one merged sentence than see
  the same caste listed twice. Not confirmed with the owner.
- **TEAM-03 / empty (unresolved).** Probe: "What is the result for empty,
  single-element, or null input?" Planner's answer: whitespace-only is no
  reason; nil map is no reasons at all; a one-worker team is normal and still
  pauses for the owner (D-14). **Assumption:** refusing on a whitespace-only
  reason is right, rather than accepting it as "the Queen chose not to explain".
- **TEAM-03 / encoding (unresolved).** Probe: "Whose definition of
  length/equality applies?" Planner's answer: the caste key in a per-worker
  reason is normalised through the SAME `resolveCasteName` path as `--castes`,
  including the alias table and both separator styles. **Assumption:** no
  reason key needs to survive as an unrecognised name for later diagnosis; an
  unresolvable key is reported through the existing unknown-name channel.
- **TEAM-03 / ordering (unresolved).** Probe: "When elements compare equal, is
  output order specified and stable?" Planner's answer: sorted, stable, and
  asserted. **Assumption:** stable sorted order is preferred to proposal order
  for the refusal list, even though proposal order is the priority ranking used
  for budget trimming. If the owner ever wants refusals in priority order this
  reverses cheaply.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| wrapper `--caste-why` argv -> runtime | Reason text is authored by a model and rendered to the owner's terminal and into JSON. |
| reason string -> owner's terminal | Free-form text reaches a human who is told to act on it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-194-05 | Spoofing | `--caste-why` reason text | medium | mitigate | A reason is display-only and grants nothing: it can make a worker eligible to be SENT (which the owner then approves on the card) but can never remove a forced reviewer or a free check. Waiving is a separate, owner-only path (plan 194-04). |
| T-194-06 | Tampering | reason text rendered to a terminal | medium | mitigate | Reason strings are printed, never executed. Where a reason is embedded in a command shown to the owner, reuse the existing `shellQuote` helper rather than printing raw text into a copyable command line (the CR-02 precedent from Phase 193). |
| T-194-07 | Repudiation | per-caste reasons in the manifest | low | mitigate | Reasons are written into `caste_decision` and the dispatch contract, both persisted, so who asked for a worker and why is recoverable after the fact. |
| T-194-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan. Gate not triggered. |
</threat_model>
