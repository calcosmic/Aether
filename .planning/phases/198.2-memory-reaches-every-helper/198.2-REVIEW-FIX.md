## Fixed Issues

### CR-01: Carry-forward never surfaces "needs owner confirmation" criteria, contradicting its own contract

**Files modified:** `cmd/phase_carry_forward.go`, `cmd/brief_growth_cap_198_2_test.go`
**Commit:** `b7dfc50d`
**Applied fix:** The criteria loop in `resolvePreviousPhaseCarryForward` had an
unconditional `if c.Passed { continue }` immediately after the `State == ""`
check, making the state check dead code -- every passed criterion was
skipped regardless of `State`, so a criterion sitting at
`needs_owner_confirmation` never reached the carry-forward section. Rewrote
the loop to branch on `!c.Passed` (unmet -- existing wording) vs.
`c.Passed && c.State != ""` (still needs the owner's confirmation -- new
branch), matching the function's own doc comment. Added
`TestCarryForwardSurfacesNeedsOwnerConfirmationCriteria`, seeded with
`Passed: true, State: criterionStateNeedsOwnerConfirmation` -- the exact
shape `criterion_evidence.go`'s own writer produces. Confirmed the new test
fails against the pre-fix code (the criterion never appears) before
restoring the fix and confirming it passes. This is a logic-shaped fix
(a dead-code branch resurrected) verified only by test, not by a build
requiring separate human sign-off -- **status: fixed**.

### WR-01: `registerColonyResearchDoc` bypasses the store's file lock on a now-automatic write path

**Files modified:** `cmd/colony_research.go`
**Commit:** `101d558c`
**Applied fix:** Routed the read-modify-write of `COLONY_STATE.json` through
`store.UpdateFile`, the same `FileLocker`-backed locked path every other
in-process writer of this file uses, instead of raw `os.ReadFile` /
`os.WriteFile`. Added a guard returning an error (non-fatal to every
caller, per the function's own doc comment) when the global store is nil or
bound to a different root than the one passed in, rather than silently
mismatching locks. The "no-op when nothing changed" path now writes the
same bytes back rather than skipping the write, so the lock is held across
the whole read-decide cycle instead of releasing between a read and a
decision not to write. `cmd/oracle_autofile_198_2_test.go`'s existing
coverage (which exercises this function through `finalizeOracleLoop`) stays
green with no changes.

### WR-02: Survey digest's per-report cap doesn't reserve room for its own truncation notice

**Files modified:** `cmd/helpers.go`, `cmd/brief_digest_198_2_test.go`
**Commit:** `5d9edc60`
**Applied fix:** `resolveSurveyDigestSection`'s per-report truncation now
reserves the truncation notice's own byte length from the per-report budget
before slicing the report's content, so the truncated body plus its notice
suffix never exceeds `surveyDigestPerReportChars` (400) -- comfortably under
`colony.SanitizeSignalContent`'s 500-char rejection ceiling. Before the fix,
a long enough survey report filename pushed `400 (content) + notice length`
over 500, causing the sanitizer to reject the report outright (landing it in
the omission list as "content rejected") instead of truncating it to fit, as
the per-report budget intended. Added a guard: if a report's remaining
budget is too small to fit even the notice, it is named as an omission
rather than producing a negative slice or a truncated fragment with no
notice.

### WR-03: `used` budget accounting includes the truncation-notice suffix

**Files modified:** `cmd/helpers.go`, `cmd/brief_digest_198_2_test.go`
**Commit:** `5d9edc60` (same commit as WR-02 -- both are in the same
truncation branch of the same loop)
**Applied fix:** `used` now accumulates only the truncated body's own length
(`len(cut)`), not the truncation notice suffix appended after it, matching
the function's own doc comment about deterministic, byte-exact budgeting.
Untruncated reports are unaffected (their full content length is still
counted, as before).

**Test added for WR-02/WR-03:**
`TestLongFilenameTruncationNoticeStaysInsideTheSanitizerBoundary` seeds a
single survey report with an 80-character filename (a realistic
worker-authored name, not fixed by this codebase) and body long enough to
require truncation. Confirmed the test fails against the pre-fix code with
exactly the predicted error (`content rejected: content exceeds maximum
length of 500 characters (530)`) before restoring the fix and confirming it
passes, along with every other test in `cmd/brief_digest_198_2_test.go`.
