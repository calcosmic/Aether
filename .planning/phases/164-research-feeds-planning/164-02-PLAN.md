<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-authored phase text -> hint computation | Phase names/descriptions come from a Route-Setter draft or user goal text and are scanned for signals |
| user selection -> decision record | The flip/approve choice becomes a durable resolution string |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-164-04 | Tampering | `computePhaseResearchProposal` reason text | mitigate | The Reason is built from a fixed `phaseResearchReasons` lookup table with only the matched signal token interpolated — never the raw phase description — so a crafted description cannot inject instruction text into the reason line the Queen relays |
| T-164-05 | Tampering | hint signals over/under-triggering research | accept | Worst case is one extra or one missing research dispatch (cost/quality), not a security boundary crossing; per 164-RESEARCH.md security domain this is explicitly low severity |
| T-164-06 | Repudiation | user override of the Queen's recommendation | mitigate | `phaseResearchDecisionResolution` records the resulting direction and phase in the durable `PendingDecision.Resolution` string, so a later replan can show what was overridden and by which path (manual vs. autopilot) |
</threat_model>
