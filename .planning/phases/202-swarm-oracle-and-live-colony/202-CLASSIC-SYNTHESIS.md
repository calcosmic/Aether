# Phase 202 Classic-to-Go Synthesis

This is the mandatory pre-plan mechanism study for Phase 202 (SYNTH-04, gated by SYNTH-07). Classic is evidence about what made watch, Swarm and Oracle feel alive — including their presentation, per the owner's D-04 steer — not code to restore. The current Go kernel (typed lifecycle results, the deterministic floor, Phase 201's checkpoint primitive, Oracle's confidence/novelty machinery) is the authority every disposition below builds on. [VERIFIED: `.planning/research/v1.28-classic-synthesis-template.md`; `.planning/phases/202-swarm-oracle-and-live-colony/202-CONTEXT.md`]

## 1. Outcome under investigation

- **Owner-visible outcome:** the owner watches a live dashboard that updates in place — workers, castes, lineage, waves, current questions, confidence, contradictions, findings, recovery state, elapsed time, cost — with a short event ticker beneath it, styled with the February-April Classic character (caste emoji + ant glyphs, ceremony framing, Queen voice); when nothing is running, they see a truthful replay of the last episode instead of a fabricated "idle" fiction; a stubborn bug gets four genuinely distinct investigators whose hypotheses are compared and ranked on screen, a checkpointed repair applied automatically, and — after three failed repairs — a plain-language architectural escalation; Oracle clarifies the actual question once, then researches autonomously with visible confidence/contradiction movement, and hands back a synthesis that leads with the recommendation; every finished (or usefully partial) piece of Swarm/Oracle work is discoverable later through status and history, honestly labelled. [VERIFIED: `202-CONTEXT.md` D-01..D-12]
- **Operational outcome:** one versioned, replayable typed event model reaches every renderer (watch, status, history); Swarm's linear investigate→fix pipeline gains a structured hypothesis-comparison step and reuses Phase 201's proven checkpoint/restore primitive rather than a second one; Oracle's already-rich `oracleStateFile` state is emitted at its existing mutation points rather than rebuilt; Oracle's preset labels align with Phase 200's Fast/Balanced/Deep/Exhaustive vocabulary without changing Oracle's own confidence/iteration economics; Swarm and Oracle episodes durably bind into the one attempt-bound evidence lineage status/history already read. [VERIFIED: `202-CONTEXT.md` "Claude's Discretion"; `202-RESEARCH.md` Summary]
- **Why this phase owns it:** the roadmap routes `SYNTH-04`, `CEC-05`, and `LIVE-01..07` here; the capability ledger routes `CAP-021`, `CAP-044`, `CAP-045`, `CAP-046`, `CAP-047`, `CAP-048`, `CAP-063`, and `CAP-072` here. [VERIFIED: `.planning/ROADMAP.md` Phase 202; `.planning/research/v1.28-classic-capability-ledger.md:71,94-98,113,122,154,177-181,196,205`]
- **Non-goals:** recruitment/delegation/pheromone causality and TypeScript-host preflight work belong to Phase 203; learning governance and outcome-backed promotion belong to Phase 204; final acceptance is Phase 205; the build/continue/run work cycle (including its own checkpoint primitive, `work_repair.go`) was delivered in Phase 201 and is reused here unchanged, not re-specified. [VERIFIED: `202-CONTEXT.md` domain boundary]

For dummies: keep the modern engine's safety (checkpoints, replay, honest idle) and its proven repair primitive — but stop leaving watch permanently idle, give Swarm's four investigators a real comparison step instead of four prompts stapled together, let Oracle's already-tracked confidence and contradictions actually reach the screen, and make the colony look and feel like the alive Feb-April version again over data that is always true.

### Core data contracts

1. **Typed event payload structs** (new, `pkg/events/bus.go` extension) — plain structs with JSON tags and a `RawMessage()` method (mirroring `CeremonyPayload`), each carrying an explicit `schema_version` field; new topic constants follow the existing dotted-namespace convention (`swarm.lens_started`, `oracle.confidence_changed`, `watch.snapshot`, etc.), checked against existing topics (`CeremonyTopicOracleIteration` already exists) before adding a duplicate.
2. **`swarmHypothesis{LensName, Claim, Confidence, Evidence []swarmHypothesisEvidence, Contradictions []string, ProposedRepair string}`** — new Swarm-owned sibling type to `oracleWorkerResponse`, same field shape, never a cross-package extension.
3. **Swarm-owned checkpoint identity** (`cmd/swarm_repair_checkpoint.go`) — a `swarmID`/target-fingerprint-keyed sibling to `repairCheckpointIdentity(phase, check)`, calling `saveRepairCheckpoint`/`restoreRepairCheckpoint` directly, never the phase/check-shaped wrappers.
4. **Swarm episode retention metadata** — new fields bound to the existing `swarmResultRecord`, never a second episode record type.
5. **Oracle preset label map** (`cmd/oracle_preset.go`) — pure mapping layer over the unchanged `oracleDepthLevels`, mirroring `planningPresetPolicies`'s struct shape.
6. **One shared partial-work label vocabulary** — extends `oracleResearchPartialLabel`'s existing discipline to Swarm's unproven repair ideas and plan research/Dreams, rather than three per-subsystem inventions.
7. **One read-only lineage index** (plan 202-14) — reads `buildAttemptRecord`, `swarmResultRecord`, and Oracle research entries as they already exist; adds no fourth record type.

### Cost/spend authority ruling (money never rides on a live event)

`renderSpendCostLine` (`cmd/spend_cost_line.go:126`) and its ledger-reading callers remain the SOLE cost authority for any figure this phase's live dashboard, Swarm episode card, or Oracle synthesis renders. No new event payload carries a currency amount, a token count intended as a cost proxy, or any parallel spend field — a live event may reference an attempt/episode ID whose cost the existing renderer resolves on demand, but it may never carry the number itself. This closes off, structurally, the exact hazard Phase 196 named and fixed once already: `spendTotals.ProviderUSD` was deleted rather than gated because "nothing read it and an unread money field on the totals struct is a standing invitation to render one" (`.planning/STATE.md` Phase 196 bullet). A second, event-carried cost field would recreate that same standing invitation one layer up, in a new subsystem, immediately after the milestone finished fixing the first one. Any plan that renders "reported cost" on the live dashboard (D-01) MUST call `renderSpendCostLine`/`renderSpendCostLineFromLedgers` directly, never duplicate or re-derive a figure.
