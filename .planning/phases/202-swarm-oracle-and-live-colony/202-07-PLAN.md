<objective>
Bracket Swarm's repair with the same checkpoint, verify and rollback transaction every other repair lane already uses, and turn the third consecutive failure into a plain-language architectural case for the owner.

Purpose: Today's Swarm goes straight from investigation to applying a fix, with no saved state to return to. The safety net LIVE-04 requires already exists and is proven — Phase 201 built and locked it — so the only correct move is to call it. The owner has chosen automatic application with the full story afterwards, which makes the rollback path the thing that must be right: a repair that fails verification has to leave the project exactly as it was, and a restore that itself fails has to say so rather than claim success.
Output: A Swarm-shaped checkpoint adapter over the existing primitives, a bracketed fix wave, and a three-strike escalation that reads as a case rather than a stop.
</objective>

It is implemented rather than re-asked because the owner decided it.</reversibility>
  <behavior>
    - A Swarm run with a selected repair saves a checkpoint before dispatching the fix wave.
    - A fix wave whose verification passes leaves the repair in place and the checkpoint is discarded.
    - A fix wave whose verification fails restores the checkpoint, announces the restore, and reports the run as a failed repair rather than a success.
    - A restore that itself fails stops the run, states that the project was not put back, names the saved copy's location and the recovery command, and does not describe the repair as rolled back.
    - No approval prompt appears at any point during the run.
    - A run that selected no repair saves no checkpoint.
  </behavior>
  <action>In `cmd/swarm_cmd.go`'s `runSwarmDestroy`, bracket the fix wave: after the comparison selects a repair and before `executeSwarmWave` dispatches the fix plans, call `saveSwarmRepairCheckpoint` and its announcement; after the verification wave returns, decide from that wave's own outcome whether the repair held. On a pass, keep the working tree and release the checkpoint's temporary copy. On a fail, call `restoreSwarmRepairCheckpoint`, announce the restore, and carry a failed-repair outcome into the run's result.

Handle the restore-failure case explicitly: when `restoreSwarmRepairCheckpoint` returns an error, stop the run, write an owner-facing message stating in ordinary words that the project was not put back, naming the directory holding the saved copy and the exact command to restore it by hand, and mark the run's outcome as repair-failed-and-not-restored — a state distinct from both success and a clean rollback. Never emit the restore announcement in this case.

Do not add any interactive prompt. Do not alter `persistSwarmResultOutcome`'s call or the values it receives beyond the outcome status the run genuinely reached.

Add `TestSwarmRepairCheckpointsBeforeTheFixWave`, `TestSwarmRepairRollsBackOnFailedVerification`, `TestSwarmRestoreFailureIsReportedHonestly` and `TestSwarmRepairAsksNothingMidFlight`, each driving the real `runSwarmDestroy` path against an isolated fixture root with a stub worker invoker.</action>

    - With restore forced to fail, the run's status is the distinct not-restored state, the output names the saved copy's directory and a runnable recovery command, and the rollback announcement text is absent.
    - No fixture run reads from standard input or emits a prompt.
