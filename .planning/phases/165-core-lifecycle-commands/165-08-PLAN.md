<objective>
Close the two Phase 165 warnings the verification named as worth fixing
alongside the blocker, because they are the same class of defect: a wrapper that
tells the model two different things, or tells it to do things in an order that
wastes or corrupts a user decision.

**WR-01 — contradictory read/write instruction.** `build.md:51` and
`continue.md:191` both say the wrapper *may read* colony state, while
`build.md:255` and `continue.md:205` both say `Do NOT read or write colony state
files by hand`. `plan.md:186` already carries the reconciled formulation
(`This wrapper never reads or writes, by hand: ...`), so plan.md is the model to
follow, not a fourth wording to invent. The substantive rule is not in dispute:
these wrappers do read state, but only through runtime commands like
`aether status` — never by opening the JSON.

**WR-04 — approval recorded against a manifest about to be discarded.**
plan.md's `## Clarification Gate` (lines 67-78) currently sits *after*
`## Decision Moment 2 — Research Batch` (lines 50-65). Decision Moment 2 runs
`aether plan-research-approve`, mutating research-approval state and requesting a
fresh manifest. The Clarification Gate then may route to `aether discuss` and
discard that very manifest. The user's approvals were spent on a manifest the
next stage throws away. Moving the gate before Decision Moment 2 costs nothing —
the gate reads `orchestrator_boundary_guidance` and `unresolved_clarifications`
from the manifest already fetched in `## Planning Manifest`.

Purpose: no lifecycle wrapper contains an instruction that contradicts another
instruction in the same file, and no user decision is collected against state
about to be thrown away.
Output: reconciled `<read_only>` blocks on build and continue across all
surfaces, a new consistency test, plan.md's stage order corrected, and all three
YAML sources updated in lockstep.
</objective>
