# Phase 198.3: Code Review Report

**Reviewed:** 2026-09-01T15:22:56Z
**Depth:** standard
**Files Reviewed:** 82
**Status:** issues_found

## Summary

The overnight-stamina implementation has multiple fail-open authorization and lifecycle paths. The most serious defects allow path traversal outside `.aether/data`, let malformed external swarm results become successful durable history, reuse an old owner approval after new work, and leave sealed or recovery state internally contradictory. The test suites are green (`go test ./...`: 8,458 tests across 20 packages; TypeScript: 540 tests), type-checking passes, and `go vet ./...` is clean, but the cases below are not covered by those gates.

In plain English: the happy path works, but crafted input, a repeated run, or one disk-write failure can make Aether approve work it did not verify or damage the state it relies on for recovery.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01 [BLOCKER]: Swarm helper IDs permit reads and writes outside the data store

**File:** `cmd/swarm.go:51-56`
**Issue:** `swarm-findings-read`, `swarm-display-init`, `swarm-display-update`, `swarm-timing-start`, `swarm-timing-get`, and `swarm-timing-eta` interpolate the public `--id` value into a store path without validation (also lines 165-170, 191-204, 243-248, 270-275, and 309-315). Only `swarm-cleanup` validates the ID. `storage.Store` resolves relative paths with `filepath.Join` and explicitly accepts absolute paths, so an ID such as `../../outside` escapes `swarms/`; the write variants can overwrite JSON outside `.aether/data`, and the read variants can disclose any JSON-readable file available to the process.
**Fix:** Validate every swarm ID through one shared helper before constructing any path. The helper should call `safeIdentifierSegment(filepath.Join(store.BasePath(), "swarms"), "swarm id", id)` and return a store-relative path only after containment succeeds. Add traversal and absolute-path tests for every public swarm helper command.

### CR-02 [BLOCKER]: Checkpoint names can overwrite files outside `checkpoints/`

**File:** `cmd/state_extra.go:28-40`
**Issue:** `state-checkpoint --name` appends `.json` to an unchecked name and passes `checkpoints/<name>.json` to `Store.SaveJSON`. Names containing `../` escape the checkpoint directory and can overwrite another JSON file with colony-state content. This is both a path-traversal vulnerability and a data-loss risk.
**Fix:** Resolve `name` with `safeIdentifierSegment(filepath.Join(store.BasePath(), "checkpoints"), "checkpoint name", name)` (or an equivalently strict single-segment validator) before the write. Reject separators, absolute paths, `.` and `..`, and test both POSIX and Windows-style traversal strings.

### CR-03 [BLOCKER]: A forged external swarm manifest writes files before its ID is validated

**File:** `cmd/swarm_cmd.go:674-680`
**Issue:** `swarm-finalize` accepts `manifest.SwarmID` from the completion file and immediately calls `initializeSwarmRun`. That helper uses the value in `os.MkdirAll` and three JSON paths at lines 543-560. `saveSwarmResultRecord` eventually validates the ID, but only after those writes have already happened. A fresh completion document with the correct root and a swarm ID such as `../../target` therefore escapes the store and writes `responses/`, `findings.json`, `display.json`, and `timing.json` before finalization fails.
**Fix:** Validate the manifest ID with both `safeIdentifierSegment` and `isValidSwarmResultID` before `beginRuntimeSpawnRun` or any filesystem mutation. Treat the generated plan-only manifest as untrusted finalizer input and add a regression test that proves no path is created for a tampered ID.

### CR-04 [BLOCKER]: External swarm results can forge worker identity and turn non-terminal states into success

**File:** `cmd/swarm_cmd.go:735-815`
**Issue:** Results are silently overwritten in maps by duplicate name/role, may match a plan by role alone, and then overwrite the manifest-owned name, caste, role, and task at lines 774-785. Status validation is also fail-open: `spawned` is explicitly promoted to `completed`, while any other unknown value survives normalization. `summarizeSwarmOutcome` only recognizes `blocked`, `failed`, and `timeout` at lines 1270-1292, so values such as `planned`, `running`, or `wedged` produce an overall `completed` result. This lets an incomplete or forged wrapper payload enter durable strike history as a successful investigate/fix/verify pass.
**Fix:** Mirror the external continue finalizer: reject duplicate and surplus results, match each result to exactly one manifest dispatch by immutable identity, call `validateWorkerResultIdentity`, and never overwrite plan-owned identity fields. Accept only the documented terminal status allowlist (`completed`/equivalents, `blocked`, `failed`, `timeout`); reject `spawned`, `planned`, `running`, empty, and unknown values before recording any run.

### CR-05 [BLOCKER]: A Critical reviewer finding with only a fix suggestion does not block continue

**File:** `cmd/codex_continue_finalize.go:865-875`
**Issue:** Review artifact validation checks severity but does not require a title or description. `mergeCodexReviewFindings` retains a row when the description is empty but `suggestion` is present (lines 985-1001). Both the direct continue path (`cmd/codex_continue.go:1692-1707`) and external finalizer (`cmd/codex_continue_finalize.go:1197-1211`) then skip that Critical row because they cannot construct description text. A payload such as `{"severity":"CRITICAL","suggestion":"rotate the exposed key"}` is therefore structurally accepted yet can let direct or externally finalized continue advance.
**Fix:** Require every structured finding to have non-blank `description` or `title`; record a blocking evidence error otherwise. As defense in depth, any Critical row must block even if its display text is malformed, using a placeholder that identifies the worker and finding index.

### CR-06 [BLOCKER]: Resolved owner checkpoints silently authorize later rebuilds

**File:** `cmd/autopilot_checkpoints.go:226-293`
**Issue:** A checkpoint key is based on type, phase, subject, session, and goal, but not on the build attempt or evidence generation. Visual work always uses the fixed subject `visual` at lines 151-164. When a later build of the same phase changes UI, `upsertAutopilotCheckpoint` finds the previously resolved row, merges the new paths, returns it still resolved, and the caller emits no checkpoint. Runtime criteria with the same task/criterion have the same problem. Thus an owner's approval of build A can silently cover different work from build B and allow seal without reviewing the new changes.
**Fix:** Bind checkpoint identity to immutable work evidence, preferably the build-attempt/execution binding plus a digest of the relevant claims or verification artifact. Replays of the same attempt should deduplicate, but a different successful attempt or changed evidence must create a new unresolved checkpoint even when the wording is identical.

### CR-07 [BLOCKER]: Stale decisions from another session or goal satisfy current owner confirmation

**File:** `cmd/handoff_decisions_cmd.go:40-55`
**Issue:** `answeredDecisionTexts` collects every resolved decision in `pending-decisions.json` without applying `pendingDecisionMatchesScope`. Its callers then suppress current handoff questions and owner-confirmation criteria solely by normalized text (`cmd/criterion_owner_confirmation.go:38-40` and 92-103). A same-text answer from an old session or different goal can therefore count as current owner approval and remove the seal blocker that the scoped pending-decision system was designed to preserve.
**Fix:** Make `answeredDecisionTexts` accept a `pendingDecisionScope` and iterate only the active half returned by `filterPendingDecisionFileForScope`, or check `pendingDecisionMatchesScope` per row. Pass the current scope explicitly from handoff and owner-confirmation callers and add cross-session/cross-goal regression tests.

### CR-08 [BLOCKER]: Replan cadence resets whenever `aether run` is restarted

**File:** `cmd/compatibility_cmds.go:710-715`
**Issue:** `phasesCompleted` starts at zero for every invocation and is the value passed to `evaluateAutopilotReplan` after advancement (lines 859-871). `lessonAwareReplanDue` only fires when that local count is an exact interval multiple. Two successful `--max-phases 1` runs with `--replan-interval 2`, or equivalent timeout/resume cycles, never reach a count of two even though two phases and confirmed lessons have accumulated since the active plan revision. This contradicts the declared "since the last successful plan" policy and causes overnight resumptions to skip required replanning indefinitely.
**Fix:** Persist or reconstruct the count of successfully advanced phases since the active plan revision/last accepted replan. Key it by plan revision, update it atomically on advancement, and reset it only when a new plan revision is accepted—not when a process invocation ends.

### CR-09 [BLOCKER]: `insert-phase` can corrupt sealed state or skip the inserted phase

**File:** `cmd/state_extra.go:448-471`
**Issue:** The mutation runs without validating lifecycle position. A Crowned Anthill can be modified successfully, leaving `StateCOMPLETED`/`Milestone=Crowned Anthill` with a newly pending phase and a summary artifact that no longer matches the plan. In an active colony, an explicit insertion before `CurrentPhase` renumbers and maps the old current phase forward, so execution skips the new earlier phase. In a completed-but-unsealed colony, only an append is reopened because `shouldReopenInsertedPhase` requires `insertAt == previousPhaseCount` at lines 521-528; a middle insertion remains unbuildable under `COMPLETED`.
**Fix:** Reject all phase insertion after Crowned Anthill. For active colonies, reject insertion before the current phase unless the command explicitly rewinds state to the inserted phase with consistent statuses. For completed unsealed colonies, either restrict insertion to append-only or reopen any allowed insertion by setting the inserted phase/current phase to ready. Validate the resulting state invariants before the atomic callback commits.

### CR-10 [BLOCKER]: Seal commits destructive state before its required artifact is durable

**File:** `cmd/codex_workflow_cmds.go:773-836`
**Issue:** `completeSealRuntime` expires FOCUS signals first, then persists `StateCOMPLETED` and `Crowned Anthill` at line 796, and only afterward writes `CROWNED-ANTHILL.md` at line 834. A state-write failure has already destroyed signal state; a summary-write failure leaves a sealed colony with no required summary. Other side effects (review archive and prior consolidation/promotion work) are also outside a transaction. The command reports failure, but its durable state is already partially committed.
**Fix:** Implement a recoverable seal transaction/journal. Stage and fsync the summary and all derived artifacts first, record a pending seal transaction, then atomically commit colony state and finalize staged files; expire signals only after the durable seal commit. On restart, finish or roll back the journal deterministically. Add fault-injection tests at each write boundary.

### CR-11 [BLOCKER]: Corrupt blocker storage is treated as zero blockers

**File:** `cmd/codex_continue.go:3808-3819`
**Issue:** The Iron Law gate and autopilot baseline use blocker readers that collapse missing, unreadable, and malformed `pending-decisions.json`/`flags.json` into the same empty snapshot. In the autopilot exception, two such empty snapshots prove "no increase" and turn a failed blocker check into a pass. `compatibility_cmds.go` uses the same fail-open value at lines 751 and 810-821, and status reports zero. A malformed or temporarily unreadable blocker file can therefore let a phase advance while actual blocker truth is unavailable.
**Fix:** Change blocker loading/snapshot APIs to return an error. Treat only `os.ErrNotExist` for both current and legacy files as an empty set; JSON, permission, lock, and I/O failures must make continue fail, make autopilot stop as `colony_not_runnable`, and make status display an explicit storage warning. Never use an unknown snapshot as an authorization baseline.

### CR-12 [BLOCKER]: A failed escalation write permanently wedges three-strike swarm recovery

**File:** `cmd/swarm_strikes.go:479-495`
**Issue:** `persistSwarmResultOutcome` saves the third failed/blocked result before writing its required escalation flag. If the result write succeeds and `pending-decisions.json` then fails, the function returns an error with strike history already at three but no flag. Every later swarm call returns the architectural-concern recovery command immediately at `cmd/swarm_cmd.go:163-169` without retrying the flag upsert. That `insert-phase` command then fails because recovery requires the missing active same-target escalation flag. A single disk/permission fault thus leaves the supported recovery path permanently unusable.
**Fix:** Make the three-strike transition recoverable. At minimum, when the pre-dispatch guard observes `StrikeCount >= 3`, idempotently upsert/repair the escalation flag before returning the concern; fail closed if that repair still fails. Prefer a journaled result-plus-escalation transaction and add a fault-injection test for success of the result write followed by failure of the flag write.

## Warnings

### WR-01 [WARNING]: Checkpoint capability issuance grows without bound and old commands remain valid

**File:** `cmd/autopilot_checkpoints.go:304-343`
**Issue:** Every checkpoint render or seal check appends another hash, and matching accepts every historical hash until the row is resolved. Repeated `aether seal`/materialization calls therefore grow `pending-decisions.json` indefinitely and keep every previously displayed capability usable, despite presenting each render as a fresh authorization command. A copied terminal/log command has a larger and unbounded validity window than necessary.
**Fix:** Store one current capability hash per checkpoint (or a small TTL-bounded generation set), replacing the prior generation atomically. Expire hashes by issuance time and cap retained generations even if multi-view support is required.

### WR-02 [WARNING]: The frozen autopilot report drops the details of the Critical finding that stopped it

**File:** `cmd/autopilot_report.go:157-175`
**Issue:** `recordSignals` persists only findings whose severity is exactly `HIGH`. A Critical finding correctly stops autopilot, but `last_report` and `aether status` retain only the generic stop reason and recovery classification; the file, line, description, and suggested fix are absent. This undermines the documented morning handoff's promise to preserve findings from newer data changes.
**Fix:** Persist all reportable findings, or at least both HIGH and CRITICAL, with an explicit severity field. Render the blocking Critical details in `Last Autopilot Run` and add a stop/restart/status regression test.

### WR-03 [WARNING]: Swarm timing accepts impossible progress and emits nonsensical ETAs

**File:** `cmd/swarm.go:309-335`
**Issue:** `--progress` is not checked for finiteness or the expected range. Values greater than 1 produce a negative ETA, and `NaN`/infinite values can produce invalid duration conversions. A future `start_at` also yields negative elapsed time. The command returns these as valid timing data instead of rejecting a corrupt measurement.
**Fix:** Require a finite progress value in `(0, 1]`, validate `start_at <= now`, and return a typed input/data error otherwise. Use `math.IsNaN`/`math.IsInf` before any duration conversion and cover zero, negative, over-100%, NaN, infinity, and future timestamps.
