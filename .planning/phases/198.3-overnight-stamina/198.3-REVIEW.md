# Phase 198.3: Code Review Report

**Reviewed:** 2026-09-01T00:19:57Z
**Depth:** standard
**Files Reviewed:** 69
**Status:** issues_found

## Narrative Findings (AI reviewer)

Phase 198.3 adds useful typed policy and durability machinery, but six release-blocking paths still fail open or leave the operator unable to perform the documented recovery. The most serious defects are that direct build preflight runs only after destructive lifecycle writes, malformed checkpoint storage can let seal proceed, workers can resolve owner-only checkpoints themselves, and malformed reviewer evidence can disappear from enforcement. The durable morning report can also fail to save while the visual command claims success, and the three-strike swarm recovery command cannot actually unlock a retry.

In plain English: the overnight runner can sometimes say “this is safely recorded for the owner” when the record was lost, forged, or never validated. Those are safety-boundary failures, not cosmetic output problems.

Focused verification passed (146 targeted `cmd` tests, 33 `pkg/codex` tests, 16 focused race-enabled tests, TypeScript typecheck plus 540 tests, `go vet`, and `git diff --check`). Those suites do not exercise the negative paths below; passing them therefore does not remove these findings.

## Critical Issues

### CR-01: Direct build preflight runs after destructive lifecycle mutation

**Classification:** BLOCKER
**File:** `cmd/codex_build.go:700-860`, `cmd/codex_build.go:2086-2118`
**Issue:** The new Phase 198.3 provider/model preflight is called inside `executeCodexBuildDispatches` at line 2116. The outer build has already begun a spawn run, removed the prior phase's verification/gate/review artifacts, written a checkpoint and build-attempt record, changed `COLONY_STATE.json` to executing, written the manifest/briefs, recorded planned workers, and transitioned the attempt to dispatching before reaching that call. A failed preflight therefore occurs after lifecycle mutation, contrary to Plan 10's “before lifecycle mutation or worker invocation” integration requirement. Rollback restores colony state, but it does not restore the evidence removed by `cleanupStaleBuildAttemptArtifacts` or erase the run/attempt/spawn records that were already written. The Phase 198.3 diff added only the late call; the surrounding mutation order is pre-existing, so this is a phase-introduced placement defect rather than a pre-existing observation.

**Fix:** Construct the invoker and perform a phase-scoped readiness check before `beginRuntimeSpawnRun`, stale-artifact cleanup, checkpoint/attempt creation, or any state/artifact write. `preflightWorkerProvider` only needs root/platform/phase, so a minimal phase-scoped dispatch can be checked early; the later dispatch chokepoint may remain as a cache hit/defence-in-depth check.

### CR-02: Corrupt pending-decision storage makes the seal checkpoint barrier fail open

**Classification:** BLOCKER
**File:** `cmd/autopilot_checkpoints.go:336-343`, `cmd/codex_workflow_cmds.go:1269-1303`
**Issue:** `autopilotCheckpointSealBlockers` converts every `LoadJSON` error into an empty blocker list. `checkSealBlockers` also treats a failed `pending-decisions.json` read as permission to fall back to the legacy flags file. Thus a malformed, truncated, or unreadable pending-decision file containing unresolved visual/runtime checkpoints is indistinguishable from “no checkpoints,” and seal can proceed. Only a genuinely absent file is a valid empty state; corruption at the final owner boundary must not authorize completion. Both the checkpoint type and its seal integration were introduced in this phase.

**Fix:** Return an error from the checkpoint loader (and from `checkSealBlockers`) or synthesize a hard blocker. Treat only `os.IsNotExist` as an empty checkpoint set; malformed JSON, permission errors, and other I/O failures must stop seal with an exact repair/inspection command.

### CR-03: Any worker can resolve the new owner-only checkpoints

**Classification:** BLOCKER
**File:** `cmd/autopilot_checkpoints.go:314-333`, `cmd/pending_decision.go:187-252`, `cmd/handoff_decisions_cmd.go:99-159`, `cmd/handoff_decisions_cmd.go:216-283`
**Issue:** Visual/runtime checkpoint recovery prints a deterministic `decision-answer` command containing only public question text and phase. `recordDecisionAnswer` resolves the first exact checkpoint row without an owner capability, and the generic `pending-decision-resolve` command can resolve the same rows directly by ID. A repository worker has the same filesystem and CLI access needed to read the row and execute either command, so it can confirm its own visual/runtime work and remove the seal blocker. The nearby forced-reviewer path already documents this exact forgery threat and requires a capability, but Phase 198.3's new owner checkpoints were not added to that protection.

**Fix:** Give each owner checkpoint a single-use random capability, persist only its hash bound to checkpoint/session/goal/phase, and require the capability on `decision-answer`. Reject `visual-checkpoint` and `runtime-verification` rows in the generic resolver, just as forced-reviewer waivers are rejected there. Consume the capability atomically when resolving.

### CR-04: Malformed reviewer artifacts are reported but do not fail the review

**Classification:** BLOCKER
**File:** `cmd/codex_continue.go:1786-1789`, `cmd/codex_continue_finalize.go:808-855`, `cmd/codex_continue_finalize.go:867-907`, `cmd/codex_continue_finalize.go:1135-1209`
**Issue:** The worker brief requires a completed Auditor to return a 0-100 `overall_score`, but an explicit malformed/out-of-range artifact clears the legacy score/findings and leaves only `EvidenceErrors`; an empty `{}` artifact leaves neither evidence nor an error. `continueReviewAutopilotSignals` copies `EvidenceErrors` into output but never activates a stop, while `externalContinueReviewReport` treats the completed reviewer as passed unless a surviving Critical finding exists. A completed Auditor can therefore emit `{}`, an invalid score, or invalid severities and advance the phase without the score floor or Critical-finding gate ever running. This is the phase-introduced structured-artifact trust boundary; merely displaying the validation error does not prevent the “malformed evidence could pass a run” threat named by the plan.

**Fix:** Keep the explicit artifact authoritative, but fail closed when it violates the contract. A completed Auditor must have a valid integer score; any artifact parse/schema/severity error should mark that review step failed or activate a dedicated `review_evidence_invalid` genuine-stop signal. Do not convert invalid explicit evidence into the same state as “no Auditor was selected.” Add end-to-end tests that assert `{}`, malformed JSON, out-of-range scores, and invalid severities prevent advancement on both direct and external lanes.

### CR-05: Final report persistence failure is hidden behind a visual success report

**Classification:** BLOCKER
**File:** `cmd/compatibility_cmds.go:605-642`, `cmd/compatibility_cmds.go:961-1016`, `cmd/autopilot_report.go:75-77`
**Issue:** Every real run ending is documented as durably writing one versioned report. When `syncRunAutopilotStateWithReport` fails, `finishAutopilotInvocation` merely adds `report_persist_error` to the in-memory result and still returns success. The visual renderer sees the in-memory `last_report`, renders it, and returns early without ever showing `report_persist_error`. On disk-full, permission, or transient write failure, the operator sees a normal completed/paused morning report even though `aether status` will read an older report or none at all. This silent durability failure is introduced by the Phase 198.3 report finalizer.

**Fix:** Make the terminal finalizer return/propagate the persistence error (while preserving the primary run outcome in the result), produce a non-zero command result, and render the persistence failure before any in-memory report. Do not claim that the morning handoff is durable or ready for seal until the report save succeeds. Add a failing-store injection test for both JSON and visual output.

### CR-06: Three-strike swarm recovery can never unlock the refused target

**Classification:** BLOCKER
**File:** `cmd/swarm_cmd.go:156-173`, `cmd/swarm_strikes.go:193-211`, `cmd/swarm_strikes.go:363-390`
**Issue:** After three failures, the shared pre-dispatch guard refuses every later command for the same normalized target and recommends `aether insert-phase "<same target>"`. Strike history resets only after a later same-target swarm result with status `completed`. Inserting and completing the corrective phase, resolving the escalation flag, or revising the plan does not change that history; because the guard prevents the next swarm from dispatching, it is impossible for the success record required to reset the streak to occur. The only practical bypass is changing the target text or manually editing durable history, neither of which is the documented recovery. This deadlock is wholly in the Phase 198.3 three-strike feature.

**Fix:** Define a new strike epoch after verified recovery. For example, bind the escalation to the inserted corrective phase/plan revision and permit one new attempt only after that phase is completed (or after an explicit owner-authorized reset); then count later results within the new epoch. Add an end-to-end test that performs the emitted recovery command, completes the corrective phase, and proves the exact original target can dispatch again without seeding a fabricated success.

## Warnings

### WR-01: Headless dry-run predicts a stop that the live typed policy will not take

**Classification:** WARNING
**File:** `cmd/compatibility_cmds.go:819-851`, `cmd/compatibility_cmds.go:874-939`, `cmd/autopilot_lessons.go:154-163`
**Issue:** The live loop makes replanning lesson-aware and uses the typed disposition: no confirmed lesson means no headless replan event, while a due headless replan is queued and execution continues. The retained dry-run simulator ignores both `opts.Headless` and confirmed lessons; at every interval it unconditionally returns `stopped_reason: replan_due` and `next: aether plan`. The newly rendered catalogue therefore says “queue and continue” while the same preview envelope says it will stop. The simulator branch is pre-existing, but Phase 198.3 changed live semantics without integrating that branch, so the drift is phase-introduced.

**Fix:** Route dry-run through the same pure replan eligibility/disposition evaluator used by live execution. Read existing lesson evidence without mutation; represent a headless due replan as a non-terminal queued event, and do not fabricate a stop when no lesson exists. If future lesson availability cannot be known, state that uncertainty explicitly rather than returning a contradictory terminal result.

### WR-02: Command-surface removal left obsolete autopilot mutation paths under test

**Classification:** WARNING
**File:** `cmd/run_visuals.go:193-251`, `cmd/autopilot_retry_record_test.go:25-157`
**Issue:** The typed run refactor removed all production callers of `pauseAutopilotRun`/`queueAutopilotPauseDecision`, leaving an old untyped pause writer (including an ignored pending-decision save error) as dead production code. Similarly, the retry test file spends most of its coverage exercising `recordAutopilotRetryExhaustion`, then explicitly proves at lines 136-157 that the run loop must never call it after whole-build retry removal. These helpers were pre-existing, but Phase 198.3 orphaned them while claiming generated/legacy surface shrink. Keeping disconnected mutation logic and green tests for it makes later reviewers think an unsupported path remains live.

**Fix:** Delete the dead pause/queue cluster and the disconnected retry-record helper with its direct unit tests. Retain the structural regression test that proves whole-build retry is not wired, and keep only helpers reachable from the typed run finalizer.
