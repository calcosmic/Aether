## Narrative Findings (AI reviewer)

### Critical Issues

#### CR-01: The new runtime minimum rejects the supported unstamped Go installation path

**Classification:** BLOCKER

**File:** `/Users/callumcowie/repos/Aether/cmd/codex_skill_surface.go:127-128`

**Related files:** `/Users/callumcowie/repos/Aether/cmd/root.go:26-74`; `/Users/callumcowie/repos/Aether/cmd/blackbox_harness_test.go:82-91`; `/Users/callumcowie/repos/Aether/README.md:129-138`.

**Issue:** `validateCodexSkillPayload` now compares the payload's `1.0.79` runtime minimum with `resolveVersion()`. The documented `go install github.com/calcosmic/Aether/cmd/aether@latest` route does not inject `cmd.Version` using Aether's release linker flags. Outside an Aether checkout and without an existing hub, `resolveVersion()` returns its `0.0.0-dev` default even when the executable contains the current implementation. It does not consult Go module build information or a binary-local release version.

Consequently, `aether install` rejects the Codex payload while preparing the shared hub and exits before any platform home is synchronized. This affects the normal bundled-assets installation path, not only an explicitly selected Codex update. The compatibility requirement itself is reasonable; the defect is treating an unidentified current executable as evidence that the executable is incompatible.

The phase also changes the shared black-box builder to inject the release version into every test binary. That makes those tests valid for stamped releases but removes coverage of the documented unstamped installation route. Its comment that rejection of such a binary is “correct” overlooks that supported route.

**Bounded reproduction:** Built the reviewed HEAD once with `go build -o <temporary-directory>/aether ./cmd/aether`, without `-ldflags`. Go build metadata identifies source revision `539215d04b69e218947c7388f31ffa656e7e07cc`. Ran the binary from a separate empty consumer directory with isolated `HOME`, `CODEX_HOME`, and `AETHER_HUB_DIR`, with no checkout or existing hub available to version resolution:

- `aether version`: exit 0, `{"ok":true,"result":"0.0.0-dev"}`.
- `aether install`: exit 2, hub error `codex skills: runtime 0.0.0-dev is older than required 1.0.79`.
- The selected hub and Codex skill installation directory remained absent.

The reproduction uses a current local build with the same missing-linker-stamp condition as Go installation; it does not claim to have downloaded or qualified a published release. The optional `--skip-build-binary` form was also checked and failed identically. The plain `aether install` result above establishes that this is not caused by that flag.

**Fix:** Supply an immutable version belonging to the executing binary when deciding runtime compatibility. A minimal reliable implementation can retain an explicitly stamped `Version` as authoritative and otherwise read the executable's own embedded release metadata. `embedded_assets.go` currently does **not** embed `.aether/version.json`, so add that asset and a small accessor if using this approach. Ensure bundled payload source identity can resolve from the same embedded metadata. A dedicated runtime-version helper can keep this compatibility decision separate from the existing display-oriented resolver.

Do not infer executable compatibility from the desired external package, a mutable installed hub, or an unrelated working checkout; do not simply exempt every `0.0.0-dev` value from minimum-version checks. Explicitly older stamped runtimes and genuinely higher payload minimums must still be refused before mutation.

**Causal regression test:** Build an executable **without** `-ldflags`, run it outside the source tree with a fresh isolated home, and execute the normal embedded `aether install` path. Assert successful hub creation, the nine public ant entrypoints, the three private support files, and the ownership manifest. Keep a separate control where the executing runtime is explicitly stamped below the required version and verify refusal without destination mutation. The existing always-stamped black-box helper cannot exercise the failing branch, so preserve a distinct unstamped build in this test.
