## Shared Patterns

### Validation and errors

This is local CLI/filesystem work; there is no web authentication middleware to copy. Authorization is the existing runtime-owned action, typed destination roots, content ownership proof, channel checks and filesystem containment.

Use early error returns with an operation and `%w` cause as in `cmd/platform_sync.go:349`, `cmd/update_cmd.go:529`, and `cmd/lifecycle_transaction.go:374`. Controllers return a truthful structured result and then the error; do not hide collisions as successful overwrites or fall back to direct writes after a transaction failure.

### Shared state and output authority

Keep runtime commands, outcome facts and lifecycle state unchanged by presentation. Preserve `RuntimeCommand` while changing `DisplayCommand`; preserve the shared `outputWorkflow` result path in `runMaintenanceUpdate`. Do not invent a second skill-owned state store or edit `.aether/data` from skill instructions.

### Dependency direction

The command guide supplies execution instructions; the public skill inventory supplies availability and naming; the migration planner supplies exact file targets; `LifecycleTransaction` commits them. User guidance and source checks consume those contracts. Neither skill discovery nor a docs renderer should decide authorization or perform installation as a side effect.

### Source checking

`sourceCheckIssue` (`cmd/source_check.go:19–25`) already carries area, path, message, expected and actual values. Add a bounded generated-Codex component that checks the declared nine entries, their parseable names, and verified route/helper references. Keep the existing Claude/OpenCode wrapper checks. Absence of 55 intentionally deferred Codex entries is not a Phase 204.1 source-check failure.

## Critical Corrections to Imported Findings

1. **The imported proof matrix's `$ant-status`/`$ant-help` smoke test is for the later full surface.** Neither belongs to this phase. Fresh-client proof must identify and invoke the actual nine skills with bounded disposable fixtures. Loading a skill and identifying its intended first step proves discovery/entry routing; it must not be described as a completed lifecycle journey.
2. **A managed marker alone does not protect edits.** The general wrapper cleanup example accepts ownership headers; this phase explicitly promises preservation of edited/custom skills, so skill migration needs stronger content/version evidence.
3. **The direct and transactional paths differ.** Install/publish call the older shim writer. The registered update controller owns a transaction and never calls it. Test the production entrypoint to prove the new connection exists.
4. **“Rollback” has a specific boundary.** Existing rollback restores failed/unverified transactions. A verified committed update cannot be undone through `LifecycleTransaction.Rollback`; a general downgrade facility is additional work, not an existing analog.
