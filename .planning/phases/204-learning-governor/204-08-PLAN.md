<objective>
Let a proposed change be tried beside the current behaviour, over the same work and over checks it was never allowed to see, graded by something it structurally cannot touch.

Purpose: everything else in this phase records what happened. This is the part that decides whether a proposed change is actually better — and it is the part with the obvious way to cheat. A candidate that can choose what it is measured against, or edit the measure, produces a number that means nothing, and this project's own history is a long list of green results that meant nothing. The defence has to be structural. A rule saying "the candidate must not edit its grader" is a comment; a type with no way to reach its grader is a guarantee.

Output: an isolated package where the grader has no setter, the candidate has no reference to it, and a candidate that wins on the visible work and loses on the held-back checks is reported as having fit itself to the test rather than solved the problem.
</objective>

## Planner Assumptions (no CONTEXT.md — owner may veto)

**Assumption P (Research Open Question 4) — a candidate is a setting or a rule, never a piece of code.**
What gets tried side by side is a changed setting or a changed decision rule — for example, which helper is sent to a kind of task. It is never a code change. Code changes go the other route in this phase, as a branch a person reviews, and never through this side-by-side path at all.
*If the owner disagrees* (wants code changes tried this way too): that needs the two sides run in genuinely separate programs so the proposed code cannot reach the grader's memory, which is a much larger piece of work and was deliberately kept out of this phase.

**Assumption Q — the grader lives in its own sealed compartment, and this deviates from the research's suggested location.**
The research proposed putting this inside the existing command package's directory. This plan puts it in the shared library area instead, alongside the other sealed-off components this project already keeps there. The reason is concrete: the command area is one single large compartment where everything can see everything, which is exactly what the sealing needs to prevent. The shared library area is where this project already puts components that must not be reachable from everywhere.

**Assumption R (edge probe, LEARN-06, unclassified — surfaced, not resolved) — "cannot select its evaluator" is read as four structural conditions, not one.**
The requirement does not say how the impossibility is achieved. This plan reads it as: the grader's fields are unreachable from outside its own compartment; the grader type has no method that changes it; no function anywhere hands out a changeable reference to it; and the candidate type has no place to hold one. All four are checked by a test that reads the source rather than by review.
*If a later reviewer wants process-level separation instead:* the affected work is this plan and the promotion gate in plan 204-09.

  <behavior>

    - A candidate that beats the baseline on both sets is reported as beneficial.
    - A candidate that beats the baseline on the visible set and loses on the holdout set is reported as overfit, and overfit is never reported as beneficial.
    - A candidate that loses on the visible set is reported as not beneficial regardless of the holdout result.
    - A candidate and baseline scoring exactly equal are reported as tied, and a tie recommends nothing.

    - Every score is carried as a numerator and a denominator; the percentage is derived for display only and is never compared against.

  </behavior>

`pkg/shadow/comparison.go` declares:

`Score` carrying a numerator and a denominator as integers and a `Percent()` method deriving the display figure. Nothing in the package compares percentages; every comparison is between numerators cross-multiplied by denominators, so two scores over different denominators compare exactly and rounding can never decide a verdict. Say that in the type's doc comment and prove it with a test using denominators that round identically and compare differently.

`Verdict` as a closed vocabulary: beneficial, not beneficial, overfit, tied, inconclusive. Declare it with the completeness convention — const block, members slice, names helper, membership predicate — the same as every other vocabulary in this phase.

`Compare(baseline Baseline, candidate Candidate, evaluator FrozenEvaluator, visible []Task, holdout []Task) (Comparison, error)` runs all four passes and returns the four scores, the verdict, the grader's digest, the baseline's digest and the candidate's identifier. Verdict rules, each named as its own small predicate rather than one nested condition: a candidate losing or tying on the visible set is not beneficial or tied respectively; a candidate winning on the visible set and losing on the holdout set is overfit; a candidate winning on both is beneficial; an empty visible set with an empty holdout set is inconclusive with no recommendation. Inconclusive never recommends promotion — a comparison with nothing to compare is not a licence.

`Compare` takes the holdout tasks as a parameter and never resolves them itself. The resolution from digests happens in the calling command, so this package holds no path to the holdout file and a candidate declaration sitting inside this package can reach nothing that names a holdout.
