# Phase 204 Classic-to-Go Synthesis

This is the mandatory pre-plan mechanism study for Phase 204 (SYNTH-06, gated by SYNTH-07). Classic feature names below — instincts, Queen wisdom, Hive, midden, pheromone decay, credit ledger — are investigation headings, not predetermined solutions. Every disposition is decided against cited historical evidence (`204-CLASSIC-HISTORICAL-EVIDENCE.md`, itself citing `6732b0ba` and `3a5b81c2` directly) and cited current Go evidence re-read this session at `current_revision` (this worktree's own HEAD after Task 1's commit, `8beb8ebc`), per `.planning/research/v1.28-classic-synthesis-template.md`.

## 1. Outcome under investigation

- **Owner-visible outcome:** the owner can trust that anything shown to a worker or to themselves as "learned" has actually been verified, not merely asserted; a note or instinct that helped keeps getting stronger and one that hurt gets weaker or quarantined, with a full undoable history, exactly as CLAUDE.md's "Biological Runtime" section already promises for pheromone notes — this phase extends the same honesty to instincts, memory items, and specialist findings; a failed pattern becomes a permanent regression test so the same mistake cannot silently ship twice; and nothing the system "learns" on its own can ever touch a skill, a workflow, source code, security, deletion, a permission, a verification step, or an external action without the owner's explicit say-so.
- **Operational outcome:** every learning-relevant store (instincts, learned-entry hypotheses, the credit ledger, midden, the event bus, hive, eternal memory, skills, the build-knowledge-delta evidence, and the doubly-orphaned relationship graph) is re-verified against live code at this session's HEAD and carries exactly one evidence-backed disposition; the highest-value orphan in the whole system (`recordRecruitmentCredit`, Phase 203's own evidence-gated outcome ledger) gets a real production writer; a worker is never shown a guess under a heading that calls it verified; a confirmed incident becomes a sanitized, versioned regression fixture; a small set of named, budgeted test gates replace ad hoc "run everything and hope it finishes inside the timeout"; a candidate improvement runs beside a frozen baseline it structurally cannot tamper with; and only genuinely reversible, low-risk knowledge or routing may enter a bounded, ownable canary.
- **Why this phase owns it:** the roadmap routes `SYNTH-06`, `LEARN-01..08` here (`.planning/ROADMAP.md` Phase 204 section); the capability ledger routes `CAP-001`, `CAP-025`, `CAP-043`, `CAP-055`, `CAP-057`, `CAP-067`, and `CAP-070` here (`.planning/research/v1.28-classic-capability-ledger.md:134,158,176,188,190,200,203`).
- **Non-goals:** the recruitment/admission gate, pheromone write/decay/quarantine mechanics, and the trophallaxis knowledge-handback packet were delivered in Phase 203 and are reused, never re-specified, here — this phase extends their outcome vocabulary (`helpful`/`neutral`/`harmful`/`pending`) to new contribution kinds (`memory_item`, `specialist_contribution`) but does not rebuild the ledger itself. Live-colony rendering and Swarm/Oracle mechanics belong to Phase 202, reused as-is. Final owner-watched UAT is Phase 205.

For dummies: right now, if the program shows you or a helper something it says it "learned," that claim might just be a guess nobody ever checked — a real, currently-running bug, not a hypothetical one. And the single best-built piece of memory this project has (a ledger that tracks whether a suggestion actually helped, hurt, or did nothing) has never once been fed real data, because nothing in the program calls the function that would write to it. This phase's job is to fix both of those — wire the good machinery that already exists instead of building more machinery next to it — and then add the genuinely new pieces: turning confirmed bugs into permanent tests, running a candidate improvement in a way it cannot cheat its own grading, and making sure nothing the system decides on its own can ever touch your code, your security settings, or delete anything without asking you first.

### Ruling (d) — the runtime's auto-skill-creation default is safer than assumed, but "propose" mode is a silent dead end

### Core data contracts

1. **Extended `recruitmentCreditRecord`** (`cmd/recruitment_credit.go`, unchanged shape) — real callers added at the observation-outcome boundary for `memory_item`/`specialist_contribution` kinds already declared and unused.
2. **Status-aware render/admission filter** (new shared helper, e.g. `learningVerifiedOutcomesFilter()`) — called at both `colony_prime_context.go:725` and `autopilot_lessons.go`'s admission predicate; no change to `pkg/learn/colony_store.go` itself, which is already correct.
3. **New event topic family** on the EXISTING `pkg/events.Bus` (liveness) plus a new, distinct durable rollup record type (durability) — deliberately shaped to avoid tripping `TestOneLiveEventModelOnly`'s AST scanner (no Kind+Timestamp-shaped struct with its own file-write path).
4. **Typed `ApplicationHistory`** replacing `instincts.json`'s `[]interface{}`, modeled on `pheromones.json`'s pointer-backed field discipline.
5. **Fixture bank** (new, versioned) — derived from `midden.json` confirmed+acknowledged entries via `colony.SanitizeSignalContent`, provenance-linked to `MiddenEntry.ID`.
6. **Named budgeted gate manifest** (new, `Makefile`/CI target definitions over the existing `go test` binary) — no new dependency.
7. **`FrozenEvaluator`** (new, isolated `shadow_comparison` package) — `sha256.Sum256` digest, no setter, per RESEARCH.md Pattern 4's proposed shape.
8. **Extended `colony.PendingSuggestion`** — a canary-candidate kind added to the SAME queue `suggest_approve.go` already reads; also the destination for ruling (d)'s corrected "propose" mode.
9. **Generalized quarantine threshold** — `noteHarmfulQuarantineThreshold`'s named-constant idiom, reused (not duplicated) for canary regression counting.

### Owner-facing summary

Right now, if the program tells you or a helper that it has "learned" something, that claim might just be a guess nobody ever checked — this is a real bug happening today, not a hypothetical risk. This phase's job is to make sure that never happens again, and to build the small number of new safety rails needed before the program is ever allowed to try improving itself on its own.

What changes: the program already has a very well-built ledger for tracking whether a suggestion actually helped, did nothing, or made things worse — but nothing has ever fed it real information, so it has been running empty. This phase connects it to real data. It also fixes the specific bug where an unverified guess gets shown to you or a helper under a label that claims it was checked. And it adds things the program has never had before: a confirmed bug turns into a permanent test so the same mistake can't silently happen twice; a proposed improvement gets tested fairly, in a way it structurally cannot rig its own scoring; and only small, safely-reversible changes (the kind of thing that's easy to undo, like adjusting which project facts to remember) are ever allowed to run automatically on a trial basis, called a "canary" here — meaning a small, watched, easily-reversible test run, not a permanent change.

What never changes without asking you first, no matter how confident the program becomes: anything that would change a skill it uses, a workflow it follows, your actual source code, a security setting, a permission, a verification step, an external action (like sending something or contacting a service), or anything that deletes data. Those are refused automatically, by name, every time — the program cannot talk itself into an exception, and only you can approve one. And if the program ever proposes a change to its own source code, that proposal can only ever become an ordinary, reviewable code change — it can never approve, merge, publish, or deploy itself.
