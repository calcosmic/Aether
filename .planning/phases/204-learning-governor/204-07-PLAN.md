<objective>
Split this repository's one enormous test run into seven named gates with declared budgets, give the confirmed-failure bank a guard index, and make it impossible for a gate to report clean on a run that only partly happened.

Purpose: this project has one documented root cause behind three separate entries in its own defect register — an unqualified full-suite run reported a result after executing roughly a third of the tests, printing a complete-looking summary of the fraction it finished. Every unqualified gate run in this repository's history was checking about a third of the suite and nobody could tell. Twenty-one minutes is also, by the owner's own named priority, too slow to run on every change. Named, budgeted gates fix both: a fast gate that is genuinely fast, and every gate carrying the discovered-equals-executed check that would have caught the original defect on day one.

Output: seven gates, a sentinel list that cannot be quietly emptied, a holdout set that cannot be read off by name, and a guard index over the confirmed-failure bank.
</objective>

## Planner Assumptions (no CONTEXT.md — owner may veto)

**Assumption M (Research Open Question 5's sibling) — we use the test tool's own features, not a new tool.**
The seven gates are seven ways of running the tests this project already has, each with its own time limit written down. Nothing new is installed and no second test runner is built. The slow ones are marked so they do not run unless asked for, which is what makes the quick one quick.
*If the owner disagrees:* the alternative is a separate orchestration tool, which doubles what has to be maintained and reintroduces exactly the partial-run problem this is fixing.

**Assumption N (edge probe, LEARN-05, unclassified — surfaced, not resolved) — a "held-back check" is one the program knows about and a person reading the code cannot list.**
The requirement asks for checks kept back so that something being tested cannot be tuned to pass them. This plan stores those checks by fingerprint rather than by name, so reading every file in the project does not tell you which ones they are. Somebody with the running program can still discover them; the goal is that a change written against the visible checks cannot be written against these too.
*If a later reviewer disagrees about the strength required:* the affected work is this plan and the comparison in plan 204-08.

**Assumption O — a fixture without a guard is listed, not hidden.**
Some confirmed failures cannot yet be turned into a check without more work than this phase has. Each of those is counted, and that count is only allowed to go down over time. It is never quietly dropped from the list.

The manifest holds a `schema_version` constant, and a `gates` array of exactly seven entries. Each entry declares: `name`, from the seven the requirement names; `packages`, the package patterns the gate runs; `build_tags`, the tags the gate passes; `run_pattern`, the test-name pattern the gate passes, empty meaning all; `requires`, the environment facts the gate needs, drawn from a closed enum with members `none`, `network`, `provider_credentials` and `long_wall_clock`; `budget_seconds`, an explicit positive integer; and `purpose`, one plain sentence saying what the gate is for.

The seven gates and their intent, which the manifest must reflect:

- **fast** — the default-tagged tests in the small packages only, no network, budget measured in tens of seconds. This is the gate run on every change.
- **focused** — a name pattern supplied at invocation against the default build, budget in the low hundreds of seconds. This is the gate run while working on one area.
- **integration** — the tests behind the integration build tag, which are excluded from the default build, no network required.
- **provider** — the tests behind the provider build tag, requiring provider credentials, never run by default.
- **overnight** — the tests behind the overnight build tag, long wall clock, the whole corpus plus anything too slow for any other gate.
- **race** — the full default build with the race detector, the budget CLAUDE.md's Verification Commands section already states in minutes rather than a guess.
- **release** — the union of fast, focused, integration and race, plus the sentinel list, which is the gate that must pass before anything is published.

Declare the gate names in `cmd/eval_gates.go` as a closed vocabulary with the completeness convention this repository uses everywhere, and declare `evalGateManifest`, `evalGate`, `loadEvalGateManifest()` and `validateEvalGateManifest()`. Validation refuses a non-positive budget by name; refuses a gate present in one of the two lists and absent from the other, naming the offender and which list it is missing from; and refuses a gate whose selection matches nothing, which it determines by listing the tests the selection would run rather than by executing them.
