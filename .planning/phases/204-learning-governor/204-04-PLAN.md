<objective>
Give every started episode a durable, append-only record of what it cost, what it decided, what gates it met and how it ended — one that is still readable months later.

Purpose: the one genuine typed event bus in this system forgets. Its query and replay both exclude anything past a thirty-day life, which is correct for a live activity feed and fatal for an outcome ledger a promotion or rollback decision may need to consult weeks later. Two of the capability rows routed to this phase — the changelog collection and the human-readable phase outcome file — are named as becoming derived views of exactly this ledger. Without it, nothing later in this phase can prove a candidate beat a baseline, because the baseline's own evidence will have quietly aged out.

Output: one durable ledger written at the episode boundary that already exists, with idempotent derived views, and new liveness topics on the one bus that already carries liveness.
</objective>

## Planner Assumptions (no CONTEXT.md — owner may veto)

**Assumption G (Research Open Question 2) — the live view keeps forgetting; the permanent record is kept separately.**
The screen that shows what is happening right now is allowed to forget old activity after a month, because that is what makes it a live screen rather than an ever-growing log. The permanent record of what each run cost and how it ended is kept in its own file that never expires. The live screen reads the first; anything that needs to look back reads the second.
*If the owner disagrees* (would rather one file kept forever): the alternative is raising the live feed's memory from one month to forever, which makes every live screen read slower over time and was explicitly designed against.
*Technical:* `TestOneLiveEventModelOnly` was read before this was decided. It is an abstract-syntax-tree scan for a second event-shaped type reaching a file write inside package `cmd`; it does not count bus constructions. A second bus instance would therefore pass it and still fork the truth, which is why this plan adds none. The durable ledger is a plain record store with no event-kind field, so it is structurally outside that detector by shape, not by exemption.

**Assumption H — what the runtime cannot measure is written down as unmeasured.**
Some runs report how much they cost and some do not. A run that did not report is recorded as not reported, never as costing nothing. A summary that adds those up says how many runs it could not account for.
