<objective>
Let the system change a small, reversible, low-risk thing about itself when it has proven that change is better — and make it structurally incapable of changing anything else.

Purpose: this is the one question in this phase that is genuinely the owner's, and there is no discussion record for it. The answer this plan takes is the narrowest one the requirement's own words allow. Two kinds of thing may be changed automatically: what the project knows about itself, and which helper gets sent at which kind of work. Nine kinds of thing may never be, and the defence is not a rule in a document — it is a list in code with no path from it to the promoting function, checked by a test that fails if that ever changes. Everything else about this plan follows from that: a change that cannot be undone cannot be tried, and a change that goes wrong is undone in the same breath as it is noticed.

Output: a gate that refuses nine categories by name, a canary that cannot start without a restore point, and a rollback that restores and quarantines as one operation.
</objective>

## Planner Assumptions (no CONTEXT.md — owner may veto)

**Assumption S — the narrowest possible answer to "how much may it change about itself".**
Two things only: facts it has learned about this project, and which kind of helper it sends at which kind of task. Nothing else — not your preferences, not the skills it uses, not how the workflow runs, not the code, not anything to do with security, not deleting anything, not what it is allowed to touch, not how it checks its own work, and not anything that reaches outside this machine. Those nine stay yours. They are not merely discouraged; there is no route from them to the automatic path, and a check reads the code to prove that.
*If the owner disagrees and wants more automated:* widening the list is one line plus a new refusal test, and doing it later costs nothing. Widening it now, with no discussion on record, would be the planner deciding something that is not the planner's to decide.

**Assumption T (edge probe, LEARN-07, unclassified — surfaced, not resolved) — "reversible" means there is a saved restore point, not merely that someone believes it could be undone.**
A change qualifies as reversible only when a restore point was genuinely saved before it, and restoring from that point is itself tested. A belief that something is undoable does not count.
*If a later reviewer disagrees:* the affected work is this plan.

**Assumption U — the program can already create a skill without asking you, and this plan stops that.**
Found while reading the code for this phase: at the end of every check the runtime looks at what was learned and, in one of its settings, writes a new skill straight into the active set with nobody approving it. Skills are one of the nine things the requirement says stay under your authority. This plan routes that creation into the same approval list you already use for everything else that waits on you.
