<objective>
Report honestly how often the system genuinely did something useful and how often the owner had to step in to prevent something — as two separate figures neither of which can be improved by moving a number from one to the other — and make a code change something this system can only ever propose.

Purpose: a system that grades its own improvement will find a way to grade itself well; that is not cynicism about this system in particular, it is the reason the requirement asks for hard failures to be non-gameable. The two things worth knowing are opposites and must never be combined: how often it finished a genuinely useful task, and how often a person had to intervene to stop it doing something wrong. One number covering both can be improved by getting worse at one and better at the other. And a system that can propose a change to its own source must be structurally unable to accept that proposal, or the whole chain of evidence above it is decoration.

Output: two separate figures with exact arithmetic and hard failures that cannot be moved, and a source path that can open a branch and nothing else.
</objective>

## Planner Assumptions (no CONTEXT.md — owner may veto)

**Assumption V (Research Open Question 5) — the sandbox is a second lock, never the only one.**
The program's execution environment already refuses to let a worker edit the project's automation settings. That is useful, but it is a property of one way of running things and may not hold elsewhere. The guarantee here is in the code: there is no route from proposing a change to accepting one, and a check reads every file to prove it. The sandbox stays as a second lock behind that.
*If the owner disagrees* (would accept the sandbox alone): that would make the guarantee depend on which tool is running the program, and it would silently disappear on another one.

**Assumption W (edge probes, LEARN-08) — a percentage is for reading, never for deciding.**
Every rate is shown as "seven out of nine" with the percentage beside it. Any decision the program makes compares the counts, not the percentage, so rounding can never change an outcome. Where a percentage is shown it is rounded to one decimal place using the convention that ties round to the nearest even digit, which is stated in the code rather than left to whatever the formatting happens to do.

  <action>Add `TestSourceProposalCannotMergePublishOrDeploy` to `cmd/source_proposal_test.go`.

Detect each family both ways. A direct invocation is a call to a function whose own name or whose package path names the operation — the publish command's own entry point, the porter's deploy path, and the repository's own version-control helpers.
