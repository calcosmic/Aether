<interfaces>
The decision chain the exploit travels, in order, for a `spawn-log --parent Queen` call
(`cmd/spawn.go`):

1. `deriveSpawnDepth(st, "Queen")` — `Queen` is a coordinator sentinel (`spawnRootParentNames`),
   so this returns depth 1 WITHOUT reading the ledger at all. The tree's state cannot influence
   it either way. This is why the budget check is the only guard standing between a corrupted
   ledger and unlimited depth-1 spawning.
2. `spawnCanSpawnDecision` — three checks in a fixed order: depth, then
   `spawnTreeBudgetReason`, then `spawnAncestorCycleReason`.
3. `spawnTreeBudgetReason(in) string` (`cmd/spawn_budget.go:99`) — already turns ANY non-nil error
   from `spawnTreeBudgetState()` into the deny sentence
   `whole-run helper budget unverifiable (<err>): refusing to spawn`. It needs no new error
   handling; it needs `spawnTreeBudgetState` to actually produce the error.
4. `st.RecordSpawn(...)` — only reached when the decision allowed.

`spawnTreeBudgetState() (spawnTreeBudget, error)` (`cmd/spawn_budget.go:58`) as it stands today:
- builds `agent.NewSpawnTree(store, "spawn-tree.txt")`;
- calls `CurrentRun()`; on `ok == false` returns `Consumed: 0` immediately — the T-173-24
  "colony that has never begun a run" exception, and the ONLY place this budget does not fail
  closed;
- calls `EntriesForRun(run.ID)`, which after plan 11 propagates a corruption error;
- counts entries whose status is not `agent.SpawnStatusAbandoned`.

Two gaps in that shape, not one:

**Gap A — the ledger.** The no-run-yet early return never touches the ledger, so corrupting
`spawn-tree.txt` AND removing `spawn-runs.json` still yields `Consumed: 0` and an allow. Ledger
integrity must be established BEFORE that early return, not only inside `EntriesForRun`.

**Gap B — the run window.** `CurrentRun()` returns `ok == false` in exactly one situation:
`runState.Runs` is empty (`pkg/agent/spawn_tree.go:183-189` — when any run exists it falls back to
the most recent one, so an old or ended run still resolves). `runState.Runs` is empty when
`spawn-runs.json` is absent, is empty/whitespace, or records zero runs. So against a VALID ledger
holding 20 live helpers, a single `rm .aether/data/spawn-runs.json` takes the no-run-yet exception
and reports `Consumed: 0`. Gap A's integrity check does not catch this, because the ledger is not
corrupt — it is perfectly valid and simply uncountable. Plan 12's original "harder variant" test
corrupted the ledger AND deleted the run file together, so the corruption was always caught first
and this route was never exercised on its own.

**How Gap B must be closed — and how it must NOT be.** The obvious rule, "no run resolves and the
ledger has entries, therefore deny", was checked against the existing suite and against the
documented worker CLI, and it is wrong. Nothing begins a run except `beginRuntimeSpawnRun`
(`cmd/spawn_runs.go:15`, called from build, continue, plan, colonize and swarm), so "the ledger has
entries and no run was ever recorded" is a ROUTINE legitimate state, not an anomaly:
- `cmd/spawn_enforce_test.go` has at least five tests that call `spawn-log Queen→W1` and then
  `spawn-log W1→H1` with no run begun, each through `runSpawnLogExpectingSuccess`; the second call
  in every pair would be refused.
- `cmd/spawn_ancestor_test.go` builds its ancestor chains the same way.
- `.aether/workers.md:292` documents workers calling `aether spawn-can-spawn {your_depth} --enforce`
  directly, so a bare-shell spawn outside a lifecycle command would start refusing.

A deny there would brick ordinary use — the same trap plan 11 avoided with the empty-status
completion line. So the two situations are separated, because they are genuinely different faults:

- **The run-state file exists and cannot be READ** — a directory at its path, a permission denial,
  or invalid JSON. Unambiguously a fault. Deny. Plan 11 makes `CurrentRun()` return an error here,
  and `spawnTreeBudgetState` already turns that into a deny with no new code.
- **No run has ever been recorded** — the file is absent, empty, or holds zero runs. Indistinguishable
  from legitimate use. Do NOT deny, and do NOT grant a free budget: count every live entry in the
  WHOLE ledger instead of the run window. This is never looser than the correct run-scoped count
  (the whole ledger is a superset of any one run's window), so it closes the vector completely —
  `rm spawn-runs.json` against a full ledger now counts 20 and refuses — while a fresh colony
  counts 0 and a two-deep ancestor chain counts 2, both still allowed.

Existing assertions that pin the deny wording and must keep passing unchanged
(`cmd/spawn_failclosed_test.go` and `cmd/spawn_budget_test.go`): the deny message for an
unverifiable budget contains both `budget` and `unverifiable`; the deny message for an exhausted
budget contains `budget`; a refused spawn leaves `spawn-tree.txt` byte-identical.

ONE existing fault axis stops testing the guard it names the moment Gap A's reordering lands, and
it must be re-pointed here rather than left to fail. `cmd/spawn_failclosed_test.go`'s
`spawn-can-spawn` axis `requester-not-recorded` (~line 305) corrupts `spawn-tree.txt` with
`not-a-timestamp|Queen|builder|A1|t|not-a-number|spawned` and asserts the deny message contains
`ancestor chain unreadable`. Today, and after plan 11 alone, that assertion holds: the test never
begins a run, so `CurrentRun()` returns `ok == false`, the budget check takes the no-run-yet
exception, and the ANCESTOR check is the branch that denies. After THIS task the integrity check
runs first and denies on the corrupt ledger, so the axis's assertion fails. That test is inside
task 1's verify command, so it fails loudly rather than quietly. Note that under Gap B's

The other two axes are unaffected and must not be touched. `run-state-unreadable` injects invalid
