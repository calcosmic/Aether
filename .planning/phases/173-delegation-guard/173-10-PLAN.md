## What each guard actually reads — established from source at planning time

This section exists because Task 2's matrix was originally written as a cross product of two files
against four guards, and three of those cells could never have been satisfied honestly. Verified
against the source on 2026-08-12:

- `cmd/spawn.go` contains **zero** references to `COLONY_STATE.json` or `colony.ColonyState`
  (`grep -in colony cmd/spawn.go` returns nothing).
- `cmd/root.go`'s `PersistentPreRunE` only builds the storage handle
  (`storage.NewStore(dataDir)`); it never loads colony state content.
- `spawnTreeBudgetReason` (plan 05) reads the spawn tree and the run-state file via
  `agent.NewSpawnTree`, `CurrentRun()` and `EntriesForRun()`. No colony state.
- `spawnAncestorCycleReason` (plan 06) reads the spawn tree only.
- `deriveSpawnDepth` (plan 02) reads the spawn tree only.
- `hookSpawnDenyReason` (plan 07) reads **neither file** — it decides from the hook's own stdin
  payload. Only `hookPreToolUseCmd`'s pre-existing `Write`/`Edit` branch touches colony state, and
  only for tracing an already-made decision and for `redirectWriteReason`, which is not a
  delegation guard.
- `spawn-can-spawn-swarm` (plan 03) is the **only** delegation guard that reads
  `COLONY_STATE.json`.

Two further source facts constrain what "corrupt the spawn tree" can mean:

- `pkg/agent/spawn_tree.go:315` `parseFile()` returns `nil, nil, nil` when
  `store.ReadFile` fails, and `parseSpawnTreeBytes` **skips malformed lines** with `continue`.
  So corrupting `spawn-tree.txt` does not itself produce an error from `Parse()`. What it produces
  is a **missing entry**, which is what the guards actually deny on.
- Run state lives in a separate file, `spawn-runs.json` (`defaultSpawnRunFile`,
  `pkg/agent/spawn_tree.go:63`). `loadRunStateLocked` returns an error only when the bytes read
  successfully but fail `json.Unmarshal` — a read failure is swallowed as empty state. So the
  budget path's genuine error injection is **invalid JSON in `spawn-runs.json`**, not a
  directory or an unreadable file.

ROADMAP corrections needed, both in Phase 173's success criteria:
- Criterion 2 currently reads "`aether spawn-tree-depth` reports the true depth (3 for a 3-deep
  tree)". D-05 and D-07, locked in `173-CONTEXT.md`, fix the number at 2 (coordinator 0, workers 1,
  helpers 2). The parenthetical predates the ruling.
- Criterion 4 currently reads "With `COLONY_STATE.json` and the spawn tree made unreadable,
  **every** delegation guard denies". That is an absolute over inputs three of the four guards do
  not read, and it is unprovable as written. D-19's own wording is already per-guard — *"every
  delegation guard denies when it cannot resolve **what it needs**"* — and D-21 requires bounded
  claims. Phase 172 set the precedent: ROADMAP line 671 records its criteria 1 and 4 as narrowed.
