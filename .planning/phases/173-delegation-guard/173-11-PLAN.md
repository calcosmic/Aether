<objective>
Make the spawn ledger's parser tell "there is no ledger yet" apart from "there is a ledger and it
has been tampered with". Today they are the same answer — an empty list and a nil error — which is
the root cause of the whole-run budget being resettable to zero by one shell write.

Purpose: 173-VERIFICATION.md reproduced a working exploit. After the run's 20-helper budget was
legitimately exhausted and the 21st helper correctly refused, one line of non-pipe-format text
written over `.aether/data/spawn-tree.txt` made the identical refused request succeed and report
`budget_consumed:1`, as if the run had never happened. No special tool access is needed: the
`PreToolUse` hook matches `Write|Edit|Agent|Task` and never `Bash`, so an ordinary shell redirect
is enough. `parseFile()` swallows every read error and `parseSpawnTreeBytes` silently discards
every line it cannot parse, so no caller can tell a legitimately empty colony from a corrupted
one. This plan fixes that at the boundary; plan 12 turns the resulting error into a refusal.

Output: a spawn-tree parser with three distinguishable outcomes (absent, valid, corrupt), a write
path that refuses to overwrite a corrupt ledger, and package-level red-proofs for each.
</objective>

Change `pkg/agent/spawn_tree.go` so a present-but-unparseable ledger is a distinct, propagated
outcome from an absent one.

Declare an exported sentinel `ErrSpawnTreeCorrupt` (via `errors.New`) whose message says, in plain
words, that the spawn ledger is present but its contents are not a valid spawn ledger. Every
corruption error must wrap it with `%w` so callers and tests can use `errors.Is`. Add `errors` and
`io/fs` to the import block.

Change `parseSpawnTreeBytes` to return `([]SpawnEntry, []completionLine, error)`. Iterate over
`strings.Split(string(data), "\n")` — NOT over `strings.TrimSpace(string(data))` as it does today —
so the reported line numbers match the file's own numbering. Track a 1-based line number. Trim each
individual line; skip it when it is empty. Classify every remaining line by exactly these rules,
in this order, and treat anything that satisfies none of them as corrupt:

1. `strings.SplitN(line, "|", 7)` returns exactly 7 fields AND `strconv.Atoi(fields[5])` succeeds —
   a spawn entry, parsed exactly as it is today.
2. Otherwise `strings.SplitN(line, "|", 4)` returns at least 4 fields AND
   `normalizeSpawnStatus(completionFields[2])` is non-empty — a completion line, parsed exactly as
   it is today.
3. Otherwise the line is corrupt: return immediately with an error wrapping `ErrSpawnTreeCorrupt`
   that names the 1-based line number and the number of pipe-separated fields observed.

Two cases that are silently skipped today become corruption errors, and this is the point of the
change: a 7-field line whose depth field is not a whole number (currently `continue // skip
malformed`), and a line with fewer than 4 pipe-separated fields (currently falls off the end of
the loop body with no branch at all — this is the exact shape the verifier's
`echo "garbage" > spawn-tree.txt` produces).

The error message must NOT contain the offending line's own text. A spawn-tree line carries the
task description a worker was given; D-11 already refuses to write task text into the failure
record for this reason, and the same reasoning applies to an error string that will be printed to
a terminal and pasted into a bug report. Name the line number and the field count; never the
content.

Change `parseFile()` to distinguish three outcomes:
- `st.store == nil` — return three nils, unchanged.
- `st.store.ReadFile(st.filePath)` returns an error: if `errors.Is(err, fs.ErrNotExist)`, return
  three nils (this is the one legitimate absent case, and it is the same justified exception
  `cmd/spawn_budget.go`'s doc comment already records as T-173-24). For ANY other read error —
  a directory at the path, a permission denial, an I/O failure — return a wrapped, non-nil error
  naming the file path. The current blanket `// File doesn't exist -- return empty` comment is
  wrong for every error except the one it names, and must go.
- The bytes read successfully: call the new three-return `parseSpawnTreeBytes` and, on error, wrap
  it once with the file path before returning it.

A zero-byte file and a whitespace-only file must still parse as an empty ledger with a nil error.
That is the "no ledger yet" half of the distinction this plan exists to draw, and plan 12 depends
on it: a fresh colony that has never spawned anything must never be locked out.

Update both write closures so a corrupt ledger is never silently rewritten. In `RecordSpawn`'s
`store.UpdateFile` closure and in `updateStatus`'s `store.UpdateFile` closure, take the new error
return from `parseSpawnTreeBytes` and return `nil, err` from the closure when it is non-nil. This
aborts the write: the corrupt bytes stay on disk as evidence and no new entry is appended. Today
the opposite happens — the corrupt line is dropped and the file is rewritten from the surviving
entries, which is the second half of the verifier's reproduction (`recorded:true`,
`budget_consumed:1`) and the step that destroys the evidence of tampering.

Leave `NewSpawnTree` and `Active()` swallowing the error, but add a comment to each stating that
they are not the guard boundary and that `Parse()`, `EntriesForRun()` and `RecordSpawn()` are the
calls whose errors enforcement depends on. `NewSpawnTree` is a constructor with no error return,
and `Active()` is the read-only operator view that must keep rendering the rest of the tree.

Correct `parseFile`'s own doc comment and `SpawnTree`'s type comment to state the new contract in
one sentence: absent means empty, unreadable means error, unparseable means error.
