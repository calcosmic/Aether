<objective>
Execute the twelve benchmark runs with a human operator at the keyboard, then generate and commit
the results.

Purpose: This is the phase's product. Everything before it built the apparatus; this plan
produces the numbers that every later phase in the programme is measured against. The runs cannot
be automated — both systems' lifecycles are interactive, the operator must supply the enumerated
scripted inputs, and the interrupted-execution category requires a person to issue the single
resume command. The operator's discipline is what makes the intervention count meaningful.

Output: `bench/results/<date>/` with twelve run directories, `bench/results/RESULTS.md`, and a
final README section recording what the baseline says.
</objective>

  <what-built>
The complete benchmark harness is built and preflighted. Twelve cells are enumerated and ready:
three lanes (GSD, Aether interactive, Aether autopilot) across four task categories (small bug
fix with a seeded failing test, brownfield feature across several files, interrupted execution
with a forced kill and one resume command, fresh-repo full lifecycle).

Each cell is one command. The harness creates a clean throwaway home directory containing only
that lane's system, makes a fresh copy of the test repository at a fixed version, prints the
inputs you are permitted to give, waits while you run the system, then measures the result by
script — tokens read from the session's own transcript file, changed files compared against a
list written in advance, and a separate judging script that decides pass or fail by running the
resulting code rather than by reading anything the system reported about itself.
  </what-built>
  <how-to-verify>
Follow `bench/RUNBOOK.md` from start to finish. In outline:

1. Export the chosen model as `BENCH_MODEL` (the exact value is recorded in
   `bench/results/<date>/PREFLIGHT.md`).
2. Start a saved terminal transcript per the runbook's `## Before you start`.
3. Work through the twelve cells in the order the runbook specifies, one command per cell:
   `bench/run.sh --lane <lane> --category <category>`.
4. At each pause, give only the inputs listed for that cell in `bench/harness/permitted-inputs.md`.
   If you type anything else, log it as unscripted — that is a measurement, not a mistake, and
   suppressing it would make the whole comparison worthless.
5. For the three interrupted-execution runs, expect the harness to kill the system 120 seconds
   after it first writes a file. That is intended. Then issue exactly the one resume command the
   runbook names for that lane, and nothing more.
6. After each cell, confirm the harness wrote `run.json` and copied the raw evidence. Do not edit
   anything by hand.
7. If a cell has to be abandoned, record it as abandoned with the reason. Do not silently re-run
   it — a re-run without a record turns one bad result into a better-looking one.

Expected outcome: twelve run directories under `bench/results/<date>/`, each containing
`run.json`, the session transcripts, the operator log and the acceptance output.

There is no expected winner. A result unfavourable to Aether is a valid result and is the one
this phase is specifically designed to be able to produce.
  </how-to-verify>
  <acceptance_criteria>

    - Every `run.json` carries a non-null acceptance verdict, an interventions object with separate scripted and unscripted counts, a token figure whose source field is `session-transcript`, a model calls count, a cleanliness score, an unnecessary-modification count, and a wall-clock-net figure
