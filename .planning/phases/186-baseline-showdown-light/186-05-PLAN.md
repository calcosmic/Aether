were written before any run.

Create four executable scripts under `bench/acceptance/`, named to match the task specs
(`01-bug-fix.sh`, `02-brownfield-feature.sh`, `03-interrupted-execution.sh`,
`04-fresh-repo-lifecycle.sh`).

Uniform contract, identical across all four so the runner can call them the same way:
- `set -euo pipefail`, doc header stating which task it judges and what pass means.
- One positional argument: the path to a fresh clone of the run's resulting repository state.
  Fail with a named message if the argument is missing or the path is not a git repository.
- A `check` helper that runs one named assertion and records pass/fail without exiting, so all
  assertions run and every failure is reported — a script that exits on the first failure hides
  how badly a lane did, and the results table wants the full picture.
- Exit 0 only when every assertion passed. Exit 1 otherwise, having printed one line per failed
  assertion in the form `FAIL <assertion name>: <what was expected> / <what was found>`.
- On success print one line `PASS <task id>` and, on both paths, emit a JSON object on file
  descriptor 3 (or to a path given by the `ACCEPTANCE_JSON` environment variable) listing every
  assertion with its verdict — the runner needs machine-readable detail, and stdout is reserved
  for the human-readable lines.

Vocabulary constraint, which is a content rule not a shape rule: no assertion may reference any
term either system invented. Specifically banned in assertion names and messages: `must_have`,
`must-have`, `criterion`, `criteria` used as a system term, `phase`, `colony`, `worker`,
`pheromone`, `instinct`, `wave`, `plan` used as a system artifact, `SUMMARY.md`, `PLAN.md`,
`COLONY_STATE`. State the rule in each script's header. The reason is that reusing either
system's verification vocabulary would let that system's own conventions decide the verdict.

Per-script content:

`01-bug-fix.sh` — assert the seeded test now passes by running the single-test command recorded
in the task spec and requiring exit 0; assert the seeded test file's contents are byte-identical
to the seeded version (the fix must not have been achieved by editing the test); assert the
repository's full test suite passes; assert the defect's actual behaviour is corrected by
exercising it directly, independently of the seeded test, so a fix that special-cases the test
input fails.

`02-brownfield-feature.sh` — assert the feature's behaviour directly by exercising it (not by
looking for the presence of files); assert the pre-existing test suite still passes; assert the
feature is reachable from the repository's own public surface rather than only existing in an
isolated file.

`03-interrupted-execution.sh` — assert everything `01-bug-fix.sh` asserts (the task is the same
task), plus: assert the work performed before the interruption is still present, by checking that
the files modified before the kill are still modified rather than reverted; assert no duplicate
or conflicting partial work exists (for example the same change applied twice). Recovery is a
property of the resulting repository, so it is asserted here rather than inferred from the
operator log.

`04-fresh-repo-lifecycle.sh` — assert the produced program exhibits its stated behaviour by
running it; assert the produced program's own tests exist and pass; assert the repository has at
least one commit and a working tree with no uncommitted changes to source files. Then the
separate assertion CONTEXT.md's Specifics block requires: take the Aether source repository path
from the `AETHER_REPO` environment variable (failing with a named message if unset) and assert
`git status --porcelain` there is empty — Aether must not have modified itself while working on
another project. Mark this assertion clearly so the results table can report it separately; it is
Phase 192's PROOF-02 check previewed here.

Every assertion must be checkable without either system running. If an assertion can only be
satisfied by asking a system what it did, rewrite it.

  <action>
Create `bench/acceptance/verify-predates-runs.sh`, executable. This script is the executable form
of the phase's third success criterion — without it the criterion is a claim in a document.

It must:
- For each file matching `bench/acceptance/*.sh`, find the commit that first introduced it using
  `git log --diff-filter=A --follow --format=%H|%ct -- <file> | tail -1`, and record that
  committer timestamp. Fail with a named message if any acceptance script is untracked or
  uncommitted — an uncommitted script has no provable date at all, which is worse than a late one.
- For each directory matching `bench/results/*/`, find the commit that first introduced it, and
  record that timestamp.
- Assert that every acceptance script's introducing commit timestamp is strictly less than the
  earliest result directory's introducing commit timestamp. On violation, print which script and
  which result directory, with both dates in a readable form, and exit non-zero.
- When no `bench/results/*/` directory exists yet, exit 0 with the message that no runs have been
  recorded so the ordering holds vacuously. State the count of acceptance scripts checked, so a
  vacuous pass is visibly vacuous rather than looking like a full check.
- Also assert that no acceptance script has been modified after the first result directory was
  committed, using `git log --format=%ct -- <file> | head -1` for the most recent change. An
  acceptance script rewritten after seeing results is the same failure as one written after them,
  and checking only creation dates would miss it.

Add a `make bench-acceptance-order` target to the Makefile invoking this script.

Create `bench/acceptance/README.md` explaining, in plain English for a non-technical reader: what
these scripts are (an independent judge that decides whether each task was actually done, by
running the resulting code rather than by reading anyone's report), why they were written before
any run happened, and how anyone can check that ordering claim themselves with one command. Name
the command. Include the rule that these scripts deliberately avoid the words either system uses
for its own checking, and say why in one sentence.
  </action>
