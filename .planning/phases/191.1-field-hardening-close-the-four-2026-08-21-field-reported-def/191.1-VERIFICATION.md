## Notable Findings (Residual Risk — Not Blocking, Recommend Developer Decision)

These were found through my own adversarial probing beyond what `191.1-REVIEW.md` covered.
Neither reproduces any of the four original field-reported symptoms, and neither contradicts the
literal phase contract text (which both are described precisely against below) — but both are
real, demonstrated facts about the current codebase worth a conscious accept-or-follow-up decision
rather than silence.

**1. `OutOfBandVerification` provenance is recorded but has zero downstream consumers.**
The phase contract says the ceremony must record "`verified-out-of-band` provenance" — and it
does (`cmd/build_attempt.go:270`, `record.OutOfBandVerification = &provenanceCopy`, confirmed
non-fabricated by my own injection test). But `grep -rln "OutOfBandVerification" cmd/*.go | grep -v _test`
returns only `cmd/build_attempt.go` itself — no other command (`aether status`, `aether recover`,
`aether reconcile`, provenance validators) reads this field. `cmd/status.go`'s
`renderBuildAttemptStatus` (lines 1051-1092) does not surface it. The ceremony's own report output
(`renderOutOfBandReport`) clearly labels an out-of-band run **at the moment the operator runs it**,
so the immediate operator is well informed — but nothing later (a future `aether status`, an
audit, a Phase 192-style gate) can currently distinguish a phase closed this way from one closed
by genuine worker dispatches. The comment on `TestVerifyOutOfBandNeverSynthesizesWorkerReceipts`
itself says the field's purpose is to "distinguish it from a genuine worker-verified close" — that
purpose is not yet realized anywhere outside its own write site and test.

**2. The CR-02 workspace fingerprint is, by design, blind to `.aether/data` (including
`COLONY_STATE.json`'s own phase-criteria definitions).** Confirmed both by code reading
(`pendingContinueAdvanceWorkspaceFingerprint` only inspects git HEAD/diff/status, matching
`codex.WorkspaceFingerprint`'s pre-existing convention of excluding this gitignored path) and by
my own probe (editing `COLONY_STATE.json` directly leaves the fingerprint byte-identical). This
is intentional and consistent with the established pattern in this codebase, and CR-02's own
demonstrated exploit was specifically about corrupted **code** (a hand-edited `main.go`), not a
criteria-definition mutation — so this is outside CR-02's literal scope, not a regression of it.
Flagging because the probe brief specifically asked whether the fingerprint "covers... the
criteria's own definition changing during pause," and the honest answer is no.

**3. Shipped test-suite coverage gap (not a runtime bug):** `TestPausedVerificationIsPreservedAndReplayedAfterResume`
(the "legitimate no-change resume still works" test) runs entirely inside `setupBuildFlowTest`'s
plain `t.TempDir()` — not a git checkout — so it only exercises the trivial, always-matching
non-git fallback branch of the fingerprint function. No test in the shipped suite proves the
"nothing changed" case through the **real**, git-diff-based fingerprint path that
`TestReplayRefusesWhenWorkspaceChangedBetweenPreserveAndReplay` uses for the corruption case. I
independently wrote and ran that missing case as a throwaway probe (real git checkout, zero
changes, confirmed replay still succeeds and advances) — the runtime behavior is correct, but a
future change to the fingerprint's git-diff logic could silently break the happy path with no test
catching it.

**4. Minor, informational only:** when a dispatch that self-reports a genuine failure is ALSO
named in another (evidenced, genuine) worker's `covered_task_ids`, the dispatch's own self-report
deterministically wins (confirmed: no false credit is ever granted) — but this is silent; no
violation or log line notes that a covering claim existed and was overridden. Not a defect (the
outcome is always correct), just unannounced.

None of these four items are structured as `gaps` in frontmatter because none represent a failed
must-have against the phase's literal, stated contract — each is disclosed here for the developer
to decide whether it warrants a follow-up phase/todo.
