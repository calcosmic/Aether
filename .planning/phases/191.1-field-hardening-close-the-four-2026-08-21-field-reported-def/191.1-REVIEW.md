# Phase 191.1: Code Review Report

**Reviewed:** 2026-08-21T13:16:20Z
**Depth:** standard

## Summary

Three plans, three defects, each demonstrated by execution (throwaway probe tests written against the real package, run, logged, then deleted — the working tree is clean).

**Plan 01 (covered_task_ids)** claims the credit mechanism "validates every entry against the manifest's own dispatches before granting any credit, never trusting the claim blindly." It validates that the *claimed task ID* exists in the manifest and isn't double-claimed — but never validates the *claimant*. A worker whose own submitted status is `failed`, with zero files/outputs, can still grant full `completed` credit — durably written into `COLONY_STATE.json` task statuses — to a dispatch it never touched, by naming it in `covered_task_ids`. Worse, the claimant doesn't even need to correspond to a real dispatch in the manifest at all: a completely fabricated worker name with no matching dispatch anywhere grants the same credit, with zero violation raised. This is the exact abuse vector the phase's own probe brief called out by name, and it is real. (CR-01)

**Plan 02 (pause-race preserve/replay)** is explicitly flagged in this phase's own brief as the highest-risk item, and the risk lands: `replayPendingContinueAdvance` re-applies a verification computed *before* a pause using only two conditions — same phase ID, same `BuildStartedAt` — with no check that the workspace it verified is the workspace that still exists at replay time. Corrupting the on-disk workspace between preserve and replay (no new build started, so `BuildStartedAt` never moves) still produces `advanced=true` / phase `completed`. Plan 03's own justification for existing ("real work happened outside the build pipeline — a hand edit, a pair session") is the exact scenario Plan 02's freshness model assumes cannot happen. (CR-02)

**Plan 03 (verify-out-of-band)** gets the two ratchets it names right — reachability and no-synthetic-receipts both hold under test — but `closeOutOfBandCeremony` performs two non-atomic writes (seal the build attempt, then advance the phase) with the first ungated by the currency check the second uses, and no rollback if the second fails. Pausing the colony before running `--force` on an otherwise-genuinely-passing, genuinely-stuck fixture deterministically leaves the attempt sealed `built`/`Recoverable: false`/`RecoveryCommand: ""` while the phase never advances — reproducing, via the command built to eliminate it, the exact "stuck with no honest exit" shape this whole phase exists to close. (CR-03)

Two further, lower-severity but demonstrated issues affect quality/robustness rather than correctness of the happy path (WR-01, WR-02), plus one confirmed-by-reading structural inconsistency (WR-03).

The catalog/ratchet fixture regenerations (`cmd/testdata/command_catalog.json`, `orphan_allowlist.json`, `orphan_allowlist_baseline.json`, `parity_snapshot.json`, `regression_snapshot.json`, `cmd/subcommand_reachability_ratchet_test.go`) and the schema diff (`completion-packet.schema.json`) were checked directly: every change is exactly the new `verify-out-of-band` command / `covered_task_ids` field landing consistently across all of them, with a documented allowlist rationale. No hand-edit anomalies found. Not a finding.

All three plans' own test suites pass as run (`TestVerifyOutOfBandHasNoLifecycleCaller`, `TestWrapperBundledWorkerCreditsAllCoveredTasks`, `TestForcedRedispatchAfterBuiltIsNotADeadlock`, `TestPausedVerificationIsPreservedAndReplayedAfterResume`, `TestCriterionCheckReportsOutcomeNotRawCommandText`, and the rest of the phase's named tests) — none of them exercise the abuse angles below, which is exactly why they pass while the underlying mechanism is exploitable.

## Critical Issues

### CR-01: `covered_task_ids` grants task credit from a claimant with no evidence and no manifest identity

**File:** `cmd/codex_build_finalize.go:1264-1330`
**Issue:**

The doc comment on `codexExternalBuildWorkerResult.CoveredTaskIDs` (`cmd/codex_build_finalize.go:73-88`) states: "mergeExternalBuildResults validates every entry against the manifest's own dispatches before granting any credit, never trusting the claim blindly." That's only half true. The `coveredBy` resolution pass (`cmd/codex_build_finalize.go:1264-1299`) validates that the *claimed task ID* resolves to a real manifest dispatch and isn't claimed twice — but it never checks:

1. Whether the covering result's own `Status` is a genuine success (`completed`/`manually-reconciled`). A `failed`, `blocked`, or `timeout` result's `covered_task_ids` claim is honored identically to a completed one.
2. Whether the covering result carries any evidence at all (`Outputs`/`FilesCreated`/`FilesModified`/`TestsWritten`).
3. Whether the covering result's `Name` corresponds to any dispatch in the manifest in the first place — an entirely fabricated worker name with no matching dispatch anywhere still resolves and grants credit.

The credit is then applied unconditionally at `cmd/codex_build_finalize.go:1316-1330`: `dispatch.Status = "completed"` for the covered dispatch, with **zero** contract violation raised. That `dispatches` slice is what `reconcileCompletedBuildTasks` (`cmd/codex_build.go:2189-2208`) uses to mark the matching task `colony.TaskCompleted` in `COLONY_STATE.json` — durably, via the real `runCodexBuildFinalize` entrypoint, not a synthetic path. `validateBuildProvenanceForManifest`/`validateBuildProvenance` (`cmd/provenance.go:14-33`) does not catch this either: it only requires that *some* worker in the whole packet reported real file changes, phase-wide — it says nothing about the specific dispatch that just received fabricated credit.

**DEMONSTRATED** by two throwaway probes (written against the real `mergeExternalBuildResults`, run via `go test`, logged, then deleted — tree confirmed clean afterward):

- A 2-dispatch manifest; the covering worker's own submitted result has `Status: "failed"` and zero `Outputs`/`FilesCreated`/`FilesModified`/`TestsWritten`, but names the other (never-submitted) dispatch in `covered_task_ids`. Result: `violations: []`, and the other dispatch is credited `status="completed"` with `summary="covered by Hammer-12 via covered_task_ids"` — while `Hammer-12` itself is `status="failed"`.
- Same manifest, but instead of using a real dispatch's name, the packet includes one extra worker result named `"totally-fabricated-ghost-worker"` (matching no dispatch in the manifest at all) with `Status: "completed"` and `covered_task_ids` naming a real, otherwise-unclaimed dispatch. Result: `violations: []`, and that dispatch is credited `status="completed"` with `summary="covered by totally-fabricated-ghost-worker via covered_task_ids"`.

Existing test `TestWrapperBundledWorkerCreditsAllCoveredTasks` already confirms (for the legitimate case) that this credit propagates all the way to `finalState.Plan.Phases[0].Tasks[...].Status == colony.TaskCompleted` through the full `runCodexBuildFinalize` path — so the same propagation applies to both fabricated cases above; only the *input* differs, the mechanism recorded a Task as `TaskCompleted` is identical either way.

**Fix:** Before adding an entry to `coveredBy`, require the covering result to be a genuine success with real evidence, and require it to correspond to a resolved manifest dispatch:

```go
for _, result := range results {
    if len(result.CoveredTaskIDs) == 0 {
        continue
    }
    coveringName := result.effectiveName()
    // Only a worker whose OWN status is a real success may grant credit to
    // another dispatch, and only when it corresponds to a real dispatch in
    // this manifest -- never a fabricated/unmatched name.
    if normalizeExternalBuildStatus(result.Status) != "completed" &&
        normalizeExternalBuildStatus(result.Status) != "manually-reconciled" {
        continue // (or: emit a distinct violation naming the disqualifying status)
    }
    if len(result.Outputs) == 0 && len(result.FilesCreated) == 0 &&
        len(result.FilesModified) == 0 && len(result.TestsWritten) == 0 {
        continue // (or: emit a distinct violation -- no evidence to honestly credit with)
    }
    if _, existsInManifest := resolvedDispatchNameSet[coveringName]; !existsInManifest {
        continue // (or: emit a distinct violation naming the unrecognized claimant)
    }
    // ... existing task-ID resolution unchanged from here
}
```
Prefer emitting a named violation (e.g. `worker.covered_task_credit_unevidenced`) over silently skipping, so a buggy/malicious packet is refused with an actionable reason rather than quietly losing the credit — consistent with this phase's own D-06 "no silent drop" principle applied everywhere else in this file.

### CR-02: pause-race replay has no freshness check against actual disk/workspace state

**File:** `cmd/advance_phase.go:191-215` (`loadPendingContinueAdvance`), `cmd/advance_phase.go:246-329` (`replayPendingContinueAdvance`); call sites `cmd/codex_continue.go:665-676` and `cmd/codex_continue_finalize.go:179-190`
**Issue:**

`replayPendingContinueAdvance` re-applies a `pendingContinueAdvanceRecord.Payload` (a verification/assessment/gates/review bundle computed *before* a pause) purely on the strength of `loadPendingContinueAdvance`'s identity check: `record.PhaseID == phaseID && runtimeStartedAtMatches(record.BuildStartedAt, currentBuildStartedAt)`. Neither this check nor `advancePhase`'s own `validateRuntimeStateStillCurrent` (`cmd/codex_build.go:2667-2692`) touches the filesystem, hashes an artifact, or fingerprints the workspace — they only compare fields already present in `COLONY_STATE.json` (`Paused`, `CurrentPhase`, phase status, `BuildStartedAt`). `BuildStartedAt` only changes when a *new build* is initiated through the runtime; it is blind to any other change to the tree.

This is a direct contradiction of this same phase's own Plan 03 justification: FIELD-05 exists specifically because "real work happened OUTSIDE the build pipeline entirely (a hand edit, a pair session)" (`cmd/verify_out_of_band.go:16-24`). Plan 02's freshness model assumes that scenario cannot occur between a preserved verification and its replay.

**DEMONSTRATED** by a throwaway probe using the production fixtures verbatim (`pauseRaceFixture`, `withTestWorkspace`, `advanceExternalContinue`, `replayPendingContinueAdvance` — the exact functions `runCodexContinue`/`runCodexContinueFinalize` call in production):

1. Colony paused mid-continue; a passing verification payload is preserved via the real `advanceExternalContinue` → `preserveIfPausedSupersession` path.
2. Between preserve and replay, `main.go` in the fixture workspace is overwritten with `"this is not valid go source }{\n"` — a real, live syntax error. No new build is started, so `BuildStartedAt` is untouched.
3. Colony resumed (`Paused = false`); `replayPendingContinueAdvance` is called exactly as `runCodexContinueFinalize`/`runCodexContinue` call it in production.
4. Result: `advanced=true`, `phase.Status=completed`. The broken `main.go` was never re-examined; the log line confirms: *"main.go on disk is now invalid Go syntax and was NEVER re-checked by the replay path."*

**Fix:** Bind the preserved payload to a content fingerprint of the workspace at preservation time (this codebase already has the primitive — `codex.WorkspaceFingerprint`, used identically for this exact purpose in `beginBuildAttempt`, `cmd/build_attempt.go:133`), and re-check that fingerprint at replay time before trusting the payload:

```go
type pendingContinueAdvanceRecord struct {
    PhaseID              int
    BuildStartedAt       *time.Time
    WorkspaceFingerprint string // new: codex.WorkspaceFingerprint(root) at preserve time
    ...
}
```
`loadPendingContinueAdvance` should reject (discard, same as the existing stale-identity path) a record whose `WorkspaceFingerprint` no longer matches a fresh `codex.WorkspaceFingerprint(root)` computed at replay time, falling through to the caller's ordinary fresh-verification path exactly as a phase/build identity mismatch already does.

### CR-03: `closeOutOfBandCeremony` can irreversibly seal a build attempt without ever advancing the phase

**File:** `cmd/verify_out_of_band.go:367-403`
**Issue:**

`closeOutOfBandCeremony` performs two separate, non-atomic mutations in sequence:

```go
attemptClosed := false
if hasAttempt && strings.TrimSpace(attemptRecord.Status) != buildAttemptBuilt {
    if err := closeBuildAttemptOutOfBand(attemptRel, provenance); err != nil {   // mutation 1
        return nil, err
    }
    attemptClosed = true
}
advanceResult, err := advancePhase(advancePhaseParams{ ... })                    // mutation 2
if err != nil {
    return nil, err   // mutation 1 already happened and is NOT rolled back
}
```

`closeBuildAttemptOutOfBand` (`cmd/build_attempt.go:253-281`) sets `Status: buildAttemptBuilt`, `Recoverable: false`, and **clears** `RecoveryCommand: ""` — unconditionally, with no check of `state.Paused` or any of the other currency conditions `advancePhase`'s own `validateRuntimeStateStillCurrent` applies moments later. If `advancePhase` then refuses (paused colony, phase status changed, a genuinely different build in flight — any of the same reasons this phase's own supersession machinery exists to catch), the build attempt is left permanently sealed and stripped of its only recorded recovery path, while `COLONY_STATE.json` never advances the phase at all. This is precisely the "stuck build with no honest exit" failure mode FIELD-05 exists to eliminate — recreated by the command built to close it.

**DEMONSTRATED**, deterministically (no race required): using the field-reproduction fixture (`setupOutOfBandStuckFixture`, the same "stuck, no worker ever ran" shape `TestVerifyOutOfBandClosesFieldReportedStuckState` uses) with a genuinely-passing bound phase:

1. Before: `status="awaiting_external" recoverable=true recovery_command="aether build 1 --force"`.
2. Colony is paused directly on disk (an entirely ordinary operational state — pausing a running colony is a first-class, documented workflow).
3. `executeVerifyOutOfBand(ctx, 1, force=true, ...)` is called. Fresh evidence gathering genuinely passes (`report.Passed=true`), but the call still returns an error: `"runtime state superseded for phase 1: colony is paused"`.
4. After: `status="built" recoverable=false recovery_command="" out_of_band=true`.

The colony being paused happens to self-heal on a later retry once resumed (a fresh `executeVerifyOutOfBand` call reloads state and re-checks currency), but any *permanent* `advancePhase` refusal reason (e.g. the phase no longer present, or its status changed to something that will never again satisfy `PhaseInProgress`) leaves this stuck forever, and even in the self-healing window the attempt is left `Recoverable: false` with no recovery command while it has not, in fact, completed — an honesty gap in the exact record this command exists to make trustworthy.

**Fix:** Either (a) call `advancePhase` first and only close the build attempt after it succeeds, reusing `advanceResult` to build `provenance` if needed, or (b) gate `closeBuildAttemptOutOfBand` behind the same currency pre-check `advancePhase` performs (at minimum `!state.Paused`), or (c) make the two writes transactional by rolling `closeBuildAttemptOutOfBand`'s mutation back (or re-opening the attempt with its original `Recoverable`/`RecoveryCommand`) when the subsequent `advancePhase` call fails. Option (a) is simplest and removes the ordering hazard entirely — nothing about `provenance` depends on the attempt already being closed.

## Warnings

### WR-01: passing-check "evidence" is a static per-check tautology, not a verified outcome

**File:** `cmd/criterion_evidence.go:601-633` (specifically line 623); `successSummaryForStep`, `cmd/codex_continue.go:3966-3982`
**Issue:** FIELD-03's fix correctly stops reporting the raw configured shell command as a passing check's "evidence" (the field-reported bug: a downstream checker treated the check's own definition as the finding). But the replacement, `step.Summary`, is itself a hardcoded, per-check-name constant for every passing run — `"tests passed"`, `"build succeeded"`, `"lint passed"`, `"type checks passed"` (`successSummaryForStep`) — with no exit code, duration, test count, or file reference. The resulting evidence line, e.g. `"tests check passed: tests passed"`, is honest but carries zero information distinguishing this run from any other. This is exactly the regression this phase's own review brief named by name: *"a bare 'passed' with no content is honest but useless."* The failure branch (three lines below) is unaffected and still reports real detail (`"tests failed: 2 failures"`) — only the passing branch degraded.

**DEMONSTRATED** by direct reading of `successSummaryForStep` (a `switch` over four hardcoded strings) plus this phase's own `TestCriterionCheckReportsOutcomeNotRawCommandText`, whose fixture asserts the exact literal strings `"tests passed"` / `"build succeeded"` are what gets reported — confirming the content, not just the mechanism.

**Fix:** Have `runVerificationStep` (`cmd/codex_continue.go:2929+`) compose a summary that includes something that varies per run — exit code, elapsed time, or a trailing line of real command output — rather than a name-keyed constant, so the evidence trail can actually distinguish "this run passed" from "the check named tests always says tests passed."

### WR-02: `covered_task_ids` duplicate-claim detection false-positives on a legitimate same-name retry resubmission

**File:** `cmd/codex_build_finalize.go:1264-1299`
**Issue:** The `coveredBy` resolution pass iterates the raw `results` slice directly, not the same-name-deduplicated `resultByName` map the main dispatch loop builds two lines above it (which uses `preferCompletedResultOverTimeout`, `cmd/finalizer_completion_contract.go:65-76`, specifically to treat "same worker name, one `timeout` one `completed`" as a single legitimate resubmission, not a conflict). Because `coveredBy` skips that dedup, a worker that legitimately resubmits under its own identical name — first as `timeout`, then as `completed`, both carrying the same `covered_task_ids` claim — trips `violationRuleCoveredTaskDuplicate` against *itself*, producing the confusing message `"Hammer-12 and Hammer-12 both claim covered_task_ids credit for task 1.2; only one worker's result can be credited for it"` and rejecting the entire otherwise-valid packet (any violation blocks the whole packet per this file's own D-06).

**DEMONSTRATED** by a throwaway probe: a manifest with a real `covered_task_ids` claim, resubmitted a second time under the identical worker name with `Status: "timeout"` (simulating a wrapper-side resend), produced exactly this spurious violation with the self-referential message quoted above.

**Fix:** Build `coveredBy` from the same deduplicated `resultByName` map the main loop already computes (post `preferCompletedResultOverTimeout` resolution), not from the raw `results` slice, so a legitimate same-name resubmission is treated identically in both passes.

### WR-03: `verify-out-of-band`'s bound-criteria evaluator skips the validation `aether continue`'s equivalent performs

**File:** `cmd/verify_out_of_band.go:246-304` (`evaluateOutOfBandBoundCriteria`); compare `cmd/criterion_evidence.go:377-391` (`evaluatePhaseCriterionEvidence`)
**Issue:** `evaluatePhaseCriterionEvidence` (the `aether continue` evaluator) calls `validatePhaseCriterionEvidence(phase)` before evaluating any criterion (`cmd/criterion_evidence.go:391`) and refuses outright if a phase's evidence requirements are structurally malformed (e.g., a requirement with neither `Artifacts` nor `Checks`, `cmd/criterion_evidence.go:202-204`). `evaluateOutOfBandBoundCriteria` never calls this validator at all — confirmed by direct search (`validatePhaseCriterionEvidence` appears exactly twice in `criterion_evidence.go` and zero times in `verify_out_of_band.go`). In the current codebase this is structurally guarded at plan-*acceptance* time (`validateNewPlanEvidenceContract` rejects a malformed requirement before it can ever reach `COLONY_STATE.json`), so it is **INFERRED, not runtime-demonstrated** — reaching it requires a plan that bypassed that acceptance-time check (a hand-edited or migrated `COLONY_STATE.json`). But given a malformed requirement (empty `Artifacts` and empty `Checks`) did reach this evaluator, the per-criterion result in `evaluateOutOfBandBoundCriteria` (`cmd/verify_out_of_band.go:262-303`) would vacuously stay `Passed: true` with zero `Evidence` and zero `BlockingIssues`, since neither the artifact loop nor the checks loop would execute — the two commands meant to agree on what "verified" means would disagree on a state `aether continue` refuses and `verify-out-of-band --force` would silently accept.

**Fix:** Call `validatePhaseCriterionEvidence(phase)` at the top of `evaluateOutOfBandBoundCriteria` (or in `gatherOutOfBandEvidence` before dispatching to it), mirroring `evaluatePhaseCriterionEvidence`'s own first line, and surface the same refusal rather than evaluating requirements neither path should trust.
