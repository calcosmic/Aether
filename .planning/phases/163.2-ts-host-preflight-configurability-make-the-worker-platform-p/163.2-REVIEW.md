# Phase 163.2: Code Review Report

**Reviewed:** 2026-08-01
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

Reviewed the preflight cost-policy implementation: the TTL cache
(`cmd/preflight_cache.go`), the shared skip/cache/probe/record gate wired into
both dispatch chokepoints, the shared probe runner with retry and temp-dir
isolation (`pkg/codex`), the TS-host parity layer, the failure-driven cache
invalidation, and the documentation with its drift-guard tests.

The core design is sound and well-tested: the cache is keyed per platform,
failures are never cached, skip is loud and short-circuits the cache, both
chokepoints demonstrably share one trust window, and the docs tests pin the
timeout default and skip-notice wording across hosts. The invalidation
classifier correctly inspects only error values, never worker report text.

However, one finding undermines the phase's own headline deliverable: the TS
host's Node-side wrapper timeout around the Go preflight adapter is hardcoded
at 120s and does not scale with `AETHER_PREFLIGHT_TIMEOUT`. Widening the knob
past ~58s — the documented purpose of the knob — makes Node SIGTERM the Go
adapter mid-retry, reintroducing the exact 27-July failure mode the code
comment memorializes. Several secondary robustness gaps (corrupt-cache
lockout, host duration-syntax drift, missing regex-parity drift guard) are
also documented below.

## Critical Issues

### CR-01: TS host's 120s adapter timeout does not scale with AETHER_PREFLIGHT_TIMEOUT, breaking the knob it exists to support

**File:** `.aether/ts-host/src/worker-dispatch.ts:473-481`
**Issue:** `preflightGoWorkerProvider` invokes `internal-worker-adapter
--preflight` with a hardcoded `120_000` ms Node-side timeout. The comment
correctly states this "must exceed the Go side's full preflight budget
(hostedPreflightTimeout x hostedPreflightAttempts ... 45s x 2) plus startup
slack" — but the Go budget is no longer a constant. This phase made it
configurable: `resolvedPreflightTimeout()` in
`pkg/codex/platform_dispatch.go:770` honors `AETHER_PREFLIGHT_TIMEOUT`, and
the docs (`preflight-configuration.md`) advertise widening it (e.g. `90s`)
for slow hosts, claiming "one knob, one value, both hosts." With
`AETHER_PREFLIGHT_TIMEOUT=90s`, the Go adapter's worst case is 90s x 2
attempts = 180s; Node kills it at 120s, 30 seconds into the retry. The retry
then exists only on the direct-Go path — the exact regression the in-code
comment describes happening at 30s ("At 30s Node SIGTERM'd the adapter before
the Go retry could ever fire"). The user who widens the knob because their
host is slow — the knob's target audience — gets a hard "cannot start"
failure on every TS-hosted `/ant-build`, `/ant-plan`, and `/ant-continue`.
The TS host already has `resolvePreflightTimeoutMs()` exported from
`platform-dispatcher.ts`; it is simply not used here.
**Fix:**
```ts
import { resolvePreflightTimeoutMs } from "./platform-dispatcher.js";

const PREFLIGHT_ATTEMPTS = 2; // mirror hostedPreflightAttempts (pin with a docs-test like the timeout default)
const budgetMs = Math.max(
  120_000,
  resolvePreflightTimeoutMs() * PREFLIGHT_ATTEMPTS + 30_000
);
const response = await callGoJSONAsync<GoWorkerAdapterResponse>(
  opts,
  ["internal-worker-adapter", "--preflight"],
  budgetMs
);
```
Also add a test asserting the wrapper budget exceeds the resolved Go budget
times attempts (the same invariant style as `TestHostsAgreeOnPreflightDefaultBudget`).

> **RESOLVED** (commit `904994f9`): `preflightGoWorkerProvider` now sizes its
> kill budget via `resolvePreflightAdapterBudgetMs()` =
> `max(120s, resolvePreflightTimeoutMs() x PREFLIGHT_GO_ATTEMPTS + 30s)`.
> The resolver was moved to a new production module
> `src/preflight-config.ts` (re-exported from the deprecated
> `platform-dispatcher.ts`) because an existing guard test forbids
> production sources from importing the retired launcher — the review's
> suggested import would have failed that guard.
> `TestHostsAgreeOnPreflightRetryAttempts` (Go) pins the attempts mirror,
> and a TS test asserts the wrapper budget always exceeds the resolved Go
> budget times attempts. dist rebuilt and committed.

## Warnings

### WR-01: Host duration-syntax drift — the same AETHER_PREFLIGHT_TIMEOUT value parses differently in Go and TS

**File:** `.aether/ts-host/src/platform-dispatcher.ts:161-174`; `.aether/docs/preflight-configuration.md:38`
**Issue:** Go accepts full Go duration syntax (`1h`, `1m30s`, `90000ms`,
`1.5h`) via `time.ParseDuration`. The TS parser accepts only a single
`<number><ms|s|m>` token. `AETHER_PREFLIGHT_TIMEOUT=1m30s` gives Go a 90s
budget and silently gives TS the 45s default. The docs table documents the
syntax as "Go duration (e.g. `90s`, `1500ms`, `2m`)" and claims "one knob,
one value, both hosts" — a user following the documented syntax with `1h` or
`1m30s` gets divergent behavior with no warning. Today the blast radius is
limited because the production TS path delegates to Go (but see CR-01, whose
fix makes this parser production-load-bearing).
**Fix:** Extend the TS regex to at least `h` and compound tokens
(`/^((\d+(?:\.\d+)?)(ms|s|m|h))+$/` with a summing loop), or narrow the
documented syntax in the table to exactly the `ms|s|m` subset both hosts
accept, and state that other Go-valid units fall back to default on the TS
host.

> **RESOLVED** (commit `ad82ab3f`): `resolvePreflightTimeoutMs` (now in
> `preflight-config.ts`) parses Go-style durations with `ms|s|m|h` units,
> compounds included (`1m30s`, `1h30m`, `1.5h`, `2m30s500ms` all covered by
> tests), summing tokens like `time.ParseDuration`. Unparseable or
> non-positive values print one loud stderr warning (deduped per value) and
> fall back to the 45s default. The docs table now names the exact shared
> syntax and states that exotic Go units (`ns`, `us`, `µs`) count as
> malformed on the TS host.

### WR-02: A corrupt preflight-cache.json permanently disables caching — silently restoring per-dispatch probe cost

**File:** `cmd/preflight_cache.go:154-181` (with `pkg/storage/storage.go:121-137`)
**Issue:** If `.aether/data/preflight-cache.json` is ever corrupted (partial
write from a crash, manual edit), the cache never recovers:
`loadFreshPreflightCache` treats the unmarshal error as a miss (correct), but
`recordPreflightSuccess` uses `UpdateJSONAtomically`, which returns an
unmarshal error for corrupt existing content *before* the mutation runs — so
the file is never rewritten. The error is discarded at the call site
(`_ = recordPreflightSuccess(...)`, `preflight_cache.go:299`). Result: every
dispatch pays the full probe again, forever, with zero notice — the exact
per-dispatch cost regression this phase exists to remove, and the failure
mode `TestGatedPreflightSkipsProbeOnWarmCache` calls out ("the test that
fails if the per-dispatch cost ever comes back") — except no test covers the
corrupt-file path.
**Fix:** In `recordPreflightSuccess`, on an unmarshal-classified error from
`UpdateJSONAtomically`, fall back to `store.SaveJSON(preflightCachePathRel, ...)`
with a fresh single-entry file (a cache is disposable; overwriting a corrupt
one is always safe). Add a test that writes garbage bytes to the cache path
and asserts the next `recordPreflightSuccess` + `loadFreshPreflightCache`
round-trip hits.

> **RESOLVED** (commit `e8331ae2`): `recordPreflightSuccess` classifies the
> `UpdateJSONAtomically` error via `errors.As` on
> `json.SyntaxError`/`json.UnmarshalTypeError`, prints a loud one-line
> notice ("preflight: cache file ... was corrupt — rewriting it fresh"),
> and replaces the corrupt file wholesale with a fresh single-entry cache
> via `SaveJSON`. `TestPreflightCacheSelfHealsAfterCorruption` writes
> garbage bytes and asserts the record + load round-trip hits and the
> notice is printed.

### WR-03: No drift-guard test for the twin auth-failure regexes, despite the code demanding byte-identity

**File:** `cmd/preflight_cache.go:316-319`; `.aether/ts-host/src/worker-dispatch.ts:518-521`
**Issue:** `providerAuthFailureRegexp` is documented as "the Go behavioural
twin of ... isAuthError. Keep the two patterns byte-identical." They are
identical today, but nothing enforces it — unlike the sibling cross-host
contracts in this same phase, which all got drift tests
(`TestHostsAgreeOnPreflightDefaultBudget`,
`TestSkipNoticeWordingMatchesAcrossHosts`). If the patterns drift, the two
hosts disagree on which failures clear the trust window: one host re-probes,
the other trusts a stale success for up to an hour after an auth lapse. Per
this repo's own Definition of Done, a comment-only invariant is exactly the
kind of claim that decays.
**Fix:** Add a `preflight_docs_test.go`-style test that extracts the regex
literal from `cmd/preflight_cache.go` (`providerAuthFailureRegexp =
regexp.MustCompile(`...`)`) and the literal from `worker-dispatch.ts`
(`isAuthError` body), normalizes the `(?i)` prefix vs `/i` flag, and asserts
the pattern bodies are byte-identical.

> **RESOLVED** (commit `e723f7ca`): `TestAuthFailureRegexMatchesAcrossHosts`
> in `cmd/preflight_docs_test.go` compares the compiled
> `providerAuthFailureRegexp.String()` (stripped of `(?i)`) against the
> `isAuthError` regex literal extracted from `worker-dispatch.ts`
> (verifying the `/i` flag), asserting byte-identical pattern bodies. It
> also fails if either side loses its case-insensitivity flag.

### WR-04: Gate and cache tests break under ambient AETHER_SKIP_PREFLIGHT / AETHER_PREFLIGHT_CACHE_TTL environment

**File:** `cmd/preflight_gate_test.go:75-156`; `cmd/preflight_cache_test.go:137-168`; `cmd/preflight_invalidation_test.go:61-160`
**Issue:** `TestGatedPreflightProbesOnColdCache`,
`TestGatedPreflightSkipsProbeOnWarmCache`, `TestGatedPreflightNeverCachesFailure`,
`TestAuthFailedDispatchClearsTrustWindow`, and the round-trip/keying tests
all call the gate or `resolvedPreflightCacheTTL()` without pinning the two
env knobs. A developer or CI runner with `AETHER_SKIP_PREFLIGHT=1` exported
(a plausible state, since the knob targets CI) makes every gate test fail
with confusing probe-count mismatches; an ambient
`AETHER_PREFLIGHT_CACHE_TTL=1ms` makes the warm-cache tests flakily miss.
These are correctness tests for the phase's core deliverable; they should not
depend on the shell they run in.
**Fix:** In `withTestPreflightStore` (the shared fixture), add
`t.Setenv(envSkipPreflight, "")` and `t.Setenv(envPreflightCacheTTL, "")` so
every cache/gate test starts from the documented defaults.

> **RESOLVED** (commit `a67677fb`): `withTestPreflightStore` now
> `t.Setenv`'s both knobs to empty exactly as suggested. Verified by
> running the gate/cache/invalidation tests under
> `AETHER_SKIP_PREFLIGHT=1 AETHER_PREFLIGHT_CACHE_TTL=1ms` — all pass.

### WR-05: recordPreflightSuccess silently downgrades an unknown future schema to version 1 while keeping its entries

**File:** `cmd/preflight_cache.go:167-180`
**Issue:** The mutation unconditionally stamps
`file.SchemaVersion = preflightCacheSchemaVersion` over whatever was loaded.
If a newer aether binary has written a schema-version-2 cache (possibly with
a different entry shape that still partially decodes into the v1 struct), an
older binary recording a success rewrites the file as `schema_version: 1`
containing entries it only partially understood. The read path is strict
about schema (`TestPreflightCacheRejectsUnknownSchemaVersion`), but the write
path is not — mixed binary versions against one repo (a real situation with
`aether` vs `aether-dev` channels) can corrupt the newer version's cache.
**Fix:** In the mutation, if the loaded `SchemaVersion` is neither 0 (new
file) nor `preflightCacheSchemaVersion`, reset `file.Entries` to a fresh map
before stamping version 1, so an old binary replaces a future-schema file
wholesale instead of splicing v1 data into half-decoded v2 entries.

> **RESOLVED** (commit `75160bd9`): implemented the stricter variant —
> refuse-to-downgrade rather than replace-wholesale. Both write paths
> (`recordPreflightSuccess` and `clearPreflightCache`) abort the mutation
> with a sentinel error when the loaded `SchemaVersion` is neither 0 nor
> current, leaving the future-schema file byte-identical on disk and
> treating it as a cache miss. `TestPreflightCacheWritePathsRefuseFutureSchema`
> asserts the file bytes are unchanged after both operations and the load
> stays a miss.

## Info

### IN-01: Cache-hit notice reports "0m left" for a valid hit with under a minute remaining

**File:** `cmd/preflight_cache.go:223-229`
**Issue:** `int(remaining / time.Minute)` floors sub-minute remainders, so a
legitimate hit with 45s left prints `preflight: cached OK for claude, 0m left
in trust window`, which reads as an expired window.
**Fix:** Print seconds when `remaining < time.Minute` (e.g. "45s left"), or
round up to 1m.

### IN-02: Dead error-path invalidation in dispatchBatchByWaveWithVisuals — DispatchWaveWithObserver never returns a non-nil error for worker failures

**File:** `cmd/dispatch_runtime.go:89-95`
**Issue:** `codex.DispatchWaveWithObserver` (`pkg/codex/dispatch.go:132-156`)
always returns `results, nil`; worker failures are embedded in the results.
The `err != nil` branch that invalidates "using whatever results were
collected from prior successful waves" is therefore unreachable in practice
(and `dispatch.go`'s own doc comment, "Returns a non-nil error if any worker
in the wave fails," is stale). Harmless defensive code today — the
post-dispatch scan at line 102 covers all real failures — but the comment
implies an invalidation path that never executes.
**Fix:** Keep the defensive call but correct the comment (or add a unit test
that would fail if `DispatchWaveWithObserver` ever starts returning errors
without this branch invalidating).

### IN-03: Unreachable second CheckedAt parse in loadFreshPreflightCache

**File:** `cmd/preflight_cache.go:139-142`
**Issue:** `preflightCacheEntryIsFresh` already rejects entries whose
`CheckedAt` fails `time.Parse`, so the re-parse error branch immediately
after a freshness pass can never fire.
**Fix:** Have `preflightCacheEntryIsFresh` return `(fresh bool, remaining
time.Duration)` (or the parsed time) so the timestamp is parsed once and the
dead branch disappears.

### IN-04: `--simulate --preflight` writes a "fake"-platform entry into the real repo's preflight cache

**File:** `cmd/internal_worker_adapter.go:141-149`; `cmd/preflight_cache.go:161`
**Issue:** `recordPreflightSuccess` excludes only `""` and `PlatformUnknown`.
`FakeInvoker.Preflight` reports `PlatformFake`/available, so running
`aether internal-worker-adapter --simulate --preflight` outside the test
harness records a `"fake"` entry in `.aether/data/preflight-cache.json`. It
can never be confused with a real platform's window, but it is a test
artifact written into colony data — the category `/ant-data-clean` exists to
scrub.
**Fix:** Add `status.Platform == codex.PlatformFake` to the no-op guard in
`recordPreflightSuccess`.

### IN-05: Deprecated TS probe drifted to more permissive flags than the Go probe

**File:** `.aether/ts-host/src/platform-dispatcher.ts:237-263`
**Issue:** The legacy `preflightArgs` uses `--permission-mode
bypassPermissions` for Claude (Go uses `--permission-mode plan` plus
`--strict-mcp-config`) and `--sandbox workspace-write` for Codex (Go uses
`read-only`), and has no timeout retry. The module header says it is
test/forensic-only and production must not import it, and host.ts only
reaches it through test-injection hooks — but the probe posture is strictly
looser than the Go probe it claims to mirror.
**Fix:** Align the legacy probe flags with Go's read-only posture (`plan`,
`--strict-mcp-config`, `read-only`) so a future accidental re-wire cannot run
a write-capable probe, or delete the legacy probe path outright now that the
Go adapter owns preflight.
