<objective>
Give the autopilot's own build-retry loop the same "leaves a readable record on exhaustion"
discipline the worker-level recovery orchestrator already has.

`runCompatibilityAutopilot` (behind the live `aether run` command) retries a failed phase build
exactly once, after a 2-second delay. On the *second* failure it does
`_ = syncRunAutopilotState(state, opts, "paused", "")` then `return nil, err` — no count, no
first-attempt error text, no durable record of either failure. Compare this to the worker-level
recovery orchestrator (`cmd/recovery_orchestrator.go`), which already produces a structured
`RecoveryLogEntry` on every outcome including exhaustion, persisted to `recovery-log-<phase>.json`
— that system needs no change; this is a *different*, less-instrumented retry loop.

Purpose: ROADMAP criterion 5 ("an exhausted retry loop leaves a readable record of what was
tried"). Depends on 188-01 because the record is written through this phase's newly-unified
midden — which doubles as end-to-end proof that 188-01's fix actually works: a value written here
becomes visible through the same four readers 188-01 fixed.

Output: a small, directly-testable record-writing function wired into the one call site that
currently discards both failures silently.
</objective>
