Define:
  type advancePhaseParams struct {
    PhaseID                int
    ExpectedBuildStartedAt *time.Time
    AllowedStates          []colony.State
    Source                 string
    Now                    time.Time
  }
  type advancePhaseResult struct {

    Final       bool
  }
  func advancePhase(params advancePhaseParams) (advancePhaseResult, error)

Deliberately, `advancePhaseParams` does NOT include a `colony.ColonyState` or `colony.Phase` field.
This is not an oversight -- it is what makes the bug in `advanceExternalContinue` (D-05 in
188-CONTEXT.md: `updated = state`, clobbering the freshly-loaded value with a stale one)
structurally impossible to reintroduce here: there is no full stale state value in scope for the
closure to assign from. Both callers still keep their own `state`/`phase` local variables for
everything OUTSIDE this function (building `continueSupersededResult`, etc.) -- only the mutation
core itself is narrowed to scalars.

Body: call `store.UpdateJSONAtomically("COLONY_STATE.json", &updated, func() error { ... })` where
`updated` is a local `colony.ColonyState`. Inside the closure, in order:
  1. Call `validateRuntimeStateStillCurrent(updated, params.PhaseID, params.ExpectedBuildStartedAt,
     params.AllowedStates...)`; return its error immediately if non-nil.
  2. Append two events using `params.Source` in place of the hardcoded `"continue"` literal from
     the source block (`verification_passed`, `gate_passed`), same message wording otherwise.
  3. Set `updated.Plan.Phases[currentIdx].Status = colony.PhaseCompleted` where
     `currentIdx := params.PhaseID - 1`, mark all of that phase's tasks
     `colony.TaskCompleted`, clear `updated.BuildStartedAt = nil` and `updated.GateResults = nil`.
  4. Compute `final := currentIdx == len(updated.Plan.Phases)-1`. If final: set
     `updated.State = colony.StateCOMPLETED`, `updated.CurrentPhase = params.PhaseID`, append the
     `phase_completed` event (using `params.Source`). Otherwise: ready the next phase if it was
     `PhasePending`/empty, set `updated.CurrentPhase = nextIdx+1`, `nextPhase = &updated.Plan.Phases[nextIdx]`,
     `updated.State = colony.StateREADY`, `nextCommand = fmt.Sprintf("aether build %d", nextIdx+1)`,
     append the `phase_advanced` event (using `params.Source`).
  5. Set `nextCommand = "aether seal"` in the final branch (mirroring the source block exactly).

After the atomic call returns, on error: return the zero `advancePhaseResult{}` and the wrapped
error unchanged (do NOT translate `errRuntimeStateSuperseded` into anything else here -- leave that
translation to each caller, since `continueSupersededResult` needs the caller's own full `state`/
`phase` values which this function deliberately does not have). On success: return
`advancePhaseResult{Updated: updated, NextPhase: nextPhase, NextCommand: nextCommand, Final: final}, nil`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Concurrent writers to `COLONY_STATE.json` | Two Aether processes (a worker crash-recovery, a second manual command, a stale background process) can race to advance the same phase. The state file itself has no external attacker in scope, but internal race conditions between Aether's own processes are exactly what this plan defends against. |
| External-dispatch completion packet -> `advanceExternalContinue` | The `continue-finalize` path is reached from a completion packet a wrapper submits after external worker dispatch -- a longer, riskier window between when state was read and when it is committed than the in-process default continue path has. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-188-04 | Tampering | `advancePhase`'s closure silently overwrites a concurrent write with stale caller data | mitigate | Structural: `advancePhaseParams` carries no full `colony.ColonyState`/`colony.Phase` value to overwrite with; Task 1's test asserts disk content is unchanged on refusal |
| T-188-05 | Repudiation | A concurrent write between load and commit is silently discarded, with no error surfaced | mitigate | `validateRuntimeStateStillCurrent` runs inside the atomic closure on both paths now; refusal returns `errRuntimeStateSuperseded`, which both callers translate into a visible `superseded: true` result rather than swallowing |
| T-188-06 | Denial of Service | A hung `UpdateJSONAtomically` call (lock contention) stalls `continue-finalize` indefinitely | accept | Unchanged from today -- `pkg/storage`'s file-lock timeout behavior is outside this plan's scope; not introduced or worsened by this change |
