# Phase 204.2 Plan 04: Bound Native Questions and Owner Answers Summary

**Native questions now reach the existing owner decision path, and their answers enter only the requesting child's exact acknowledged context message.**

In plain English, an answer belongs to the helper and job that asked for it. An unrelated helper, a later job or an ordinary flag command cannot turn that answer into permission.

## What changed

The existing PendingDecision row gains optional NativeBinding. Its identity includes schema, goal hash, session, phase, full ExecutionBinding, attempt, launch, worker, task, child, host session, workspace, dispatch/prompt digests, stable question key and exact question digest. Row identity uses assignment plus stable question key, so two workers asking identical text remain distinct; reusing one key with changed text refuses.

Admission and answering use the existing repository mutation session, then worker mutex, then atomic pending-decision update. They revalidate current saved assignment and live state inside that boundary, sharing the established native state validator. Changed goal/session/run/plan/attempt/child and paused state cannot create or renew a question. A valid identical question or answer replay returns the original row without writes; a conflicting answer cannot replace it.

The strict `decision-answer --native-request <path>` route accepts a bounded regular file under the established temporary-request directory policy. It resolves only an existing exact question. Generic decision-answer text, discuss resolution and pending-decision resolution cannot resolve native rows. Material native questions cannot impersonate reviewer waivers or current owner checkpoints; native rows also reject protected authorization metadata.

Only a first successful answer commit invokes the existing feedback and intervention fact routines. The feedback is a content-free receipt notice, and the intervention contains the existing answered-worker-question classification. Neither copies question/answer text into globally injected signals. These retain the existing best-effort fact semantics: replay does not retry or duplicate their emission. Actual text remains in the bound decision row and targeted context renderer.

Native rows are excluded from ordinary answered-text suppression, broad clarified-intent rendering, specification clarification inputs and generic conflict scanning. The last exclusion prevents an indirect feedback leak. The conservative generic text-only guard also refuses a question matching historical native text; a current explicit non-native clarification ID remains answerable through its existing discuss route, including in a later colony. This deliberate ambiguity refusal is covered by `TestCodexNativeDecisionOrdinaryIDCompatibility`.

The registered question operation branches before the bridge's mutation locks to avoid recursive session acquisition. It returns the exact saved question, pending/answered status, terminal status and a runtime-generated temporary answer template with an empty answer. A terminal result can supply its preserved worker/task handoff open_decisions; stable keys derive from the accepted event and handoff position. Terminal result integrity is rechecked against its accepted digest. Answering a terminal question never reopens the child or changes its result journal.

Native context uses the existing answer renderer, packing budget, exact decision IDs and immutable envelope. Only a matching live child receives the native answer. After rendering, the route recomposes the selected answer set and refuses if the actionable payload changed. Reading context never acknowledges it. Only the existing successful bound send observation records delivery; replay returns the original acknowledgement and later reads omit delivered IDs.

Codex Build guidance names the implemented question, owner answer, context and ACK routes, plus pending, answered, stale, paused, resumed and terminal cases. The shared Claude/OpenCode guide catalog and exact wrapper/finalizer steps remain unchanged. The canonical Codex support source was edited; no shared installation or hub was updated.

## Shared flag compatibility

Final inspection found ordinary FlagsFile writers discarded native and protected metadata, while direct flag resolve/acknowledge and age housekeeping could alter any decision ID. With explicit orchestrator approval, the two-file extension preserves unrecognized row/envelope fields during FlagsFile persistence. Ordinary FlagEntry JSON views keep their existing projection, so this does not expose newly retained bindings or capability metadata.

Direct flag resolve/acknowledge refuse native and existing checkpoint/waiver provenance; age and verification cleanup skip those rows. All five flag mutation paths use the existing atomic store update and reload current data before mutation. A stale preliminary read or legacy fallback cannot overwrite a native answer committed in the meantime. No new lock or ledger was introduced.
