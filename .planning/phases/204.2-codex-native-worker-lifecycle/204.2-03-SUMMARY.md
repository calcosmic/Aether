# Phase 204.2 Plan 03: Exact Native Context and Acknowledged Updates Summary

**Native reservations return the full runtime prompt unchanged, while later answers travel in exact child-bound messages that become delivered only after a completed host send is observed.**

In plain English, the helper receives its saved instructions and background. Looking up a new answer does not pretend the helper received it; a successful send has to be recorded separately.

## What changed

`composeCodexNativePrompt` is consumed directly by the production reserve response. The host reads `worker.native.prompt`; the test serializes that response, decodes it as a downstream consumer, and asserts the delivered field. Capsule, exact brief bytes, matched skills and newer clarification follow their established order. Required files must be regular, stay inside the accepted workspace and match `brief_sha256`. A missing, unreadable, substituted or mismatched path refuses without reservation. Inline fallback remains valid only when no path is present. Invalid UTF-8 is refused rather than silently changed by JSON serialization. The existing strict request-file decoder accepts a valid exact 2 MiB envelope and refuses an extra byte, partial JSON or an extra JSON object without journal writes. Prompt bytes are never truncated to satisfy that request limit.

`clarifiedIntentRenderResult.DecisionIDs` tracks admitted lines after the existing integrity and budget checks. Capsule assembly captures only IDs whose complete renderer-produced byte prefix survived packing, including bounded answers; it does not search prose for IDs or rerun a second steering resolver. The manifest retains those IDs, the reserved native record retains all IDs actually included at launch, and later delta rendering excludes them before applying the same answer budget. Remaining answers can therefore advance through later deliveries even when earlier ones filled the capsule or launch delta.

The new manifest `context_scope` pins the existing normalized goal hash and exact session ID. The context route validates that scope, full ExecutionBinding, latest attempt, canonical workspace, worker/task/launch/host/child and original dispatch/prompt digests. It rechecks current scope and journal identity after rendering, and refuses newly actionable output if pause, phase, run or plan currency changes during that read. Launch/context currency shares Plan 05's explicit-native state validator, including before the first worker is reserved; the native launch gate still refuses paused state. All context reads leave the store unchanged. Cancellation-pending and terminal children cannot receive new work messages.

A context envelope includes its exact payload, SHA-256, answer IDs and complete target binding. Its delivery ID hashes that envelope with an empty delivery-ID field. Completed-send observations require matching child and payload digest plus actual observed time and source event ID/SHA. Pending, failed, missing-event, wrong-child and altered-payload sends refuse. Acknowledged envelopes and observations append to the existing native journal; the original prompt and terminal authority are untouched. Historical delivered lookups and acknowledgement replay recheck saved payload/delivery hashes, exact target fields and the matching saved acknowledgement observation. Identical acknowledgement replay returns the original receipt without timestamps or writes, including under concurrent submission. When a new answer arrives during send, acknowledgement revalidates the sent answer set; the newer answer stays pending.

`inspect --phase N` and `stage --phase N` derive the current saved binding without creating a transient request file. They are mutually exclusive with `--request`. Inspect remains read-only. Stage retains its existing delegation outside the native bridge mutation lock; Plan 05 owns shared staging's lock and completion authority. Its eligibility predicate now recognizes the existing `no_launch` terminal through `codexNativeWorkerIsTerminal`.

## Interface handoff

**Launch:** `codexBuildDispatch.BriefSHA256` is populated when brief files are prepared. `codexBuildManifest.ContextDecisionIDs` and `ContextScope` accompany the saved capsule. `codexNativeWorkerBinding.ContextDecisionIDs` records the IDs delivered in its immutable launch prompt. Existing reserved prompt/result receipts remain the authority; reservation replay does not recompose them. Legacy unreserved manifests without brief identity cannot silently adopt changed bytes. Legacy manifests without context scope cannot receive newly asserted scoped deltas.

**Read:** call `codex-native-worker context --request <file>` with the existing schema/phase/execution binding, worker_name, task_id, launch_id, host_session_id, child_id, dispatch_sha256, prompt_sha256 and exact canonical workspace. Response `context_status` is `awaiting_delivery`, `no_updates` or `delivered`. An optional `context_delivery_id` looks up the exact acknowledged envelope or checks the still-current pending envelope. A read never sends or acknowledges anything.

**Send and acknowledge:** the host sends `context_delivery.payload` unchanged to `context_delivery.child_id` using its native message operation. Only after the host observes that send completed, call `observe` with the same binding, `observation_status: "context_delivered"`, the exact `context_delivery`, `context_send: {status: "completed", child_id, message_sha256}`, `observed_at`, `source_event_id` and `source_event_sha256`. `message_sha256` equals the envelope's `payload_sha256`. Failed or merely queued sends remain unacknowledged. The receipt retains `context_delivery_id` and `context_payload_sha256`; `Native.ContextDeliveries` saves the exact envelope/observation and `ContextDeliveryIDs` lists successful deliveries. Host activity projection skips context-only observations rather than claiming the worker is doing useful work.

**Plan 04 hook:** `renderCodexNativeContextAnswers(manifest, dispatch, launch, child, excluded, onlyIDs)` currently uses the existing ordinary scoped-decision resolver and integrity renderer. `onlyIDs == nil` means normal pending-answer packing; an explicit set revalidates an already-sent envelope during acknowledgement. Extend this hook with the exact protected native-question renderer and keep its answer IDs stable. Protected question admission, owner-answer authorization and installed guide/message orchestration belong to Plan 04.

**Plans 05/06:** phase-only inspect/stage flags are implemented. Stage uses the shared staging authority and does not hold the bridge session/mutex around it. Manifest metadata is additive; completion-schema generation may need regeneration after integrating these fields. No finalizer/journal authority files were edited. Plan 05 must be integrated with this plan because `validateCodexNativeLaunchCurrency` calls its `validateCodexNativeAttemptState(record, state)`; the explicit native helper validates goal/run/plan even before a native worker exists.
