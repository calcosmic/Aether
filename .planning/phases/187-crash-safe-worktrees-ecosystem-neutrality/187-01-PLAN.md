  <action>
Create a new file `cmd/worktree_safety.go` in package `cmd`.

Define an exported-within-package result type `worktreeSafety` with fields:
`Safe bool`, `Reason string`, `DirtyFileCount int`, `UnmergedCommitCount int`,
`Path string`, `Branch string`.

Define `func worktreeDestructionSafety(root string, entry colony.WorktreeEntry) worktreeSafety`.
It answers exactly one question: may this worktree be destroyed without losing work?

Evaluation order, returning on the first condition that matches:

1. Resolve the absolute path: if `entry.Path` is not absolute, join it onto `root`.
2. If the path does not exist on disk (`os.Stat` returns `os.IsNotExist`), return
   Safe=true with Reason "worktree path no longer exists on disk". A missing directory
   holds no work. This mirrors the existing short-circuit at
   `cmd/codex_build_worktree.go:1070`.
3. Run `git -C <absPath> status --porcelain`. If the command errors, return Safe=false
   with Reason "cannot determine whether this worktree has unsaved changes" — a guard
   that cannot see must refuse, never assume safe. If output after `strings.TrimSpace`
   is non-empty, set DirtyFileCount to the number of newline-separated lines and return
   Safe=false with Reason naming the count of uncommitted changes.
4. Check for unmerged commits. Determine the integration branch by trying
   `git -C <root> rev-parse --verify main` and falling back to `master`, matching the
   checkout fallback already used at `cmd/codex_build_worktree.go:1146-1154`. Then run
   `git -C <root> rev-list --count <integrationBranch>..<entry.Branch>`. If that command
   errors, return Safe=false with Reason "cannot determine whether this branch holds
   unmerged commits". If the parsed count is greater than zero, set UnmergedCommitCount
   and return Safe=false with Reason naming the count of commits not yet on the
   integration branch.
5. Otherwise return Safe=true with Reason "clean and fully merged".

Two rules this function must obey, both stated as code comments so a future reader
cannot undo them by accident:

- It MUST NOT skip `colony.WorktreeOrphaned` entries. `scanDirtyWorktrees`
  (`cmd/recover_scanner.go:269`) skips them, which is correct for a read-only health
  report but catastrophic for a pre-destruction gate: `preserveWorktree` in
  `reconcileWorktreeWave` (`cmd/codex_build_worktree.go:443`) marks an entry Orphaned
  specifically to protect it, and `gcOrphanedWorktrees` then treats Orphaned as
  delete-me. Inheriting the skip would blind the guard on the exact case it exists for.
- Every failure to determine an answer resolves to Safe=false. Uncertainty is not
  permission.

Use `context.WithTimeout(context.Background(), GitTimeout)` for each git invocation,
matching `removeGitWorktree`'s existing timeout discipline.

Note on the audit's own caveat: `.planning/WORKTREE-BRANCH-AUDIT-2026-07-27.md` records
that `git rev-list --count` overstates loss for diverged lineage. That is acceptable
here — this guard is deliberately conservative, and over-preserving is the safe error
direction under D-01. Record that reasoning in a comment so a later reader does not
"fix" it into a lossy check.

Extend `cmd/worktree_safety.go` with the preservation half.

Add `func preserveWorktreeWork(root string, entry colony.WorktreeEntry, safety worktreeSafety) (preserved bool, detail string, err error)`.

Behaviour, per D-01 ("preserves the work and continues — it does not delete, and it does
not stop and ask"):

- If `safety.Safe` is true, return `(false, "", nil)` immediately. There is nothing to
  preserve and this function must never act on a clean worktree.
- If `safety.DirtyFileCount > 0`, run `git -C <absPath> stash --include-untracked` —
  the exact command already used and tested at `cmd/recover_repair.go:645`. On success,
  set detail to a phrase naming the file count and that the changes are stashed on the
  worktree's own branch. On failure, return the error wrapped with context; the caller
  must then still not destroy anything.
- If only `safety.UnmergedCommitCount > 0` (branch holds commits, working tree clean),
  there is nothing to stash — the commits are already durable on the branch. Return
  `(true, ...)` with detail naming the commit count and the branch that holds them. The
  preservation action here is the decision NOT to run `branch -D`; say so.
- If the safety reason was an inability to determine state, preserve by doing nothing
  destructive and return `(true, ...)` with detail explaining that Aether could not
  check the worktree so it left it alone.

Never call `removeGitWorktree`, `git branch -D`, or `git worktree remove` from this
function. Never read from stdin — `confirmRepair`'s interactive prompt shape is
explicitly rejected by D-01 because it blocks unattended runs.

Add `func describeWorktreePreservation(safety worktreeSafety, detail string) string`
returning a single plain-English line for a non-technical reader. It must name the
branch, say the work was kept rather than deleted, and say how to get it back. Required
content, per D-02 and per this repo's non-technical-owner rule in CLAUDE.md:
  - the branch name
  - the words "kept" (or "keeping") — never "cleaned", never "pruned"
  - the recovery instruction naming the command `aether recover`
Do not use the words "orphaned", "GC", "ratchet", "residue" in this string — those are
repo-invented terms the owner does not know.

Add `func reportWorktreePreservation(safety worktreeSafety, detail string)` which writes
that line to `os.Stderr` with `fmt.Fprintf`, matching the existing precedent at
`cmd/init_cmd.go:202`. It must write unconditionally on every call — D-02 states
"reported in plain language on every occurrence" and "silent handling is prohibited on
this path". Add a code comment recording that a caller which swallows this report
reintroduces the defect that let ten branches strand unnoticed between May and July 2026.

Finally add `const worktreeDestructionCategory = "worktree_destruction"` and extend
`isDestructiveCategory` in `cmd/recover_repair.go` is NOT in scope here — instead add a
sibling helper `func isDestructiveWorktreeAction(action string) bool` in this file
returning true for `worktreeDestructionCategory`, so plan 03's named destruction command
can classify itself the same way `recover` classifies `dirty_worktree`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Aether process → user's git repository | Aether executes destructive git commands against work the user has not committed or pushed. This is the boundary the whole phase exists to defend. |
| colony state JSON → destruction decision | A state entry's `Path` and `Branch` fields are interpolated into git commands that delete things. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-187-01 | Denial of Service (data loss) | `worktreeDestructionSafety` returning Safe=true on an error path | mitigate | Every git-command error branch returns `Safe: false`; asserted by `TestWorktreeSafetyRefusesWhenGitCannotAnswer` |
| T-187-02 | Tampering | `entry.Path` / `entry.Branch` from COLONY_STATE.json passed to `exec.Command` | mitigate | Use `exec.CommandContext` with separate argv elements (never a shell string), matching existing `removeGitWorktree` practice — no shell interpolation is possible |
| T-187-03 | Denial of Service | A hung `git status` or `git rev-list` in a large worktree stalls resume/continue | mitigate | Wrap every git call in `context.WithTimeout(..., GitTimeout)`; a timeout resolves to Safe=false, so a hang preserves rather than destroys |
| T-187-04 | Repudiation | Preservation happens silently and the user never learns work was kept | mitigate | `reportWorktreePreservation` writes to stderr unconditionally on every occurrence (D-02); no conditional may wrap it |
</threat_model>
