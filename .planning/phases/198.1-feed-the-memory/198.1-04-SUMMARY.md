# Phase 198.1 Plan 04: Feed the Memory (feedback and redirect signals) Summary

**Finishing a phase, answering a worker's question, and a repeated failure now each write into the same notes file (pheromones.json) every worker prompt already reads from -- and a valuable note survives its own expiry into the shared long-term memory file instead of vanishing.**

## Performance

- **Duration:** ~75 min
- **Completed:** 2026-08-30T11:15:45Z
- **Tasks:** 3
- **Files modified:** 11 (2 created, 9 modified)

## Accomplishments

- Finishing a phase (via `aether continue`) now leaves one note naming the phase and what it produced for memory -- lessons captured, failures recorded, instincts promoted -- built from the exact numbers `runPhaseEndConsolidation`'s own summary reports, never a separate guess.
- Answering a worker's open question (`aether decision-answer`) now leaves one note carrying the question and the owner's own exact answer, written only after the answer is durably saved -- a failed save produces no note.
- Three or more failures of the same kind piling up unacknowledged in the failure log now automatically produce one "don't do this" note naming the newest failure's own words; a fourth occurrence of the same failure reinforces that same note instead of writing a second one, and acknowledging the entries clears the count.
- A note worth keeping -- a hard-constraint note, or any note the colony independently re-emitted -- now survives its own expiry into the shared, cross-project long-term memory file, in the exact shape the existing `eternal-store` command already writes; a one-off note that nobody echoed is not kept, and the hub being unwritable never blocks the expiry itself.
- Along the way, proving this against the real test suite (not a hand-typed fixture) surfaced and fixed a genuine pre-existing gap: the closing screen every `aether build`/`continue`/`recover` command ends with never actually showed the project's current notes, even though a separate section earlier in the same screen did -- so a note this plan writes now is visible in the actual screen the owner reads, not just in a later re-check.

### Auto-fixed Issues

**1. [Rule 1 - Bug] `recordDecisionAnswer`'s new note emission silently repaired a corrupted pheromones.json before the seal ceremony's curation sentinel could detect it**
- **Found during:** `go test ./cmd/ -run 'TestSeal' -count=1` regression pass
- **Issue:** `recordDecisionAnswer` also backs the seal ceremony's "finish anyway?" confirmation gate (a caller the plan's own read_first section did not name). `TestSealDoesNotDoublePromoteOnCurationFailure` deliberately corrupts `pheromones.json` to prove the curation sentinel detects it and aborts; the confirmation-answer step now runs before the sentinel and, via the new note emission, loaded-then-saved `pheromones.json` -- which silently repairs a corrupt file back to valid JSON as a side effect of the fallback-on-load-failure pattern `writePheromoneSignal` inherited unchanged from the original CLI. The sentinel then found nothing corrupt.
- **Fix:** `emitDecisionFeedback`'s call inside `recordDecisionAnswer` is skipped when `source` has a `"seal-"` prefix -- the seal confirmation gate is an internal system checkpoint, not a worker's question, so it was never actually in scope for this plan's "answering a worker's open question" deliverable.
- **Files modified:** cmd/handoff_decisions_cmd.go
- **Verification:** `TestSealDoesNotDoublePromoteOnCurationFailure` and the full `TestSeal*` suite pass; `TestAnsweredQuestionLeavesANoteCarryingTheAnswer` (source `"worker-handoff"`) still passes unaffected.
- **Committed in:** `4dab554a`

**2. [Rule 1 - Bug] The shared closing card never showed the project's current notes, so a note this plan writes never appeared in the screen it was written during**
- **Found during:** `go test ./cmd/ -count=1` full regression pass
- **Issue:** `TestWorkLoopCardsComeFromTheResolver`'s "checking the work" case failed: the card the resolver produces from a fresh read of the project (via `loadNextActionInputForCommand`, which does read live signals) contained a "Your standing instructions" section with this plan's new phase-completion note, but the actual printed closing screen (built via `nextActionInputForState`, a lighter-weight builder deliberately documented as skipping "display-only" signal reads) did not. This was a pre-existing gap invisible before this plan because no `continue` run had ever written a pheromone signal to surface it.
- **Fix:** `nextActionInputForState` now also calls `extractSignalTexts(8)`, matching `loadNextActionInputForCommand`'s behaviour, since every caller of this function is itself the closing card a finished command prints once -- not a hot loop the original "wasted reads" comment was guarding against.
- **Files modified:** cmd/codex_visuals.go
- **Verification:** `TestWorkLoopCardsComeFromTheResolver` and `TestGoldenContinueVisualOutput` pass (golden fixture regenerated and confirmed stable across 3 repeated runs); the broader `TestNextAction|TestEveryDeciderAgreesOnTheNextCommand|TestGolden|TestLifecycle|TestWorkLoop` test group passes.
- **Committed in:** `4dab554a`

**3. [Rule 3 - Blocking] `extractSignalTexts` panicked on a nil store**
- **Found during:** Full `go test ./cmd/ -count=1` regression pass, after fix #2 above
- **Issue:** `TestContinueFinalPhaseCelebratesProjectComplete` calls `renderContinueVisual` directly without setting the package-level `store` global; `extractSignalTexts` (now reachable from `nextActionInputForState`) called `store.LoadJSON` unconditionally, causing a nil-pointer panic.
- **Fix:** Added a `store == nil` guard returning `nil` at the top of `extractSignalTexts`, matching the pattern every other store-reading helper in this package already uses.
- **Files modified:** cmd/context.go
- **Verification:** `TestContinueFinalPhaseCelebratesProjectComplete` passes; full `cmd` package suite (244s) passes clean.
- **Committed in:** `4dab554a`
