# Phase 198.1 Plan 01: Feed the Memory (build half) Summary

**Build workers' failures and lessons now write to the same failure log (midden.json) and observation log (learning-observations.json) `aether memory-capture` already uses, from one shared boundary both build lanes call.**

## Performance

- **Duration:** ~55 min
- **Started:** 2026-08-29T~22:15Z (approximate; not captured at session start)
- **Completed:** 2026-08-29T23:12:24Z
- **Tasks:** 3
- **Files modified:** 5 (2 created, 3 modified)

## Accomplishments

- A build worker whose merged status is a failure status now leaves exactly one deduped entry in `midden.json`, whose message begins with the worker's own reported reason (first blocker, else first known failure, else summary) — verified against a completion packet decoded by the real `loadExternalBuildCompletion` parser, never a hand-built struct literal.
- That failure sentence now reaches the next worker's build brief verbatim: `composeBuildManifestBrief`'s self-contained caller (the one caller with no accompanying colony-prime capsule of its own) gained a "Recent Failures" section mirroring the capsule's existing rendering.
- A build worker's `do_not_repeat` and `next_worker_instructions` handoff sentences are now captured as observations (`redirect` / `pattern` wisdom types) through the exact same `learn.NewObservationService` `aether memory-capture` uses — no second, parallel store.
- Both the wrapper-driven (delegate) and in-process (native) build dispatch loops now call the same `recordDispatchWorkerOutcome` function, proved by a structural AST guard rather than a comment.
- A memory-feed failure (e.g. an unwritable store) never changes what a build reports: `recordDispatchWorkerOutcome` returns exactly what the pre-existing `persistDispatchWorkerHandoff` returned, regardless of what the new memory-feed calls did.

## Files Created/Modified

- `cmd/memory_feed.go` - The shared feed boundary: `recordDispatchWorkerOutcome`, `feedMemoryFromWorkerOutcome`, midden dedup (`appendMiddenEntryOnce`), the failure message builder, the recent-failures brief section, and observation capture
- `cmd/memory_feed_test.go` - 8 tests covering both lanes, dedup, admissibility, trust scoring, and the structural one-boundary guard
- `cmd/codex_build_finalize.go` - Delegate lane: reads the merged dispatch status (trust boundary) and calls `recordDispatchWorkerOutcome`
- `cmd/codex_build.go` - Native lane calls `recordDispatchWorkerOutcome`; `composeBuildManifestBrief` renders recent midden failures for its self-contained caller
- `pkg/learn/wrappers.go` - Adds `IsAdmissibleInstinctContent`, the cmd/-facing wrapper for the memory package's admissibility gate

## Decisions Made

- **AST guard scoped to build-lane files, not the whole `cmd` package.** `cmd/codex_continue_finalize.go` carries a pre-existing call to `persistDispatchWorkerHandoff` on the continue lane, which this plan's own scope fences (198.1-CONTEXT.md) assign to a later plan in this phase ("build half of FEED-01/FEED-02"). Scanning the whole package would have failed the guard against work this plan never touched; the guard's comment documents this explicitly so a later plan wiring the continue lane knows to widen it.
- **Added a "Recent Failures" render to `composeBuildManifestBrief`'s self-contained path.** The plan's acceptance criteria required the failure sentence to reach `composeBuildManifestBrief`'s own return value, but that function never called the colony-prime capsule (`resolveCodexWorkerContext`) that already renders midden content — only the wrapper/plan-only lane gets that capsule as a separate field. `resolveRecentFailuresSection` mirrors the existing capsule renderer's shape (same truncation, same cap, same unacknowledged-only filter) for the one caller (the self-contained direct-lane manifest) that had no other channel for it.
- **`persistExternalBuildHandoffs` now reads `dispatch.Status`, not a re-normalized `result.Status`.** Per the plan's explicit instruction: the merge path (`mergeExternalBuildResults`) is the trust boundary, and re-deriving status from the raw submitted result a second time would let a worker's own unvalidated claim reach the memory-feed decision.
