# Phase 203 Classic-to-Go Synthesis

This is the mandatory pre-plan mechanism study for Phase 203 (SYNTH-05, gated by SYNTH-07). Classic feature names below — recruitment, trophallaxis, pheromone propagation — are investigation headings, not predetermined solutions. Every disposition is decided against cited historical evidence (`3a5b81c2`, `v5.4.0`) and cited current Go/TypeScript evidence read this session, per `.planning/research/v1.28-classic-synthesis-template.md`. `.aether/dreams/2026-09-01-comprehensive-aether-colony-review.md` is the authoritative owner brief per the capability ledger, but it is a local-only, gitignored file that does not exist in this worktree checkout — this study relies on the already-derived STATE.md/CONTEXT.md/RESEARCH.md/capability-ledger record of its content instead, and that substitution is itself recorded as an unresolved edge probe in §8 rather than silently assumed away.

## 1. Outcome under investigation

- **Owner-visible outcome:** a worker mid-task can ask for help and — within program-enforced limits, with no approval prompt — get a helper, visibly (one inline line per recruit, D-04), while a refused request never stalls the work and is shown both inline and in the end-of-run summary (D-03/D-06); at the end, the owner sees the whole family tree with costs (D-05); suggested and imported notes take effect only after a quick tick-to-approve pass (D-07/D-10), and a note that changed a decision is called out inline and in a summary list (D-08), with outcomes automatically strengthening good notes and quarantining bad ones under full, undoable history (D-09).
- **Operational outcome:** a typed `RecruitmentIntent` is admitted or refused atomically by Go (never the LLM) against depth, tree budget, cycle, permission, path, and cost rules layered onto the existing `spawnCanSpawnDecision` chokepoint; the child's result binds exactly once via a reused handoff-ID/transaction/receipt pattern; a `TrophallaxisPacket` carries that result to an acknowledged parent or one named follow-on and the downstream decision it produced is itself recorded; pheromone signals move from prompt-only display to outcome-governed decision inputs read through one canonical resolver.
- **Why this phase owns it:** the roadmap routes `SYNTH-05`, `CEC-07`, `BIO-01..08` here (`.planning/ROADMAP.md` Phase 203); the capability ledger routes `CAP-002`, `CAP-009`, `CAP-014`, `CAP-030`, `CAP-031`, and `CAP-058` here (`.planning/research/v1.28-classic-capability-ledger.md:142,147,150,163,164,191`).
- **Non-goals:** learning governance and outcome-backed instinct promotion belong to Phase 204 (`LEARN-03`); the build/continue/run accept-verify-advance path and its checkpoint primitive were delivered in Phase 201 and are reused here, not re-specified; Phase 202's typed live-event boundary is reused, not rebuilt; final owner-watched acceptance is Phase 205.

For dummies: today a helper working on a task cannot actually ask another helper for backup — the instructions describing that ability exist, but no helper's tool grant lets it happen, and a separate, forgotten TypeScript scheduler that WOULD govern such requests turns out to already be silently running unchecked on one delivery path. This phase's job is to make "ask for help" a real, safely-limited thing, make the safety check the ONE place both delivery paths go through, and make the notes-and-observations system (pheromones) something the program actually weighs when deciding what to do next, not just prose stapled onto a prompt.

### Core data contracts

1. **`RecruitmentIntent`** (new, superset of `spawnDecisionInput`) — parent/attempt identity, requested caste/capability, bounded objective, reason, evidence, permissions, urgency, scope, cost limit; a companion `RecruitmentDecisionResult{Allowed, Reason, Detail}` mirrors `spawnDecisionResult`'s exact convention.
2. **Extended `spawnCanSpawnDecision`** — the SAME package-level `var` function, four new ordered steps appended after the existing three, each fail-closed by the `spawnAncestorCycleReason` discipline.
3. **`RecruitmentResult`** (new, `PauseHandoff`-shaped) — `RecruitmentResultID` (HandoffID-equivalent) + `Transaction` + optional `Receipt`.
4. **`TrophallaxisPacket`** (new, `workerHandoffRecord`-shaped) — the same 16-field carrier plus an `Acknowledgement` field and a `DecisionID` join to `colony.LifecycleDecision`.
5. **One pheromone resolver** (new function, replacing `resolvePheromoneSection`'s naive read) — effective scope/expiry/strength/provenance/quarantine, called by `extractSignalTexts`, `filterSignalsForPrompt`'s callers, and `codex_plan.go`'s REDIRECT scan alike.
6. **Extended `PendingSuggestion`** — a new quarantine lifecycle state alongside the existing `Dismissed` bool; same struct, same commands, both D-07 and D-10 routed through it.
7. **Populated `AgencyReceiptEvidence`** — `ChangedDecision`/`EffectEvidence` fields (already typed) fed from real Phase 202 event evidence; `SwarmPhase202Limitation`'s call site deleted.
8. **Extended `agent.SpawnTree`** — new caste/status/cost fields for recruitment entries, same file, same parser.
9. **New event topic family** — `ceremony.recruitment.*` on the EXISTING Phase 202 `pkg/events.Bus`, never a second bus.

| Actor/component | Responsibility |
|---|---|
| Go runtime (`cmd/spawn*.go`, new `cmd/recruitment_*.go`) | Owns the single admission chokepoint (extended, not forked), atomic manifest amendment, fail-closed discipline on every new check. |

### Compatibility and migration

- `spawnDecisionInput`/`spawnDecisionResult` remain unchanged in shape; `RecruitmentIntent` is additive, sharing the same `Reason` vocabulary discipline.
- `agent.SpawnTree`'s existing readers (`spawn-tree-active`, `spawn-tree-depth`, `spawn-efficiency`) remain compatible via `omitempty` additions, per this codebase's established compatibility pattern (Phase 195/196 precedent).
- `PendingSuggestion`'s existing `Dismissed`-only consumers keep working unchanged; the new quarantine state is additive.
- No new external dependency for any BIO requirement (RESEARCH.md Standard Stack, unchanged by this study).
- `SwarmPhase202Limitation`'s type/field shape (`AgencyReceiptEvidence`) is unchanged; only its assignment site and the data feeding it change.

## Owner-facing summary

Right now, if a helper working on your project runs into something bigger than expected, it cannot actually ask another helper for backup — even though the instructions describing that ability exist, no helper is actually allowed to use the tool that would let it happen. Worse, we found a second, forgotten scheduler (a piece of code called the TypeScript host) that already grants and counts these help-requests on one of the two ways your work gets dispatched — silently, without checking the real safety limits at all. This phase's job is threefold: make "ask for help" a real, working thing with one safety authority that both delivery paths obey (never two separate counters that can disagree); make sure a refused request never stops the helper's work, and that you always see who joined the run, why, and what it cost, right in your one working window — never a second screen; and make the notes system (what the project calls "pheromones" — think of them as sticky-note reminders the system leaves itself, like "focus here" or "never do this again") something the program actually pays attention to when deciding what to do, rather than just prose it stuffs into a prompt and never checks back on. We also found that your notes are currently being read three slightly different ways in three different places — one place ignores whether a note has expired, another uses a different fade-out threshold than the other two — so a note you thought you'd retired could still be influencing decisions in one of those three spots. That gets fixed to one consistent rule everywhere.
