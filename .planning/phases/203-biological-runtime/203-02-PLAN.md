<objective>
Prove the whole biological-runtime architecture end to end on one thin path before any layer is built out: a worker asks for help, Go decides, a real child runs in a leased workspace, its result binds exactly once, and the owner sees one line about it in the terminal they are already looking at.

Purpose: this phase adds six layers that each have a plausible-looking home in the existing code. If they are built layer by layer, the first genuine architectural surprise — that the interactive lane has no child-dispatch path at all while the host lane has one that never consults Go — surfaces after ten commits instead of one. The tracer is production-quality code that stays: it is the skeleton every expansion plan builds onto, not a prototype.
Output: a working `aether recruit` command, one admitted child, one refusal, one exactly-once result, and two live event kinds on the existing model.

Reversibility: **costly** — `aether recruit` becomes a published command surface. Removing it later means the Phase 199 hidden exact-token redirect treatment rather than a clean delete. The name and flag set are therefore chosen once here, in line with the synthesis, rather than iterated.

Flagged planner assumptions (unresolved edge probes, category `unclassified`):
- BIO-01: "authenticated parent identity" is not defined anywhere. This plan assumes authentication means the parent's name resolves to a recorded spawn-tree entry whose depth is therefore authoritative — the same standard `spawn-log` already applies — and not a cryptographic identity. Surfaced, not resolved.
- BIO-02: "parent authority" as an admission dimension is not defined separately from depth and permission. This plan assumes it means the named parent exists in the ledger, is not terminal, and is the entry the depth was derived from. Surfaced, not resolved.
- BIO-03 and BIO-04 assumptions are surfaced in plans 203-04 and 203-07, which own those requirements in full.
</objective>

  <action>Wire ONE recruitment path through every layer this phase touches. One caste, one child, one happy path plus its refusal. No batching, no second call site, real error handling on the single path.

**Intent layer** — create `cmd/recruitment_intent.go` holding `recruitmentSchemaVersion` with the value `recruitment/v1` and a `recruitmentIntent` struct. For the tracer it carries only: `SchemaVersion`, `ParentName`, `ParentDepth`, `DepthIsAuthoritative`, `AttemptID`, `Caste`, `Objective`, `Reason`, `Workspace`. Plan 203-03 adds the remaining BIO-01 fields; do not add them here. Add `recruitmentDecisionResult` mirroring `spawnDecisionResult`'s exact shape — `Allowed bool`, `Reason string`, `Detail string` — with `Reason` drawn from the same fixed-string enum convention the existing codes `depth`, `budget` and `ancestor-cycle` already use.

**Public work path** — create `cmd/recruitment.go` holding `recruitCmd`, a Cobra command with `Use: "recruit"`, registered on `rootCmd` in this file's own `init()` beside its flags. Flags for the tracer: `--parent` (required), `--caste` (required), `--objective` (required), `--reason` (required), `--workspace` (optional; defaults to the colony root). Resolve the parent's authoritative depth exactly the way `spawnCanSpawnCmd` already does — `agent.NewSpawnTree(store, "spawn-tree.txt")` then `latestSpawnEntryByName` — and set `DepthIsAuthoritative` accordingly. Build a `spawnDecisionInput` from the intent and call `spawnCanSpawnDecision` unchanged; that call is the only admission decision in this command. On deny: emit the refusal live event, print the refusal with the reason class and detail, return exit status zero, and state in the output that the caller should complete the work alone. On allow: record the spawn through the existing `SpawnTree.RecordSpawn` path exactly as `spawnLogCmd` does, emit the admitted live event, then dispatch.

**Dispatch layer** — create `cmd/recruitment_dispatch.go` holding `dispatchRecruitment`. Validate the requested workspace with the existing `validateSpendContainedPath` helper against the colony root, label it `recruitment workspace`, and refuse rather than dispatch when it escapes. Resolve the platform CLI binary through the existing platform resolution used by the worker dispatcher, build the child argv, and run it with `exec.CommandContext` under a context whose deadline comes from a resolver function `resolvedRecruitmentTimeout` reading the environment variable `AETHER_RECRUIT_TIMEOUT` in Go duration syntax and defaulting to ten minutes. Call `configureWorkerCommand` on the command so the deadline is enforced against the whole process group, not just the direct child — the bare `exec.CommandContext` mistake `runAvailabilityProbeOnce`'s comment documents must not be repeated here. Set `cmd.Dir` to the validated workspace.

**Result layer** — create `cmd/recruitment_result.go` holding `recruitmentResult` and `bindRecruitmentResult`. `recruitmentResult` carries `SchemaVersion`, `RecruitmentID`, `IntentID`, `ChildName`, `ParentName`, `TerminalStatus`, `Summary`, a `colony.LifecycleTransactionReference` and an optional `*colony.LifecycleReceiptReference` — the same field shape `colony.PauseHandoff` already uses for exactly this purpose. `bindRecruitmentResult` stores results under `recruitment/results.json` through `store.UpdateJSONAtomically`; a second call carrying an already-stored `RecruitmentID` returns the stored receipt and mutates nothing. Do not invent a second idempotency mechanism. Also record the child's terminal result into the existing worker handoff store by reusing `persistDispatchWorkerHandoff`'s record shape, so the next worker brief reads the child's summary through the path that already exists.

**Live layer** — add to `pkg/events/colony_live.go` the constants `LiveTopicRecruitAdmitted` with value `live.recruit.admitted` and `LiveTopicRecruitRefused` with value `live.recruit.refused`, add both to `ColonyLiveTopics()`, and add one new string field `Reason` to `ColonyLivePayload` carrying the worker's stated why on an admission and the refusal reason class plus detail on a refusal. Add no currency-shaped field. In `cmd/live_events.go` add `emitColonyLiveRecruitAdmitted` and `emitColonyLiveRecruitRefused`, each a thin wrapper over the existing `emitColonyLive` boundary and each setting `ParentWorkerID`, `Caste`, `WorkerName`, `Workspace`, `Reason` and `Status`. Introduce no second emission function and no direct `bus.Publish` call.</action>
