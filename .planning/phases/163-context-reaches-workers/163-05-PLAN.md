<objective>
`suggest-analyze` and `suggest-approve` are fully built — 25 base patterns,
content-hash deduplication, prompt-injection sanitisation, an approve/dismiss
CLI — and `suggest-analyze` has never executed once. Its only documented call
site sat in a playbook the runtime never loaded. This is the exact failure
CLAUDE.md's Definition of Done exists to stop.

Purpose: give it a real caller at a real moment (end of build), and put its
output in front of the user once, at the end, as a list they can tick (D-11).

Output: the analysis logic factored into a callable function, one live call site
in `runCodexBuildFinalize`, and a closeout block that shows what was suggested
and how to approve it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repository contents → suggestion text → pheromone signal | Scanned code and config become prompt-affecting steering signals |
| Suggestion persistence → COLONY_STATE.json | An automated writer now runs on every build finalize |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-163-13 | Tampering / Spoofing | repository-derived suggestion text becoming a pheromone that steers future workers | mitigate | `colony.SanitizeSignalContent` stays inside `runSuggestAnalyze` (acceptance criterion greps for exactly one occurrence, in the extracted function), so every caller inherits injection rejection; suggestions require explicit user approval via `suggest-approve` before becoming active signals. |
| T-163-14 | Denial of Service | unbounded PendingSuggestions growth from running on every build | mitigate | Existing content-hash dedup against active pheromone hashes and the merge-with-existing behaviour are preserved verbatim by task 1; the change-detection threshold (5 changed files) already suppresses re-analysis on small builds. |
| T-163-15 | Availability | a suggestion-engine failure blocking a successful build | mitigate | The finalize call is explicitly non-blocking, asserted by a test that requires finalize to succeed with a zero count when analysis fails. |
</threat_model>
