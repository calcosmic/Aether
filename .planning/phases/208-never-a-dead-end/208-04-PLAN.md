<objective>
A failed check stops being a dead end: it writes the unfinished work back onto the phase as tasks
an owner can act on, always names the one command that works on them, and the status screen is
worked out from what is on disk — believing the less-finished record when the two disagree.

Purpose: `continueNextCommandForBlocked` can return the empty string today, by design
("Don't suggest looping back to continue with blockers"). That is a literal dead end: the check
fails, the screen names no way forward, and the owner is left to guess. Carrying on means the work
list moves, never the phase.

Output: recovery tasks appended idempotently to the phase, a blocked check that always names a next
command, and one shared on-disk progress resolution the status screen reads.
</objective>
