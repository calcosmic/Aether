<objective>
Make the completion-packet schema's strictness real at runtime: validate the bytes the wrapper
submitted, not a re-marshal of the struct those bytes were decoded into.

Purpose: closes VERIFICATION.md gaps 1 and 2 (requirements 163.1-REQ-1 and 163.1-REQ-2), both of
which share one root cause. `validateCompletionPacketSemantics` (cmd/codex_build_finalize.go:726)
feeds `validateCompletionPacketStructure` the output of `completionPacketAsRaw`
(cmd/codex_build_finalize.go:751) — a `json.Marshal` of the already-decoded Go struct. Any field
name the struct does not know (`files_modifed` instead of `files_modified`) is dropped by
`json.Unmarshal` in `loadExternalBuildCompletion` (cmd/codex_build_finalize.go:207) long before the
schema is consulted, so all 21 `additionalProperties: false` clauses in
`.aether/schemas/completion-packet.schema.json` are unreachable for the exact failure class the
schema exists to catch. Separately, a single wrong-typed field makes that same `json.Unmarshal`
return one unaccumulated Go error, so the packet is rejected with one problem instead of the full
batch D-05/D-06 promised.

Output: the loader keeps the submitted, envelope-unwrapped JSON value alongside the decoded struct
and stops treating a type mismatch as a fatal parse failure; structural validation consumes that
value; the stage-time path inherits the fix without a signature change because it validates the
same `completion` value.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| wrapper completion file → runtime decode | Untrusted, possibly LLM-authored JSON crosses into the finalizer; this plan widens what the runtime inspects there |
| submitted bytes → schema validator | Arbitrary nesting and size reach the compiled JSON Schema validator |
| tolerated type error → partially decoded struct | Decoding no longer aborts on a type mismatch, so downstream code may see a partially populated packet |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-163.1-40 | Tampering | A near-miss field name (`files_modifed`) silently dropping a worker's real claims, so a phantom build finalizes clean | mitigate | Structural validation now runs on the submitted bytes; `additionalProperties: false` rejects the packet naming the offending property; proven by the Task 3 CLI test |
| T-163.1-41 | Elevation of Privilege | A partially decoded struct (after a tolerated type error) reaching state mutation with zero-valued fields | mitigate | The tolerated type error always surfaces as a schema violation on the raw value, and `validateCompletionPacketSemantics` runs before any checkpoint save, attempt bind, or transition (cmd/codex_build_finalize.go:322-328); a violation list is a hard rejection |
| T-163.1-42 | Denial of Service | A deeply nested or enormous submitted packet expanding into `any` and then walked twice by the validator | accept | The completion file is operator/wrapper-supplied on the local machine through an explicit `--completion-file` path already restricted by `validateFinalizerCompletionFilePath`; no network-facing surface, and the file was already fully read and decoded before this change |
