<objective>
Make the first `aether publish` after a version bump succeed, by removing the second,
disagreeing version-resolution path inside the hub sync.

Purpose: Requirement 7. The reported symptom is "the first publish after a bump fails
verification (binary 1.0.44 does not match hub 1.0.43); rerunning succeeds," and the
roadmap framed it as a verify-before-sync ordering bug. Research disproved that framing:
`runPublish` (cmd/publish_cmd.go:36-141) already calls `setupInstallHub` at :109 and only
reads `hubVersion` at :127, after the sync. The real defect is that `setupInstallHub`
(cmd/install_cmd.go:687, :804-812) independently calls `resolveVersion(packageDir)` when
writing the legacy top-level `hubDir/version.json` — and `resolveVersion` (cmd/root.go:30-34)
prefers the ldflags `Version` baked into the binary *currently executing publish*, which on
the first run after a bump is still the OLD binary. Meanwhile `syncDirToHub` correctly copies
the bumped `.aether/version.json` to `hubDir/system/version.json`, and
`readHubVersionAtPath` (cmd/publish_cmd.go:249-256) checks the stale legacy file first. A
rerun "fixes" it only because the second invocation launches the freshly built binary.

`runPublish` already documents the correct principle at cmd/publish_cmd.go:69-72 — it just
does not enforce it on its callee.

Output: `setupInstallHub` takes the resolved version as a parameter, and a regression test
that fails when the stale in-process version reappears.
</objective>
