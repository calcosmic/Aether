<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| wrapper-spawned worker → runtime | The completion packet is untrusted input; this plan is the trusted-side validation gate |
| completion packet → colony state | Accepting a packet mutates `COLONY_STATE.json`, claims, and the attempt journal |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-163.1-06 | Tampering | Path traversal / absolute path / null byte in claimed file paths | mitigate | `validateAndNormalizeClaimPathToRoot`'s existing rejections are preserved exactly; the refactor only changes when they are reported, never whether. A test asserts each rejection class still produces a violation |
| T-163.1-07 | Tampering | Refactor accidentally converts a hard rejection into a warning, letting a bad packet through | mitigate | `validateCompletionPacketSemantics` returning any violation is an unconditional rejection before any state write; `TestCompletionPacketRejectionIsAtomic` asserts no state mutation on rejection |
| T-163.1-08 | Elevation of Privilege | Partial acceptance creating split-brain state where one worker's bad result is dropped but others commit | mitigate | D-06 atomicity: rejection happens before checkpoint save, attempt begin, digest bind, and any transition. Deliberately not implementing per-worker quarantine (deferred) |
| T-163.1-09 | Information Disclosure | Violation `Value` field echoing an absolute filesystem path back into logs | accept | The path was supplied by a local worker on the user's own machine and is exactly what the user needs to fix the claim; no third party reads this output |
| T-163.1-10 | Repudiation | A rejected packet leaving no record of why | mitigate | The structured violation list is returned in the `details` envelope, so the rejection reason is machine-readable and reproducible rather than a single prose line |
</threat_model>
