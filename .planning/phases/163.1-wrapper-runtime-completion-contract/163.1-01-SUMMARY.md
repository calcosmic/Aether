## Decisions Made

- Pinned `invopop/jsonschema` to v0.14.0 and `santhosh-tekuri/jsonschema/v6` to v6.0.2 — the latest stable versions available via `go list -m -versions` at generation time, no floating `latest`
- Left the schema's default `additionalProperties: false` behavior (invopop's default for structs) rather than opting into `AllowAdditionalProperties` — this accurately mirrors Go's own `json.Unmarshal`, which silently drops unrecognized keys; a schema that were more permissive than the runtime would misrepresent the actual contract
- Did not set `ExpandedStruct: true` on the reflector — the top-level schema is `{"$ref": "#/$defs/codexExternalBuildCompletion", "$defs": {...}}` rather than inlining the root type's properties at the top level. Both forms are valid draft 2020-12 documents and validate identically; the `$ref` form was simpler to leave at the library default and the plan's acceptance criteria don't require inlining

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] stringList's naive reflected schema rejected the doc's own worked example**
- **Found during:** Task 2 (`TestContractDocExampleValidatesAgainstSchema`)
- **Issue:** `pkg/codex/handoff.go`'s `WorkerHandoff` fields use a custom `stringList` type whose `UnmarshalJSON` deliberately accepts `null`, a bare string, or an array (documented rationale: LLM-authored worker payloads routinely send a single sentence where a list was asked for). The naive invopop/jsonschema reflection over the underlying `[]string` Kind produced a strict `{"type":"array","items":{"type":"string"}}`, which rejected the shipped worked example in `.aether/references/contracts/worker-handoff-contract.md` (`"next_worker_instructions": "Run full suite after unrelated compile failure is resolved."` — a bare string). This is exactly the drift-detection gap the plan exists to close: the schema described a *stricter* contract than the runtime actually enforces.
- **Fix:** Added `func (stringList) JSONSchema() *invopopjsonschema.Schema` implementing invopop's `customSchemaImpl` hook, returning `oneOf: [null, string, array]` — matching `UnmarshalJSON`'s three accepted shapes exactly.
- **Files modified:** `pkg/codex/string_list.go`
- **Verification:** `TestContractDocExampleValidatesAgainstSchema` passes; manually reverting the fix and re-running reproduces the original failure at `/dispatches/0/handoff/next_worker_instructions (type): got string, want array`
- **Committed in:** `44ed930b` (Task 2 commit)

**2. [Rule 3 - Blocking] Golden command-inventory snapshots needed refreshing**
- **Found during:** Task 2 (`go test ./cmd/... -count=1`, run to satisfy the plan's overall verification step)
- **Issue:** Adding the new `contract-schema` command legitimately changed the CLI's command inventory (398 → 399 commands), which three pre-existing golden-snapshot tests (`TestRegressionSnapshot`, `TestAuditCatalogGolden`, `TestPlatformParityGolden`) assert against fixture files under `cmd/testdata/`. All three failed with their own documented `-update-golden` refresh instruction.
- **Fix:** Ran each test's own `go test ... -update-golden` refresh path. Diffed each resulting change before committing: `regression_snapshot.json` changed only `command_count: 398 → 399`; `parity_snapshot.json` gained one line inserting `"contract-schema"` alphabetically into the command list; `command_catalog.json` gained the new command's catalog entry. No other counts (18 contracts, 26 castes, 33 artifacts, 7 sync pairs, 16 gates) changed.
- **Files modified:** `cmd/testdata/regression_snapshot.json`, `cmd/testdata/command_catalog.json`, `cmd/testdata/parity_snapshot.json`
- **Verification:** `go test ./cmd/... -count=1` and `go test ./... -race -count=1` both exit 0 after the refresh
- **Committed in:** `44ed930b` (Task 2 commit)
