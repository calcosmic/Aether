# Phase 163.1 Plan 03: Stage-Time Contract Parity and the Rebind Window Summary

**`stageBuildAttemptCompletion` now runs the exact same semantic validation `build-finalize` runs before it writes anything, and a non-terminal attempt (anything short of a committed `built` state) accepts a corrected packet instead of forcing a brand-new attempt.**

## Performance

- **Duration:** ~140 min
- **Started:** 2026-08-01 (worktree base reset to `c6bcdb6b`, after wave 2 merge)
- **Completed:** 2026-08-01
- **Tasks:** 2/2 completed
- **Files modified:** 4 (0 created, 4 modified)

## Accomplishments

- **Task 1 (D-07):** `stageBuildAttemptCompletion` calls `validateCompletionPacketSemantics(buildAttemptWorkspaceRoot(), completion)` right after the attempt-identity check and before `store.AtomicWrite` or `store.UpdateJSONAtomically`. A packet finalize would reject now returns `*completionContractError` from staging too, and writes absolutely nothing -- no durable completion file, no `CompletionSHA256`, no `CompletionPath`, no history entry, no status change. The `build-completion-stage` CLI handler unwraps the error via `errors.As` and passes `Violations` through `outputError`'s `details` field, exactly matching the `build-finalize` pattern plan 02 established.
- **Task 2 (D-08):** Added `buildAttemptCompletionSealed(record buildAttemptRecord) bool`, comparing against `buildAttemptBuilt` specifically (not `buildAttemptStatusTerminal`, not the `buildAttemptTerminal` constant) with an inline rationale comment explaining why -- `buildAttemptTerminal` is written mid-finalize, before the built lifecycle state actually commits, so gating on it would close the rebind window before finalize succeeded. All four digest-mismatch rejection guards (`bindBuildAttemptCompletion`, `stageBuildAttemptCompletion`'s pre-write check, its atomic closure, and `codex_build_finalize.go`'s pre-check) and the sibling `CompletionPath` guards are now gated on `buildAttemptCompletionSealed(...) &&`. A rebind while unsealed that would (defensively) change the durable completion path deletes the superseded file after the atomic update succeeds, so nothing orphaned claims to belong to the attempt.
- Correcting a rejected packet no longer requires a new attempt, a new manifest, or a `-rN`-renamed worker -- the mechanism the M4L six-round-trip session hit is closed for any attempt that hasn't finalized successfully yet.

## Decisions Made

See `key-decisions` in frontmatter: (1) semantic validation runs immediately after identity, before the digest/path guards; (2) the stale-file deletion on rebind is defensive code exercised by a seeded test, since `durableBuildCompletionPath` cannot yet produce two different paths for one attempt through the real API; (3) the pre-existing "any attempt rejects" test was retargeted at a sealed attempt rather than deleted.

## Deviations from Plan

None beyond what the plan itself anticipated in `<action>` for Task 2 ("Update the existing tests ... For each one, decide explicitly whether it was asserting 'sealed attempts reject' ... or 'any attempt rejects' ... Record which tests changed and why in the summary"). One test changed:

- `TestBuildCompletionStageRejectsChangedPacketWithoutDeletingRecoveryEvidence` (`cmd/build_attempt_external_test.go`) originally staged a packet against a non-terminal (`awaiting_external`) attempt and asserted any changed resubmit is rejected without deleting the durable file. That "any attempt" contract is precisely what D-08 removes. Retargeted: the test now transitions the attempt to `built` before attempting the changed resubmit, keeping its original intent (sealed rejection must not destroy recovery evidence already on disk) intact. The non-terminal rebind-succeeds case this test used to (incorrectly) cover now lives in `TestStageBuildAttemptCompletionAllowsRebindWhileNonTerminal`.

One observation, not a deviation: the plan's acceptance criteria describes a `grep -n 'CompletionSHA256 != "" && '` check expecting every match preceded by the sealed guard. The literal grep also matches an unrelated line (`build_attempt.go:502`, `projectedBuiltState := latest.CompletionSHA256 != "" && ...`) inside `validateBuildAttemptManifestBinding` -- a boolean projection flag, not a rejection guard, and out of this plan's scope. All four actual rejection sites are gated correctly.

## Issues Encountered

`ValidateWorkerHandoff` (pkg/codex) is deliberately lenient -- an entirely blank `WorkerHandoff{}` does not fail it (only an invalid `VerificationStatus` string does; the mandatory-content-free-handoff rejection lives in a separate, later check inside `persistExternalBuildHandoffs`, outside `validateCompletionPacketSemantics`'s accumulator). The plan's suggested corruption ("blank a worker's handoff") does not by itself produce a `handoff.valid` violation through the entrypoint this task validates. Adjusted the multi-violation test to corrupt `VerificationStatus` with an invalid value instead, which does trigger `violationRuleHandoffValid`, combined with an absolute path in `files_modified` for the second violation -- still a genuine multi-violation, still exercised through the real accumulator.
