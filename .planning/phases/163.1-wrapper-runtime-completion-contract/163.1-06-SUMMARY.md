# Phase 163.1 Plan 06: Reconcile Escape Hatch (Read-Only Artifact Evidence) Summary

**A criterion bound to a file a task legitimately never modified is now satisfiable via `aether continue --reconcile-task X --read-only-artifact X:path`, which records hash-verified evidence scoped to that exact task without ever creating a false `files_modified` claim.**

## Accomplishments

- `codexBuildArtifactEvidence` gained two runtime-set-only fields, `ReadOnly` and `ReadOnlyTaskID` — documented as never accepted from a worker's own completion packet, and locked by `TestArtifactEvidenceReadOnlyNotSettableByWorker`, which proves `attachBuildArtifactEvidence`'s wholesale rebuild from the claimed file lists strips any worker-submitted `read_only:true`.
- `evaluatePhaseCriterionEvidence`'s claimed-gate check now looks up `evidenceByPath[artifact]` before failing on an unclaimed artifact: if the recorded evidence is `ReadOnly:true` and its `ReadOnlyTaskID` exactly matches the requirement's `TaskID`, the artifact falls through into the existing (unchanged) hash-and-size match check instead of being rejected. Satisfied read-only artifacts are recorded distinguishably as `artifact %s sha256:%s (read-only)` in the criterion's evidence list.
- `criterionClaimSets` (the D-02 disjoint-claim-set boundary) is untouched — verified via `git diff` showing no edit to that function across every commit in this plan.
- New `cmd/readonly_evidence.go` adds `parseReadOnlyArtifactSpec` (splits `<task-id>:<path>`), `validateReadOnlyArtifacts` (rejects an unknown task ID with the same error shape as `validateContinueReconcileTasks`, and rejects a task ID not also passed to `--reconcile-task`), and `recordReadOnlyArtifactEvidence` (reuses `normalizeCriterionArtifactPath` and `snapshotBuildArtifact` — no hashing or path validation reimplemented, confirmed by `grep -n 'os.Open\|sha256.New' cmd/readonly_evidence.go` returning nothing).
- `--read-only-artifact` is registered on `continueCmd`, parsed at both option-construction sites, mirrored through `codexContinueOptions` → `codexContinuePlanManifest` → the finalize validation site (matching how `--reconcile-task` is mirrored), and included in the plan-equivalence comparison (`continueOptionsMatchCurrent`) so a changed set invalidates a stale plan-only manifest.
- `TestReconcileTaskReadOnlyEvidenceSatisfiesCriterion` proves the whole path end-to-end through the real `continue` CLI: without the flag, a criterion bound to an untouched file blocks on `artifact untouched_source.go was not claimed by the current build for task 1.1`; with the flag, that specific blocking issue disappears and `criteria_passed` flips to `true`; the persisted `last-build-claims.json` carries a `read_only:true` entry scoped to task `1.1` while the task's `files_modified` claim list is unchanged (no false claim manufactured); and editing the artifact after recording, then re-running `--reconcile-task` alone (without re-recording), blocks again with `changed after build evidence was recorded`.
- Regenerated two generated artifacts caught by the full `go test ./cmd/... -count=1` run: `.aether/schemas/completion-packet.schema.json` (via `aether contract-schema --write`, since `ReadOnly`/`ReadOnlyTaskID` feed the completion-packet schema) and `cmd/testdata/command_catalog.json` (via `-update-golden`, since the new `--read-only-artifact` flag changed `continueCmd`'s flag list).

## Decisions Made

- **Insertion point for recording:** placed right after `validateContinueReconcileTasks`/`validateReadOnlyArtifacts` pass and the reconcile-completed-tasks block settles `state`/`phase`/`manifest`, but before the abandoned-build detection block. This keeps recording out of early-return paths (missing manifest, blocked task set) while guaranteeing `evaluatePhaseCriterionEvidence` (called later in the same function) reads the freshly recorded evidence.
- **Re-snapshot semantics:** `recordReadOnlyArtifactEvidence` always re-hashes the current file on every call for that spec — it is not a one-time seal. This means tamper detection between two `--read-only-artifact` runs for the *same* path would just re-baseline (not block); the plan's tamper-detection acceptance criterion is satisfied by editing the file, then running `--reconcile-task` **without** re-passing `--read-only-artifact` (the durable evidence from the prior recording run is what gets checked). Documented in the test's comments so this isn't rediscovered as a bug later.
- **`--reconcile-task` always warns, and that warning always blocks:** `assessCodexContinue` unconditionally appends `"Warning: N task(s) were manually reconciled..."` to `assessment.BlockingIssues` whenever any `--reconcile-task` is passed, and `runCodexContinueGates` unconditionally folds `assessment.BlockingIssues` into `gates.BlockingIssues` regardless of individual gate outcomes. This means `aether continue --reconcile-task X` — with or without `--read-only-artifact` — is **always** `blocked:true` at the top level; this is pre-existing, orthogonal behavior (see `TestContinue_ReconcileDoesNotBypassClaims`, which this plan's Task 2 explicitly forbids weakening) that this plan does not touch. `TestReconcileTaskReadOnlyEvidenceSatisfiesCriterion` therefore proves the escape hatch by the criterion-specific blocking issue disappearing and `criteria_passed` flipping to `true`, not by asserting `blocked:false`/`advanced:true` at the top level — see "Deviations" below.
