<objective>
Stop the verification report claiming a check passed when nothing ran, and stop truncating
documented multi-line commands at their first line.

Purpose: Requirement 4 and decisions D-10/D-11, applying Phase 160 D-01's gate-vs-enrichment
rule. `runVerificationStep` (cmd/codex_continue.go:2667-2708) returns
`{Skipped:true, Passed:true}` from two separate paths — the empty-command guard and the
`isCommandUnresolvable` branch after a real exec attempt. The criterion gate
(cmd/criterion_evidence.go's `evaluateCriterionCheck` default branch) then independently
fails with "required tests check was skipped". Green step report, red gate: the user sees a
pass and a block at the same time with no actionable next step. Separately,
`extractVerificationCommands` (cmd/codex_continue.go:2451-2487) parses fenced blocks strictly
line by line, so a documented command continued across lines with a trailing backslash is
silently reduced to its first fragment.

Output: required-aware verification steps that halt loudly with configuration guidance, and
a parser that joins continuations before parsing.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository documentation → shell execution | `extractVerificationCommands` reads AGENTS.md / CLAUDE.md / codebase.md and the resolved string is executed as a shell command |
| verification result → phase advancement gate | What a step reports decides whether a phase is allowed to advance |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-163.1-21 | Elevation of Privilege | Line-continuation joining lets a crafted doc assemble a longer shell command than reviewers see on any single line | mitigate | Joining is restricted to inside fenced blocks, drops only the trailing `\`, and inserts exactly one space — it cannot introduce `;`, `&&`, or a newline that was not already in the source. The joined command is echoed in the step's `Command` field so what ran is visible in the report |
| T-163.1-22 | Elevation of Privilege | The verification command source is repository-controlled and executed with the user's privileges | accept | Pre-existing behavior unchanged by this plan; these are the user's own project docs in their own checkout, and the executed command is surfaced in `Command` |
| T-163.1-23 | Repudiation | A gate reporting `passed:true` when nothing ran, so an unverified phase advances with a clean-looking record | mitigate | This is the requirement: required checks now report `Passed:false, Blocked:true`, and the report agrees with the criterion gate. A test asserts both paths |
| T-163.1-24 | Denial of Service | Making every unresolvable check blocking, hard-stopping colonies with no lint script | mitigate | Only checks named by the phase's bound criterion requirements are required; everything else keeps the warn-and-continue behavior, per Phase 160 D-01. `TestRunVerificationStepOptionalSkipWarns` guards it |
| T-163.1-25 | Denial of Service | A pathological continuation chain (thousands of `\`-terminated lines) in a doc | accept | Bounded by the file's own line count; parsing is a single linear pass over content already fully read into memory |
