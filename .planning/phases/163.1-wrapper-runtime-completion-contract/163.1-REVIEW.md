# Phase 163.1: Code Review Report (Gap-Closure Plans 08-09)

**Reviewed:** 2026-08-01T11:20:28Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This review covers the changes landed since commit `3e74abf3` by plans 163.1-08
(submitted-bytes completion-packet validation) and 163.1-09 (read-only artifact
criterion evidence on the plan-only → continue-finalize path).

The core mechanics of both plans are sound: structural validation now inspects
the wrapper's literal submitted bytes rather than a struct re-marshal
(confirmed by tracing `loadExternalBuildCompletion` → `structuralInput()` →
`validateCompletionPacketSemantics`, and by the CLI-surface test), and criterion
evidence evaluation now runs on both external-review snapshot paths. All new
and changed tests pass (`go test ./cmd/` on the ten affected test functions,
5.9s, ok), `go vet ./cmd/` is clean, and the completion-packet schema carries
`additionalProperties: false` throughout, so tolerated type errors are reliably
caught downstream before any state mutation on the finalize path.

However, tracing the read-only evidence recording path against
`evaluatePhaseCriterionEvidence`'s hash check exposes one critical defect: the
escape hatch can silently overwrite build-time artifact evidence for artifacts
that were genuinely claimed by a task, replacing the build-time hash with a
current-content re-hash and thereby laundering post-build tampering — the exact
property the code's own comments (T-163.1-46) declare must never be destroyed.
Two edge-case regressions in the new completion-loading logic were also
confirmed empirically with an `encoding/json` probe, plus a test whose name
promises phase advancement it never asserts.

## Critical Issues

### CR-01: `--read-only-artifact` silently replaces build-time evidence for claimed artifacts, defeating post-build tamper detection

**File:** `cmd/readonly_evidence.go:108-118` (with `cmd/codex_continue_plan.go:115-119` wiring it into plan-only)
**Issue:** `recordReadOnlyArtifactEvidence` re-snapshots the artifact's CURRENT
content and then unconditionally replaces any existing `ArtifactEvidence` entry
with the same path:

```go
replaced := false
for i := range claims.ArtifactEvidence {
    if claims.ArtifactEvidence[i].Path == evidence.Path {
        claims.ArtifactEvidence[i] = evidence   // build-time hash destroyed
        replaced = true
        break
    }
}
```

Nothing checks whether the entry being replaced is build-time evidence for an
artifact a task actually claimed. `validateReadOnlyArtifacts` only verifies the
spec's task ID exists and was reconciled — it never verifies the artifact is
absent from claim lists, even though the whole design premise (the D-01 comment
in `criterion_evidence.go:430-434`, "an artifact absent from the task's claim
lists") is that read-only evidence is for *unclaimed* artifacts.

Two concrete exploit paths, both persisted durably into
`last-build-claims.json` by `applyReadOnlyArtifactEvidence`:

1. **Same task:** Task 1.1 claimed `shared.go` (`files_modified`), build
   finalize recorded its build-time hash via `attachBuildArtifactEvidence`.
   The file is then tampered with. Running
   `aether continue --plan-only --reconcile-task 1.1 --read-only-artifact 1.1:shared.go`
   re-hashes the *tampered* content and overwrites the build-time entry. The
   criterion check `current.SHA256 != recorded.SHA256` (`criterion_evidence.go:450`)
   now passes; the "artifact shared.go changed after build evidence was
   recorded" blocker that existed before the flag is gone.
2. **Cross-task:** `--read-only-artifact 1.2:shared.go` (task 1.2 known and
   reconciled) replaces evidence for `shared.go` even though it is task 1.1's
   claimed artifact — task 1.1's tamper detection is erased by a flag that
   never named task 1.1, violating the disjoint-claim-sets intent (D-02).

The claims file is shared by every later continue attempt, including the direct
`aether continue` path where advancement is possible — so the laundered hash is
not confined to the (always-blocked-by-reconcile) external path. This directly
contradicts the invariant the same plan wrote into
`verifyPlanReadOnlyArtifactEvidence`'s comment: re-hashing "would silently
overwrite the hash captured at plan-only time, destroying tamper detection …
the one property that makes this escape hatch safe" (T-163.1-46). That property
is enforced at finalize but violated at record time.

**Fix:** In `recordReadOnlyArtifactEvidence` (or `validateReadOnlyArtifacts`,
which already has the phase), reject any spec whose normalized path appears in
any task's claim lists / already has non-read-only evidence recorded:

```go
if existing := findEvidenceByPath(claims, evidence.Path); existing != nil && !existing.ReadOnly {
    return fmt.Errorf("read-only artifact %q already has build-time claimed evidence; "+
        "the escape hatch is only for artifacts the build did not claim", spec)
}
```

and add a test asserting that a claimed-then-tampered artifact still blocks
when `--read-only-artifact` names it.

## Warnings

### WR-01: Envelope completion with an explicit `null` top-level manifest key is now rejected — a regression from prior accept behavior

**File:** `cmd/codex_build_finalize.go:295-312`
**Issue:** The raw-unwrap condition treats a top-level `dispatch_manifest` or
`manifest` key as "present" even when its value is `null`, while the struct
decode treats `null` as absent. Confirmed empirically: for
`{"dispatch_manifest": null, "result": {"dispatch_manifest": {…valid…}}}`,
`envelope.Result.activeManifest()` is non-nil (the envelope decodes fine), but
`unwrappedRaw` stays the full top-level map (because `hasDispatchManifest` is
true for the null key), so `manifestKeyPresentAsObject(unwrappedRaw)` is false
and the packet is rejected with the bare "completion file must include
dispatch_manifest". Before this change, the same bytes were accepted via the
envelope path. Fails closed, but with a wrong diagnostic and a silent
behavioral regression for wrappers that serialize absent fields as `null`
(common from JS/TS hosts — the ts-host path is a live producer of these
packets).
**Fix:** In the unwrap condition, treat a manifest key as blocking the unwrap
only when its value is a JSON object (mirror `manifestKeyPresentAsObject`'s
per-value check), e.g. `_, hasDispatchManifest := rawMap["dispatch_manifest"].(map[string]any)`.

### WR-02: `manifestKeyPresentAsObject`'s either-key semantics lets a wrong-typed `dispatch_manifest` shadow a valid `manifest` and suppress the structural violation

**File:** `cmd/codex_build_finalize.go:269-280, 328-348`
**Issue:** For `{"dispatch_manifest": "bad", "manifest": {…valid…}}` (confirmed
empirically): the struct decode allocates a zero-valued `DispatchManifest`
before failing with a tolerated `UnmarshalTypeError`, and `activeManifest()`
prefers `DispatchManifest` — returning the zero struct instead of the valid
`Manifest`. The cross-check `manifestKeyPresentAsObject(raw)` returns true
because *the other* key ("manifest") is an object, so the packet is accepted at
load with a corrupt active manifest. `runCodexBuildFinalize` then fails at the
`!manifest.PlanOnly` check with "dispatch_manifest must come from `aether build
--plan-only`" — the schema violation for the string-typed `dispatch_manifest`
(the whole point of T-163.1-43's improved diagnostics) is never reported,
because the semantic-validation call sits after that early return. The comment
calls `raw` the "ground truth" cross-check, but checking either key defeats
per-key ground truth.
**Fix:** Make the cross-check key-specific: `activeManifest()` selected
`DispatchManifest` ⇒ require `raw["dispatch_manifest"]` to be an object;
selected `Manifest` ⇒ require `raw["manifest"]` to be an object. When the check
fails, fall through to the structural-violation branch as already done.

### WR-03: Two read-only specs for the same path with different task IDs are silently unsatisfiable, and the recovery hint loops

**File:** `cmd/readonly_evidence.go:105-118, 194-201`
**Issue:** `codexBuildArtifactEvidence` carries a single `ReadOnlyTaskID` per
path, and `recordReadOnlyArtifactEvidence` is last-spec-wins on path
replacement. Given specs `1.1:file` and `1.2:file` (both tasks valid and
reconciled — legitimate when two tasks' bound criteria share one artifact),
plan-only records only task 1.2's scope; task 1.1's criterion then blocks
("was not claimed by the current build"), and at finalize
`verifyPlanReadOnlyArtifactEvidence` reports spec `1.1:file` missing with the
hint "rerun `aether continue --plan-only --reconcile-task 1.1
--read-only-artifact 1.1:file`" — which, if followed, flips the recorded task
ID and makes `1.2:file` fail instead. The operator is sent in a circle with no
error ever naming the actual conflict.
**Fix:** Either support multiple task scopes per path (e.g.
`ReadOnlyTaskIDs []string`), or detect two specs sharing a normalized path with
differing task IDs in `validateReadOnlyArtifacts` and reject up front with a
message naming both specs.

### WR-04: `TestContinueFinalizeReadOnlyArtifactEvidenceAdvancesAndDetectsTamper` never asserts advancement — the plan's "advance" outcome is unproven

**File:** `cmd/continue_criterion_evidence_finalize_test.go:159-266`
**Issue:** The test function name and its first subtest ("advances and
preserves claims when evidence is recorded") promise phase advancement, but the
test deliberately skips asserting `advanced`/`blocked` — its own comment
(lines 206-216) concedes `blocked:true` is *unavoidable* on this path because
`--reconcile-task` always appends a blocking warning, and `--read-only-artifact`
requires `--reconcile-task`. So on the external plan-only → finalize path the
escape hatch can never actually produce an advancing phase; only the
criterion-specific sub-fields flip. Under the project's Definition of Done
("a command exists that someone can run, and that command fails when the
requirement is unmet"), the end-to-end outcome the name claims is not
executable-verified, and a future regression that blocks advancement for a new
reason would not be caught here.
**Fix:** Rename the test/subtest to what it proves (e.g.
`...CriteriaPassAndDetectsTamper`, "criteria pass and claims are preserved"),
and add an explicit assertion of the *expected* blocked state with the
reconcile warning as the sole blocker class — so the test fails if a new,
unrelated blocker appears or if the reconcile-warning behavior ever changes.

## Info

### IN-01: `verifyPlanReadOnlyArtifactEvidence` has two dead parameters

**File:** `cmd/readonly_evidence.go:162`
**Issue:** Neither `root` nor `phase` is used in the function body. `root` is
deliberately unused (no re-hashing, per the T-163.1-46 comment), but dead
parameters invite the assumption that phase-membership validation happens here
(it happens earlier in `validateExternalContinueState`).
**Fix:** Drop both parameters, or rename to `_` with a comment if the signature
is kept for symmetry.

### IN-02: Claims-path derivation duplicated between `applyReadOnlyArtifactEvidence` and `loadCriterionEvidenceClaims`

**File:** `cmd/readonly_evidence.go:140-143` vs `cmd/criterion_evidence.go:525-529`
**Issue:** The `claimsRel` fallback + `strings.TrimPrefix(..., ".aether/data/")`
logic is copy-pasted. If `loadCriterionEvidenceClaims`'s derivation ever
changes, the save path in `applyReadOnlyArtifactEvidence` silently diverges and
evidence gets written to a file criterion evaluation never reads.
**Fix:** Extract a shared `criterionClaimsRel(manifest) string` helper used by
both load and save.

### IN-03: Continue-side completion loader has none of the build-side submitted-bytes machinery

**File:** `cmd/codex_continue_finalize.go:69-106`
**Issue:** `loadExternalContinueCompletion` still hard-fails on the first
`UnmarshalTypeError` with a bare "parse completion file" message and performs
no structural validation of submitted bytes; unknown fields in a continue
completion are silently dropped. Plan 163.1-08 was scoped to build packets, but
the asymmetry means the continue path retains exactly the failure modes
(T-163.1-40/43) the build path just fixed — including for the
wrapper-controlled `read_only_artifacts` field this same phase made
load-bearing.
**Fix:** Track as a follow-up: mirror the raw-first decode, type-error
tolerance, and schema validation for `codexExternalContinueCompletion`.

### IN-04: Guard-state test's byte-identical invariant only holds for phase-1 fixtures

**File:** `cmd/completion_packet_submitted_bytes_test.go:207-239` (vs `cmd/codex_build_finalize.go:417,443`)
**Issue:** `assertSubmittedBytesGuardStateUnchanged` claims a rejected packet
leaves `COLONY_STATE.json` byte-for-byte unchanged ("no checkpoint save, no
attempt mutation, nothing"). But
`reconcilePriorCompletedPhaseTasksFromTrustedManifests` (line 417) can rewrite
`COLONY_STATE.json` via `UpdateJSONAtomically` *before*
`validateCompletionPacketSemantics` runs (line 443) whenever `phaseNum > 1` and
prior-phase task repairs apply. The fixture uses phase 1, so the test can never
observe this; the D-06 comment's "before any state is touched" is over-broad as
stated.
**Fix:** Either scope the comment/test claim to packet-derived state, or move
the prior-phase reconciliation below packet validation if strict rejection
atomicity is intended.

### IN-05: `--plan-only` now durably mutates `last-build-claims.json`

**File:** `cmd/codex_continue_plan.go:115-119`
**Issue:** Recording read-only evidence at plan-only time is deliberate (D-01,
so the same invocation's criterion evaluation sees it), but it makes a
plan/inspection-flavored command a durable state mutator: a plan-only run whose
verification subsequently blocks, or whose manifest is discarded, still leaves
read-only evidence recorded in the claims file, where it will be honored by any
later continue attempt with no further operator action. Given the project's
corollary about inspection commands not mutating state, this deserves an
explicit note in the wrapper-runtime contract docs and/or a line in the
plan-only output listing what was recorded.
**Fix:** Document the mutation in the plan-only result payload (e.g.
`"read_only_evidence_recorded": [...]`) so the operator can see it happened.
