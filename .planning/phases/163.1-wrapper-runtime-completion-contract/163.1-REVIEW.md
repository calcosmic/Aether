# Phase 163.1: Code Review Report

**Reviewed:** 2026-08-01T09:57:54Z

## Summary

Reviewed the wrapper-runtime completion contract phase: the generated completion-packet JSON Schema and drift gate (plan 01), accumulated violation reporting (plan 02), stage-time validation and the rebind window (plan 03), `brief_path` and stable re-plan names (plan 04), required-verification halt honesty (plan 05), the `--read-only-artifact` reconcile escape hatch (plan 06), and the first-publish version fix (plan 07). The diff for the phase (`63592bd6..HEAD`) was used to focus scrutiny; full production files were read, tests were skimmed for what they actually prove, and the targeted test suite plus `go vet` were run locally (all pass).

The work is generally strong: the drift gate is real (byte-compare against regenerated schema), the D-06 atomicity test asserts on-disk state, the read-only escape hatch reuses the existing hashing/path-validation machinery rather than reimplementing it, and worker-submitted `read_only` evidence is provably wiped by `attachBuildArtifactEvidence` at finalize.

However, the phase's central contract claims are stronger than the code delivers. The structural schema validation runs on a re-marshaled Go struct, which makes two of the schema's core protections unreachable at runtime (Critical below). Stage-time validation is a subset of finalize-time validation, contradicting the D-07 comments and tests. The mandatory-handoff rule fires mid-mutation, not during the atomic validation pass. And `--read-only-artifact` is plumbed into the plan-only/continue-finalize path where it is validated, persisted, and then never takes effect.

## Critical Issues

### CR-01: Structural schema validation validates the re-marshaled struct, so unknown fields are silently discarded and type errors are never accumulated

**File:** `cmd/codex_build_finalize.go:726-761` (`validateCompletionPacketSemantics`, `completionPacketAsRaw`), `cmd/codex_build_finalize.go:187-224` (`loadExternalBuildCompletion`)
**Issue:** `validateCompletionPacketStructure` is fed `completionPacketAsRaw(completion)` — a round-trip through the already-decoded Go struct — never the raw file bytes. Two consequences:

1. **Unknown/misspelled fields can never be rejected.** `loadExternalBuildCompletion` uses plain `json.Unmarshal` (no `DisallowUnknownFields`), so a wrapper that writes `"files_modifed"` or `"test_written"` has that data silently dropped before validation runs. Every `additionalProperties: false` in the committed schema (`.aether/schemas/completion-packet.schema.json`) is dead weight at runtime. This is precisely the M4L failure class (model emits a near-miss field name) that the schema was generated to catch — claims evidence vanishes without any violation, and finalize proceeds with an incomplete claim set (or falls back to `discoverChangedFilesFromGit`, attributing files the worker never claimed).
2. **Wrong-typed fields abort with one unaccumulated parse error.** A packet with `"status": 5` fails inside `json.Unmarshal` with a single `"parse completion file: ..."` error before `validateCompletionPacketSemantics` ever runs — contradicting D-05/D-06's "one rejection lists every violation." The only structural violations that can actually fire post-round-trip are nil-slice-vs-required-array cases (e.g. missing `claims.files_created` marshaling to `null`).

**Fix:** Validate the original decoded bytes, not the struct. In `loadExternalBuildCompletion`, keep the raw `data`, decode it once into `any` with `json.Unmarshal(data, &raw)`, and pass that `raw` (unwrapping the `{"result": ...}` envelope when present) through `validateCompletionPacketStructure` alongside — or instead of — the round-tripped struct:

```go
// in loadExternalBuildCompletion: retain raw bytes and return them
var raw any
if err := json.Unmarshal(data, &raw); err != nil { ... }
// later, in validateCompletionPacketSemantics:
violations = append(violations, validateCompletionPacketStructure(rawFromFile)...)
```

Type mismatches then surface as accumulated schema violations (decode the tolerant struct only after, or make the struct decode best-effort), and `additionalProperties: false` starts doing its job. If raw-bytes validation is deferred, at minimum document that the schema currently cannot reject unknown fields at runtime, because the code comments in `cmd/contract_schema.go:78-86` (T-163.1-01) imply otherwise.

## Warnings

### WR-01: Stage-time validation is a subset of finalize-time validation, contradicting the D-07 parity claim

**File:** `cmd/build_attempt.go:346-352` (comment and `stageBuildAttemptCompletion`), `cmd/codex_build_finalize.go:277-337`
**Issue:** The D-07 comment states "staging validates exactly what finalize validates ... so staging and finalizing never disagree," and the wrapper docs promise a staged packet is finalize-ready. But staging runs only `validateCompletionPacketSemantics` (+ binding identity). Finalize additionally enforces: `validateBuildProvenanceForManifest` (SAFE-01/02 phantom-build rejection), `validateFinalizerManifestFreshness`, `validateBuildManifestPlanRevision`, `validatePhaseCriterionEvidence`, `validateBuildManifestTaskSetForPhase`, `validateSelectedBuildTasks`, `runPreBuildGates`, and `validateCodexBuildState`. A phantom-build packet (no successful file-modifying worker) stages cleanly — durable file written, digest and recovery command bound to the attempt journal — and then finalize rejects it, leaving a recovery command (`aether build-finalize N --completion-file <path>`) that can never succeed.
**Fix:** Either run `validateBuildProvenanceForManifest` (cheap, packet-local, wrapper-fixable — the same class as the semantic checks) inside `stageBuildAttemptCompletion` before the durable write, or correct the comment/test claims to say staging validates the packet-local contract only and name the finalize-only gates explicitly.

### WR-02: Empty-handoff rejection for completed workers fires mid-mutation, outside the atomic validation pass

**File:** `cmd/codex_build_finalize.go:947-955` (`persistExternalBuildHandoffs`), `pkg/codex/handoff.go:38-52` (`ValidateWorkerHandoff`)
**Issue:** `ValidateWorkerHandoff` (the check that participates in `validateCompletionPacketSemantics` via `mergeExternalBuildResults`) accepts a fully empty handoff (`verification_status: ""` is allowed). The rule "a completed worker must relay a non-empty handoff" is enforced only in `persistExternalBuildHandoffs`, which runs at `cmd/codex_build_finalize.go:417` — after the checkpoint save, attempt bind, two attempt transitions, the claims write, the build manifest write, and the spawn-tree recording. This breaks two of the phase's own guarantees: (a) D-06 atomicity — a packet defect aborts finalize mid-mutation and the deferred handler marks the attempt `interrupted`; (b) D-07 stage parity — a completed-worker/empty-handoff packet stages cleanly and then fails finalize. The wrapper text ("an empty handoff will be rejected by the finalizer", `.claude/commands/ant/build.md:87`) is true only in the non-atomic sense, and the rejection is one worker at a time, not an accumulated violation list.
**Fix:** Move the check into `mergeExternalBuildResults`: after `status := normalizeExternalBuildStatus(...)`, add

```go
if status == buildWorkerCompleted && codex.IsEmptyWorkerHandoff(result.Handoff) {
    violations = append(violations, contractViolation{
        Worker: dispatch.Name, Field: "handoff", Rule: violationRuleHandoffValid,
        Message: "completed worker must relay a non-empty handoff",
    })
    continue
}
```

Keep the `persistExternalBuildHandoffs` check as defense-in-depth.

### WR-03: `--read-only-artifact` is validated and persisted on the plan-only → continue-finalize path but never takes effect there

**File:** `cmd/codex_continue_plan.go:95,138`, `cmd/codex_continue_finalize.go:181,509`, `cmd/readonly_evidence.go:128` (`applyReadOnlyArtifactEvidence`), `cmd/codex_continue.go:1925` (`assessCodexContinue`)
**Issue:** `applyReadOnlyArtifactEvidence` is called only from `runCodexContinue` (the direct path). On the classic-ceremony path, `runCodexContinuePlanOnly` validates specs and stores them in the plan manifest, and `runCodexContinueFinalize` validates them again and passes `plan.ReadOnlyArtifacts` into `assessCodexContinue` — but `assessCodexContinue` never reads `options.ReadOnlyArtifacts` (dead parameter), and no code on that path records the evidence into the claims file. Today this is masked by a larger pre-existing gap: `runCodexContinueVerificationSnapshot` (used by both plan-only and finalize) never calls `evaluatePhaseCriterionEvidence` at all, so bound criteria are not gated on the external-review path — the direct path blocks on them, the heavy path does not. The moment criterion gating is added to the snapshot, the read-only escape hatch will fail there despite the flag being accepted.
**Fix:** Either call `applyReadOnlyArtifactEvidence(root, manifest, plan.ReadOnlyArtifacts)` in `runCodexContinueFinalize` before `runCodexContinueVerificationSnapshot`, or reject `--read-only-artifact` combined with `--plan-only` with an explicit "not supported on the external-review path" error. Separately, remove the dead `ReadOnlyArtifacts` pass-through into `assessCodexContinue` or make it consume the field. The snapshot-vs-direct criterion-gating asymmetry deserves its own tracked item even though it predates this phase.

### WR-04: TOCTOU in `stageBuildAttemptCompletion` can leave the durable completion file mismatched with the sealed digest

**File:** `cmd/build_attempt.go:339-402`
**Issue:** The seal/digest pre-checks run on a `LoadJSON` snapshot (`existing`), then the durable completion file is overwritten via `store.AtomicWrite`, and only afterwards are the definitive checks re-run inside `store.UpdateJSONAtomically`. If another process seals the attempt (finalize commits `built` with digest D1) between the load and the write, the durable file — the sole crash-recovery artifact, at a path that is a pure function of phase+attempt — is clobbered with packet P2 while the journal's sealed `CompletionSHA256` remains D1. The in-update check then rejects the rebind, but the rollback (`os.Remove` guarded by `os.IsNotExist(durableAlreadyExists)`) only deletes the file when it did not pre-exist; it never restores the prior contents. Result: the surfaced recovery command `aether build-finalize N --completion-file <path>` fails digest verification forever. Low likelihood (requires concurrent stage/finalize), but it destroys exactly the evidence this feature exists to guarantee.
**Fix:** Write the durable packet to a temp name and rename it into place only after `UpdateJSONAtomically` succeeds; or read and stash the pre-existing file contents and restore them when the update callback rejects.

### WR-05: A crash-staged packet expires after 24 hours, contradicting the stage/resume contract

**File:** `cmd/codex_build_finalize.go:297` (`validateFinalizerManifestFreshness`), `cmd/finalizer_completion_contract.go:15`
**Issue:** The staged durable packet path exists so "if the wrapper stops after this point, `aether resume` must offer this exact packet rather than redispatching workers" (SKILL.md step 14, `command_guide.go`). But finalize still applies the 24-hour `validateFinalizerManifestFreshness` gate to the embedded manifest's `generated_at` on this path (the attempt is `awaiting_external`, state not yet BUILT, so neither the idempotent nor reconcile shortcut applies). A user who resumes the day after a crash gets "stale dispatch_manifest ... rerun the plan-only command" — i.e., redispatch workers and lose the completed work, which is the exact outcome staging was built to prevent.
**Fix:** When `binding.Bound` and the packet digest matches the journal's staged `CompletionSHA256` (integrity already proven by the durable attempt + digest), skip or lengthen the freshness gate; staleness protection for staged packets is already provided by `validateBuildAttemptManifestBinding`'s state-hash and supersession checks.

### WR-06: Stable-name exclusion frees names that other phases' spawn-tree entries or actually-run failed workers already own

**File:** `cmd/codex_build.go:2617-2635` (`ensureUniqueBuildDispatchNames`)
**Issue:** To keep names stable across re-plans, all of the latest same-phase attempt's dispatch names are `delete()`d from the global `used` set whenever that attempt's status is anything other than `built`. Two gaps: (1) the doc comment's premise — "`built` [is] the one status meaning workers actually ran and produced attributable results" — is false: `recordBuildAttemptTerminal` writes `failed` after real workers ran and produced spawn-tree entries, and `interrupted` attempts can also have run workers; their names are freed and re-issued, so `recordExternalBuildSpawnTree`'s `UpdateStatus` will overwrite the earlier run's lineage under the same name. (2) `SpawnEntry` carries no phase, so if builds run out of order (phase 2 planned before phase 1 built), a name freed for phase 2's re-plan can collide with an identical name later recorded by phase 1's actually-run worker — re-opening the exact cross-phase attribution hole the D-09 guard closes. Both are edge cases, and re-using names on retry may be intended UX, but the invariant as documented does not hold.
**Fix:** Record the phase (or attempt ID) in spawn-tree entries and scope the exclusion to entries provably owned by the current phase's superseded attempt; at minimum correct the comment and add a test for the failed-attempt-with-run-workers case.

## Info

### IN-01: Dead stdin branch in `loadExternalBuildCompletion`

**File:** `cmd/codex_build_finalize.go:197-199`
**Issue:** `if path == "-" { data, err = io.ReadAll(os.Stdin) }` is unreachable — `validateFinalizerCompletionFilePath` at line 192 rejects `"-"` first (`cmd/finalizer_completion_contract.go:32-34`).
**Fix:** Delete the branch or move the validation after it if stdin support is intended.

### IN-02: `durableAlreadyExists` holds an `error` but is named as a boolean

**File:** `cmd/build_attempt.go:360,398`
**Issue:** `_, durableAlreadyExists := os.Stat(durableAbsolute)` binds the stat error, later consumed as `os.IsNotExist(durableAlreadyExists)`. The logic is correct but reads inverted (the name says "exists", the value is non-nil when it does NOT exist).
**Fix:** Rename to `durableStatErr` and/or compute `preExisted := durableStatErr == nil` at the stat site.

### IN-03: `firstDifferingLine` reports line 0 for trailing-newline-only drift

**File:** `cmd/contract_schema.go:348-368`
**Issue:** If generated and committed differ only by a trailing newline (`"a\n"` vs `"a"`), `strings.Split` yields `["a",""]` vs `["a"]`, and the loop treats the out-of-range side as `""`, returning 0. The user then sees "first differing line: 0".
**Fix:** Compare lengths after the loop and return `min(len)+1` when contents match but line counts differ.

### IN-04: build.md instructs spawning by `agent_name`, which is absent from `dispatch_manifest`

**File:** `.claude/commands/ant/build.md:95`, `.opencode/commands/ant/build.md:95`, `cmd/codex_build.go:1728`
**Issue:** The wrapper is told to parse `result.manifest.dispatch_manifest` and to "spawn the matching platform agent using `agent_name` as the subagent type" — but `codexBuildDispatch` (and the generated schema) has no `agent_name`; it exists only in the top-level `result.dispatches` convenience maps (`codexBuildDispatchMaps`). A wrapper following the documented parse source literally has no `agent_name` and may invent one.
**Fix:** Either add `agent_name` to `codexBuildDispatch` (and regenerate the schema), or reword the wrapper step to say the subagent type comes from `result.dispatches[].agent_name` / is derived from `caste` via the platform agent naming convention.

### IN-05: `mergeExternalBuildResults` error return is now always nil

**File:** `cmd/codex_build_finalize.go:785-880`, caller at 329-332
**Issue:** After the plan-02 refactor every wrapper-fixable case became a violation and no code path returns a non-nil `error`; the `if err != nil` at the finalize call site (and in tests) is dead. Harmless, but the three-value signature implies internal failures that cannot occur.
**Fix:** Either drop the error return or add a comment stating it is reserved and currently always nil (the doc comment partially does this; the caller check could then be removed).

### IN-06: Near-duplicate empty-handoff helpers

**File:** `pkg/codex/handoff.go:26-35,92-102` (adjacent to reviewed `pkg/codex/string_list.go` and used by `cmd/codex_build_finalize.go`)
**Issue:** `IsEmptyWorkerHandoff` (exported, ignores `Freshness`) and `workerHandoffIsEmpty` (unexported, includes `Freshness`) are 90% identical; a future field added to one but not the other will silently diverge the "empty" definition used by the finalize gate.
**Fix:** Implement one in terms of the other (e.g. `workerHandoffIsEmpty(h) == IsEmptyWorkerHandoff(h) && strings.TrimSpace(h.Freshness) == ""`).
