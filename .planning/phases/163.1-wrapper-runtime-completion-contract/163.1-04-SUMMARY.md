- `writeCodexBuildArtifacts` now writes the already-composed brief (base + pheromone signals + prior handoffs) to `worker-briefs/{name}.md` instead of the base-only render, and every dispatch carries `brief_path` pointing at that file — a test proves byte equality between file and `dispatch.Brief` for every dispatch, including one with an active pheromone signal

## Decisions Made

- SKILL.md's Plan Flow "verbatim" instruction (a different section, about Route-Setter/Scout dispatches which have no `brief_path` field) was deliberately left untouched; only the Build Flow instruction was extended, since `brief_path` is `codexBuildDispatch`-only.
- Verified via `grep -n '.Brief =' cmd/codex_plan.go cmd/codex_colonize.go cmd/swarm_cmd.go` that plan/colonize/swarm dispatches use their own struct types unrelated to `codexBuildDispatch`, so this phase's `BriefPath` addition is correctly scoped to build only.
- `ensureUniqueBuildDispatchNames`'s exclusion condition is `record.Status != buildAttemptBuilt` rather than `buildAttemptStatusActive(record.Status)` — confirmed by tracing both call sites (`runCodexBuildPlanOnlyWithOptions`, `runCodexBuildWithOptions`) that any same-phase attempt still "active" gets force-interrupted via `interruptLatestBuildAttempt` before name allocation runs, so by the time the function executes a same-phase record is always terminal (built/failed/interrupted) or absent.

## Threat Model Findings

- **T-163.1-16** (brief_path must resolve only under the store base path): confirmed by `TestDispatchEntryCarriesBriefPath`, which asserts `brief_path` never contains `..` and resolves to an existing file under `store.BasePath()`. `brief_path` is set only from `displayDataPath(briefRel)` where `briefRel` is built from `buildDirRel` + `"worker-briefs"` + the dispatch name — never from worker or user input.
- **T-163.1-17** (worker names must not contain `/` or `..`): confirmed during implementation. `deterministicAntName` (cmd/codex_visuals.go) always returns `<prefix>-<number>`, where prefixes come only from `castePrefixes`/`fileCastePrefixes` — static, repo-controlled caste name lists, never runtime worker or user input — and `ensureUniqueBuildDispatchNames` only appends `-r<N>` to that base. No path-separator injection is possible through this path.
- **T-163.1-20** (name reuse scoped to the same phase's unfinalized attempt only): confirmed by `TestEnsureUniqueBuildDispatchNamesSuffixesCollisionFromDifferentPhase` and `TestEnsureUniqueBuildDispatchNamesSuffixesCollisionFromSealedAttempt`.

## Issues Encountered

- Initial `ensureUniqueBuildDispatchNames` implementation gated the exclusion on `buildAttemptStatusActive(record.Status)`, which turned out to be dead code in practice: `interruptLatestBuildAttempt` (called by both build entrypoints before name allocation) already no-ops unless the record is active, converting it to `buildAttemptInterrupted` first. By the time `ensureUniqueBuildDispatchNames` runs, a same-phase record's status is always terminal or absent — traced this via the call-order in `runCodexBuildPlanOnlyWithOptions`/`runCodexBuildWithOptions` and switched the condition to `record.Status != buildAttemptBuilt`, which is what actually distinguishes "workers ran and produced results under these names" from everything else.
- `go test ./... -race` intermittently reported a `cmd` package failure with no `--- FAIL:` line captured in three separate runs (once via a background process whose captured output was accidentally truncated by a `| tail -30` in the command itself, twice more with no diagnosable cause). Isolated reruns of `go test ./cmd/... -race -count=1 -v` and a final foreground `go test ./... -race -count=1` both passed cleanly with zero failures, confirming the earlier failures were transient/resource-contention flakes unrelated to this plan's changes, not a real regression.
