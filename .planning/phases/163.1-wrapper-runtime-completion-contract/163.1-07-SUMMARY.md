**Removed the second, disagreeing version-resolution path inside `setupInstallHub` so the first `aether publish` after a version bump succeeds without a rerun, proven by a targeted regression test and confirmed against the real hub (1.0.45 -> 1.0.46).**

## Accomplishments

- `setupInstallHub` now takes an explicit `version string` parameter instead of independently calling `resolveVersion(packageDir)` — the root cause of a stale binary's baked-in ldflags version overwriting a freshly bumped `.aether/version.json` on the first publish after a bump
- `runPublish` passes the version it already resolved from the source checkout (`readRepoVersion`) at `cmd/publish_cmd.go:73`; `aether install`'s call site preserves its existing behavior by passing `resolveVersion(packageDir)` explicitly
- Added `TestPublishSucceedsOnFirstRunAfterVersionBump`, which simulates the exact bug condition (stale in-process `Version` override) and asserts both hub version files agree with the source version after a single publish invocation — verified to fail with `does not match hub version` when the fix is reverted, and to pass when restored
- Confirmed against the real hub on this machine: bumped `.aether/version.json` 1.0.45 -> 1.0.46, ran `aether publish` exactly once, got `Publish complete: Aether v1.0.46 published to /Users/callumcowie/.aether` with no `publish verification failed` message and no rerun, then `aether version --check` exited 0 at 1.0.46

## Decisions Made

- Left `readHubVersionAtPath`'s file-preference order and the legacy top-level `hubDir/version.json` write untouched. Nine call sites across `integrity_cmd.go`, `medic_scanner.go`, `porter_cmd.go`, `publish_cmd.go`, `root.go`, `setup_cmd.go`, and `update_cmd.go` read that legacy file; once `setupInstallHub` writes the correct version there, both hub version files agree and a reorder/removal was assessed as unnecessary risk for this fix's scope.
- `setupInstallHub`'s empty-version fallback to `resolveVersion(packageDir)` exists only as a safety net for callers that pass nothing — the publish path is structured so it never exercises that fallback (it always has a non-empty source-resolved version in scope).
- `aether install`'s call site was changed to pass `resolveVersion(packageDir)` explicitly rather than relying on an implicit default inside `setupInstallHub`, so install's existing behavior (deriving from the running binary) is preserved verbatim and visibly at the call site instead of hidden inside the shared function.
- Per the publish-update runbook and CLAUDE.md's "Publishing Changes" guidance, the real-hub verification bootstrapped with `go run ./cmd/aether publish --channel stable --binary-dest "$HOME/.local/bin"` (from-source) since this plan changes publish/install logic itself — running the not-yet-rebuilt installed binary would not have exercised the fix.
