<objective>
Make staging validate exactly what finalize validates, before it binds anything, and let a
non-terminal attempt accept a corrected packet.

Purpose: Requirement 3 and decisions D-07/D-08. Today `stageBuildAttemptCompletion`
(cmd/build_attempt.go:324-388) writes the durable completion file and binds
`CompletionSHA256` before any semantic validation runs — that only happens later when
`build-completion-finalize` reads the staged file. A packet finalize will reject therefore
poisons the attempt, and the three digest-mismatch guards then accept only a byte-identical
resubmit, forcing a new attempt, a new manifest, and `-rN`-renamed workers. That is the
mechanism behind the M4L session's six round-trips.

Output: stage-time validation ahead of binding, and a rebind window that closes on the
first successful finalize.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| wrapper → attempt journal | Staging writes durable state (`CompletionSHA256`, `CompletionPath`, a durable packet file) on behalf of untrusted worker output |
| attempt journal → colony state | A bound completion packet is what finalize commits into `COLONY_STATE.json` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-163.1-11 | Tampering | Rebind window abused to swap in a different worker's results after the fact | mitigate | The window is scoped to the same attempt ID and phase (identity checks run first and are unchanged), closes permanently at `built`, and every rebind must pass the full `validateCompletionPacketSemantics` — it is never a validation bypass |
| T-163.1-12 | Tampering | Gating the seal on the wrong status constant, leaving a finalized attempt mutable | mitigate | `buildAttemptCompletionSealed` compares against `buildAttemptBuilt` (written only after the built lifecycle state commits at cmd/codex_build_finalize.go:411), with a rationale comment and `TestBuildAttemptRejectsRebindAfterTerminal` as the failing-on-regression gate |
| T-163.1-13 | Repudiation | A stale durable completion file left on disk after a rebind, later mistaken for the accepted packet | mitigate | The superseded durable file is deleted after the atomic update succeeds; a test asserts it is gone |
| T-163.1-14 | Denial of Service | Repeated invalid stages filling the build directory with durable packet files | mitigate | D-07 means an invalid packet writes nothing at all, so failed submissions leave no residue |
| T-163.1-15 | Integrity | Race between two concurrent stages of different packets for the same attempt | accept | All record mutations go through `store.UpdateJSONAtomically` (existing house pattern with file locking); a single local wrapper process stages at a time |
</threat_model>
