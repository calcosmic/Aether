## User Constraints (from CONTEXT.md)

### Locked Decisions

The user delegated all four gray areas ("you decide"). Decisions below are locked with rationale; downstream agents should treat them as chosen, not open.

**Reconcile escape hatch (ROADMAP req 5)**
- **D-01: Read-only artifact evidence is the mechanism.** A criterion bound to an artifact the task legitimately did not modify is satisfiable by hash-verified evidence: verification confirms the criterion against the artifact's current content and records its hash, without requiring a `files_modified` claim. `codexBuildClaims.ArtifactEvidence` (cmd/codex_build.go:146) already exists as a struct field — extend that path rather than inventing a parallel one. `--reconcile-task` gains the ability to record read-only evidence. Rationale: covers the observed failure (test-only task, criterion bound to an untouched source file) without ever legitimizing a false modification claim; task-scoped claim strictness stays intact.
- **D-02: Cross-task claim satisfaction is NOT added.** Task-scoped claim sets stay disjoint (cmd/criterion_evidence.go:520-540 behavior preserved). Read-only evidence makes cross-task credit unnecessary, and keeping tasks accountable for their own claims preserves the anti-Frankenstein integrity the rest of the system depends on.

**Contract source of truth (ROADMAP req 1)**
- **D-03: Go structs remain canonical; the JSON Schema is generated from them.** Matches the project's UX architecture rule ("runtime owns truth"). A generator emits the completion-packet JSON Schema from the Go types (codexExternalBuildCompletion, codexExternalBuildWorkerResult, codex.WorkerHandoff) into `.aether/schemas/`, run via publish or a `go:generate` step — drift between struct and shipped schema must fail a test, not be discoverable only downstream.
- **D-04: Docs and brief text are pinned by tests, not generated.** Two invariant tests: (a) the contract doc's worked example validates against the generated schema; (b) the wrapper field list (build.md) and the worker response contract (pkg/codex/worker.go) name exactly the schema's fields. Per phase-163 D-05 ("instructions, permissions, and schemas must agree") and the Definition of Done: a command exists that fails when they disagree.

**Failure report shape (ROADMAP req 2)**
- **D-05: All violations, one response, structured + human-readable.** Batch validation collects every violation across every worker and returns them in the error envelope's `details` field as a list of `{worker, field, value, rule, message}` objects, plus a multi-line human summary. No more one-error-per-round-trip.
- **D-06: The packet stays atomic (all-or-nothing acceptance).** One worker's bad paperwork does not silently drop that worker — the whole packet is rejected with the full violation list, and the corrected packet is cheap to resubmit because of D-07/D-08. Rationale: partial acceptance creates split-brain staging state; atomicity plus cheap retry is simpler and equally recoverable. (Note: sanctioned-path claims already stopped being violations in commit 4b54f88e.)

**Attempt recovery model (ROADMAP req 3)**
- **D-07: Stage-time validation equals finalize-time validation.** The staged path (`build-completion-stage`) runs the same semantic validation as direct finalize BEFORE binding the packet digest — a packet that would fail finalize never binds to the attempt.
- **D-08: Non-terminal attempts accept a corrected digest.** Until an attempt reaches a terminal state (finalize succeeded), a new completion packet may replace the bound one (`CompletionSHA256` rebind allowed; cmd/build_attempt.go:313,346,369 sites). First successful finalize seals the attempt; after that, only byte-identical resubmits (idempotent) are accepted, as today.
- **D-09: Worker names stay stable across re-plans of the same phase.** `ensureUniqueBuildDispatchNames` (cmd/codex_build.go:2574-2603) stops suffixing `-rN` for re-plans of an unfinalized attempt of the same phase — dedup keys on (phase, attempt lifecycle), not global spawn-tree history. Manual result-remapping across retries must never be needed again.

**Verification honesty (ROADMAP req 4 — direction pre-decided by Phase 160 D-01)**
- **D-10: Skipped-required is a HALT, not a pass.** `runVerificationStep` (cmd/codex_continue.go:2659-2696) stops returning `passed:true` for skipped/unresolvable commands. A required check with no resolved command surfaces as its own loud state (`blocked: no verification command resolved`) with actionable guidance naming where to configure one (AGENTS.md / CLAUDE.md `## Verification Commands`, `.aether/data/codebase.md`). Gates halt; enrichment warns — per Phase 160 D-01.
- **D-11: Line-continuation joining.** `extractVerificationCommands` (cmd/codex_continue.go:2452-2481) joins backslash-continued lines inside fenced blocks before parsing, so documented multi-line commands are not silently truncated to their first line.

**Brief file channel (ROADMAP req 6)**
- **D-12: Dual channel for one release, file preferred.** The composed brief (`composeBuildManifestBrief` output — base + pheromone + handoff sections) is written to `worker-briefs/{name}.md` (today the file holds only the base brief — that mismatch is the bug), a `brief_path` field is added to each dispatch entry, and the wrapper contract sanctions reading the file at `brief_path` as the verbatim source. The inline `brief` field remains in the manifest for compatibility this release. All four contract surfaces update together per build.yaml's drift guard (Claude wrapper, OpenCode wrapper, Codex skill, cmd/command_guide.go).

## Summary

This phase closes seven gaps in Aether's wrapper-to-runtime completion contract, all independently surfaced by a real-world M4L usage session and re-verified with file:line evidence. The work has two flavors: **envelope validation** (reqs 1-2: a generated JSON Schema plus batch semantic validation replacing six one-error-per-round-trip failures) and **recovery/honesty fixes** (reqs 3-5, 7: stage-time binding order, read-only evidence, verification skip semantics, publish hub-sync). Req 6 is a carriage-channel fix (write the already-composed brief to the file that four separate contract surfaces already claim holds it verbatim).

None of this is greenfield — every requirement targets an existing, named Go function with a concrete defect, not a net-new subsystem. The go.mod has zero JSON-Schema tooling today; `pkg/codex/worker.go`'s hand-rolled `jsonSchema` struct exists but serves a different, narrower purpose (the OpenAI strict-subset per-worker output schema) and is not a template to reuse for the wrapper-facing completion-packet schema, which has normal (non-strict) JSON Schema semantics. `invopop/jsonschema` (generation) + `santhosh-tekuri/jsonschema/v6` (validation) are both current, actively maintained, draft-2020-12-compliant, and give an error shape that maps cleanly onto D-05's `{worker, field, value, rule, message}` violation objects.

The most consequential finding beyond the CONTEXT.md decisions is req 7's actual root cause (Pitfall 6): the publish pipeline is not mis-ordered — it already verifies after syncing — but `setupInstallHub` independently re-resolves the version via the *currently-executing binary's own ldflags* when writing a legacy top-level `hubDir/version.json`, which `readHubVersionAtPath` checks before the correctly-synced `system/version.json`. This is a self-referential bug (the publish tool trusts its own stale in-memory version over the file it just synced) that explains both the failure and why a bare rerun "fixes" it (the second invocation runs the freshly-built binary from disk). The planner should scope req 7 around this mechanism, not a generic reorder.

**Primary recommendation:** Add `invopop/jsonschema` + `santhosh-tekuri/jsonschema/v6` as the only new dependencies; restructure the four cited hand-rolled validators (`mergeExternalBuildResults`, `validateAndNormalizeClaimPathsToRoot`, the finalize sequence, `stageBuildAttemptCompletion`) from early-return to violation-accumulation using a shared `type contractViolation struct{ Worker, Field, Value, Rule, Message string }`; fix req 7 by making `setupInstallHub` accept the already-resolved `version` string as a parameter instead of calling `resolveVersion(packageDir)` internally, and/or by flipping `readHubVersionAtPath`'s preference to `system/version.json` first.

### Pattern 1: Violation accumulation instead of early return

**What:** Replace `for _, x := range xs { if err := check(x); err != nil { return nil, err } }` with a loop that appends to a `[]contractViolation` slice and only returns an error after the loop, carrying all collected violations in `details`.
**When to use:** Any of the four cited early-return sites (req 2).
**Example:**
```go
// Source: pattern derived from cmd/codex_build_finalize.go:653-716 (existing early-return shape)
type contractViolation struct {
    Worker  string `json:"worker,omitempty"`
    Field   string `json:"field"`
    Value   string `json:"value,omitempty"`
    Rule    string `json:"rule"`
    Message string `json:"message"`
}

func mergeExternalBuildResults(manifest codexBuildManifest, results []codexExternalBuildWorkerResult) ([]codexBuildDispatch, []contractViolation, error) {
    var violations []contractViolation
    // ... existing loop, but instead of `return nil, err`:
    violations = append(violations, contractViolation{
        Worker:  dispatch.Name,
        Field:   "handoff",
        Rule:    "handoff.valid",
        Message: err.Error(),
    })
    // continue the loop instead of returning
    // ...
    if len(violations) > 0 {
        return nil, violations, fmt.Errorf("%d completion packet violation(s)", len(violations))
    }
    return dispatches, nil, nil
}
```

### Pattern 2: Schema-validate structurally, then semantically

**What:** Run the generated JSON Schema validator first (catches shape/type/enum errors cheaply and generically), then run the existing hand-rolled Go semantic validators (claim-path policy, handoff business rules, provenance) — merge both violation lists before returning.
**When to use:** Entry point of `build-completion-stage` and `build-completion-finalize`/direct finalize (req 1 + req 2 combined).
**Example:**
```go
// Source: santhosh-tekuri/jsonschema/v6 usage pattern (github.com/santhosh-tekuri/jsonschema)
sch := compiledCompletionPacketSchema() // compiled once, package-level
if err := sch.Validate(rawJSONAsAny); err != nil {
    var ve *jsonschema.ValidationError
    if errors.As(err, &ve) {
        violations = append(violations, flattenSchemaViolations(ve)...)
    }
}
```

### Anti-Patterns to Avoid

- **Reusing `pkg/codex/worker.go`'s `jsonSchema` struct for the completion-packet schema:** it encodes OpenAI's strict-subset dialect (every property in `required`, no true optionals). The envelope schema needs normal JSON Schema optionality. Keep them separate.
- **Adding cross-task claim credit to satisfy req 5:** explicitly rejected by D-02. Do not let a read-only-evidence implementation accidentally let Task B's claims satisfy Task A's criterion.
- **Partial-packet acceptance to make batch validation "friendlier":** explicitly rejected by D-06 (deferred). The packet stays atomic; only the violation *reporting* becomes batched.
- **Fixing req 7 as a pure reorder:** the code already verifies after sync (see Pitfall 6). A reorder change would touch the wrong function and leave the actual bug (independent version re-resolution in `setupInstallHub`) in place.

## Common Pitfalls

### Pitfall 1: Treating `stageBuildAttemptCompletion`'s existing digest-mismatch rejection as "working as intended"

**What goes wrong:** `bindBuildAttemptCompletion`/`stageBuildAttemptCompletion` (cmd/build_attempt.go:305-388) already reject any completion packet whose SHA-256 differs from one already bound to the attempt. It looks like a safety feature, but it's the exact mechanism req 3 identifies as broken: it makes ANY correction to an already-staged (but not yet finalized) packet impossible without minting a brand-new attempt.
**Why it happens:** The digest check was designed for idempotent-resubmit detection (accept identical bytes), not for correction. There is no state distinguishing "attempt is terminal" from "attempt is merely staged."
**How to avoid:** D-08 requires: while `record.Status != buildAttemptBuilt` (or whatever the terminal-success state constant ends up being — `buildAttemptTerminal`/`buildAttemptBuilt` both exist as candidates at cmd/build_attempt.go:24-27), allow `record.CompletionSHA256` to be overwritten by a new digest, provided semantic validation (req 3) passes on the new packet first.
**Warning signs:** A test that asserts "resubmitting a corrected packet to a non-terminal attempt succeeds" is the invariant to add; its absence today is why six round-trips forced new attempts.

### Pitfall 2: Confusing `buildAttemptTerminal` with `buildAttemptBuilt`

**What goes wrong:** cmd/build_attempt.go:20-27 defines both `buildAttemptTerminal = "terminal"` and `buildAttemptBuilt = "built"` as distinct status string constants. D-08's "first successful finalize seals the attempt" needs the planner to pick the correct status value(s) that mean "no more rebinding" — using the wrong one could either lock rebinding too early (before finalize actually ran) or leave it open after finalize succeeded.
**Why it happens:** Two similarly-named constants for what looks like one concept.
**How to avoid:** Trace actual usage of both constants (`grep -n 'buildAttemptTerminal\|buildAttemptBuilt' cmd/*.go`) before deciding which one (or which combination) gates the D-08 rebind window; do this at plan time, not assumed from the name alone.

### Pitfall 3: Writing the `ReadOnly` evidence path so it can be triggered without `--reconcile-task`

**What goes wrong:** If any code path lets a worker's own claims JSON set `ArtifactEvidence[].ReadOnly = true` directly (rather than only a server-side `--reconcile-task` recording flow setting it), a worker could mark a modified file as "read-only" to dodge the modification-claim requirement — reopening exactly the false-claim risk D-01's rationale explicitly guards against ("without ever legitimizing a false modification claim").
**Why it happens:** `codexBuildClaims.ArtifactEvidence` (cmd/codex_build.go:146) is currently populated purely from the build's own claim lists via `attachBuildArtifactEvidence` — extending the JSON shape to accept a worker-supplied `ReadOnly` flag on submission would let an untrusted claimant set it themselves.
**How to avoid:** The `ReadOnly` marker must only ever be set by runtime-side code responding to an operator-invoked `--reconcile-task` (with an explicit evidence-recording action), never accepted verbatim from a worker's completion packet. Validate this with a test that a worker-submitted `read_only: true` in `artifact_evidence` is either ignored or rejected.

### Pitfall 4: Scoping req 4's fix to only the empty-command case

**What goes wrong:** `runVerificationStep` has TWO paths that currently return `{Skipped: true, Passed: true}`: the empty-command guard (line ~2671) and the `isCommandUnresolvable` branch after a real exec attempt fails with exit 127 or an ecosystem-specific "no such script" message (line ~2696). A fix that only changes the first path leaves the second — arguably the more common real-world case (a resolved-but-wrong command) — still lying about pass/fail for required checks.
**Why it happens:** The two paths look similar in the diff but have different call sites and different reasons for existing (one never tried to run anything, one tried and got a "the tool itself is missing" signal).
**How to avoid:** D-10's HALT behavior must apply to both `codexVerificationStep` return sites that set `Skipped: true`, gated on whether the check is "required" per the phase's criterion-evidence checks list (cmd/criterion_evidence.go's `evaluateCriterionCheck`), not on which code path produced the skip.

### Pitfall 5: Fixing only `.claude/commands/ant/build.md` and missing the other three drift-guarded surfaces

**What goes wrong:** req 6 lists four contract surfaces that must move together: `.claude/commands/ant/build.md`, `.opencode/commands/ant/build.md`, `.aether/skills/colony/aether-colony-build-cycle/SKILL.md` (the "Codex skill"), and `cmd/command_guide.go` (Go-rendered guidance also consumed by Codex flows). All four currently say "verbatim" in reference to `dispatch.brief`; none currently mention `brief_path`. `build.yaml:16`'s `drift_guard` field names exactly these four and nothing else — a fix touching fewer than all four leaves the guard's own promise broken.
**Why it happens:** `cmd/command_guide.go` looks like pure Go source and is easy to miss when searching only `.md` files for wrapper text; it is functionally a fifth "wrapper" even though it lives in `cmd/`.
**How to avoid:** `grep -rln "verbatim" .claude/commands/ant/build.md .opencode/commands/ant/build.md .aether/skills/colony/aether-colony-build-cycle/SKILL.md cmd/command_guide.go` before and after the change — the count of matches for "brief_path" (or equivalent new instruction) should be 4/4 after.

### Pitfall 6: Scoping req 7 as a simple "verify after sync" reorder

**What goes wrong:** `runPublish` (cmd/publish_cmd.go:36-141) already reads `hubVersion` AFTER calling `setupInstallHub` (the sync). A reorder change would be a no-op against a bug that isn't there. The real bug: `setupInstallHub` (cmd/install_cmd.go:687-812) does two separate things that can disagree —
1. `syncDirToHub(srcAether, systemDir)` (~line 702) correctly copies the just-bumped `.aether/version.json` from the source checkout into `hubDir/system/version.json`.
2. Separately, at cmd/install_cmd.go:802-810, it writes a **legacy top-level** `hubDir/version.json` using `resolveVersion(packageDir)` — and `resolveVersion` (cmd/root.go:30-34) returns the `Version` ldflags variable **baked into the binary that is currently executing this `publish` command**, not the freshly bumped source version, whenever that variable isn't the dev default. On the first `aether publish` after a version bump, the process running `publish` is still the OLD binary (the new one is only just being written to disk in the same invocation) — so this legacy file gets stamped with the OLD version.

`readHubVersionAtPath` (cmd/publish_cmd.go:249-256) checks `hubDir/version.json` (the stale legacy file) FIRST, only falling back to `system/version.json` (the correct one) if the first is empty — so it reliably picks the wrong value whenever both exist, which is every publish after the very first one ever run.

**Why it happens:** Two independent code paths resolve "the version" differently within the same function, and the wrong one is checked first by the reader. It's a self-referential bug: the publish tool trusts its own currently-loaded (stale) binary version over the file it just synced from source.

**Why rerunning "fixes" it:** The first invocation's `buildLocalBinary` step already overwrote the on-disk `aether` binary with the new version before `setupInstallHub` ran. A second `aether publish` invocation launches the FRESH binary from disk, whose `Version` ldflags now correctly equals the bumped version, so `resolveVersion` returns the right value and the legacy file gets the correct content on the second pass.

**How to avoid:** Either (a) change `setupInstallHub`'s signature to accept the already-resolved `version` string as a parameter from `runPublish` instead of calling `resolveVersion(packageDir)` internally, or (b) flip `readHubVersionAtPath`'s check order to prefer `system/version.json` (the freshly-synced file) over the legacy root file, or both. Add a regression test that runs `setupInstallHub` (or the full publish path) with a *simulated stale in-process `Version` var* and asserts the hub ends up with the source-checkout's version, not the invoking binary's.
