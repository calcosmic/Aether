<objective>
Stop `/ant-go` announcing that a job "turned out bigger than it looked" when the truth is that
it could not run the project's checks at all. Defect register entry 61.

Purpose: a brand-new project has no check command configured. That is the ordinary state of
the projects the owner is about to use this in for a fortnight, so as things stand every quick
job there escalates spuriously and then shows him a planning screen about work that is already
finished and correct.
Output: an escalation rule that fires on a genuine check failure and not on an unrunnable one.
</objective>

<the_gap>
Measured live on 2026-09-24, `209-TIMING.md` run 5, session
`92b11308-8302-4062-8d4d-59b7f1382d5e` — a real unattended session in a fresh practice
project. The small route ran and completed the job correctly. The screen then said:

> 🧭 This is the planning route: the project's own checks did not pass on the quick attempt (status: not_checked)
>
> ⚠️ This turned out bigger than it looked -- the project's own checks did not pass on the quick attempt (status: not_checked) -- so it has been moved up to the planning route.

Nothing about the job was bigger. The practice project simply has no resolvable check command,
so the quick attempt came back `not_checked`.

**Where it comes from.** `jobSizeAttemptEscalationReason` (`cmd/go_route.go`) escalates on
`colony.WorkOutcomeBlocker` or `colony.WorkOutcomePartial` and calls that "the project's own
checks did not pass". A quick attempt that could not run its checks lands on exactly that
partial verdict, carrying `checks_status` `not_checked`.

**Why this is unambiguously wrong here, not a judgement call.** The quick path already draws
this exact distinction deliberately, and says so in its own words at
`cmd/command_truth.go:455`:

> "passed, they failed, or nothing could actually be run (no verification command resolved, or
> it ran out of time). 'Not checked' is never folded into either passed or failed -- a change
> nothing could verify is reported honestly as unverified, never as a pass."

Three statuses exist for this reason: `quickChecksPassed`, `quickChecksFailed`,
`quickChecksNotResolved`. The escalation rule folds the third into the second — the very
conflation the quick path exists to avoid. Fixing it restores an existing project rule rather
than inventing a new one.
</the_gap>
